# 前端对接变更说明（2026-10-31）

> 本次变更主题：**OTA 升级状态细化** 与 **固件版本号格式统一**。
> 与 `docs/前端对接文档_草稿.md` 保持一致，冲突时以草稿为准。
> 本次**不涉及**设备在线状态（`ONLINE`/`OFFLINE`/`SLEEPING`/`SHUTDOWN`/`LOCAL_TF`）的任何变化，`GET /api/device/online` 的入参出参均未改动。

---

## 一、OTA 任务状态新增 `VERIFYING`

### 1.1 涉及接口

| 接口 / 通道 | 变化 |
|---|---|
| `POST /api/device/ota` | 出参不变（仍返回 `msgid`） |
| `GET /api/device/ota/status?msgid=` | `status` 字段新增枚举值 `VERIFYING` |
| WS `ota.result` | `status` 字段新增枚举值 `VERIFYING` |

### 1.2 完整枚举

| `status` | 含义 | 是否终态 | 建议前端文案 |
|---|---|---|---|
| `SENT` | 指令已下发，设备尚未响应 | 否 | 已下发 |
| `DOWNLOADING` | 设备开始下载固件包 | 否 | 下载中 |
| `FLASHING` | 固件包已下载完成，正在刷写 | 否 | 刷写中 |
| **`VERIFYING`** | **设备回报「执行成功」（协议 `result=113`），升级包已写入，等待设备重启后确认** | **否** | **升级完成**（副文案建议：「等待设备重启」，由前端自行撰写） |
| `SUCCESS` | 设备重启后报出的版本号已变化，升级确认成功 | 是 | **此状态当前流程下为后端所用，OTA 步骤页不纳入** |
| `FAILED` | 升级失败（含设备回报失败码、版本号未变化） | 是 | 升级失败 |
| `TIMEOUT` | 超时未完成 | 是 | 升级超时 |

**重要约定：**

1. **`VERIFYING` 不是终态。** 它只代表「设备说它执行完了」，还不能证明新固件真的在运行。前端**不要在 `VERIFYING` 时显示最终的成功勾选**，建议显示为「升级完成 · 等待设备重启」这类过程态。
2. **`SUCCESS` / `FAILED` 一定在设备重启之后才会出现**，由服务端比对设备报回的版本号决定，前端不需要自己做版本判断。
3. `UPLOADED` 属于投屏任务使用，OTA 不会出现，前端遇到按未知值降级即可。
4. 与以往约定一致：**服务端只返回值，不返回中文文案**；遇到未识别的新枚举请按「未知状态」降级展示，不要白屏或抛错。

### 1.3 OTA 步骤页状态对齐

OTA 步骤页（与配网页同一种形态）只消费下面这几个状态：

| 步骤 | 对应 `status` | 建议展示 |
|---|---|---|
| 第 1 步 | `SENT` | 已下发，等待设备响应 |
| 第 2 步 | `DOWNLOADING` | 设备下载固件中 |
| 第 3 步 | `FLASHING` | 设备写入固件中 |
| 第 4 步 | **`VERIFYING`** | **升级完成**（副文案建议「等待设备重启」） |
| 任意步骤 | `FAILED` / `TIMEOUT` | **升级失败**（在该步打 X） |

**约定：**

1. **`VERIFYING` 就是步骤页的成功终点。** 前端到这里即可让用户离开，不需要等待 `SUCCESS`。
2. **`SUCCESS` 不纳入步骤页**，它只用于服务端判定与结果通知（第四节），前端在步骤页逻辑里可以直接忽略。
3. 步骤页只在**存在进行中的 OTA 任务**时进入；升级完成（`VERIFYING`）退出后、或设备版本已是最新时，不再进入步骤页。
4. 步骤页需要处理的状态只有：`SENT` / `DOWNLOADING` / `FLASHING` / `VERIFYING` / `FAILED` / `TIMEOUT`。
5. **`FAILED` / `TIMEOUT` 在任意一步都可能出现**（含第 1 步 `SENT`），不是只在最后一步。前端处理规则统一为：
   - 把**当前正在执行的这一步**标记为失败（打 X）
   - **不再继续执行后续步骤**
   - 页面提示「升级失败」，并给出重试入口

### 1.4 失败口径

**`FAILED` / `TIMEOUT` 在四个步骤中的任意一步都可能出现**，前端按 1.3 第 5 条的规则统一处理。

| 状态 | 覆盖范围 |
|---|---|
| `FAILED` | ① 设备回报失败码（`102/103/104/105/109/110/112` 及其它未定义的码）；② 设备重启后版本号未变化 |
| `TIMEOUT` | ① 下发后 300 秒内没有任何 ack；② 进入下载/刷写/待确认后 1800 秒无进展 |
| （非状态） | **指令下发本身失败**（MQTT 发布失败）不产生 `FAILED`，而是直接返回 HTTP `5000`，同时任务被撤销 |

### 1.5 WS 推送示例

```json
{
  "type": "ota.result",
  "deviceNo": "3844BE2E5220",
  "msgid": "1793425086943534",
  "status": "VERIFYING",
  "version": "0.6.2",
  "corrected": false
}
```

- `version`：本次下发的目标版本号
- `corrected`：仅在最终结果里可能为 `true`，表示服务端之前已判定失败、后来由设备报回的版本号纠正为成功。前端展示为「升级成功」即可，不必特殊处理。

### 1.6 超时口径

| 阶段 | 超时时长 |
|---|---|
| 下发后一直没有任何 ack | 300 秒 → `TIMEOUT` |
| 收到 ack 后一直无新进展 | **1800 秒** → `TIMEOUT`（本次从 900 秒调大） |

`GET /api/device/ota/status` 返回的 `elapsedSeconds` 是「从下发到现在」的秒数，前端可用它做进度提示。

## 二、固件版本号格式统一

### 2.1 变化

设备上报的版本号有两个来源，格式此前不一致：

```
login 的 ver  →  "M H:3 F:0.6.1"
心跳的 version →  "0.6.1"
```

**现在服务端统一归一化成后者（纯版本号）再对外返回。**

### 2.2 受影响字段

| 接口 | 字段 | 变化 |
|---|---|---|
| `GET /api/device/info` | `firmwareVersion` | 由 `M H:3 F:0.6.1` 变为 **`0.6.1`** |
| `GET /api/device/info` | `shadow.version` | 同上，归一化为 `0.6.1` |
| `GET /api/device/ota/status` | `baseVersion` | 同上，归一化 |
| 后台设备列表 / 详情 | `firmwareVersion` | 同上 |

`shadow.espVersion`（心跳来源）本来就是 `0.6.1`，不变。

### 2.3 对前端的意义

- **不需要再解析 `M H:3 F:` 前缀**，直接按 `x.y.z` 做字符串或数字段比较即可。
- 历史数据会在设备下一次 `login` 或心跳后自动变成新格式；若读到仍是旧格式的值，说明该设备自上线以来还没重新上报过，前端比较时按「无法判断」处理即可，不要报错。

## 三、OTA `msgid` 的保存要求（交互约定）

服务端**不新增**「按设备查当前升级任务」的接口。OTA 进度仍然只通过 `msgid` 查询，因此需要前端配合保存 `msgid`。

### 3.1 保存要求

1. **下发成功后立即保存 `msgid`**，保证一台设备只保留一条进行中的升级记录。
2. **重新打开 OTA 页面时**：
   - 本地有未完成的 `msgid` → 调 `GET /api/device/ota/status?msgid=` 接着展示当前步骤；
   - 本地没有 → 显示正常状态（可升级 / 已是最新）。
3. **收到终态（`SUCCESS` / `FAILED` / `TIMEOUT`）后清除本地 `msgid`**。
4. **查询返回「任务不存在」（`4044`）时清除本地 `msgid`**（服务端任务只保留 2 小时）。
5. 用户关闭 App、锁屏、切后台都**不影响升级进度**；重新进入后按第 2 条恢复展示。

### 3.2 必须带类型标识（重要）

`msgid` 由服务端统一生成，格式为「13 位毫秒 + 3 位随机数」，**在投屏、轮播、OTA、休眠等所有指令之间共用同一个生成器**。

数值上不会重复，但**类型上会混淆**：如果只存一个裸 `msgid`，前端无法判断它是投屏的还是 OTA 的。

**要求：保存时必须带上指令类型**，例如：

```json
{
  "deviceNo": "3844BE2E5220",
  "type": "ota",
  "msgid": "1793425086943534"
}
```

或用独立的存储 key（如 `ota_inflight:{deviceNo}`）与投屏记录区分开。

原因：投屏有 `GET /api/device/play/status?msgid=`，OTA 有 `GET /api/device/ota/status?msgid=`，**用错接口只会返回「任务不存在」，不会报错**，会表现为「进度莫名丢失」，排查成本很高。

### 3.3 展示「有新版本」之前必须先检查进行中的任务

设备回报 `113` 后到重启完成之间，**设备上报的版本号仍然是旧的**。如果这段时间 App 只做版本比较，会再次判定「有新版本」，导致重复弹升级框。

**要求：**

1. 展示「有新版本」提示**之前**，先查本地是否有该设备进行中的 OTA 记录（且状态非终态）。
2. **有** → 不弹升级框，改为展示「升级进行中 · 等待设备重启」。
3. **没有** → 正常做版本比较。

**判断依据是「有没有进行中的 OTA 任务」，不是「版本号比没比上」。**

### 3.4 兜底：服务端会拦截重复下发

即使本地记录丢失（重装、清缓存、换设备登录）导致重复点了升级，**服务端也会拦截，不会真的下发第二次**：

| 错误码 | 含义 | 前端处理 |
|---|---|---|
| `4000` | 该设备已有进行中的升级任务 | 提示「设备正在升级，请稍候」，**不要显示成普通失败** |
| `4045` | 设备升级中 | 同上 |

拿到这两个码时，建议直接把页面切到「升级进行中」状态，并提示用户稍后再看结果。

### 3.5 前端不需要做的

- 不需要自己判断升级是否成功
- 不需要轮询设备版本号变化
- 不需要为「等待设备重启」单独设计阻塞页面——`VERIFYING` 之后用户可以直接离开，最终结果通过消息通知送达（见第四节）

## 四、OTA 结果消息通知（新增 `OTA_SUCCESS` / `OTA_FAILED`）

升级结果会进入**设备消息通知**，与上下线通知同一套（`notification.new` WS 推送 + 通知列表接口）。

### 4.1 何时发送

**只在设备重启后版本号确认时发送**，也就是 `VERIFYING` → `SUCCESS` / `FAILED` / `TIMEOUT` 的那一刻。设备自报的 `113` **不会**触发成功通知。

### 4.2 通知类型

| `type` | 触发时机 | 建议文案 |
|---|---|---|
| `OTA_SUCCESS` | 设备重启后报出的版本号已变化 | 固件升级成功 |
| `OTA_FAILED` | 版本号未变化 / 设备回报失败码 / 升级超时 | 固件升级失败 |

`category` 固定为 `DEVICE`。

### 4.3 携带参数

```json
{
  "version": "0.6.2",
  "baseVersion": "0.6.1",
  "reason": "timeout"
}
```

| 字段 | 说明 |
|---|---|
| `version` | 本次目标版本 |
| `baseVersion` | 升级前的版本 |
| `reason` | 可选；`timeout`=超时，`corrected`=先前判超时、后来由版本号纠正为成功；成功且无特殊情况时不带 |

> `corrected=true` 对应的通知类型是 `OTA_SUCCESS`，前端按「升级成功」展示即可。

### 4.4 与页面状态的关系

用户在 `VERIFYING` 后退出步骤页不会丢结果：最终结果通过消息通知触达。

步骤页**不提供「查看历史升级结果」的入口**——升级结束后页面回到「已是最新」，`SUCCESS` / `FAILED` 只用于服务端判定与结果通知，不参与步骤页展示。
