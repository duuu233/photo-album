# OTA / DFU 协议

> 状态：current  
> 最后核对：2026-08-11  
> 适用范围：`utils/ota-ble.js`、`subpackages/device/ota/ota.js`  
> 权威来源：《电子相框产品需求规格书 1.5》§6.3.2 / §6.3.3 / §6.3.4 与 §8 传输流程图

v1.5 相对旧版的协议变化（本文已按 v1.5 更新）：

- 新增**第一包 128 字节头信息握手**：升级包文件结构为 `[128 字节头信息][原始 bin payload]`。
- `DATA(0xF2)` **去掉 2 字节包序号**，帧内只有数据 + checksum。
- `END(0xF3)` 方向**改为 APP → 设备**：payload 发完后由 APP 主动发结束包，设备校验整包后回 ACK。
  旧版把 `0xF3` 当作「设备主动上报的最终结果」，现已不是。
- 新增结果码 `0x0A ~ 0x0E`（头信息握手校验失败的细分原因）。

## GATT

- 服务：`FF10`
- 控制与数据特征：`FF11`，同时承担 `writeNoResponse` 和 Notify
- 辅助/调试通道：`FF12`（扩展数据、调试信息；正常升级流程不使用）
- OTA 不使用普通设备协议的 `0xAA` 应用层帧格式，直接在 `FF11` 上传输 OTA opcode 帧

## OpCode

| OpCode | 值 | 方向 | 含义 |
| --- | --- | --- | --- |
| START | `0xF1` | APP → 设备 | 开始 OTA，携带对象类型和固件大小 |
| DATA | `0xF2` | APP → 设备 | 首包为 128 字节头信息握手包，后续为 bin payload 分片 |
| END | `0xF3` | APP → 设备 | payload 发完后的结束包，设备据此校验整包并回 ACK |
| ACK | `0xFC` | 设备 → APP | START / DATA / END 的应答帧头，**不是错误码** |

所有 APP → 设备请求最后一字节为前面所有字节累加和的低 8 位。

## 帧格式

```text
START 请求
F1 OBJ_TYPE FW_SIZE(4, little-endian) CHECKSUM
  FW_SIZE = 升级包文件大小 - 128（即 bin payload 大小，见 computeFwSize）

START 应答
FC F1 RESULT MTU(1, =251) PRN(1, =3) CHECKSUM

DATA 请求（首包 = 128 字节头信息；后续 = bin payload 分片）
F2 DATA... CHECKSUM

DATA 应答
FC F2 RESULT CHECKSUM

END 请求
F3 CHECKSUM

END 应答
FC F3 RESULT CHECKSUM
```

当前规格参数：

- 固件大小范围：`0x30000 ~ 0x3C000`（约 192KB ~ 240KB）  
  注：规格书正文印作 `0x3000 ~ 0x3C000`，实际按 `0x30000` 下限执行。代码只告警不拦截
  （`MIN_FW_SIZE` / `MAX_FW_SIZE`），最终以设备应答为准。
- MTU：251，GATT 实际数据约 244 字节
- PRN / Credit：3，规格书原文「固件返回 3，APP 每发送 3 个 DATA 包等待一次 ACK」
- ⚠️ **OTA 段没有「1 秒未应答即中断」这条红线**。本文此前写的那条是 §6.4 **图传**协议的参数
  （`MTU 247 / Credit 5 / 超时 1s`），被搬串了。图传有 `0x23` 累计确认与按包号重传，OTA 没有——
  OTA 的应答只出现在 §8 流程图「`loop [每 PRN 个 DATA 包]`」里，成败最终由 END 的整包校验裁决。
  端上各阶段的等待时长因此按设备实际忙碌程度给：DATA 窗口 1.5s、头信息握手 10s、END 整包校验 15s。

## 升级流程（规格书 §8）

1. **START**：`FF11` 写入 `0xF1`，设备初始化写入区与 DFU 状态，回 `0xFC` ACK（含 MTU / PRN）。
2. **头信息握手**：第一个 `0xF2` 包承载升级包文件最前面的 128 字节头信息（设备按首包长度识别）。
   设备校验 `OTAINFO`、头部版本、面板类型、头部 CRC16、版本号后回 ACK。
   `RESULT != 0x00` 即停止升级，并按结果码提示失败原因。
   ⚠️ **「不应答」与「回错误码」是两回事**：包不对/面板不匹配/CRC 不过设备都会明确回 `0x0A~0x0E`；
   等到超时只可能是设备侧 OTA 状态没复位。所以端上等 10s（START 后设备要初始化写入区、擦 Flash），
   超时后按「会话卡死」处理——断链复位再整轮重来一次，而不是提示用户去查面板型号。
3. **数据传输**：后续 `0xF2` 包承载从升级包第 129 字节起的原始 bin payload 分片，按 PRN 信用窗口收 ACK。
   设备对后续 F2 包不再校验长度，直接缓存写入并累计 `total_bytes`。
   ⚠️ **收尾不足一个 PRN 窗口的那 1~2 包收不到 DATA ACK，这是正常的**：设备每收满 `prn` 包才回一次。
   包数不是 `prn` 的整数倍时（673 包 / PRN=3 → 最后一窗只剩 1 包）必然等不到最后那次应答，
   端上**不得**据此判失败——现场表现正是「已发送 673/673 包后未在 1.5s 内应答（疑似丢包）」，
   而数据其实已全部发出。收尾窗口的 ACK 按可选处理，直接进 END，成败交给下一步的整包校验。
4. **END 与整包校验**：APP 发 `0xF3`，设备校验 `total_bytes == bin_size` 且 `CRC32(payload) == bin_crc32`，
   通过回 `0x00`，否则回 `0x09`。成功后设备约 100ms 复位运行新固件。

## 发包前的本地预检（`assertPackageLooksRight`）

刷错固件不可逆，「传错文件」不该等刷到设备上才由错误码告诉用户。`prepareFirmware` 在发第一帧前
按下表解析头信息（**只读不改**，APP 仍原样发送这 128 字节），四类明确不对的直接终止：

| 检查 | 拦截理由 |
| --- | --- |
| 偏移 0 不是 `OTAINFO\0` | 根本不是 OTA 升级包（传错文件 / 下载被截断） |
| 头部长度字段 ≠ 128 | 不是本协议的包 |
| 声明的 bin 大小 ≠ 文件实际 payload 长度 | 包不完整 |
| 固件类型与设备面板不符（设备面板判得出时） | 刷错面板会变砖 |

**CRC16 / CRC32 只记日志不拦**：规格书没写这两个校验的多项式口径，本地算法与固件不一致时
误拦会把好包挡在门外；这两项本就该由设备校验（`0x0D` / `0x09`）。版本号不同形也只告警
（后端写 `V1.0.2`、包内写 `..._V102` 是正常的，真不匹配设备回 `0x0E`）。

设备面板由 `panelOfDevice(device)` 从 `screenType` 或分辨率换算（`3.7寸/480×720 → 3D7`，
`5.89寸/680×960 → 5D89`）；判不出返回 0，该项检查自动跳过，不误伤。

## 128 字节头信息（规格书 §6.3.4）

该头信息已由固件方预先打进升级包文件最前端，**APP / 小程序只负责按文件内容原样读取并发送**，
不自行计算 CRC16 / CRC32、不改写任何字段。

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 8 | 协议匹配字段 | 固定 `"OTAINFO\0"`，ASCII |
| 8 | 1 | 头部格式版本 | 当前 `1` |
| 9 | 1 | 固件类型 | `1` = 3D7 面板，`2` = 5D89 面板 |
| 10 | 2 | 头部长度 | 固定 128（`0x80 0x00`），小端 |
| 12 | 4 | 原始 bin 文件大小 | 不含本 128 字节头，小端 |
| 16 | 4 | 原始 bin CRC32 | 不含本头的 payload CRC32，小端 |
| 20 | 2 | 版本号字符串长度 | ≤ 104，小端 |
| 22 | 2 | 头部 CRC16 | 覆盖偏移 0~21 + 24~127，小端 |
| 24 | len | 版本号 ASCII 字符串 | 格式见下 |
| 24+len | 104-len | 填充 | `0x00` |

版本号按 `_` 拆分为 6 段：产品前缀（固定 `BR1601A02`）、构建日期（6 位）、SVN 版本（`r` + 4 位）、
项目号（固定 `5139`）、面板型号（`3D7` 或 `5D89`）、固件版本（`V` + 3 位）。

完整示例：`BR1601A02_260702_r8285_5139_5D89_V100`

## 结果码

| 码 | 含义 | 常见原因 |
| --- | --- | --- |
| `0x00` | 成功 | — |
| `0x01` | 校验或芯片信息错误 | — |
| `0x02` | ACK 超时 | — |
| `0x03` | 主机主动终止 | — |
| `0x04` | 设备主动终止 | — |
| `0x05` | 设备状态错误 | **最常见的是「上一轮 DFU 半途中断，设备状态机还停在升级态」**。复用同一条 GATT 连接再 START 只会一直被拒；必须断链让设备复位后重连重发。`ota-ble.upgradeFirmware` 已做：失败即断链，遇 0x05 自动断链复位重试一次，仍被拒才提示用户断电重启设备 |
| `0x06` | 不支持的 opcode | — |
| `0x07` | 资源不足 | — |
| `0x08` | 固件大小超限 | — |
| `0x09` | 参数错误 | END 阶段整包大小 / CRC32 不匹配 |
| `0x0A` | 协议匹配字段不匹配 | 非 OTA 包或文件损坏 |
| `0x0B` | 头部版本不兼容 | 工具链需升级 |
| `0x0C` | 固件类型与面板不匹配 | 5D89 固件刷到 3D7 设备 |
| `0x0D` | 头部 CRC16 校验失败 | 传输丢包或文件截断 |
| `0x0E` | 版本号校验失败 | 格式 / 产品 / 面板不一致 |

这套结果码与普通图传 `0x7F` 通用应答码表不同。

## 失败后的连接处置（2026-08-11 现场教训）

DFU 任何一步失败/中断后，`upgradeFirmware` 都会**断开 OTA 链路**再抛错。留着这条连接的代价是
设备的 DFU 状态机停在半途，之后每次点升级都被回 `0x05`，用户只能重启设备才能再升——
实测就是「第一次传输超时，后面全是 0x05」。下一轮升级由 `ota.js ensureConnectedDevice` 重新扫连。

**整轮重试一次**：失败若发生在「设备还一个 payload 字节都没收下」的阶段（START 回 `0x05`、
或头信息握手无应答），`upgradeFirmware` 会自动断链 → 等 3s → 重连 → 从 START 整轮重来一次
（START 本身会重置设备的写入区与 `total_bytes`，所以重来是安全的）。两轮都不成才如实提示
「请断电重启电子纸设备」。已进入 payload 传输之后的失败**不自动重试**，交给用户重新发起。

> 与规格书的出入：§8 流程图在失败分支写的是设备「保持连接或等待 APP 重新发起 DFU」，
> 而真机是回 `0x05` 拒绝同一连接上的再次 START。上面这套断链复位是端上的兜底，
> 该差异建议向固件方确认。

## 成功判定

- 成败以 **APP 发 `END(0xF3)` 后设备回的 ACK 结果码**为准，`RESULT == 0x00` 才算升级成功。
- 未收到 END ACK 不能判「软成功」：`ota.js` 在这种情况下如实报「未确认(请重试)」，
  不上报 success、不把本地版本改成新版、保留升级包并开放「重新升级」。
- 头信息握手阶段 `RESULT != 0x00` 立即停止，并把 `0x0A~0x0E` 的设备语义透传给用户。

## 小程序端入口

- 设备详情页「固件升级」行：`detail.js goOtaUpgrade` —— 检测版本（**走后端接口，不需要蓝牙**）
  → 有新版本弹二次确认 → 「立刻更新」经 `enterOtaUpgrade` 确保连上设备后进升级页（`auto=1`）。
- 启动强制升级拦截：`app.js checkForcedFirmwareUpgrade` —— 选中设备 `upgradeMode === 'force'`
  时弹窗阻断，「稍后」关闭小程序 /「立刻更新」进升级页。
- 升级页：`subpackages/device/ota/ota.js`，唯一入参 `auto=1`（进页面自动开始）。
  升级前若未连接会**就地自动扫连**（`ensureConnectedDevice` → `activeDevice.ensureConnectedForAction`），
  连不上如实提示并保留「连接并升级」重试。
