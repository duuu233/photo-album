## 二、休眠设置：后端已补齐，前端需要实现

### 2.1 后端现状

- 设置：`POST /api/device/sleep`，支持 `mode=0` 关闭、`mode=1` 一次性、`mode=2` 周期。
- **本次新增查询**：`GET /api/device/sleep?deviceNo=...`，返回当前休眠计划，设备离线也能查。

```json
{
  "code": 0,
  "data": {
    "deviceNo": "XT20260001",
    "configured": true,
    "mode": 2,
    "enabled": true,
    "beginTime": null,
    "endTime": null,
    "sleepTime": "22:00",
    "wakeTime": "07:00",
    "updatedAt": "2026-10-27 21:00:00"
  }
}
```

- `configured=false`：从未设置过。
- `mode=0` 且 `configured=true`：用户主动关闭过休眠。
- `mode=1` 用 `beginTime/endTime`（`yyyy-MM-dd HH:mm`）；`mode=2` 用 `sleepTime/wakeTime`（`HH:mm`）。
- 只要求设备权限，设备离线可查；无权限 `403`、token 无效 `401`、服务异常 `5000`。

### 2.2 前端需要实现

1. 设备详情新增“休眠设置”入口。
2. 打开页面先调 `GET /api/device/sleep` 回显当前设置。
3. 三种模式：
   - 关闭：确认后提交 `{ "mode": 0 }`；
   - 周期：两个 `HH:mm` 选择器，不能相同，提交 `{ "mode": 2, "sleepTime": "...", "wakeTime": "..." }`；
   - 一次性：日期+时间选择器，必须开始早于结束，提交 `{ "mode": 1, "beginTime": "...", "endTime": "..." }`。
4. 前端只传本地时间，**不要自行转 UTC**；服务端负责转 UTC 下发。
5. 设备必须在线才能设置；离线提示「设备已离线」。

### 2.3 期望结果

- 打开页面能看到当前模式和对应时间；从未设置时显示“未开启休眠”。
- 设置周期后再次进入页面，回显 `mode=2`、`sleepTime/wakeTime` 与提交值一致。
- 设置一次性后回显 `mode=1`、`beginTime/endTime` 一致。
- 关闭后回显 `mode=0`、`configured=true`。
- 休眠窗口内设备断开，设备状态显示“休眠中”，不产生离线消息。
- 参数不合法返回 `4000` 并提示具体字段；设备离线返回 `4041`；无权限 `403`。

## 三、消息中心：后端完整，前端需要实现

### 3.1 后端已有接口

| 能力 | 接口 |
|---|---|
| 消息列表 | `GET /api/notification/list?deviceNo=&page=&size=&unreadOnly=` |
| 未读数 | `GET /api/notification/unread-count?deviceNo=` |
| 标记已读 | `POST /api/notification/read`（`ids` 为空 = 全部已读） |
| 新消息推送 | WS `notification.new`（需先订阅该设备） |

消息字段：`id`、`category`、`type`、`payload`、`read`、`createdAt`；列表额外返回 `total`、`unreadCount`。消息保留 90 天。

### 3.2 前端需要实现

1. **设备详情新增“消息中心”入口**，带未读角标（调 `unread-count`）。
2. 消息列表：
   - 分页加载，默认 `page=1&size=20`，支持下拉刷新/加载更多；
   - 支持“只看未读”开关（`unreadOnly=true`）；
   - 按 `type` 翻译文案，`payload` 展示关键参数；未知 `type` 显示通用文案。
3. 标记已读：
   - 进入消息详情或点击单条调 `POST /api/notification/read { deviceNo, ids: [id] }`；
   - 提供“全部已读”：`ids` 传空数组。
4. 实时更新：订阅设备后监听 `notification.new`，收到后刷新列表和未读数（服务端只推信号，不推详情）。
5. 空态：“暂无消息”；错误态显示重试。

### 3.3 期望结果

- 设备详情入口角标数与 `unread-count` 一致。
- 列表按时间倒序，分页无重复/漏项；`unreadOnly` 切换正确。
- 点击单条后该条不再未读，角标减 1；全部已读后角标消失。
- 收到 WS `notification.new` 后列表和角标在 1~2 秒内更新。
- 无权限 `403`、token 无效 `401`、服务异常 `5000` 有对应提示。

## 四、确认项 3：轮播中平台是否知道当前图片

**结论：目前不知道；固件不改的前提下，服务端准备用“设备下载行为反推当前图”作为备选方案。**

协议事实：

- `strategy_bin` 由设备在本地按策略计算要显示哪张图，平台只下发时间规则和列表地址。
- `strategy_ack` 只有 `result`、`ack_msgid`，没有 `imgid` / `imgurl`；心跳也没有当前图片字段。
- 顺序模式理论上可按时间推算，但设备实际切图时间会漂移；随机模式完全无法推算。

备选方案（服务端做，前端无需改接口）：

- 设备轮播时从反代下载 bin，路径是 `/oss/wififile/{deviceNo}/xxx.bin`，天然带设备号。
- 在 Nginx 访问日志（或下载前回调）记录**最后一次成功下载的图**，写入 Redis `currentImage:{deviceNo}`。
- 删除时服务端用这个值判断“删的是不是当前图”，是才自动 `play` 下一张。
- 前提：设备必须是**每次切图下载一张**，而不是收到策略后批量下载缓存。这一点需要先用测试设备观察 Nginx 日志确认；确认有效后再上线，失效时自动回退到下面的“轮播范围判断”。

**在反推上线前，删除交互按下面规则，前端按“服务端知道”来对接即可：**

1. 前端不自行判断当前图，正常先删老服务相册记录，再调 `POST /api/device/photo/delete`。
2. 删除时传 `nextImageUrl`（轮播中的下一张）；如果不知道，可以不传，服务端只删文件不切图。
3. 服务端判断“被删图是否在本轮轮播范围内”：
   - 配置了 `imgUrls`：判断被删 URL 是否在 `selected_images` 里；
   - 轮播全部相册：保守认为在范围内；
   - 在范围内且轮播运行中 → 服务端强切下一张（可能多刷一次屏）；
   - 不在范围内 → 只删文件，不切图。
4. 前端以响应里的 `current`、`deviceAction`、`deviceNotified` 为准展示结果，不依赖自己推算当前图。

> 说明：轮播中删除“范围内的非当前图”也会多刷一次屏；这是固件无法上报当前图时的取舍。下载反推上线后可以消除这次多余刷屏。

## 五、确认项 4：设备何时拉取图片列表

**建议：按“每次到点都重新拉 `/device/playlist`”设计。**

依据：

- 协议 3.9 / 3.10 描述的是“服务端下发更新时间，设备定时到服务端拉图”，`strategy_bin.path` 就是查询图片列表的地址。
- 服务端已按此实现：设备每次请求 `/device/playlist` 都返回当前相册列表；轮播保存、照片删除都会清 60 秒缓存。

建议固件确认并保持该行为。如果实测是“只在收到 `strategy_bin` 时拉一次”，则：

- 增删图片后必须重新下发一次 `strategy_bin` 才能生效；
- 需要产品确认“重发是否打断当前轮播”；
- 后端可以在照片删除/相册变更后自动重发，但要额外记录每台设备的轮播参数，属于后续增量。

## 六、轮播中重新选图的交互

**结论：不需要先关闭轮播，直接重新保存即可；保存后立即切到第一张选中图。**

前端流程：

1. 进入轮播设置页，先调 `GET /api/device/strategy?deviceNo=`。
2. 用返回的 `imgUrls` 回显勾选状态：
   - `imgUrls` 为数组：按数组勾选对应照片，顺序保持；
   - `imgUrls=null`：表示“轮播全部相册”，页面上全选；
   - `imgUrls=[]`：选择已全部失效，提示重新选择。
3. 用户修改选择后，直接调 `POST /api/device/strategy`，沿用原来的时间参数（`updateType`、`beginTime/endTime/timingTime` 或 `updateDays/updateTimeList`、`mode`、`idle`），只替换 `imgUrls`。
4. 保存成功后，前端立即调 `POST /api/device/play`，用**第一张选中的图**、`refresh=true` 播放，让屏幕马上切换。
5. 如果选择的是“全部相册”，第一张取相册顺序的第一张。

期望结果：

- 再次进入页面时，上一次选中的图片已勾选，顺序一致。
- 保存后屏幕立即切到第一张选中图，不需要等下一个轮播周期。
- `GET /api/device/strategy` 随后返回新的 `imgUrls`，后续轮播按新列表执行。
- 不选照片时不允许提交空数组（`4000`）。

> 当前后端保存轮播只下发 `strategy_bin`，不会自动播放；上面的“立即切第一张”由前端在保存成功后调用 `play` 完成。如果希望后端保证这个动作，可以后续给 `POST /strategy` 增加 `playFirst=true` 参数，前端就不用再调一次 `play`。

## 七、轮播后休眠开关（`idle`）

**接口和下发逻辑是正确的，但状态展示有一个缺口。**

- `POST /api/device/strategy` 和 `GET /api/device/strategy` 都有 `idle` 字段：
  - `0` = 轮播后休眠；
  - `1` = 不休眠（默认）。
- 前端开关映射：开启“轮播后休眠” → 传 `idle=0`；关闭 → 传 `idle=1`。
- 服务端原样保存，并在 `strategy_bin` 的 `idle` 字段下发给设备，协议 3.10 定义一致。

缺口：

- `idle` 的休眠是设备在轮播后的自主行为，和 `POST /api/device/sleep` 的休眠计划是两套东西。
- 服务端目前只有“休眠计划”才把断开判定为 `SLEEPING`；如果设备因为 `idle=0` 在轮播后断开，服务端可能显示 `OFFLINE` 并发送离线通知。
- 需要固件确认：`idle=0` 时设备是否会断开 MQTT、断开多久。确认后才能决定是否把“轮播中 + `idle=0` 的断开”判定为 `SLEEPING`；当前未改。

前端暂时按 `idle` 下发即可，状态展示仍以服务端 `status` 为准。
