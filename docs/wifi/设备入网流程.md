# WiFi 版设备入网流程

> 日期：2026-10-27
> 范围：App ↔ 设备 BLE/BluFi；设备 ↔ EMQX；本服务 ↔ EMQX/Redis/MySQL；老服务负责设备绑定。
> 说明：本文是 WiFi 版设备入网的最终流程，按此实现即可。搜索阶段（STEP 1）已联调通过，本文从配网开始。

## 一、关键约束

1. **绑定必须先于在线查询**：`GET /api/device/online` 会调用老服务 `checkPermission`，设备未绑定时返回 `403`。流程顺序是：BLE 配置 → 设备上线 → 老服务绑定 → 查询在线。
2. **BluFi 自定义消息必须带 `msgid`**：`mqtt_config`、`wifi_set_country_code` 都要带 `msgid`，设备回执用 `ack_msgid` 匹配；没有 `msgid` 无法匹配。
3. **`/api/device/info` 不返回产品型号**：它只返回在线状态、固件版本和影子。型号、尺寸、旋转、方向由 App 直接调老服务 `getProductByDevice`，不经过本服务。
4. **心跳间隔必须小于在线 TTL**：服务端配置 `xt.device.online-ttl-seconds=90`；心跳间隔大于 90 秒时必须同步调大该配置，否则设备会闪断离线。
5. **心跳 `type` 不作为 `statype`**：影子 `statype` 只认 login 的 `statype` 或心跳显式 `statype` 字段；心跳 `type` 不写入影子。
6. **国家码**：取值和格式按协议 2.2.4；App 通过自身方法获取国家信息，传真实国家码（`CN`、`US`、`JP` 等）；小程序使用通用值 `01`。运行时可通过 `POST /api/device/country` 修改。
7. **deviceId 格式统一**：广播名、绑定、MQTT `clientid`、`deviceNo` 都使用 12 位十六进制大写（例如 `A61F5AE3A12D`）。

## 二、入网流程

| # | 参与方 | 动作 | 关键参数 / 接口 | 期望返回 |
|---|---|---|---|---|
| 1 | 设备 | 开机 / 首次上电 / RESET | 进入配网模式 | 蓝灯闪烁（亮 3 秒灭 3 秒） |
| 2 | 设备 | 建立 BLE 广播 / WiFi 热点 | BLE：`IJ_{deviceId}`（12 位十六进制设备 ID）；热点：`XT_ESP_{MAC后4位}` / `1234567890` | 可被搜索 |
| 3 | App | 通过 BLE 连接设备（BluFi） | 设备已由 STEP 1 搜索流程选中 | BLE 已连接 |
| 4 | App → 设备 | 下发 WiFi 信息（标准 BluFi） | `opmode=0x00`（STA）+ SSID + 密码 | BluFi 标准回执 |
| 5 | App → 设备 | 下发 MQTT 参数（自定义 `mqtt_config`） | 见 3.1，必须带 `msgid` | `mqtt_config_ack.result=0`、`ack_msgid` |
| 6 | App → 设备 | 下发国家码 | 小程序固定 `01`，App 传真实国家码；见 3.2，必须带 `msgid` | `wifi_set_country_code_ack`，处理 `pending` |
| 7 | 设备 | 退出配网，连接 WiFi | — | 蓝灯常亮 30 秒（成功）/快闪（网络异常） |
| 8 | 设备 | 连接 EMQX | TCP `mqtt.boltfox.cn:11883`，账号 `xt-boltstar-device` | MQTT 已连接 |
| 9 | EMQX → 本服务 | 上报 `client.connected` webhook | `POST /internal/emqx/event` + `X-Webhook-Token` | Redis 在线 key、`iot_device` upsert、`device.status` |
| 10 | 设备 → 本服务 | 上报 `login` | 见 3.3 | 本服务回 `login_ack` |
| 11 | 本服务 | 记录登录信息 | `iot_device.firmware_version`、影子 `version/statype`、`iot_log` | 见 4.1 |
| 12 | 设备 → 本服务 | 上报 `heart` | 见 3.4 | 本服务按 `ack=1` 回 `heart_ack` |
| 13 | 本服务 | 续期在线、更新影子、判告警 | 在线 key 90s、影子 7 天、低电量/WiFi/TF | 见 4.2 |
| 14 | App → 老服务 | 完成设备绑定 | `userNo ↔ deviceNo`，老服务 `addUserProduct` 等 | 绑定成功 |
| 15 | App → 本服务 | 查询在线 | `GET /api/device/online?deviceNo=&since=` | `online=true` |
| 16 | App → 本服务 / 老服务 | 查询设备信息 + 产品规格 | `GET /api/device/info` + `getProductByDevice` | 电量/信号/版本 + 型号/尺寸/方向 |

> WiFi 版蓝牙广播：后台蓝牙广播 ID 填 `IJ_*`；前端匹配规则是广播名含 `*` 时按 `*` 拆分前后缀分别比对，`*` 覆盖的中间部分为 12 位 `deviceId`；不含 `*` 时完全匹配（BLE 版固定名 `EF6-370` / `EB-169`）。细则见 [对接开发进度.md](对接开发进度.md) STEP 1，搜索已联调通过。
>
> 绑定（步骤 14）与设备上线（步骤 8~13）并行：App 在 BLE 配置完成后即可调用老服务绑定，不必等设备 `login`。
>
> WiFi 热点 `XT_ESP_{MAC后4位}` 是协议附录的另一种配网方式；使用 BLE BluFi 时不需要连接设备热点。
>
> 老服务通过 `https://api.boltfox.cn` 访问；应用服务器已配置 hosts，将该域名指向内网老服务。
>
> EMQX webhook 示例（`X-Webhook-Token` 按服务端配置）：
>
> ```json
> { "event": "client.connected", "clientid": "A61F5AE3A12D", "username": "xt-boltstar-device" }
> ```

### 2.1 设备 MQTT 连接约定

| 项 | 值 |
|---|---|
| 协议 / QoS | MQTT 3.1.1，QoS 1 |
| 上行 Topic | `/device/report/{clientid}` |
| 下行 Topic | `/inkjoyap/{clientid}` |
| `clientid` | 等于 `deviceNo`（12 位大写十六进制） |
| 账号 | `xt-boltstar-device`（仅设备使用；服务端账号是 `xt-boltstar-server`，不写入设备） |

- 本服务订阅 `/device/report/+`，所有下行指令发到 `/inkjoyap/{clientid}`。
- App 不连接 MQTT：App 只通过 BLE 把 MQTT 参数写给设备，通过 HTTP/WebSocket 与本服务交互。
- 服务端按 Topic 中的 `clientid` 识别设备；JSON 里的 `clientid` 仅在 Topic 缺省时兜底。

### 2.2 配网 4 步与指令时序

| 步骤 | 页面文案 | App 动作 | 完成条件 |
|---|---|---|---|
| 1 | 手机网络正常 | 本地检测手机网络（WiFi / 蜂窝） | 有可用网络 |
| 2 | 设备网络配置已完成 | 通过 BLE 依次下发 WiFi 信息 → `mqtt_config` → 国家码，回执完成或超时后断开 BLE | WiFi 信息回执成功且 `mqtt_config_ack.result=0`；国家码成功、`pending=1` 或超时均不阻塞；必答回执失败停留本步提示重试 |
| 3 | 设备正在连接 WiFi | 展示状态；调用老服务完成设备绑定 | 绑定成功（设备侧无状态上报） |
| 4 | 设备正在连接云端 | 轮询 `GET /api/device/online?since=<配网开始毫秒>` | `online=true`，停止轮询进入成功页 |

- 3 条 BLE 指令全部在步骤 2 完成；步骤 3 开始后设备已退出配网，BLE 可能断开，不能再补发指令。
- 指令顺序固定：WiFi 信息 → `mqtt_config` → 国家码。
- 绑定在步骤 3 期间完成；绑定成功后开始步骤 4 轮询，绑定失败提示重试，不开始轮询。
- 轮询间隔 1~2 秒，最长 60 秒；轮询超时提示「设备联网超时，请检查 WiFi 密码或信号后重试」；`503` 表示权限服务不可用，保留页面稍后重试，不按配网失败处理。
- BLE 指令回执超时时间由 App 设定（建议 5 秒）；超时可重试，重试必须使用新的 `msgid`。
- 设备只支持 2.4GHz WiFi；SSID 和密码通过 BluFi 直传设备，不经过本服务，App 需提示仅支持 2.4G。
- 重新配网只能由设备端重置触发，App 无法远程触发，也没有“删除设备”操作；相关显示与交互见 [待办项.md](待办项.md)。

## 三、App 下发给设备的具体参数

BluFi 自定义消息使用 JSON 文本（UTF-8），单帧最大 64K；帧封装按乐鑫 BluFi 官方 demo（EspBluFi）实现。设备固件 V0.1.1 及以上支持自定义配置消息。

### 3.1 MQTT 参数 `mqtt_config`

```json
{
  "msgid": "1756108400173123",
  "action": "mqtt_config",
  "data": {
    "host": "mqtt.boltfox.cn",
    "port": 11883,
    "usr": "xt-boltstar-device",
    "pwd": "<设备 MQTT 密码>"
  }
}
```

| 字段 | 值 | 说明 |
|---|---|---|
| `msgid` | 13 位毫秒 + 3 位随机（16 位） | App 生成，需全局唯一；设备回执原样放入 `ack_msgid` |
| `host` | `mqtt.boltfox.cn` | `iot.boltfox.cn` 也可，两者解析到同一公网 IP |
| `port` | `11883` | TCP MQTT；1883 未开放，8883 TLS 未启用 |
| `usr` | `xt-boltstar-device` | 设备侧账号，不使用 `xt-boltstar-server` |
| `pwd` | 设备 MQTT 密码 | 与 EMQX `xt-boltstar-device` 账号一致；不写入仓库 |

- `host`、`port`、`usr`、`pwd` 是固定值，由后端单独提供给前端；不写入文档、不提交仓库，本服务不提供获取 MQTT 凭证的接口。
- App 需等待 `mqtt_config_ack`；超时或 `result!=0` 时提示配网失败并允许重试，重试必须换新的 `msgid`。`result` 的具体错误码由固件定义，前端按失败处理即可。

设备回执：

```json
{
  "action": "mqtt_config_ack",
  "data": { "result": 0, "ack_msgid": "1756108400173123" }
}
```

- `result=0` 成功；非 0 失败。
- `mqtt_config` 不包含 clientId；设备使用自己的 clientid，服务端要求它等于 `deviceNo`（例如 `A61F5AE3A12D`）。

### 3.2 国家码 `wifi_set_country_code`

```json
{
  "msgid": "1756108400180123",
  "action": "wifi_set_country_code",
  "data": { "country": "01" }
}
```

设备回执：

```json
{
  "action": "wifi_set_country_code_ack",
  "data": {
    "result": 0,
    "pending": 1,
    "ack_msgid": "1756108400180123"
  }
}
```

- `country` 使用 ISO 3166-1 alpha-2；世界通用模式为 `01`。只能传协议 2.2.4 列表内的值。
- 小程序统一传 `01`；App 通过自身方法获取国家信息，传真实国家码 `CN`、`US`、`JP` 等，无法获取时传 `01`。
- `pending=1` 优先于 `result`，表示设备暂缓执行；App 继续配网，最终生效值以心跳 `country_code` 为准。
- 无 `pending` 且 `result!=0` 时表示设置失败，提示用户重试（换新 `msgid`）；重试仍失败则继续配网，不影响 WiFi 连接。

### 3.3 登录 `login`

```json
{
  "action": "login",
  "clientid": "A61F5AE3A12D",
  "msgid": "1712800547780",
  "stamac": "A61F5AE3A12D",
  "data": { "ver": "xtap_001", "statype": "2" }
}
```

- `clientid` = 设备编号 = 本服务 `deviceNo`；服务端按 Topic 中的 `clientid` 识别设备。
- `stamac` = MAC，通常与 clientid 相同。
- `ver` = 固件版本，写入 `iot_device.firmware_version` 和影子 `version`。
- `statype` = 基站类型；`2` 表示 WiFi 基站；缺省时不覆盖影子已有值。
- 没有 `msgid` 时本服务不回 `login_ack`，但登录仍会生效。
- 本服务回 `login_ack`：

```json
{ "action": "login_ack", "data": { "ack_msgid": "1712800547780" } }
```

### 3.4 心跳 `heart`

```json
{
  "action": "heart",
  "clientid": "A61F5AE3A12D",
  "msgid": "1712800547781",
  "stamac": "A61F5AE3A12D",
  "data": {
    "type": 3,
    "ack": 1,
    "tf": "present",
    "tfsize": 1000,
    "tfused": 100,
    "battery": 86,
    "wifi_rssi": -46,
    "version": "0.1.2",
    "country_code": "1",
    "fpga_ver": "0.0.1"
  }
}
```

- `ack=1` 且带 `msgid` 时本服务回 `heart_ack`；`ack!=1` 或缺 `msgid` 不回。
- 本服务把 `battery`、`wifi_rssi`、`tf/tfsize/tfused`、`version`、`country_code`、`fpga_ver` 写入影子。
- 可选字段 `wifi_ch`、`wifi`、`ble`、`ble_rssi`、`wifi_name`、`orientation` 出现时同样写入影子，分别对应 `wifiCh`、`wifiOn`、`bleOn`、`bleRssi`、`wifiName`、`orientation`。
- `tfsize`/`tfused` 单位按协议为 MB；服务端按数值字符串存储，查询时转数字。
- `type` 是消息类型，不写入 `shadow.statype`；`statype` 以 login 或显式心跳 `statype` 为准。
- 固件心跳间隔建议 30~60 秒，必须小于在线 TTL（90 秒），否则设备会闪断离线。

## 四、本服务写入的存储（联调验证）

### 4.1 连接 / 登录

| 存储 | 内容 | 说明 |
|---|---|---|
| Redis `xt:boltstar:dev:online:{deviceNo}` | `"1"`，TTL 90 秒 | `client.connected`、`login`、`heart` 都会续期 |
| Redis `xt:boltstar:dev:shadow:{deviceNo}` | hash，TTL 7 天 | login 写 `version`、`statype` |
| Redis `xt:boltstar:notify:state:{deviceNo}` | `"online"` / `"offline"` | 通知状态迁移键，无 TTL |
| Redis `xt:boltstar:dev:registered:{deviceNo}` | `"1"`，TTL 1 天 | 心跳自动注册去重标记 |
| MySQL `iot_device` | `device_no`、`online=1`、`last_online_at`、`firmware_version` | upsert（异步，查询稍等）；`firmware_version` 来自 login `ver` |
| MySQL `iot_log` | `category=ONLINE_OFFLINE`、`action=login`、`msgid`、`detail=ver=..., statype=...`、`result=SUCCESS` | 每次 login 一条；心跳不逐条写日志 |
| MySQL `iot_notification` | `category=DEVICE`、`type=DEVICE_ONLINE`、`payload={}` | 状态从离线变在线时生成一次 |
| WS | `device.status`，`online=true` | 订阅并具备设备权限后推送，不落库 |

`client.connected` webhook 还会写 `iot_log` 的 `action=connected`；设备 login 也会触发在线状态，所以没有 webhook 时 login 仍能注册设备。

### 4.2 心跳

| 存储 | 内容 |
|---|---|
| Redis `online:{deviceNo}` | 续期 90 秒 |
| Redis `shadow:{deviceNo}` | `battery`、`wifiRssi`、`wifiCh`、`wifiOn`、`bleOn`、`bleRssi`、`wifiName`、`tfStatus`、`tfTotal`、`tfUsed`、`espVersion`、`fpgaVersion`、`orientation`、`countryCode`、`lastHeartAt`，TTL 7 天；`statype` 以 login 或显式心跳 `statype` 为准 |
| MySQL `iot_notification` | `LOW_BATTERY`、`WIFI_WEAK`、`TF_FULL`；条件出现时发一次，恢复后重置 |
| MySQL `iot_log` | 心跳不写日志；只有命令、ack、登录等会写 |

### 4.3 不参与入网的存储

- `iot_device_strategy`：只有 App 调 `POST /api/device/strategy` 并成功下发后才写入。
- `iot_notification_read`：只有 App 标记已读才写。
- `iot_alarm`：已下线，不再读写。

## 五、国家码处理

### 5.1 配网阶段（BluFi）

- 使用 `wifi_set_country_code`，字段是 `country`，不是 `country_code`。
- 取值：ISO 3166-1 alpha-2（`CN`、`US`、`JP` 等）；世界通用模式 `01`。仅支持协议 2.2.4 列出的国家码。
- 必须带 `msgid`；用 `wifi_set_country_code_ack.ack_msgid` 匹配。
- `pending=1` 优先于 `result`：表示稍后执行，App 继续配网，最终生效值以心跳 `country_code` 为准。
- 国家码影响 WiFi 信道和发射功率；传错可能导致连不上或不符合当地法规。

### 5.2 小程序与 App 的取值

- **小程序统一传 `01`**：取值按协议 2.2.4，`01` 是世界通用安全模式，兼容所有地区，代价是 WiFi 信道范围和发射功率受限。
- **App 传真实国家码**：App 通过自身方法（系统区域、定位或用户选择）获取国家信息，传 `CN`、`US`、`JP` 等真实值；无法获取时传 `01`，不要猜测。
- 设备国家与设备实际使用地一致；用户跨境时，以设备所在地为准。

### 5.3 心跳里的 `country_code`

- 设备心跳上报 `country_code`，世界通用模式为 `1`；具体国家为固件上报的国家码。
- 本服务把原始值写入影子 `countryCode`，不做 ISO 映射。
- App 展示时把 `1`/`01` 映射为“世界通用模式”，其他值直接展示原始值。

### 5.4 运行时修改（设备已在线）

```
POST /api/device/country
{ "deviceNo": "A61F5AE3A12D", "countryCode": "CN" }
```

```json
{ "code": 0, "msg": "ok", "data": { "msgid": "1756108400181" } }
```

- `countryCode` 允许两位大写字母或 `1`/`01`；只能传协议 2.2.4 列表内的国家码。
- 服务端把 `"1"` 归一化为 `"01"`，通过 MQTT 下发 `country` 指令，数据字段是 `country_code`（与 BluFi 的 `country` 区分）。
- 当前控制指令只保证“已下发”；设备回 `country_ack`，服务端记录日志，不提供执行结果查询接口。
- 运行时修改需要设备在线，且 App 已绑定/有权限；设备离线返回 `4041`，无权限返回 `403`，参数不合法返回 `4000`。

## 六、返回值与错误

### 6.1 `GET /api/device/online`

```
GET /api/device/online?deviceNo=A61F5AE3A12D&since=1756108400000
Header: userToken
```

| 参数 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `deviceNo` | query | 是 | 12 位大写十六进制 |
| `since` | query | 否 | 配网开始毫秒时间；只有 `lastOnlineAt > since` 才返回 `online=true` |
| `userToken` | Header | 是 | 用户 token，服务端实时校验设备权限 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "deviceNo": "A61F5AE3A12D",
    "online": true,
    "lastOnlineAt": "2026-10-27 10:00:00"
  }
}
```

设备从未上线时（离线但仍上线过时 `lastOnlineAt` 为最后一次上线时间）：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "deviceNo": "A61F5AE3A12D",
    "online": false,
    "lastOnlineAt": null
  }
}
```

- `lastOnlineAt` 为 `Asia/Shanghai` 的 `yyyy-MM-dd HH:mm:ss`；设备从未上线时为 `null`。
- `since` 传本次配网开始毫秒时间；设备未登记或 `lastOnlineAt <= since` 时返回 `online=false`，避免重配网旧连接误判。
- 未绑定设备返回 `403`；token 无效返回 `401`；参数缺失或类型错误返回 `4000`；老服务不可用返回 `503`；其他异常返回 `5000`。

### 6.3 BLE 回执

| 消息 | 字段 | 说明 |

| `mqtt_config_ack` | `result`、`ack_msgid` | `result=0` 成功 |

### 6.4 WebSocket `device.status`

订阅该设备且具备设备权限后（订阅方式见 [前端对接文档_草稿.md](前端对接文档_草稿.md) 1.6），设备上下线会推送：

```json
{ "type": "device.status", "deviceNo": "A61F5AE3A12D", "online": true }
```

- 只推信号，不推详情；收到后调 6.1 / 6.2 补查。
- 设备未绑定时收不到该设备的推送，不能替代 6.1 轮询。
- 升级期间设备断连不推送 `online=false`。

### 6.5 设备绑定（老服务）

- 绑定由老服务完成，本服务不提供绑定接口；App 在 `mqtt_config_ack.result=0` 后调用。
- 本服务所有设备接口都实时调用老服务 `checkPermission`，未绑定时返回 `403`。
- 设备已绑定到其他账号时的处理以老服务返回为准，前端展示对应错误提示。
