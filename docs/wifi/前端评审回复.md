## 二、P0 逐条回复

### 1. 设备标识与设备类型

**评审意见**：`deviceNo`、6 字节设备 ID、`userProductId` 三者关系未定义；也没说如何区分 WiFi/BLE 设备。

**回复**：

- 本服务的 `deviceNo` 是设备 MQTT 登录的 `clientid`。文档里的 `XT20260001` 是占位示例；协议示例里的 `A61F5AE3A12D` 更接近真实格式（12 位十六进制 MAC，无冒号）。
- 6 字节 ID `AA:BB:CC:DD:EE:FF` → 去冒号 `AABBCCDDEEFF`（12 位）。如果固件登录上报的 `clientid` 就是这 12 位，则 `deviceNo` 就是它。
- `userProductId` 是老服务绑定记录主键，本服务不使用；本服务不保存用户-设备绑定关系。
- 设备通信类型：本服务只处理 WiFi 设备；BLE 设备不连 MQTT。BLE/WiFi 类型应由老服务设备列表返回 `commType`（建议值 `BLE` / `WIFI`），本服务无法替老服务补。
- 需要老服务配合：`getUserProductList` / `getUserProductDetail` 增加 `deviceNo`、`commType`。这是老服务改造，不在本仓库。
- 文档立即补充：`deviceNo` 格式、大小写、冒号处理、三者的关系图；3.6 的 `deviceId` 给出完整示例。

**状态**：部分接受；文档可立即改，老服务字段需老服务排期。

### 2. 登录凭证

**评审意见**：老服务同时下发 `userToken` 和 `jwtToken`，新服务认哪个？401 后重新登录还是刷新？

**回复**：

- 新服务只认登录接口返回的 `userToken`。HTTP 请求放 Header `userToken`；WS 握手放 Header `userToken`，也兼容 `?token=`（仅为兼容，推荐 Header）。
- 新服务**不读取 `jwtToken`**，也不做 token 刷新。401 表示 `userToken` 失效，前端应重新登录。
- 新服务每次请求实时调用老服务 `GET /Client/User/getUserInfo`，用 `userToken` 鉴权。
- `?token=` 会进入 Nginx access log，建议 Nginx 对 `token` 参数脱敏；WS 优先用 Header。

**状态**：接受，文档已可明确。

### 3. 时区与时间格式

**评审意见**：写死 Asia/Shanghai 对海外用户错时；`yyyy-MM-dd HH:mm:ss` 在 iOS 上解析失败。

**回复**：

- 当前实现确实按 Asia/Shanghai：休眠时间由服务端转 UTC；轮播 `beginTime`/`endTime` 原样下发，没有转 UTC。两处口径不一致，评审指出的问题成立。
- 建议方案（STEP 5 设备控制一起做）：
  - 休眠、轮播入参增加 `timeZone`（IANA，如 `Asia/Tokyo`）或 `utcOffsetMinutes`；不传时默认 `Asia/Shanghai` 保持兼容。
  - 更合理的是设备维度保存时区：配网时由 App 上报，服务端按设备时区换算，避免用户出差时手机时区变化影响相框。
  - 轮播时间明确为“设备本地时刻”，跨午夜（如 `22:00`–`06:00`）和 `beginTime == endTime` 的语义需要产品定义。
- 时间字段：建议方案 A（推荐）——保留现有字符串，同时给关键时间字段增加毫秒时间戳，如 `createdAtTs`、`lastOnlineAtTs`、`sentAtTs`、`updatedAtTs`。这样 iOS 不解析字符串也能用，老代码不破坏。方案 B（ISO 8601 带偏移）也可以，但会改变现有字段格式。
- 本期 STEP 1~3 先用现有字符串；前端临时可用 `new Date(str.replace(' ', 'T'))` 解析。正式时间戳字段在 STEP 0 的兼容性改造里加。
- **拆分结论**：时间戳是响应格式问题，放 STEP 0（纯新增字段，前端不用二次改）；时区换算是设备控制语义问题，放 STEP 5（休眠/轮播），海外首发临近再提前。两者不要绑在一起。

**状态**：接受；时区换算放 STEP 5，时间戳字段放 STEP 0。

### 4. 错误码体系

**评审意见**：HTTP 状态与 body.code 混用；需要总表；4041/4044 一码多义；429 缺 `retryAfter`。

**回复**：

- 现有约定：
  - HTTP 401 = 未登录/token 失效；HTTP 404 = 路径不存在；HTTP 503 = 老服务不可用。
  - 业务错误统一 HTTP 200 + body `code`；`403`、`429` 也是 HTTP 200 + body code。
- 接受评审建议：
  - 在文档增加「HTTP 状态 + body.code + 含义 + 可重试 + 前端动作」总表。
  - 新增 `4040` 设备不存在；`4041` 只表示设备离线；`4044` 只表示任务不存在/过期。后台设备详情缺失改用 `4040`。
  - `429` 增加 `retryAfter`（秒），同时设置 HTTP Header `Retry-After`。投屏并发阈值是 `xt.play.max-concurrent=10`；图片列表限流是 10 次/分钟。
  - 明确 Nginx 413/502/504 可能返回 HTML，前端需要按网络错误兜底。
  - 明确 `msg` 只用于开发排查，前端按 `code` 做多语言。
- 4040/retryAfter 需要改代码；总表和 Nginx 说明是文档/运维。

**状态**：接受；STEP 0 完成代码和文档。

### 5. 固件升级 URL 安全

**评审意见**：App 传任意 URL 可让设备刷任意固件，属于设备劫持风险；应改为服务端按版本下发。

**回复**：

- 评审成立，当前 `POST /api/device/ota` 由 App 传 `url`，只校验 http/https，确实不安全。
- **已拍板：延用老服务现有的固件管理**。App 不再传任意 URL；服务端按 `deviceNo` + `type`/`version` 查老服务的固件信息（如 `newVersionNo`、`downloadPath`、`isUpdate`、`updateType`），校验后下发。
- 短期只做防御性校验：只允许 `https`，host 必须在固件/OSS 域名白名单内；不需要在本服务新建固件发布表。
- 新增 `GET /api/device/ota/check?deviceNo=` 代理老服务的更新信息，返回 `hasUpdate`、`version`、`size`、`releaseNote`、`force`。
- 分享用户是否允许升级需产品确认，由服务端按角色判定。
- 如果老服务没有可用的固件查询接口，再讨论是否在本服务建 `iot_firmware` 表；当前优先复用老服务。

**状态**：接受；短期白名单可在 STEP 6 做，中期发布表需要产品/运维确认。

### 6. 配网确认

**评审意见**：绑定前 403；重配网 `online=true` 可能是旧连接；`mqtt_config` 内容来源未说明。

**回复**：

- 三个问题都成立。
- 短期（STEP 2，已实现）：
  - `GET /api/device/online` 增加 `since` 参数（毫秒时间戳）：只有 `lastOnlineAt > since` 才返回 `online=true`。这样重配网时旧连接不会误判成功。
  - 明确推荐顺序：BLE 配置 → 老服务绑定 → 用 `since` 轮询在线。绑定失败时不要重复配网，先重试绑定。
- 中期（配网会话接口，STEP 2 后续）：
  - 新增配网会话：`POST /api/provision/session` 返回 `sessionId`、`mqttConfig`、`expireAt`；`GET /api/provision/status?sessionId=` 返回 `WAITING/ONLINE/EXPIRED`，只认 `loginAt > session.createdAt`。
  - 会话免设备权限，但必须有登录态 + 会话 ID + 频率限制，避免被枚举。
- `mqtt_config` 的字段来源：当前本服务不生成设备侧 MQTT 凭证（设备侧账号由设备使用，本服务只配置服务端账号）。需要老服务/运维/固件明确 host、port、username、password、clientId 的生成方式。会话接口可以原样返回，但前提是有可信来源。
- 绑定前后失败回滚：如果先绑定后配网，配网失败会留下“已绑定未联网”记录；建议配网成功后再绑定，或由老服务提供解绑/重试。需要老服务配合。

**状态**：部分接受；`since` 可做，会话接口和 `mqttConfig` 需要外部确认。

### 7. 无鉴权接口与内网信息

**评审意见**：管理后台无鉴权；设备图片列表无鉴权且 `deviceNo` 可枚举；OSS 公共读；前端文档写了内网地址。

**回复**：

- 管理后台：**已拍板不做鉴权**，前端直接在管理后台对接接口加功能。前提：`/admin/**` 只在内网/VPN 暴露，不能对公网开放；文档会标注风险。共享 token 仍保持空，不启用。
- 设备图片列表：接受签名建议。`deviceNo` 可枚举，需要设备级签名或设备 token。方案：`strategy_bin` 的 `path` 带 `ts` + `sig=HMAC(deviceSecret, deviceNo+ts)`，服务端校验有效期；或在设备登录时下发短期 token。需要固件配合（设备只是原样访问 URL，不需要验证签名，服务端验证即可）。
- OSS：建议私有桶 + 带过期时间的签名 URL，有效期覆盖设备下载耗时（如 10 分钟）。需要运维改 OSS 权限；当前代码生成 `binUrl` 的方式也要改。
- 文档拆分：接受。前端对接文档删除“内部接口”章节和内网地址，拆到单独的 `docs/内部接口文档.md`；变更记录对不兼容变更加 `⚠️ BREAKING`。

**状态**：接受；管理后台访问控制、OSS 私有桶、播放列表签名需要运维/固件配合，文档拆分本期做。

### 8. 投屏入参与相册数据

**评审意见**：`type` 未定义；图片规格/大小上限未定义；投屏后是否写老服务相册记录、TF 与相册如何对应未定义。

**回复**：

- `type`：本服务原样传给老服务 `/Client/Basic/imageDitheringBinDownload` 的 `type`，语义与 BLE 版一致：`0` 默认，`1` 为 480×720。`color=BWRYGB`、`imageDitheringModes=2` 由服务端固定。文档会写清。
- 图片规格：
  - 当前 Spring multipart 上限 `20MB` / `25MB`，`maxBinBytes=20MB`，超过返回 `4130`。
  - 服务端不裁剪、不旋转，原图直接送老服务转 bin；建议前端按设备物理分辨率裁剪后再上传。
  - 接受格式由老服务 `imageDitheringBinDownload` 决定；需要老服务确认 JPG/PNG/HEIC 支持范围，文档补上。
- 相册记录：
  - 本服务目前**不写**老服务的 `setUserProductUpload` / `editUserProductImgRecord`；投屏只负责转 bin、上传 OSS、下发。
  - WiFi 设备的轮播列表来自老服务 `getProductImgRecordList` 的 `imgBle`；「我的相册」仍应由老服务/前端维护。
  - WiFi 设备没有 BLE 版的 `imgIndex` 槽位概念；设备按 `strategy_bin` 的 `path` 拉列表。
  - `clean_tf` 只下发清空 TF 卡指令，不会清空老服务相册记录。是否需要同步清空，需要产品确认。
  - 需要产品明确：WiFi 投屏是否还要写相册、由谁写、清空 TF 是否同步清空相册。
- `userNo`：**已拍板去掉必填**。服务端从 `userToken` 解析 `userNo`（`AuthInterceptor` → `LegacyUserClient.getUserInfo`），投屏任务存 `userNo`，失败通知用这个 `userNo`。App 不需要再传，也不会再出现“与登录用户不一致”的 4000。

**状态**：部分接受；`type`/规格/`userNo` 可改，相册归属需要产品/老服务确认。

### 9. Long 型 ID 按字符串返回

**评审意见**：通知 `id`、日志 `id` 是数字，JS 可能丢精度；`ids` 入参也应字符串。

**回复**：

- 接受。`msgid` 已经是字符串；通知 `id`、后台日志 `id`、`play/ota` 的 `msgid` 统一按字符串返回。
- 实现方式：只对 ID 字段加 `@JsonSerialize(using = ToStringSerializer.class)`，不要全局序列化 Long，否则 `battery`、`binSize` 也会变字符串。
- `ids` 入参改成 `List<String>`，服务端解析为 Long；兼容数字和字符串。
- 需要在文档「通用约定」写一句：所有 ID 按字符串收发。

**状态**：接受；STEP 0 做。

## 三、P1 逐条回复

### 10. 控制指令的执行结果

**评审意见**：轮播、休眠、国家码只返回 msgid，用户不知道设备是否生效。

**回复**：

- 接受。协议各指令都有 `*_ack`，服务端已收到，只是当前只做 pending 删除和日志。
- 方案：
  - 新增通用指令状态：Redis Hash 记录 `action`、`status`、`result`、`sentAt`、`ackAt`，TTL 1 小时。
  - `GET /api/device/command/status?msgid=` 返回 `SENT|SUCCESS|FAILED|TIMEOUT`。
  - WS 推送 `{type:"command.result", deviceNo, msgid, action, status, result}`。
  - 超时统一 30 秒，按 action 可配置。
  - 休眠返回两个 `msgids`，两个都 SUCCESS 才算成功。
- 需要新增代码，放 STEP 5 设备控制。

**状态**：接受；STEP 5。

### 11. 幂等与重复下发

**评审意见**：小程序网络层会自动重试，POST 指令可能重复下发。

**回复**：

- 接受。POST `/api/device/*` 支持 Header `Idempotency-Key`：前端每次用户操作生成 UUID，重试复用。
- 服务端 Redis `SETNX` 占位 + 缓存首次响应，TTL 10 分钟；同一 key 返回首次结果，不再下发。
- 投屏尤其需要：重复投屏会多生成 bin、多下发、多写相册。
- 需要新增过滤器/拦截器，放 STEP 0，STEP 3 投屏先用上。

**状态**：接受；STEP 0 / STEP 3。

### 12. 批量接口

**评审意见**：设备列表 N 台设备就是 N 次 online + N 次 unread-count；WS 需要多设备订阅。

**回复**：

- 接受。计划：
  - `GET /api/device/online/batch?deviceNos=a,b,c` 或 POST body，上限 100；无权限设备单条返回 403，不整体失败。
  - `GET /api/notification/unread-count/batch?deviceNos=...`，上限 100；后续可加“当前用户全部设备未读总数”。
  - WS `subscribe` 支持 `deviceNos` 数组，返回逐台结果；单连接建议最多 100 台，超过返回错误。
- 注意：批量接口内部仍要对每台设备调 `checkPermission`，老服务压力不会消失，但前端请求数会下降。后续可与老服务协商批量权限接口。

**状态**：接受；STEP 4 / STEP 7。

### 13. WebSocket 协议细节

**评审意见**：`error` 不带 deviceNo/code；事件无时间戳；踢订阅无感知；多实例推送。

**回复**：

- 接受：
  - `error` 增加 `deviceNo`、`code`、`reqId`；`unsubscribed` 增加 `deviceNo`。
  - 所有事件增加 `ts`（毫秒）。`seq` 需要按设备维护递增序号（Redis），本期先做 `ts`，`seq` 后续。
  - 踢订阅增加 `{type:"subscription.revoked", deviceNo}` 信号；前端退出设备页并刷新列表。
  - 文档写明：订阅随连接失效，重连后需要重新 `subscribe`。
  - 心跳 90 秒；Nginx `proxy_read_timeout` 必须大于 90 秒（建议 120 秒）。
- 多实例：当前生产是单实例，`BoltStarPushSessionRegistry` 是内存结构；如果扩多实例，需要 Redis Pub/Sub 按设备/用户广播，踢订阅也要广播。本期先文档说明单实例限制，扩缩容前再实现。

**状态**：接受；STEP 4 / STEP 7，多实例单列。

### 14. 投屏状态细节

**评审意见**：`play.result` 失败不带原因；TIMEOUT 时长未写；投屏初始状态 `DOWNLOADING` 与 OTA `SENT` 不统一；`corrected` 状态查询没有；ack 1 的成功含义。

**回复**：

- 失败原因：接受。`play.result` 和 `GET /api/device/play/status` 增加 `result`（原始码）和 `reason`（`PLAY_DOWNLOAD_FAILED`/`PLAY_STORAGE_ERROR`/`PLAY_FAILED`）。
- TIMEOUT：当前投屏 ack 超时是 `xt.protocol.ack-timeout-seconds=60` 秒，超时扫描 10 秒；文档写明。
- 初始状态：**已拍板统一为 `SENT`**。投屏接口返回 `SENT`，收到 `100/106` 后进入 `DOWNLOADING`，与 OTA 状态机一致。前端进度条：`SENT` →「指令已下发，等待设备」；`DOWNLOADING` →「设备下载中 / 屏幕即将刷新」；`FLASHING` →「设备刷屏中」。
- `corrected`：接受，状态查询增加 `corrected`。
- ack `1`：当前按成功处理（`0/1/113`），依据是协议示例 `result:1`；需要固件确认 `1` 的确切含义，已记入待办。

**状态**：接受；失败原因/超时/`corrected` 在 STEP 3，初始状态待前端确认。

### 15. 轮播参数

**评审意见**：入参秒、出参分钟不对称；时区/跨午夜未说明；与老服务 `carouselInterval` 双数据源。

**回复**：

- 接受 `intervalMinutes`：新增可选入参 `intervalMinutes`，同时兼容 `timingTime`；优先用 `intervalMinutes`，两者都传时以 `intervalMinutes` 为准。
- 时区/跨午夜：见第 3 条。需要产品定义：轮播时间是否设备本地时间、跨午夜是否支持、`beginTime == endTime` 是否全天。
- 数据源：建议 WiFi 设备以新服务 `iot_device_strategy` 为准，老服务 `carouselInterval` 不再维护；如果老服务页面还要展示，需要新服务回写老服务或老服务改为调新服务。这是产品/老服务决策。

**状态**：接受 `intervalMinutes`；时区和数据源待产品/老服务确认。

### 16. 休眠两条指令非原子

**评审意见**：`wifimode` 和 `wifi_sleep` 两条指令，第一条成功、第二条失败时接口返回什么？设备中间状态怎么办？有没有查询接口？

**回复**：

- 评审成立。当前 `sleep` 依次下发 `wifimode` 和 `wifi_sleep`，第二条发布失败会抛 5000；第一条可能已经生效，设备可能处于“休眠模式已开、时间段未设”的中间状态。
- 方案（STEP 5）：
  - 返回结构化失败：`code=5000` 时 body 带 `stage`（`WIFIMODE`/`WIFI_SLEEP`）和已成功的 `msgid`，前端可提示“部分生效”。
  - 第二条失败时尽力补偿：再下发一次 `wifimode` 实时模式，尽量回到原状态。
  - 新增 `GET /api/device/sleep?deviceNo=` 回显最近一次休眠设置；服务端把最近配置存 Redis/MySQL。
  - 两条都成功才返回 `msgids`；否则返回错误 + `msgids`（已成功的）。
- 需要设备确认：设备收到 `wifi_sleep` 前是否会保持 `wifimode` 状态；补偿指令是否安全。

**状态**：接受；STEP 5，需固件确认中间状态。

### 17. 字段规范

**评审意见**：`payload.wifi_rssi` 下划线；空值口径；枚举未列全；心跳间隔；TF 单位。

**回复**：

- payload 驼峰：接受。`wifi_rssi`→`wifiRssi`、`tfsize`→`tfSize`、`tfused`→`tfUsed`；这是不兼容变更，文档会标 `⚠️ BREAKING`，前端一起改。
- 空值：建议统一为“字段始终存在，无值为 `null`”；`shadow` 也返回全部已知字段，缺的为 `null`。不全局配置 `NON_NULL`，避免字段消失。`/device/playlist` 的错误响应是设备侧特殊格式，单独说明。
- 枚举：文档补 `statype`、`tagType`、`tagDeviceCode`、`orientation` 等全表；`statype` 是字符串是因为协议原样上报字符串，服务端不转数字。
- 心跳间隔：需要固件确认；文档会写“电量最多滞后一个心跳周期”，具体秒数以固件为准。
- TF 单位：协议是 MB；服务端返回整数（`asLong`），如果设备上报小数会被截断。需要固件确认是否会有小数；如果有，改成 BigDecimal/字符串。

**状态**：接受；STEP 7 做 payload 驼峰和字段表，枚举/心跳/TF 先补文档。

### 18. 权限校验性能

**评审意见**：每请求实时调 `checkPermission`，列表页/批量/WS 会放大老服务压力；建议短缓存。

**回复**：

- 项目规范明确要求“每请求实时调老服务，不缓存”，所以本期不引入 Caffeine/Redis 权限缓存；这需要产品/安全确认并修改项目规范。
- 本期用批量接口减少前端请求数；批量内部仍逐台调权限，但可以并行/合并。
- 后续可讨论“只缓存有权限结果 30~60 秒 + 踢订阅失效 + 高危操作绕过缓存”，前提是修改规范并做安全评审。

**状态**：本期不采纳缓存；接受批量接口方案。

### 19. 上传与网关配置

**评审意见**：Spring multipart 默认 1MB、Nginx 默认 1MB，超限返回 HTML。

**回复**：

- 本服务 `application.yml` 已经是 `max-file-size: 20MB`、`max-request-size: 25MB`，`maxBinBytes=20MB`，不是 1MB/10MB 默认值。超过上限由 `MaxUploadSizeExceededException` 返回 `4130` JSON。
- 需要运维确认 Nginx：
  - `client_max_body_size` 建议 `25m`（略大于 Spring 的 20MB），让超限请求进到 Spring，统一返回 `4130` JSON。
  - `proxy_read_timeout` 建议 `120s`，覆盖投屏同步处理和 WS 90 秒心跳。
- 如果 Nginx 先拦，仍可能返回 HTML 413/504；前端按网络错误兜底。

**状态**：Spring 侧已满足；Nginx 配置交运维，文档补说明。

## 九、STEP 1 搜索补充（前端改造建议）

### 9.1 背景

- WiFi 版蓝牙广播名：`IJ_` + 设备 ID，示例：`IJ_E348C21ED428`。
- BLE 版是固定广播名，例如 `EF6-370`、`EB-169`，不含占位符。
- 后台目前同时配置了 WiFi 版广播和 BLE 版固定广播；不能只按某个固定前缀硬过滤。
- 前端现在用后台配置的完整广播名做**完全匹配**；WiFi 版后台会配置 `IJ_*`，完全匹配会搜不到。

### 9.2 推荐改法：`*` 通配匹配

后台“蓝牙广播 ID”只配置两种形式：

1. **固定广播名**（BLE 版）：如 `EF6-370`、`EB-169`，前端完全匹配。
2. **通配广播名**（WiFi 版）：配置 `IJ_*`。

前端匹配规则：

- 配置含 `*`：按 `*` 拆成 prefix / suffix，匹配 `name.startsWith(prefix)` 且 `name.endsWith(suffix)`；**被 `*` 替换的中间部分必须是 12 位**，作为 `deviceId`。固定 suffix 可以为空。
- 配置不含 `*`：`name === 配置值` 完全匹配。
- **不依赖 MAC**：iOS 拿不到 MAC，直接读广播 local name 即可；不需要拿 MAC 做比较。
- 如果前端已知目标设备的 `deviceId`（老服务设备列表返回），直接比较字符串；不知道时，展示所有 `IJ_` 候选，让用户选择。
- 绑定需要的 `deviceId` 格式（是否带冒号）由老服务决定，前端在绑定前转换。
- 按广播名去重、按 RSSI 排序。

### 9.3 后台配置建议

- WiFi 版：配置 `IJ_*`。
- BLE 版：配置固定广播名，如 `EF6-370`、`EB-169`。
- 如果同一产品同时有 WiFi/BLE 两版，配置两条：`IJ_*` + 固定名，前端匹配任意一条。
- 不需要其他通配写法，只认 `*`。

### 9.4 前端伪代码

```js
function matchBle(name, config) {
  if (!config) return null;
  if (config.includes('*')) {
    const [prefix, suffix] = config.split('*');
    if (!name.startsWith(prefix) || !name.endsWith(suffix)) return null;
    const deviceId = name.slice(prefix.length, name.length - suffix.length);
    return deviceId.length === 12 ? { deviceId } : null;
  }
  return name === config ? { deviceId: null } : null;
}

// configs 来自后台配置，例如 ['IJ_*', 'EF6-370', 'EB-169']
const matched = configs.map((c) => matchBle(name, c)).find(Boolean);
```

### 9.5 验收标准

- 配置 `IJ_*` 时，`IJ_E348C21ED428` 能命中，`deviceId=E348C21ED428`。
- 配置 `IJ_*ABC` 时，`IJ_E348C21ED428ABC` 能命中，`deviceId=E348C21ED428`。
- 配置固定 `EF6-370` / `EB-169` 时，只命中对应固定广播。
- 同一产品配置多个模式时，命中任意一个即可。
- 同一设备不重复出现，RSSI 排序正常；绑定后第 4 步轮询 `online=true` 成功。
- iOS 真机能从广播 local name 读到完整 `IJ_...` 名称（不是只放在 scan response）。

### 9.6 WiFi 产品规格查询与未知设备

- 搜索列表共用老接口，IoT 端不提供搜索列表接口，也不处理设备类型。
- WiFi 版调用新接口（老服务侧）：
  ```
  GET https://api.boltfox.cn/Client/Product/getProductByDevice?deviceNo=<12位deviceId>
  ```
  例如：`deviceNo=D0CF13F02FF8`。该接口专门按 WiFi 设备 ID 查询产品信息（尺寸、旋转、方向等），用于 App 展示和参数操作。
- 查到：根据返回值展示产品规格/型号，展示哪些字段由前端决定。
- 查不到、返回空或接口失败：设备信息处显示「未知设备」；**禁止连接**，点击直接弹窗「未知设备，请联系客服开通」。
- 按 `deviceNo` 缓存 5~10 分钟；**暂不做超时重试**，失败/超时按「未知设备」处理；重新进入搜索页时可再查一次。
- 小程序 request 合法域名需要增加 `api.boltfox.cn`。

### 9.7 iOS 与 MAC 的说明

- iOS CoreBluetooth 不提供外设 MAC 地址，只提供系统生成的 UUID 和广播数据；所以匹配不能依赖 MAC。
- WiFi 版广播名 `IJ_...` 已经把设备 ID 放在名称里，前端直接解析 12 位中间部分即可。
- 如果固件只把名称放在 scan response、不在 advertising packet 里，部分 iOS 版本可能拿不到；需要真机确认。
- 名称可以被伪造，绑定/权限仍由老服务校验；如果设备支持，连接后可用 BluFi/设备信息再校验一次 deviceId。

### 9.8 与产品型号的关系

- WiFi 版 `IJ_` 广播只有 `deviceId`，没有产品型号；型号/规格以 `getProductByDevice` 返回为准。
- BLE 版的固定广播名（如 `EF6-370`、`EB-169`）本身就是固定值，可以按名称区分 BLE 产品；但它们不是 WiFi 7.09/10.1/13.3 的型号标识。
