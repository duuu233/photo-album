# WiFi 版投屏画质问题分析

> 状态：draft（静态分析，未真机复现）
> 日期：2026-10-28，`main-wifi`
> 现象：WiFi 版投屏到设备上的图片效果很不理想（蓝牙版同类图片正常）

## 结论先看

两版在预览页**构图导出完全相同**，差别从「导出图交给谁转成设备图」开始：蓝牙版由小程序带齐参数调出帧接口、并对结果做尺寸铁闸；WiFi 版只把 jpg 和一个 `type` 交给 IoT 服务，由服务端「调用老服务转 bin」，**转换参数、算法和产物小程序都看不到、也不校验**。因此最可能的问题集中在服务端转换这一段，其次是 WiFi 机型的尺寸 / `type` 配置。

| # | 可疑点 | 可能性 | 在哪一侧 | 典型表现 |
| --- | --- | --- | --- | --- |
| 1 | 服务端转 bin 缺颜色 / 抖动参数，或用的不是蓝牙版那套出帧 | 高 | 服务端 | 颜色发灰、偏色、颗粒粗、细节糊 |
| 2 | `type` 对 WiFi 屏取错（一律传 `0` = 5.89 寸蓝牙屏策略） | 高 | 小程序 + 服务端约定 | 抖动 / 色彩策略不适配大屏 |
| 3 | WiFi 产品没配或配错宽高，导出图不是屏幕物理分辨率，且 WiFi 链路没有尺寸铁闸 | 中高 | 后台配置 + 小程序 | 模糊、马赛克、拉伸、比例不对 |
| 4 | 横竖向 / 旋转角按蓝牙屏口径套用 | 中 | 小程序 + 后台配置 | 图转了 90° / 180°、横竖反 |
| 5 | bin 的颜色索引 / 扫描顺序与 WiFi 固件不一致 | 中（若出现花屏、串色则为高） | 服务端 + 固件 | 串色、花屏、错位 |
| 6 | 两版共有的成像因素（大图缩放、jpg、电子纸本身） | 低 | 共有 | 与蓝牙版同一张图对比差不多 |

## 两条链路在出图之后的差别

| 环节 | 蓝牙版 | WiFi 版 |
| --- | --- | --- |
| 交给谁转 | 小程序直接调 `/Client/Basic/imageDitheringBinDownload` | `POST /api/device/play`，服务端再「调用老服务转 bin」（对接文档 1.1 超时说明） |
| 传的参数 | `color=BWRYGB`、`imageDitheringModes=2`、`type`、`file`（`utils/dithering.js:166`） | 只有 `deviceNo`、`type`、`file`（+ `refresh` / `addToCarousel`）（`utils/iot-api.js:35`） |
| 产物校验 | 帧字节数必须 = 宽 × 高 ÷ 2，否则不发（`result.js` 铁闸） | 不校验，返回的 `binSize` 只进日志 |
| 尺寸异常时 | 被铁闸拦下并报错 | 照常上传，由服务端处理 |

## 逐项分析

### 1. 服务端转换参数 / 算法（最优先确认）

- 蓝牙版 2026-07-22 起**不再用老服务转码的 `.bin`**，改走六色抖动出帧（`color=BWRYGB`、`imageDitheringModes=2`），2026-10-23 迁到我方 `/Client/Basic/imageDitheringBinDownload`，参数不变（见 [服务器出帧方案（历史）](../archive/designs/server-image-processing-ble-transfer.md) 2026-07-22 条）。
- WiFi 版的 `/api/device/play` 接口文档只写「调用老服务转 bin」，没说调的是哪个接口、带什么参数；小程序也只传了 `type`。
- 如果服务端调用的是蓝牙版已经弃用的老转码，或者调的是出帧接口但没带 `color` / `imageDitheringModes`（走了接口默认值），出来的效果就会明显比蓝牙版差。**这和「同一张图蓝牙版正常、WiFi 版差」最吻合。**

### 2. `type` 取值

- `dithering.typeForDevice` 只认 480×720 → `1`，其余一律 `0`（`utils/dithering.js:107`）。`0` 的原定义是「5.8 寸大设备 EF6-589（680×960）」的出帧策略。
- WiFi 结果页沿用同一个函数（`wifi-result.js` `run`），所以 WiFi 设备不论屏多大都传 `0`。
- 协议文档里设备内置图是 1200×1600（`XT相框通讯协议_V1.4.md` 开机图配置），对接文档的消息示例里出现过 `type=3`（`前端对接文档_草稿.md` 第 1008 行）。说明服务端 / 老服务可能有别的 `type` 取值对应 WiFi 屏，而小程序没传。
- 需要后端给出：WiFi 各机型应传的 `type`，以及 `type` 在转换里具体控制什么。

### 3. 导出尺寸与 WiFi 链路缺少铁闸

- 导出画布 = 设备记录的 `width × height`；**这两个字段缺失时回退 480×720**（`preview-page.js:11` `DEFAULT_DEVICE_SIZE`、`getDeviceCropSize`）。WiFi 产品若后台没配宽高，大屏拿到的就是 480×720 的小图，服务端放大后必然模糊、发块。
- 宽高配了但与屏幕物理分辨率或原生方向不一致（例如屏是 1200×1600，后台配成 1600×1200 或别的比例），服务端转换时要么缩放拉伸，要么行宽对不上导致错位。
- 预览出图有四个**静默回退原图**的出口（`coverCropOne` 三处 + `bakeEditedImage`，见 [图片投屏流水线](../architecture/image-projection-pipeline.md)「出图有四个静默逃生口」）。蓝牙版回退后会被帧长铁闸拦下；**WiFi 版没有铁闸，原图（任意尺寸、比例）会直接上传**，效果取决于服务端怎么缩放。
- WiFi 投屏日志（开发版 / 体验版结果页可复制）已经记了「接口宽高」「导出记录宽高」「实际像素」和 `play` 返回原文（含 `binSize`），可以直接判断这一项。

### 4. 横竖向与旋转角

- 已知问题：WiFi 产品接口宽 > 高时，预览「竖向 / 横向」显示反了（[WiFi版投屏与设备详情](../changes/2026-10-27-WiFi版投屏与设备详情.md)「已知问题」）。
- 导出角沿用蓝牙屏口径：横向取 `rotationDegree`（缺失按 270°），竖向取 `verticalRotation`（缺失按 0°）（`utils/device-rotation.js`）。WiFi 屏的安装方向、服务端或固件会不会再转一次，都还没确认；任何一边多转或少转都会让成像方向不对。
- 这一项主要表现为方向错，不是画质发糊；但如果宽高与屏幕方向不一致又叠加了旋转，也会出现拉伸。

### 5. 颜色索引 / 扫描顺序

- 蓝牙版的六色索引映射是按蓝牙固件核对过的；WiFi 设备是另一套固件（ESP32），bin 格式只在服务端和固件之间约定，协议文档的 `play` 指令只给下载地址，没定义 bin 格式（`XT相框通讯协议_V1.4.md` `play`）。
- 如果服务端给 WiFi 固件的 bin 仍按蓝牙屏的色序或扫描方式生成，会出现串色、花屏、错行。看到的若是这类现象，这一项优先级最高。

### 6. 两版共有的因素（排除用）

- 导出 jpg 质量 0.92（`preview-page.js` `EXPORT_QUALITY`），在设备分辨率上对六色量化影响很小。
- 超大原图一次缩到设备尺寸时 canvas 缩放可能产生摩尔纹，抖动后会放大；但蓝牙版同样经过这一步。
- 电子纸六色本身与手机预览的全彩差距很大。若同一张图在同尺寸蓝牙设备上效果也差不多，则不属于 WiFi 版问题。

## 定位步骤（按成本从低到高）

1. **看投屏日志**（开发版 / 体验版结果页「复制」）：核对「接口宽高」是否等于屏幕物理分辨率、「实际像素」是否等于接口宽高、导出角是多少；`play` 返回里的 `binSize` 是否等于 宽 × 高 ÷ 2（4bpp 六色时）。宽高缺失、像素不符或 `binSize` 对不上，直接锁定第 3 / 5 项。
2. **测试图投屏**：投一张六色纯色条 + 灰阶渐变 + 细网格 + 「上 / 左」方向标记的测试图。纯色条错位→第 5 项；方向标记错→第 4 项；网格糊或比例不对→第 3 项；纯色对但渐变、照片很差→第 1 / 2 项。
3. **对照同一张导出图的两种转换**：把日志里的导出 jpg 用蓝牙版参数（`BWRYGB` / `2` / 对应 `type`）调出帧接口，与 `binUrl` 下载的 bin 按同一调色板解码成 png 对比。两者差很多→服务端转换有问题（第 1 / 2 项）；两者一样但设备显示差→固件或色序（第 5 项）。
4. **向后端确认**（见下节）。

## 需要后端 / 固件确认

- `/api/device/play` 调的是老服务哪个转换接口？传了哪些参数（`color`、`imageDitheringModes`、`type`）？是否和蓝牙版出帧接口同一套算法？
- 服务端会不会对上传图缩放、裁剪、二次压缩？以什么尺寸为准？
- WiFi 各机型应传的 `type` 值及含义；示例中的 `type=3` 对应什么。
- WiFi 固件要求的 bin 格式：分辨率、原生方向、每像素位数、颜色索引顺序、扫描方向。
- WiFi 产品后台的 `width / height / rotationDegree / verticalRotation` 是否按屏幕物理参数配置。

## 可做的改动方向（待上面确认后再定）

- 服务端按蓝牙版同参数出帧；或接口开放 `color` / `imageDitheringModes`，由小程序与蓝牙版同口径传入。
- `typeForDevice` 补 WiFi 机型的 `type` 对照表，不再一律回退 `0`。
- WiFi 链路补铁闸：设备宽高缺失时不投屏并提示（不回退 480×720）；导出像素不等于设备宽高时不上传；`binSize` 与期望不符时在日志标红。
- 横竖向按「取景方向与屏幕方向是否一致」修正导出角（见已知问题），以真机确认 90° / 270°。
