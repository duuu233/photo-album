# WiFi 版：设备分享方案（小程序 + APP）

> 日期：2026-10-29｜分支：`main-wifi`（小程序 / APP 同名分支）｜状态：方案草案，未实施

## 结论速览

- **推荐「邀请码」模式**：所有者 A 发起分享时由服务端生成一次性邀请码，邀请码可以装进微信卡片、二维码或一串口令发给 B；B 打开后看到设备和所有者信息，点「接受」，由服务端给 B 建一条非所有者的设备记录。B 不用配网，接受后直接在设备列表里看到、直接使用。
- **不推荐**让客户端直接调 `addUserProduct` 并传 `isToHave=0`、`shareUserId=A`：这两个字段由客户端填写，任何人知道设备 ID 就能自称被分享，甚至自称所有者。
- **小程序端**：以微信卡片（`onShareAppMessage`）为主要分享方式，加一个接受页、一个分享成员页。
- **APP 端**：第一期用「微信卡片（拉起小程序）+ 复制口令」，B 在 APP 里有「输入邀请码加入」入口；第二期再做二维码扫码和通用链接。
- **前提**：服务端要补邀请、接受、移除成员三类接口，设备列表要带上「是否所有者」；还要确认小程序账号（手机号）和 APP 账号（邮箱 / 微信）是否已经打通，否则 B 在小程序接受后，用 APP 登录看不到这台设备。

## 场景与规则

| 角色 | 怎么来的 | 能做什么 |
|---|---|---|
| 所有者 A | 配网并绑定这台设备的人（第一个绑定者） | 全部操作；分享、查看成员、移除成员；删除设备时所有成员一并解除 |
| 成员 B / C… | 接受 A 的邀请 | 直接使用设备（见下表）；不能分享，不能配网；可以自己「退出共享」 |

- 只有 WiFi 版设备（产品 `versionType=2`，`broadcast-match.isWifiDevice` 判定为 WiFi 版）显示分享入口；蓝牙版不变。
- 设备只有一个所有者；成员不能再分享（服务端也要拦截，不能只靠前端隐藏入口）。

建议的权限划分（打 ★ 的需要产品定）：

| 功能 | 所有者 | 成员 | 说明 |
|---|---|---|---|
| 查看在线 / 电量 / 信号、消息中心 | ✅ | ✅ | IoT 接口按老服务 `checkPermission` 放行，成员同样有权限 |
| 投屏、「我的相册」记录 | ✅ | ✅ | 投屏记录按各自的 `userProductId` 存，A、B 各看各的；屏幕只有一块，后投的覆盖先投的 |
| 轮播、休眠设置、刷新屏幕 | ✅ | ★ 建议 ✅ | 设备级设置，后改的覆盖先改的；产品决定成员能否改 |
| 设备昵称 | ✅ | ✅ | 昵称本来就按用户存（`editUserProduct`），各改各的，互不影响 |
| 删除指定照片 | ✅ | ★ | 删的是设备上的图，会影响所有人 |
| 清空 TF 卡、OTA 升级 | ✅ | ★ 建议 ❌ | 高危或影响所有人；OTA 权限在《前端评审回复》里已列为待产品确认 |
| 重新配网（改 WiFi） | ✅ | ❌ | 需求明确成员不需要配网 |
| 分享 / 查看成员 / 移除成员 | ✅ | ❌ | 成员详情页只显示「所有者：A」 |
| 删除设备 | ✅（所有成员一并解除） | 改为「退出共享」 | 只删自己那条记录 |

## 现状：已经有的基础

老服务（BoltFox，`api.boltfox.cn`）的 Swagger 里已经有分享相关字段和接口，但两端都还没用：

| 接口 / 字段 | 现状 | 对分享的意义 |
|---|---|---|
| `addUserProduct` 入参 `isToHave`（是否所有者）、`shareUserId`（分享者 userId，默认 0） | 小程序、APP 都没传 | 说明后端数据模型里「一台设备多条用户记录 + 区分所有者」已经设计好 |
| `getUserProductDetail` 出参 `isToHave`、`shareUserId` | 两端没读 | 详情页可以据此区分所有者 / 成员 |
| `getUserProductList` 出参 | **没有** `isToHave` | 列表要显示「共享」标签、要隐藏入口，需要后端补字段 |
| `GET /Client/UserProduct/getShareUserProductList?deviceId=` | 返回 `avatar`、`userName`、`isToHave`、`userProductId`（分页） | 可直接用作 A 的分享成员列表 |
| `GET /Client/UserProduct/getUserNoList?deviceNo=` | 「获取绑定设备的用户」 | 服务端内部用（如移除成员时踢订阅） |
| `GET /Client/UserProduct/checkPermission?deviceNo=` | IoT 服务每次请求都调它 | 成员的投屏、状态、订阅权限都由它决定，成员需要返回 true |
| IoT 内部接口 9.2「踢出订阅」 | 已就绪，文档里写明用于「所有者移除分享者」「所有者删除设备」 | 移除成员后，B 不再收到该设备推送 |

客户端现状：

- 小程序 `api.bindWifiDevice` 只按当前用户自己的列表判断「是否已绑定」，后端对「这台设备已被别人绑定」的返回尚未知（待确认）。
- 小程序 IoT 客户端遇到 403 时提示「无该设备操作权限」，不会自动刷新列表或退出设备页；B 被移除后会停在设备页看到这个提示。
- 小程序没有任何页面实现 `onShareAppMessage`；APP 已接入 `fluwx`（目前只用来微信登录），已配置 iOS 通用链接域名和 `boltstar://` scheme（目前只用于支付回跳）。

## 方案对比

### 一、B 怎么拿到邀请（分享方式）

| 方式 | 小程序 A → B | APP A → B | 优点 | 缺点 |
|---|---|---|---|---|
| ① 微信卡片 | `button open-type="share"`，卡片 `path` 带邀请码 | `fluwx` 分享小程序卡片，B 点开进小程序 | 最顺手；B 不装 APP 也能接受 | APP 分享小程序卡片要求 APP 与小程序在同一个微信开放平台账号下；B 必须用小程序接受 |
| ② 二维码 | 服务端生成小程序码（`scene` = 邀请码）或普通链接二维码 | 同一张码在 APP 里展示 | 当面分享方便 | 小程序码只能用微信扫；APP 要扫码需新增扫码插件；普通链接二维码要配置「扫普通链接二维码打开小程序」 |
| ③ 口令（复制邀请码） | 复制一串文字发给 B | 同左 | 不依赖任何平台，APP ↔ APP、APP ↔ 小程序都能用；实现最简单 | 体验最差，要手动粘贴 |
| ④ 按账号邀请（输入 B 的手机号 / 邮箱） | 输入框 | 输入框 | 不用转发任何东西 | 需要后端按账号查人，有隐私顾虑；B 要先注册；小程序是手机号账号、APP 是邮箱 / 微信账号，查不准；B 要在消息中心接受，链路最长 |

推荐 ① + ③ 先做，② 第二期补，④ 暂不做。

### 二、B 接受后服务端怎么建关系

| 做法 | 说明 | 结论 |
|---|---|---|
| 甲：前端直接调 `addUserProduct(deviceId, isToHave=0, shareUserId=A)` | 不用新接口 | ❌ 不安全：客户端可以伪造 `shareUserId`、`isToHave`，也绕过了所有者同意 |
| 乙：邀请码，服务端校验后建记录 | A 申请邀请码 → B 凭码接受 → 服务端核对码有效、A 仍是所有者、B 不是本人且未加入 → 建 B 的记录（`isToHave=0`，`shareUserId=A`） | ✅ 推荐 |

同时，`addUserProduct` 要补一条规则：**设备已有所有者时，其他人直接绑定一律拒绝**（返回明确的码和提示，如「该设备已有所有者，请联系所有者分享给你」）。否则 B 在搜索页找到设备、走一遍配网就能绕过分享，还会把 A 设备的 WiFi 配置改掉。

## 推荐方案

### 服务端需要提供

接口名只是示意，以后端实际定义为准：

| 接口 | 调用方 | 说明 |
|---|---|---|
| `POST createShareInvite { userProductId }` → `{ inviteCode, expireAt }` | A | 只允许所有者、只允许 WiFi 版；建议一次性、24 小时有效；成员数到上限时拒绝 |
| `GET getShareInvite { inviteCode }` → 设备名、产品图、尺寸、所有者昵称 / 头像、状态 | B（需登录） | 状态区分：有效 / 已过期 / 已被使用 / 自己的设备 / 已经是成员 / 成员已满，接受页按状态展示 |
| `POST acceptShareInvite { inviteCode }` → `ClientUserProductDetailApiOut` | B | 建 B 的记录（`isToHave=0`、`shareUserId=A`）；邀请码作废；可选：通过 IoT 9.1 给 A 写一条「B 已加入」消息 |
| `getShareUserProductList`（已有） | A | 只允许所有者调；建议补加入时间 |
| `POST removeShareUser { userProductId }` | A | 删除成员 B 的记录，并调 IoT 9.2 踢出 B 的订阅 |
| `delUserProduct`（已有，规则调整） | A / B | A 删除 = 设备及所有成员一并解除，踢所有人订阅；B 删除 = 只退出自己 |
| `getUserProductList` 出参补 `isToHave`（建议再补所有者昵称） | 两端 | 列表显示「共享」标签、控制入口 |
| `addUserProduct` 规则：设备已有所有者时拒绝他人绑定 | 两端 | 见上节 |
| 设备绑定状态查询（可选）`GET deviceOwnerState { deviceNo }` → `{ bound, mine }` | 两端搜索页 | 配网前先查，已被别人绑定就不进配网，避免改掉 A 的 WiFi |
| 小程序码生成（第二期） | 服务端 | `getwxacodeunlimit`，`scene` 放邀请码（不超过 32 个字符） |

另外，WebSocket 被踢订阅时目前「不发送客户端消息」，B 停在设备页收不到任何通知。《前端对接文档评审建议》里提过推一条 `subscription.revoked`，建议这次一起做；不做的话，两端只能靠 403 兜底。

### 小程序端实现

| 位置 | 改动 |
|---|---|
| `utils/api.js` | 新增 `createShareInvite` / `getShareInvite` / `acceptShareInvite` / `getShareUsers` / `removeShareUser`；`normalizeDevice` 读出 `isToHave`、`shareUserId`，归一成 `isOwner` |
| `subpackages/device/list`、首页设备卡 | WiFi 卡片上，成员设备显示「共享」标签 |
| `subpackages/device/wifi-detail` | 所有者：显示「设备分享」入口；成员：隐藏分享、重新配网、清空等入口，「删除设备」改为「退出共享」，显示「所有者：A」 |
| 新页 `subpackages/device/wifi-share`（分享成员） | 第一行是「我（所有者）」，下面是成员（头像、昵称、加入时间、移除）；底部「邀请成员」按钮用 `open-type="share"` |
| 分享卡片 | 页面 `onShareAppMessage` 返回 `{ title, imageUrl, path: '/subpackages/device/wifi-share-accept?code=…', promise }`：用 `promise`（3 秒内 resolve）在用户点分享时现场申请邀请码，超时则用默认卡片并提示重试；第一期同时提供「复制邀请口令」 |
| 新页 `subpackages/device/wifi-share-accept`（接受） | 读 `options.code`（第二期兼容小程序码 `options.scene`）；未登录先走现有 `ensureLogin` 再回到本页；调 `getShareInvite` 按状态展示；点「接受」后调 `acceptShareInvite`，刷新设备列表，跳到 `wifi-detail` |
| 「加入共享设备」入口（口令） | 放在搜索设备页或「我的设备」右上角：粘贴口令 → 解析出邀请码 → 进接受页 |
| 搜索 / 配网 | 搜到 WiFi 设备后，若后端提供绑定状态查询，已被他人绑定的提示「请联系所有者分享」，不进配网；`bindWifiDevice` 处理「已有所有者」的拒绝码 |
| IoT 403 / 被踢 | 设备页收到 403（或 `subscription.revoked`）时提示「你已不是该设备成员」，刷新列表并返回 |

### APP 端实现

APP 的 WiFi 功能按「与小程序 `main-wifi` 对齐」的约定开发（`lib/src/features/wifi/`），改动与小程序一一对应：

| 位置 | 改动 |
|---|---|
| `lib/src/network/boltfox_api.dart` | 同小程序的邀请、接受、成员、移除接口；设备模型读出 `isToHave` |
| 设备列表 / WiFi 设备详情 | 「共享」标签、所有者 / 成员入口区分、「退出共享」 |
| 分享成员页 | 同小程序 |
| 分享方式 | 第一期：① `fluwx` 分享小程序卡片（`WeChatShareMiniProgramModel`，`path` 同小程序接受页，需要小程序原始 ID `gh_…`），B 在微信里直接进小程序接受；③ 复制口令。第二期：展示二维码 |
| 接受入口 | 第一期：「加入共享设备」页，粘贴口令 → 调 `getShareInvite` → 接受；第二期：扫码（需新增扫码插件，属于功能必需的依赖）与通用链接（`https://…/share/<code>` 直接拉起 APP 到接受页） |
| IoT 403 / 被踢 | 同小程序 |

### 主流程

```
A（所有者，小程序或 APP）                服务端                          B（小程序或 APP）
设备详情 → 设备分享 → 邀请成员
        ── createShareInvite ──────────→ 生成一次性邀请码
        ←─ inviteCode ─────────────────
发微信卡片 / 复制口令 ───────────────────────────────────────────────→ 打开卡片 / 粘贴口令
                                                                   （未登录先登录）
                                         ←── getShareInvite ──────── 看设备和所有者
                                         ←── acceptShareInvite ───── 点「接受」
                                         校验码 → 建 B 的记录（isToHave=0）
                                         ── 设备记录 ──────────────→ 进列表 / 详情，直接投屏
                                         （可选）9.1 通知 A「B 已加入」
A 移除 B ── removeShareUser ───────────→ 删 B 的记录 + 9.2 踢订阅 ──→ 下次请求 403 / 收到 revoked，退出设备页
```

## 分期

| 期 | 服务端 | 小程序 | APP |
|---|---|---|---|
| 第一期 | 邀请 / 接受 / 移除 / 退出接口；列表补 `isToHave`；拒绝他人重复绑定 | 分享成员页、微信卡片、口令、接受页、成员权限收口、403 兜底 | 分享成员页、`fluwx` 小程序卡片、口令、加入页、成员权限收口 |
| 第二期 | 小程序码 / 普通链接二维码、绑定状态查询、`subscription.revoked`、加入 / 移除消息 | 二维码展示、配网前查绑定状态 | 二维码展示、扫码、通用链接 |

## 待确认

| 对象 | 事项 |
|---|---|
| 服务端 | 小程序手机号账号与 APP 邮箱 / 微信账号是否是同一个用户（按 unionid 或手机号合并）；不是的话，B 在哪一端接受就只能在哪一端看到设备 |
| 服务端 | `addUserProduct` 遇到已被他人绑定的设备现在返回什么；`isToHave` 现在由谁写入（第一个绑定者是否自动为 1） |
| 服务端 | `checkPermission` 对成员是否已返回 true |
| 产品 | 邀请码有效期、一次性还是可多人使用、成员上限 |
| 产品 | 成员能否改轮播 / 休眠、删指定照片、清空 TF、OTA（见权限表 ★） |
| 产品 | B 是否能看到其他成员；A 是否需要看到「待接受」的邀请并撤回 |
| 产品 / 运营 | APP 与小程序是否在同一个微信开放平台账号下（决定 APP 能否直接分享小程序卡片）；第二期普通链接二维码用哪个域名 |
| 固件 | BluFi 未加密，任何人靠近都能连设备改 WiFi；服务端拒绝绑定只能挡住「占为己有」，挡不住「改坏配网」，是否需要固件侧限制（如仅在配网模式下接受 BluFi） |
