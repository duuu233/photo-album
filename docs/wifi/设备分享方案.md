# WiFi 版：设备分享方案（小程序 + APP）

> 日期：2026-10-29（同日修订：APP 端改为通用链接，补一次性链接规则和实现方案）｜分支：`main-wifi`（小程序 / APP 同名分支）｜状态：方案，未实施

## 结论速览

- **邀请码模式**：所有者 A 发起分享时，由服务端生成邀请码。B 凭邀请码接受后，服务端给 B 建一条非所有者的设备记录。B 不用配网，直接在设备列表里看到并使用。
- **小程序端**：用微信卡片（`onShareAppMessage`，卡片路径带邀请码）分享，同时提供复制口令；另做接受页、分享成员页。
- **APP 端**：用通用链接分享，链接形如 `https://badmin.boltfox.cn/share/d/<邀请码>`。
  - B 在浏览器、短信、备忘录等地方点开链接，直接拉起 APP 进接受页。
  - 没装 APP，或在微信里点开（微信不放行通用链接）时，落到同一地址的落地页。落地页可以「在小程序中接受」，也可以引导「在浏览器打开 → 拉起 APP」或下载 APP。
- **一次性链接：要上**。
  - 一个链接只能被一个人接受成功，24 小时有效，所有者可以撤回。
  - 「一次性」指**接受成功才作废**，打开、预览、登录都不消耗。
  - 要邀请多人，就分别生成多个链接。
- **小程序口令和 APP 链接用同一个邀请**：口令文本里就是这条链接，两端都能识别。
- **两件事必须先确认**：
  - 小程序账号（手机号）与 APP 账号（邮箱 / 微信）是否是同一用户；
  - 服务端部署 iOS / Android 的域名关联文件。iOS 的 `apple-app-site-association` 目前仍未部署：2026-10-29 实测返回后台页面 HTML。

## 场景与规则

| 角色 | 怎么来的 | 能做什么 |
|---|---|---|
| 所有者 A | 配网并绑定这台设备的人（第一个绑定者） | 全部操作；分享、查看成员与待接受邀请、撤回邀请、移除成员；删除设备时所有成员一并解除 |
| 成员 B / C… | 接受 A 的邀请 | 直接使用设备（见下表）；不能分享、不能配网；可以「退出共享」 |

- 只有 WiFi 版设备（产品 `versionType=2`，`broadcast-match.isWifiDevice` 判定为 WiFi 版）显示分享入口；蓝牙版不变。
- 一台设备只有一个所有者。成员不能再分享，服务端也要拦截，不能只靠前端隐藏入口。

成员权限（打 ★ 的需产品定）：

| 功能 | 所有者 | 成员 | 说明 |
|---|---|---|---|
| 查看在线 / 电量 / 信号、消息中心 | ✅ | ✅ | IoT 接口按老服务 `checkPermission` 放行 |
| 投屏、「我的相册」记录 | ✅ | ✅ | 记录按各自的 `userProductId` 存，各看各的；屏幕只有一块，后投的覆盖先投的 |
| 轮播、休眠设置、刷新屏幕 | ✅ | ★ 建议 ✅ | 设备级设置，后改的覆盖先改的 |
| 设备昵称 | ✅ | ✅ | 昵称按用户存（`editUserProduct`），互不影响 |
| 删除指定照片 | ✅ | ★ | 影响所有人 |
| 清空 TF 卡、OTA 升级 | ✅ | ★ 建议 ❌ | 高危或影响所有人 |
| 重新配网 | ✅ | ❌ | |
| 分享、成员管理 | ✅ | ❌ | 成员的详情页只显示「所有者：A」 |
| 删除设备 | ✅（所有成员一并解除） | 改为「退出共享」 | |

## 一次性链接：要不要上

**要上，规则如下：**

| 规则 | 做法 | 原因 |
|---|---|---|
| 一个链接只能接受成功一次 | 服务端原子更新：`status=PENDING → ACCEPTED`，同时写入接受人 | 链接会在微信群里被转发；设备在 A 家里，陌生人加入后就能往屏上投图 |
| 打开不消耗，接受才消耗 | 预览、登录跳转都不改状态 | 微信 / iMessage 会抓取链接做预览；B 可能打开后先去登录，或通用链接失败后改用浏览器再打开 |
| 有效期 24 小时（★ 产品可调） | 过期后状态显示「已过期」 | 链接长期有效，等同于永久后门 |
| 所有者可撤回 | 成员页显示「待接受」邀请，可以撤回 | 发错人时能补救 |
| 邀请码不可猜 | 不少于 128 位随机数，用 base62 编码（约 22 个字符，满足小程序码 `scene` 不超过 32 个字符）；服务端只存哈希；查询接口限频 | 链接即凭证 |
| 已接受后再打开 | 接受人本人打开：「你已加入」，直接进设备；其他人：「邀请已被使用，请联系所有者重新邀请」 | |

不推荐的另外两种做法：

- **可多人使用的链接**（有效期内谁都能加入，只设人数上限）：A 省事，但转发出去就失控。如果产品坚持要，至少加上人数上限、短有效期，并且每加入一人就通知 A。
- **按账号邀请**（输入 B 的手机号 / 邮箱）：要按账号查人，有隐私问题；小程序和 APP 的账号体系不同，查不准。

## 实现方案

### 邀请的三种载体（同一个邀请码）

| 载体 | 内容 | 谁用 |
|---|---|---|
| 通用链接 | `https://badmin.boltfox.cn/share/d/<code>` | APP 分享出去的主载体；小程序「复制口令」也复制这条链接 |
| 小程序卡片 | `path: /subpackages/device/wifi-share-accept?code=<code>` | 小程序分享 |
| 小程序码（第二期） | `scene=<code>` | 当面扫码 |

路径选在 `/share/` 下，与微信登录用的 `/app/` 分开，互不干扰。域名沿用已关联的 `badmin.boltfox.cn`，省去改 entitlements 和重新审核关联域名；如果想换成面向用户的独立域名，需要另配 Associated Domains 和证书（★ 待定）。

### 服务端

**接口**（名称只是示意）：

| 接口 | 调用方 | 说明 |
|---|---|---|
| `POST createShareInvite { userProductId }` → `{ code, url, expireAt }` | A | 仅所有者、仅 WiFi 版；成员数达上限时拒绝；`url` 由服务端拼好，两端不各自拼 |
| `GET getShareInvite { code }`（需登录） | B | 设备名、产品图、尺寸、所有者昵称 / 头像；状态：有效 / 已过期 / 已被使用 / 已撤回 / 自己的设备 / 已是成员 / 成员已满 |
| `GET shareInvitePreview { code }`（免登录） | 落地页 | 只返回产品图、所有者昵称（可打码）、状态，不返回设备号；限频 |
| `POST acceptShareInvite { code }` → `ClientUserProductDetailApiOut` | B | 原子消耗邀请码；建 B 的记录（`isToHave=0`，`shareUserId=A`）；可选：IoT 9.1 通知 A「B 已加入」 |
| `GET listShareInvites { userProductId }` / `POST revokeShareInvite { code }` | A | 待接受的邀请与撤回 |
| `getShareUserProductList`（已有） | A | 仅所有者；建议补加入时间 |
| `POST removeShareUser { userProductId }` | A | 删除 B 的记录 + IoT 9.2 踢订阅 |
| `delUserProduct`（已有，调整规则） | A / B | A 删除：设备及所有成员一并解除，踢所有人订阅；B 删除：只退出自己 |
| `getUserProductList` 补 `isToHave`（建议再补所有者昵称） | 两端 | 显示「共享」标签、控制入口 |
| `addUserProduct` 规则 | 两端 | 设备已有所有者时拒绝他人直接绑定（给明确的码和提示），否则 B 搜到设备走一遍配网就能绕开分享 |

**邀请表**：`code_hash`、`owner_user_id`、`user_product_id`、`device_no`、`status`（PENDING / ACCEPTED / REVOKED / EXPIRED）、`expire_at`、`accepted_user_id`、`accepted_at`。接受时 `UPDATE … WHERE code_hash=? AND status='PENDING' AND expire_at>now()`，影响行数为 1 才建记录，保证并发下也只有一个人接受成功。

**`badmin.boltfox.cn` 站点配置**（目前整站返回后台 SPA）：

| 路径 | 内容 |
|---|---|
| `/.well-known/apple-app-site-association` | 纯 JSON、`Content-Type: application/json`、不能有跳转；`appID` 为 `S2HZK3227W.com.boltfox.boltstar`，`paths` 在已有的 `/app/`、`/app/*` 之外加 `/share/*` |
| `/.well-known/assetlinks.json` | 包名 `com.boltfox.boltstar`，加上**每个分发渠道签名证书**的 SHA-256 指纹（各应用商店重签名时指纹不同） |
| `/share/d/*` | 静态落地页（见下），不能被后台 SPA 的路由接管 |

**微信小程序 URL Link**：服务端调用 `generate_urllink` 生成跳转链接，`path` 为接受页、`query` 为 `code=…`；落地页「在小程序中接受」按钮用它。

### 落地页（`/share/d/<code>`）

只有通用链接**没能**拉起 APP 时，B 才会看到这个页面。打开时调用 `shareInvitePreview` 显示设备和所有者，按环境给不同按钮：

| B 的环境 | 页面行为 |
|---|---|
| 微信内置浏览器（最常见：A 把链接发到微信） | 主按钮「在小程序中接受」（URL Link）；次按钮「用 APP 打开」→ 提示点右上角「在浏览器打开」；已关联服务号时可用 `wx-open-launch-app` 直接拉起 APP（★ 可选） |
| Safari / Chrome，已装 APP | 同域名页面内点链接不会触发通用链接，所以按钮改用 scheme `boltstar://share/d/<code>`；iOS 另加 Smart App Banner（`apple-itunes-app` meta，`app-argument` 填链接） |
| 没装 APP | 应用商店下载按钮；「复制邀请链接」，装好后在 APP 里粘贴 |
| 邀请已过期 / 已使用 / 已撤回 | 只显示状态和「请联系所有者重新邀请」 |

| IoT 403 / 被移除 | 设备页收到 403 时提示「你已不是该设备成员」，刷新列表并返回 |

### APP 端（通用链接）

**原生层：接收链接，不新增插件。** 照 PayPal 回跳的做法把链接交给 Dart，不打开 `FlutterDeepLinkingEnabled`。

| 平台 | 改动 |
|---|---|
| iOS `SceneDelegate.swift` | 覆写 `scene(_:continue:)`：`webpageURL` 的路径以 `/share/` 开头时，存入 `ShareLinkStore` 并通知 Dart，不再交给 `super`；其他链接照旧交给 `super`（`fluwx` 接微信 `/app/` 回跳）。覆写 `scene(_:willConnectTo:options:)`：冷启动时从 `connectionOptions.userActivities` / `urlContexts` 取同样的链接 |
| iOS `Info.plist` | `CFBundleURLSchemes` 增加 `boltstar`，供落地页按钮兜底；`scene(_:openURLContexts:)` 里把 `boltstar://share/…` 拦给 `ShareLinkStore`，其他 URL 照旧转发 |
| Android `ShareLinkActivity`（新增，与 `PayPalRedirectActivity` 同构） | 透明、`noHistory`、不进最近任务。`intent-filter` 加 `android:autoVerify="true"`，匹配 `https://badmin.boltfox.cn/share/` 前缀，另加一条 `boltstar://share`。只做两件事：把链接记进 `ShareLink` 单例；用 `getLaunchIntentForPackage` 把原任务提回前台。不挂到 `MainActivity` 上，原因同 PayPal（`taskAffinity=""` 会导致重建任务） |
| 两端 `device_api` 通道 | 新增 `consumeShareLink`：返回待处理的链接后清空；新链接到达且 App 在前台时，原生主动 `invokeMethod('onShareLink')` 通知 Dart |

**Dart 层：**

| 位置 | 改动 |
|---|---|
| `lib/src/native_device_api.dart` | `consumeShareLink()`，以及 `onShareLink` 的回调注册 |
| 新增 `lib/src/features/wifi/wifi_share.dart` | 解析 `/share/d/<code>` 或 `boltstar://share/d/<code>`，校验 code 格式；冷启动、回前台（`AppLifecycleState.resumed`）、收到 `onShareLink` 时各读一次。未登录时先把 code 存进内存，登录成功后再处理；已登录则直接打开接受页。同一个 code 正在处理时不重复打开 |
| `lib/src/routes/app_routes.dart` | 新增「接受分享」「分享成员」两个命名路由（显式 push，不走 URL 路由） |
| `lib/src/network/boltfox_api.dart` | 与小程序同一组接口；设备模型读出 `isToHave` |
| 设备列表 / WiFi 设备详情 | 「共享」标签、所有者 / 成员入口区分、「退出共享」 |
| 分享成员页 | 同小程序。「邀请」生成链接后提供：「分享到微信」（`fluwx` 网页卡片，链接即通用链接）、「复制链接」、「更多」（系统分享面板，由原生通道调用 `UIActivityViewController` / `Intent.ACTION_SEND`，不加插件） |
| 「加入共享设备」（粘贴链接） | 与小程序相同，覆盖没装 APP、后来才装的情况。不自动读取剪贴板（iOS 会弹粘贴授权） |
| IoT 403 / 被移除 | 同小程序 |

### 主流程

```
A（APP）                         服务端                                  B
设备分享 → 邀请
  ── createShareInvite ───────→ 生成一次性 code（24h）
  ←─ url ─────────────────────
分享到微信 / 复制 / 系统分享 ────────────────────────────────────────→ 点开链接
                                                     ┌ 已装 APP，非微信环境：通用链接直接拉起 APP
                                                     ├ 微信内：落地页 → 在小程序中接受 / 浏览器打开 → APP
                                                     └ 没装 APP：落地页 → 下载 / 复制链接
                                ←── getShareInvite ─────────────── 接受页（未登录先登录）
                                ←── acceptShareInvite ──────────── 点「接受」
                                原子消耗 code → 建 B 的记录（isToHave=0）
                                ── 设备记录 ──────────────────────→ 进列表 / 详情，直接投屏
A 移除 B ── removeShareUser ──→ 删 B 的记录 + 9.2 踢订阅 ─────────→ 下次请求 403，退出设备页
```

小程序 A 分享时，B 点卡片直接进小程序接受页；复制出去的口令就是上面那条链接，走同样的分支。
