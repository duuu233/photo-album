# 前端对接变更说明（2026-10-29）

> 本次变更主题：**TF 卡本地播放**。
> 涉及：设备状态新增值、`play-tf` 完整交互、消息通知类型调整、`play_tf_ack` 结果推送。
> 与 `docs/前端对接文档_草稿.md`（v0.57）保持一致，冲突时以草稿为准。

---

## 一、设备状态新增 `LOCAL_TF`

`device.status` 推送、`GET /api/device/online`、`GET /api/device/info`、后台设备列表/详情中的 `status` 字段新增枚举值：

| `status` | `online` | 含义 | 建议前端文案 |
|---|---|---|---|
| `ONLINE` | `true` | 在线 | 在线 |
| `OFFLINE` | `false` | 离线 | 离线 |
| `SLEEPING` | `false` | 休眠中（服务端有休眠计划） | 休眠中 |
| `SHUTDOWN` | `false` | 已关机 | 已关机 |
| `LOCAL_TF` | `false` | **已切到 TF 卡本地播放，与云端断开** | **本地模式** |

约定（重要）：

1. 服务端**只返回状态值**（`LOCAL_TF`），**不返回中文文案**；「本地播放」等文字由前端自行映射。
2. `LOCAL_TF` 时 `online` 固定为 `false`：设备不可远程控制、不可投屏、查不到影子（心跳已停止，`tf*`/电量/信号全部冻结）。
3. 服务端判定顺序：`ONLINE` > `SHUTDOWN` > `LOCAL_TF` > `SLEEPING` > `OFFLINE`。
4. 前端遇到**未识别的新枚举值**时请按「未知状态」降级展示，不要抛错或白屏。

WS 推送示例：

```json
{
  "type": "device.status",
  "deviceNo": "XT20260001",
  "online": false,
  "status": "LOCAL_TF"
}
```

## 二、完整交互流程

### 2.1 时序

```
App                          服务端                        设备
 |                             |                            |
 |-- POST /api/device/play-tf ->|                            |
 |                             |-- 校验：权限 / 升级中 / 在线 / 已插 TF 卡
 |                             |-- MQTT play_tf ----------->|
 |<-- { msgid } ---------------|   （记一条本地模式标记，24h） |
 |                             |                            |
 |                             |<------------ play_tf_ack --|
 |<-- WS command.result -------|   success=true / false      |
 |                             |                            |
 |                             |<-- （设备进入本地模式，断开 MQTT）
 |<-- WS device.status --------|   status=LOCAL_TF, online=false
 |<-- 消息通知 ---------------—|   type=TF_LOCAL_MODE（不发 DEVICE_OFFLINE）
 |                             |                            |
 |         ... 用户只能在设备端重新配网 / 按键恢复联网 ...
 |                             |                            |
 |                             |<------------ login --------|
 |<-- WS device.status --------|   status=ONLINE, online=true（标记已清除）
 |<-- 消息通知 ---------------—|   type=DEVICE_ONLINE
```

### 2.2 第 1 步：发起切换

```
POST /api/device/play-tf
Header: userToken
Content-Type: application/json
```

```json
{ "deviceNo": "XT20260001" }
```

成功返回：

```json
{ "code": 0, "msg": "ok", "data": { "msgid": "1793253810962576" } }
```

服务端前置校验与错误码：

| 场景 | `code` | `msg` |
|---|---|---|
| 无该设备权限 | `403` | `no permission for device` |
| 设备升级中 | `4045` | 设备升级中，请稍后 |
| 设备离线（含已经是 `LOCAL_TF`） | `4041` | 设备已离线 |
| 影子 `tfStatus=absent`（`/api/device/info` 的 `tfStatus` 为 `absent`） | `4000` | 设备未插 TF 卡 |

> - `tfStatus` 未知（设备还没上报过心跳）时**不拦截**，照常下发，避免误伤新设备。
> - HTTP 成功只代表**指令已下发到 MQTT**，不代表设备已执行；执行结果看 2.4 的 `command.result`。

### 2.3 第 2 步：前端立即反馈

- 收到 HTTP 成功后按钮进入 loading，等待 `command.result`（建议 30 秒超时）。
- 超时未收到：提示「设备未响应，请稍后重试」，**不要**直接显示「已切换」。
- 需要做loading，防止重复点击。
- 点击前必须二次确认：设备会断网，恢复只能由用户在设备上操作。

### 2.4 第 3 步：`play_tf_ack` 结果推送（本次新增）

服务端收到设备 `play_tf_ack` 后，通过 WebSocket 推送 `command.result`：

```json
{
  "type": "command.result",
  "deviceNo": "XT20260001",
  "action": "play_tf",
  "msgid": "1793253810962576",
  "success": true,
  "result": 0
}
```

| 字段 | 说明 |
|---|---|
| `type` | 固定 `command.result` |
| `deviceNo` | 设备编号 |
| `action` | 当前仅 `play_tf`；后续指令接入会复用该结构 |
| `msgid` | 与 HTTP 返回的 `msgid` 一致，前端按它匹配请求 |
| `success` | `true`=设备接受（`result` ∈ `0/1/100/106/107/113/255`）；`false`=设备拒绝 |
| `result` | 设备原始状态码；失败常见 `112`（指令执行失败）、`101`~`118` |

前端处理：

- `success=true`：提示「设备已切换，即将进入本地播放」，转入「等设备断开」状态。
- `success=false`：提示「设备拒绝切换（result=xxx）」，**保持联网状态不变**（服务端已清除本地模式标记，不会误报 `LOCAL_TF`）。
- 同一条 `command.result` 只推一次（服务端按 pending 去重）；WS 断线期间可能丢失，重连后请调用 `GET /api/device/online` 补查。
- 推送前需按 1.6 订阅该设备，未订阅不会收到。

### 2.5 第 4 步：进入本地播放

设备执行成功后会在数秒内断开 MQTT，服务端推送：

1. WS `device.status`：`online=false`、`status=LOCAL_TF`
2. 消息通知：`category=DEVICE`、`type=TF_LOCAL_MODE`（**不再发 `DEVICE_OFFLINE`**）

前端展示：

- 设备状态显示「本地播放」，不要显示「离线」。
- 该设备所有远程操作按钮（投屏、轮播、刷新、OTA、清空 TF 等）置灰，提示「设备处于本地播放模式，需在设备上恢复联网后使用」。
- 建议记录进入时间，展示为「本地播放中（自 xx:xx 起）」。

### 2.6 第 5 步：恢复联网

恢复只能由用户在设备端操作（重新配网或设备按键），**协议没有远程切回指令**，服务端不做也不管这个过程。

设备重新连上后：

1. 服务端清除本地模式标记；
2. 推送 WS `device.status`：`online=true`、`status=ONLINE`；
3. 消息通知：`type=DEVICE_ONLINE`。

前端收到后重新拉取 `GET /api/device/info` 刷新 `tfStatus` / `tfUsed` / 电量 / 信号，并恢复操作按钮。

> 边界：本地模式标记有 24 小时有效期。若 24 小时内未回连，标记自然过期，此后该设备断开按普通 `OFFLINE` 处理（此时多为用户长期本地播放或设备真实离线，前端按离线展示即可）。

## 三、消息通知类型

消息通知的 `type` 枚举**新增一个值**，接口与数据结构均无变化：

| `type` | `category` | 说明 |
|---|---|---|
| `TF_LOCAL_MODE` | `DEVICE` | 设备进入 TF 卡本地播放（`payload` 为空对象） |

前端只需给这个新值配一段文案（建议「设备已进入本地播放」），其余逻辑不变。该场景下设备不再推 `DEVICE_OFFLINE`。

---

## 四、清空 TF 卡（`clean-tf`）

**本次不做变更**，接口行为与 v0.56 完全一致：固定下发 `type=ALL`、需 `confirm=true`。

- 已知风险不变：`ALL` 会连同设备内置的 `LOCAL` 图片一并清空且不可恢复。
- 后续若要改为只清云端下发到 TF 的图片（`type=OTHER`），会另行发版并更新对接文档；**在此之前前端不要改变现有交互**。

## 五、错误码（本次涉及）

| `code` | 含义 |
|---|---|
| `0` | 成功（指令已下发） |
| `4000` | 参数错误 / 设备未插 TF 卡 |
| `403` | 无权限 |
| `4041` | 设备已离线 |
| `4045` | 设备升级中 |
| `5000` | 服务端异常（MQTT 下发失败等） |

无新增错误码。
