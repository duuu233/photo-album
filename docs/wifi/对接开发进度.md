## 二、STEP 1 搜索（当前阶段）

### 目标

App 扫描 BLE 设备，按后台配置匹配广播名；搜索列表共用老接口，WiFi 设备查询产品规格，查不到标记「未知设备」并拦截连接。

### 搜索流程

1. **BLE 扫描**：读取广播 local name；iOS 拿不到 MAC，不依赖 MAC。
2. **广播匹配**：后台配置列表逐条匹配。
   - WiFi 版配置 `IJ_*`：按 `*` 拆 prefix/suffix，匹配前后缀，捕获中间 12 位作为 `deviceId`。
   - BLE 版配置固定广播名：如 `EF6-370`、`EB-169`，完全匹配。
   - 同一设备按广播名/deviceId 去重，按 RSSI 排序。
3. **搜索列表**：共用老接口，IoT 端不新增搜索列表接口，也不处理设备类型；前端按老接口返回的列表展示。
4. **WiFi 产品规格查询**：调用新接口（老服务侧）：
   ```
   GET https://api.boltfox.cn/Client/Product/getProductByDevice?deviceNo=<12位deviceId>
   ```
   例如：`deviceNo=D0CF13F02FF8`。该接口专门按 WiFi 设备 ID 查询产品信息（尺寸、旋转、方向等），用于 App 展示和参数操作；展示哪些字段由前端决定。
   - 查到：展示产品规格/型号。
   - 查不到、返回空或接口失败：设备信息处显示「未知设备」；禁止连接。
5. **未知设备**：点击连接直接弹窗提示「未知设备，请联系客服开通」，不进入配网。
6. **缓存与重试**：不做缓存，与老逻辑一致，每次搜索实时查询（2026-10-26 调整，原为按 `deviceNo` 缓存 5~10 分钟）；暂不做超时重试，失败/超时按「未知设备」处理；重新搜索或重新进入搜索页时会再查一次。
7. **域名**：小程序 request 合法域名需要增加 `api.boltfox.cn`。

### 关键约定

- WiFi 版广播名：`IJ_` + 12 位 deviceId，示例 `IJ_E348C21ED428`；BLE 版固定广播名 `EF6-370`、`EB-169`。
- 后台广播 ID：WiFi 配置 `IJ_*`；BLE 配置固定广播名。
- 匹配只认 `*`：拆 prefix/suffix，前后缀匹配，**被 `*` 替换的中间部分必须 12 位**；不含 `*` 时完全匹配。
- 不依赖 MAC：iOS 只能读广播 local name；已知 deviceId 时比较字符串，未知时展示候选让用户选择。
- WiFi 型号/规格以 `getProductByDevice` 返回为准，不依赖 BLE 广播名。
- 绑定需要的 `deviceId` 格式（是否带冒号）由老服务决定，前端在绑定前转换。

### 已确认 / 约定

- `getProductByDevice` 是新接口，专门按 WiFi 设备 ID 查询 WiFi 产品信息（尺寸、旋转、方向等），用于 App 展示和参数操作；由老服务侧提供。
- 搜索列表共用老接口，IoT 端不新增搜索列表接口，也不处理设备类型。
- 未知设备禁止连接，点击直接弹窗「未知设备，请联系客服开通」。
- 产品查询暂不做超时重试；失败/超时按「未知设备」处理。
- WiFi 前缀固定为 `IJ_`；前端按后台配置里是否包含 `*` 拆分匹配，中间 12 位作为 deviceId；如后续出现其他前缀/格式，另行更新文档。

### 验收标准

- 配置 `IJ_*` 时，`IJ_E348C21ED428` 能命中并解析出 12 位 `deviceId`。
- 配置 `IJ_*ABC` 时，`IJ_E348C21ED428ABC` 能命中，`deviceId=E348C21ED428`。
- 配置固定 `EF6-370`/`EB-169` 时只命中对应固定广播。
- WiFi 设备调用 `getProductByDevice`：查到则展示规格/型号；查不到/失败显示「未知设备」，点击弹窗「未知设备，请联系客服开通」并禁止连接。
- 暂不做超时重试；重新进入搜索页可重新查询。
- iOS 真机能从广播 local name 读到完整 `IJ_...` 名称。
- 同一设备不重复出现，按 RSSI 排序。

## 三、STEP 2 配网

### 小程序实现情况（2026-10-26，`main-wifi`）

- 已确认：`mqtt_config` 来源未定，先留接口位、不下发（`config.iotMqttConfig` 为 null 即跳过）；绑定 deviceId 用 `AA:BB:CC:DD:EE:FF`；BluFi 先不加密。
- `utils/blufi.js`（乐鑫 BluFi 帧与会话）、`utils/wifi-provision.js`（四步流程）、`api.bindWifiDevice`（老服务 addUserProduct，已绑定则复用）。
- 顺序按本节约定：BluFi 下发 WiFi →（有配置时 mqtt_config）→ 连接 WiFi 等设备状态报告 → 老服务绑定 → 带 `since` 每 2s 轮询在线、60s 超时；503/403 继续轮询，401 停止。
- 配网流程（2026-10-26 产品定）：App 蓝牙连接设备 → **设备扫描附近 WiFi**（BluFi 0x09/0x11，3~5 秒，显示「正在搜索网络...」）→ 列表（名称 + 4 格信号）→ 选中进 **WiFi 账号密码页** → 配网状态页下发 WiFi 参数（+ MQTT 参数，来源未定前不发）。不再用手机扫描，两端一致；连不上 / 设备没回列表可重新搜索或手动输入。依赖固件实现 BluFi 获取 WiFi 列表，待联调确认。
- 第一步在搜索页用蓝牙连上设备（「连接设备中」），连上才进列表页；列表页「正在连接设备...」→「正在搜索网络...」（最多等 60 秒），设备报扫描失败（0x12）即时提示；开发版 / 体验版有联调日志（每一步与收发原始帧）。
- 本设备 WiFi 列表实测走自定义数据（0x13）文本：`ssid:<名称>,rssi:<dBm>,ch:<信道>`，带信道、双频。按信道只留 2.4G（ch 1~14，国内外通用），设备分批回时边收边显示，最后一批后再等 5 秒结束。
- 设备 WiFi 列表字段（乐鑫标准 0x11 格式）：乐鑫标准格式只有 SSID + RSSI，没有信道 / 频率，按协议做不了频段过滤（ESP32 多为单 2.4G）；开发版 / 体验版列表页在每个 WiFi 下打出回包全部字段与原始字节，供核对固件是否追加了字段。
- 搜索列表尺寸：WiFi 版、蓝牙版同一口径，直接显示 `sizeModel`，没配显示「--寸」；WiFi 版查询中显示小圆圈 loading。
- 详见 [变更记录](../changes/2026-10-26-WiFi版配网STEP2.md)。测试未运行、未真机，BluFi 未与本固件联调。

### 目标

App 完成“手机网络正常 → 设备网络配置完成 → 设备正在连接 WiFi → 设备正在连接云端”四个状态的展示和推进。

### 接口与实现

| 步骤 | 页面状态 | 完成方 | 对接方式 |
|---|---|---|---|
| 1 | 手机网络正常 | 前端 | App 本地检测，不调用服务端 |
| 2 | 设备网络配置完成 | 前端 | BLE BluFi `mqtt_config`，设备回 `result=0` |
| 3 | 设备正在连接 WiFi | 前端/设备侧 | 设备内部状态，无服务端接口 |
| 4 | 设备正在连接云端 | 本服务 | 轮询 `GET /api/device/online?deviceNo=&since=`，`online=true` 即成功 |

> `since` 已实现：传本次配网开始毫秒时间，只有 `lastOnlineAt > since` 才返回 `online=true`，避免旧连接误判。

### 关键约定

- 第 4 步接口会调老服务 `checkPermission`，设备未绑定时返回 `403`；推荐顺序：BLE 成功 → 老服务完成绑定 → 轮询在线。
- 绑定需要的 `deviceId` 格式（是否带冒号）由老服务决定，前端在绑定前转换。
- 轮询建议 1~2 秒一次，最长 60 秒；`503` 表示权限服务不可用，保留页面稍后重试。
- `getProductByDevice` 查不到的「未知设备」不允许进入配网。

## 四、STEP 3 投屏

### 目标

App 完成图片上传、进度展示、设备状态跟踪、成功/失败/超时处理。

### 接口与实现

| 环节 | 接口 / 事件 | 说明 |
|---|---|---|
| 上传 | `POST /api/device/play` | multipart：`deviceNo`、`file`、`type`；`userNo` 由服务端从 token 解析 |
| 上传进度 | 客户端 multipart 上传进度 | 0-100% 由客户端计算 |
| 服务端处理 | 接口同步处理 | 转 bin、上传 OSS、下发 MQTT，最长约 8 秒 |
| 接口返回 | `status=SENT` / `FAILED` | `SENT` 表示指令已下发；`FAILED` 表示 MQTT 下发失败 |
| 设备下载 | WS `play.result` `DOWNLOADING` | 设备返回 `100/106` |
| 设备刷屏 | WS `play.result` `FLASHING` | 设备返回 `107/255` |
| 成功 | WS `play.result` `SUCCESS` | 设备返回 `0/1/113` |
| 失败/超时 | WS `play.result` `FAILED` / `TIMEOUT` | 失败码见前端文档 |
| 断线兜底 | `GET /api/device/play/status?msgid=` | 切后台、WS 重连后补查 |

### 进度条方案

1. 0-100%：图片上传到本服务的真实上传进度。
2. 100% 但接口未返回：显示「图片处理中」。
3. 接口返回 `SENT`：显示「指令已下发，等待设备」，进度保持 100%。
4. `play.result=DOWNLOADING`：显示「设备下载中 / 屏幕即将刷新」。
5. `play.result=FLASHING`：显示「设备刷屏中」。
6. `SUCCESS` / `FAILED` / `TIMEOUT`：终态。

> 协议没有设备下载进度，0-100 不是设备下载百分比；详见前端文档 1.4 和第五节。

### 待确认

- [ ] 失败时进度弹窗是否要显示具体原因（下载失败/存储异常/通用失败）？当前 `play.result` 只有 `FAILED`，失败类型在通知表里；如需立即展示，需要给 `play.result` 增加 `errorType`/`result`。
- [ ] 设备很快时 `play.result` 可能早于 HTTP 响应到达，前端是否已按 `msgid` 缓存事件？
- [ ] 投屏超时时间是否接受 60 秒（服务端 ack 超时）？

### 验收标准

- 正常投屏：上传进度 → 即将刷新 → 刷屏中 → 成功。
- 失败投屏：能展示失败并允许重试。
- 超时投屏：能展示超时，等待 3 秒后允许重试；迟到成功可修正。
- WS 断开/切后台后，通过状态查询能恢复正确状态。

## 七、STEP 6 固件升级 OTA

| 查询状态 | `GET /api/device/ota/status?msgid=` |

验收：升级中其他控制接口返回 `4045`；升级成功/失败/超时状态正确；重连后版本变化能修正为成功。
