# XT IoT 平台前端对接文档 · 小程序端评审建议

> 状态：draft
> 负责人：小程序端
> 最后核对：2026-10-26
> 适用范围：后端（Java IoT 服务）、小程序
> 权威来源：[前端对接文档_草稿.md](前端对接文档_草稿.md)（v0.27，2026-10-25）

这份文档是小程序端针对 WiFi 版对接草稿 v0.27 的评审意见，供后端（Java）同学评估与答复。

草稿整体质量很高。状态只进不退、`corrected` 修正、WS 只推信号再走 REST 补查、401/503 语义区分、休眠时间由服务端统一转 UTC，这些约定前端都认可，下面不再重复。本文只列**需要改、需要补、需要确认**的部分。每条尽量写清现状、问题、建议改法和 Java 侧实现参考。

**优先级说明**

| 级别 | 含义 |
| --- | --- |
| **P0** | 联调前必须定下来，不定前端无法开工或上线后会出事故（安全、数据错乱、海外用户错时） |
| **P1** | 强烈建议本期做，不做前端能绕，但体验或稳定性明显变差 |
| **P2** | 后续迭代考虑 |

## 一、总览

| # | 级别 | 主题 | 一句话 |
| --- | --- | --- | --- |
| 1 | P0 | 设备标识与设备类型 | `deviceNo`（`XT20260001`）与小程序现有设备 ID / `userProductId` 的映射没有定义；也没说如何区分 WiFi 设备与 BLE 设备 |
| 2 | P0 | 登录凭证 | 老服务同时下发 `userToken` 与 `jwtToken`，需明确新服务认哪一个 |
| 3 | P0 | 时区与时间格式 | 写死 Asia/Shanghai 对海外用户错时；`yyyy-MM-dd HH:mm:ss` 在 iOS 上 `new Date()` 解析失败 |
| 4 | P0 | 错误码体系 | HTTP 状态码与业务 `code` 混用，需要一张「错误 → HTTP 状态 + body.code」的总表；4041/4044 一码多义 |
| 5 | P0 | 固件升级 URL 由客户端传 | 安全问题：任意 URL 可被下发到设备刷机，应改为服务端按版本下发 |
| 6 | P0 | 配网确认 | 绑定前 403 无法确认；重配网时 `online=true` 可能是旧连接，会误判成功；`mqtt_config` 内容来源未说明 |
| 7 | P0 | 无鉴权接口与内网信息 | 管理后台接口无鉴权；设备图片列表接口无鉴权且 `deviceNo` 可枚举；对外文档写了内网地址 |
| 8 | P0 | 投屏入参与相册数据 | `type` 未定义；图片规格/大小上限未定义；投屏后是否写老服务相册记录、TF 卡与相册如何对应未定义 |
| 9 | P0 | Long 精度 | 所有 Long 型 ID 需按字符串返回（`msgid` 已是，通知 `id` 等尚不是） |
| 10 | P1 | 控制指令无执行结果 | 轮播、休眠、国家码等只知道「已下发」，建议统一指令状态与 `command.result` 推送 |
| 11 | P1 | 幂等 | 客户端网络层有自动重试，POST 指令需支持幂等键，避免重复下发 |
| 12 | P1 | 批量接口 | 设备列表在线状态、未读数、WS 订阅都需要批量能力 |
| 13 | P1 | WebSocket 协议细节 | `error` 不带 `deviceNo`/`code`；事件无时间戳/序号；被踢订阅客户端无感知；多实例部署推送 |
| 14 | P1 | 投屏状态细节 | `play.result` 失败不带原因码；投屏 TIMEOUT 时长未写；与 OTA 状态机命名不统一 |
| 15 | P1 | 轮播参数 | 入参秒、出参分钟不对称；时间窗时区与跨午夜未说明；与老服务 `carouselInterval` 双数据源 |
| 16 | P1 | 休眠两条指令非原子 | 第一条成功、第二条失败时的返回和设备状态未定义 |
| 17 | P1 | 字段规范 | `payload` 下划线与驼峰混用；`null`/缺省/空对象口径；枚举值未列全 |
| 18 | P1 | 权限校验性能 | 每次请求实时调老服务 `checkPermission`，建议短缓存 + 踢订阅时失效 |
| 19 | P1 | 上传与网关配置 | Spring multipart 与 Nginx 默认 1MB 上限；超限时返回非 JSON |
| 20 | P2 | 投屏接口异步化 | 同步 8 秒占用请求线程，可改为先返回再推进度 |
| 21 | P2 | 其他 | 小程序订阅消息、`traceId`、接口版本前缀、文档拆分 |

## 二、P0：联调前必须确定

### 1. 设备标识 `deviceNo` 与设备类型

**现状（小程序端）**

- 小程序现在识别一台相框靠两个 ID：
  - 设备 ID：通过 BLE 读出的完整 6 字节 ID，形如 `AA:BB:CC:DD:EE:FF`。绑定时以 `deviceId` 传给老服务 `addUserProduct`。
  - 老服务绑定记录主键 `userProductId`：后续详情、编辑、删除、投屏记录都用它。
- 草稿示例里的 `deviceNo` 是 `XT20260001`，格式与上面两者都不同。3.6 节又出现「`deviceId`：设备 ID 前 12 位」，看起来像 6 字节 ID 去掉冒号。

**问题**

1. 前端拿到老服务设备列表后，不知道该用哪个字段调新服务。
2. 不知道一台设备是 WiFi 版还是 BLE 版。两者功能入口完全不同：BLE 版走蓝牙投屏，WiFi 版走云端投屏。

**建议**

- 老服务 `getUserProductList` / `getUserProductDetail` 每条设备补两个字段：
  - `deviceNo`：新服务使用的设备编号；
  - `commType`（名字可议）：例如 `BLE` / `WIFI`，或用位标记表示「同时支持」。
- 文档里写清三者关系：`deviceNo` ⇄ 6 字节设备 ID ⇄ `userProductId`。还要写清是一一对应，还是同一 `deviceNo` 可被多个用户绑定、产生多条 `userProductId`（分享场景）。
- 写清 `deviceNo` 的格式与字符集，3.10 已给出正则 `^[A-Za-z0-9_-]{1,64}$`，建议提到「通用约定」里统一。说明大小写是否敏感，以及 6 字节 ID 转换时带不带冒号、大写还是小写。
- 3.6 设备配置的 `deviceId`「设备 ID 前 12 位」请举一个完整的例子：6 字节 ID → `deviceNo` → `deviceId`。

### 2. 登录凭证：`userToken` 还是 `jwtToken`

**现状**：老服务登录接口 `setWechatAppLogin` 同时下发 `userToken` 和 `jwtToken`。小程序的每个请求都带上：

- Header `userToken`；
- Header `Authentication: Bearer <jwtToken>`；
- `/Client/*` 接口 query 里也带 `userToken`。

**问题**：草稿只写「Header 携带 `userToken`，沿用 App 现有登录 token」。之前在 AI 服务对接时踩过坑：两个 token 接错了不报错，只是静默认不出用户。

**建议**

- 文档明确：新服务认的是登录接口返回的 `userToken` 字段，还是 `jwtToken`。
- 两个 token 有效期与刷新方式不同的话，写明新服务 401 后前端是重新登录，还是先刷新 token。
- WS 握手同理。小程序 `wx.connectSocket` 支持自定义 `header`，前端会用 Header 方式。建议服务端把 query `token` 方式的访问日志做脱敏，避免 token 落到 Nginx access log 里。

### 3. 时区与时间格式

**问题 1：写死 Asia/Shanghai**

- 产品会出海：小程序已支持简中、繁中、英文、日文，3.8 节有国家码，OSS 在新加坡区域。
- 草稿约定「休眠 `sleepTime`/`wakeTime` 传 Asia/Shanghai 本地时间，服务端转 UTC」。日本用户在界面选「22:00 休眠」，服务端按 +8 换成 14:00 UTC，设备实际在东京时间 23:00 才休眠，差 1 小时；欧美用户差得更多。
- 轮播 `beginTime`/`endTime` 也有同样问题。而且草稿没说轮播时间是否转 UTC：休眠转、轮播不转的话，两处口径还不一致。

**建议**

- 所有「设备本地时刻」类入参（休眠、轮播时间窗）增加时区参数：
  - 入参 `timeZone`：IANA 名，如 `Asia/Tokyo`；
  - 前端拿不到 IANA 名时，允许传 `utcOffsetMinutes`，如 `540`。
  - 服务端按该时区转 UTC；不传时才默认 Asia/Shanghai，保持兼容。
- 或者在设备维度保存时区（配网时由 App 上报），服务端下发时统一用设备时区换算。这种更合理：用户出差时手机时区变了，相框所在地的时区并没变。
- 注意夏令时：按 IANA 时区换算时，固定的 `HH:mm` 在切换日前后对应不同 UTC。设备只认 UTC `HH:mm` 的话，这类地区需要服务端在切换日重新下发，可列为已知限制。

**问题 2：iOS 无法解析返回的时间字符串**

小程序 iOS 端 `new Date('2026-10-20 11:02:43')` 返回 `Invalid Date`，Android 正常。这是小程序开发里很常见的坑。

**建议**（二选一，推荐 A）：

- A：所有时间字段额外返回毫秒时间戳，如 `createdAtTs: 1729393363000`，前端按用户时区格式化。
- B：统一改为 ISO 8601 带偏移，如 `2026-10-20T11:02:43+08:00`。

Java 侧参考：

```yaml
# application.yml：保持现有格式，同时显式指定时区，避免依赖服务器系统时区
spring:
  jackson:
    time-zone: Asia/Shanghai
    date-format: yyyy-MM-dd HH:mm:ss
```

```java
// 方案 A：DTO 里同时给出时间戳
private LocalDateTime createdAt;
public Long getCreatedAtTs() {
    return createdAt == null ? null
        : createdAt.atZone(ZoneId.of("Asia/Shanghai")).toInstant().toEpochMilli();
}

// 休眠/轮播：按请求时区把本地 HH:mm 换算为 UTC HH:mm
ZoneId zone = ZoneId.of(req.getTimeZone() != null ? req.getTimeZone() : "Asia/Shanghai");
LocalTime utc = LocalDate.now(zone).atTime(LocalTime.parse(req.getSleepTime()))
        .atZone(zone).withZoneSameInstant(ZoneOffset.UTC).toLocalTime();
```

### 4. 错误码体系

**现状**

- 「通用约定」说 `code=0` 为成功。
- 2.3 节说只有 401/404/503 用非 200 HTTP 状态，其余业务错误 HTTP 200，以 body `code` 为准。
- 但 body `code` 里同时出现 HTTP 风格的 `401`/`403`/`429`/`503` 和四位业务码 `4000`/`4041`/`4130`/`5001`。
- 3.10 设备侧接口又用 `400`/`429`/`500`。

**问题**

1. 403、429 到底是 HTTP 状态还是 HTTP 200 + `code=403`，读文档判断不出来。
2. 走网关/Nginx 的 413、502、504 会返回 HTML，不是 JSON，前端需要知道这些情况也会出现。
3. `4041`「设备不存在或离线」一码两义：前端无法区分「提示检查设备网络」和「设备已被删除，刷新列表」。
4. `4044` 在 1.5/3.9.1 表示「任务过期」，在 7.5 表示「设备不存在」。

**建议**

- 文档增加一张总表，每个错误一行：`HTTP 状态 | body.code | 含义 | 是否可重试 | 前端动作`。例如：

  | HTTP | code | 含义 | 可重试 | 前端动作 |
  | --- | --- | --- | --- | --- |
  | 401 | 401 | 未登录 / token 失效 | 否 | 清会话，跳登录 |
  | 200 | 403 | 无设备权限 | 否 | 提示无权限，返回列表并刷新 |
  | 200 | 429 | 频率超限 | 是 | 按 `retryAfter` 秒后重试 |
  | 503 | 503 | 依赖的老服务不可用 | 是 | 保留登录态，稍后重试 |
  | 200 | 4040 | 设备不存在 | 否 | 刷新设备列表 |
  | 200 | 4041 | 设备离线 | 是 | 提示检查设备网络 |
  | 200 | 4044 | 任务不存在或已过期 | 否 | 按「结果未知」处理 |

- 拆分 `4040` 设备不存在 / `4041` 设备离线。`4044` 只用于「任务不存在/过期」，后台「设备不存在」改用 `4040`。
- 业务码分段写进文档：`4xxx` 客户端可修正，`5xxx` 服务端异常，HTTP 风格三位码只保留 401/403/429/503。
- 429 时 body 带 `retryAfter`（秒），同时设置 HTTP Header `Retry-After`。草稿写了「同账号同时投屏过多」，请写明具体阈值。
- `msg` 只作为开发排查用，前端不会直接展示给用户（多语言由前端按 `code` 维护）。文档写一句即可。

Java 侧参考：统一由 `@RestControllerAdvice` 出口，避免各 Controller 各写各的：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ResponseEntity<R<Void>> biz(BizException e) {
        // 每个 ErrorCode 枚举自带 httpStatus，与文档总表一一对应
        return ResponseEntity.status(e.getCode().getHttpStatus()).body(R.fail(e.getCode(), e.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public R<Void> invalid(MethodArgumentNotValidException e) {
        // msg 里带出字段名，方便联调定位：如 "sleepTime: must match HH:mm"
        return R.fail(ErrorCode.PARAM_INVALID, e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage()).collect(Collectors.joining("; ")));
    }
}
```

### 5. 固件升级：URL 不应由客户端传入（安全）

**现状**：3.9 `POST /api/device/ota` 由 App 传 `url`（允许 http/https）、`type`、`version`，服务端解析后直接下发给设备。

**问题**

- 任何拿到有效 `userToken` 且有设备权限的人，都能让设备从任意地址下载并刷入固件，这属于设备劫持级别的风险。
- 被分享的用户同样有设备权限，也能触发。
- 允许 `http`，固件可能在传输中被篡改。

**建议**

- App 侧接口只接收 `deviceNo` + `firmwareId`（或 `type` + `version`）。下载地址、文件大小、校验值由服务端从固件发布表查出后下发。
- 新增检查更新接口，替代现在老服务 `getUserProductDetail` 里的 `newVersionNo`/`downloadPath`/`isUpdate`/`updateType`：

  ```
  GET /api/device/ota/check?deviceNo=XT20260001
  → { hasUpdate, firmwareId, type, version, releaseNote, force, size }
  ```

- 只允许 https；协议若支持，下发时附 `md5`/`sha256`，设备校验通过后再刷写。
- 是否只允许设备所有者（非分享者）升级，请产品确认，由服务端判定。
- 管理后台若需要「指定 URL 升级」，放在后台内部接口，不放在 App 接口里。

### 6. 配网确认

**问题 1：绑定前无法确认联网**。2.4 节已经指出 `GET /api/device/online` 要求设备已绑定，否则返回 403。但小程序绑定流程目前是：BLE 扫描 → 匹配产品 → 老服务 `addUserProduct`。WiFi 版要在中间插入 BluFi 配网。如果先绑定再配网，配网失败就留下一条「已绑定但从未联网」的设备记录。

**问题 2：重配网会误判成功**。设备原本在线时（例如用户换路由器重新配网），轮询 `online` 第一次就返回 `true`。这个 `true` 是旧连接的，并不代表新 WiFi 连上了。再加上离线确认有约 10 秒窗口，误判概率很高。

**问题 3：`mqtt_config` 的内容从哪来**。文档说 App 通过 BluFi 发送 `mqtt_config`（协议 2.2.3），但没说 App 要写哪些字段：MQTT 地址、端口、设备凭证、`batchKey` 等。这些不能写死在小程序里。

**建议**

- 新增配网会话接口（免设备权限，按会话校验）：

  ```
  POST /api/provision/session   { deviceNo }               → { sessionId, mqttConfig: {...}, expireAt }
  GET  /api/provision/status?sessionId=xxx                  → { state: WAITING | ONLINE | EXPIRED, onlineAt }
  ```

  - 服务端在会话创建后、设备新一次 `login` 时才置为 `ONLINE`，即只认 `loginAt > session.createdAt`，避免问题 2。
  - `mqttConfig` 由服务端生成，App 原样通过 BluFi 转发，解决问题 3。
  - 会话 5~10 分钟过期，同一 `deviceNo` 同时只保留一个会话。
- 如果本期不做配网会话，至少让 `GET /api/device/online` 支持 `since` 参数（配网开始时间，或毫秒时间戳）：只有 `lastOnlineAt > since` 才返回 `online=true`。同时请文档给出推荐的「配网 / 绑定」先后顺序和失败回滚方式。

### 7. 无鉴权接口与内网信息

- **7 章管理后台「当前无鉴权」**：
  - 如果这些接口和 App 接口同域名对公网暴露，任何人都能列出全部设备号、在线状态和日志。
  - 计划中的 `X-Internal-Token` 也不适合给浏览器里的后台用：token 会写在前端 JS 里，等于公开。
  - 建议：上线前至少在网关层限制来源 IP / 只在内网暴露；正式方案用后台登录态（Session / JWT + 角色），而不是共享密钥。
- **3.10 设备图片列表 `GET /device/playlist?deviceNo=`**：
  - 无鉴权，`deviceNo` 若是 `XT2026xxxx` 这类顺序编号，可被遍历拿到所有用户的图片地址（隐私问题）。
  - 建议 `strategy_bin` 下发的 `path` 里带设备级签名，例如 `path=/device/playlist?deviceNo=...&sig=HMAC(deviceSecret, deviceNo+ts)&ts=...`，服务端校验。或使用设备登录时拿到的设备 token。
- **OSS 图片地址**：`binUrl` 若是公共读，建议改为私有桶 + 带过期时间的签名 URL（过期时间覆盖设备下载耗时即可）。
- **9 章内部接口**：写着内网地址 `172.16.1.236:18081` 和 `X-Internal-Token` 用法。这些不是前端需要的内容，建议移到单独的「内部接口文档」，前端对接文档里删除。

### 8. 投屏入参与相册数据

**现状（小程序 BLE 版投屏）**

- 前端先按设备物理分辨率（来自老服务设备的 `width`/`height`）把图片裁成竖版画布，导出 JPG（质量 0.92）。
- 然后调老服务 `/Client/Basic/imageDitheringBinDownload`：参数 `color=BWRYGB`、`imageDitheringModes=2`、`type`，返回 6 色 4bpp 帧，再走蓝牙图传。
  - `type` 是抖动策略：480×720（3.7 寸）传 `'1'`，其余传 `'0'`。
- 同时调 `setUserProductUpload` 上传原图建记录，投屏成功后回写 `imgIndex`（设备图片槽位）。「我的相册」页面就是靠这些记录展示的。

**问题与建议**

1. **`type`「透传参数，值由前端决定」**：请写明它最终透传给谁、取值含义。若与现在的抖动 `type` 同义，请直接写「同 `imageDitheringBinDownload.type`：`0` 默认，`1` 为 480×720」。`color`、`imageDitheringModes` 是否由服务端固定，也请写出来。
2. **上传图片规格**：前端是否继续裁到物理分辨率再上传（推荐，流量小、所见即所得），还是传原图由服务端裁？请写明：
   - 接受的格式（JPG/PNG/HEIC？）；
   - 最大字节数（`4130` 的阈值）；
   - 是否要求宽高等于设备分辨率；
   - 横竖屏 / `orientation` 由谁处理（前端已经按设备角度导出，服务端不要再转一次）。
3. **相册记录与槽位**：WiFi 投屏后，「我的相册」还要不要有这条记录？请明确：
   - 服务端是否代为写老服务的投屏记录（`setUserProductUpload` / `editUserProductImgRecord` 的等价物）？还是前端仍需自己调？若前端调，投屏成功的判定口径以 `play.result=SUCCESS` 为准。
   - WiFi 设备是否还有「槽位」`imgIndex` 概念？图片是存 TF 卡、还是设备每次按 3.10 拉列表？
   - 3.5 清空 TF 卡后，老服务相册记录是否同步清空（BLE 版清空后前端会调 `clearUserProductImg`）？
   - 3.10 的列表来自老服务 `imgBle`：哪些图片会进入轮播列表，由谁维护，App 用哪个接口增删？
4. **`userNo` 必填且必须与 token 一致**：服务端既然能从 token 解析出 `userNo`，建议去掉这个入参或改为可选，服务端以 token 为准。多一个必须一致的字段，只会多一种 `4000`。

### 9. Long 型 ID 统一按字符串返回

`msgid` 已经是字符串，很好。但 8.1 通知 `id`（`101`）、7.3 日志 `id`（`1001`）是数字。JS 的安全整数上限是 2^53−1（约 9.007×10^15）。若这些 ID 用雪花算法或将来增长到 16 位以上，前端会静默丢精度，标记已读时传回的 `ids` 就对不上了。

建议：所有 Long 型 ID（包括 8.3 入参 `ids`）一律按字符串收发，文档写进「通用约定」。

```java
// 全局：Long 序列化为字符串
@Bean
public Jackson2ObjectMapperBuilderCustomizer longToString() {
    return b -> b.serializerByType(Long.class, ToStringSerializer.instance)
                 .serializerByType(Long.TYPE, ToStringSerializer.instance);
}
```

> 注意：全局开启后，`battery`、`binSize` 这类 Long/long 数值字段也会变成字符串。可以只对 ID 字段加 `@JsonSerialize(using = ToStringSerializer.class)`，或数值字段改用 `Integer`。

## 三、P1：建议本期完成

### 10. 控制指令的执行结果

**现状**：3.x 控制接口只返回 `msgid`，「不建任务状态机，不返回执行结果」。

**问题**：用户在小程序点「保存轮播设置」「开启休眠」「切换国家码」后，前端只能提示「已下发」，无法告诉用户设备是否真的生效。设备离线时已经有 `4041` 拦截，但「在线但执行失败」完全无感知。BLE 版是同步拿到设备应答的，WiFi 版体验会明显倒退。

**建议**：协议里各指令都有 `*_ack`，服务端已能收到。建议复用投屏/OTA 的做法，做一个通用、轻量的指令状态：

- 新增 `GET /api/device/command/status?msgid=` → `{ msgid, action, status: SENT|SUCCESS|FAILED|TIMEOUT, result }`，保留 1 小时。
- WS 推送 `{ "type": "command.result", "deviceNo", "msgid", "action", "status", "result" }`。
- 超时可统一 30 秒，按 action 配置。
- 休眠返回两个 `msgids`，前端两个都 SUCCESS 才算成功。

Java 侧不需要复杂状态机：Redis Hash `cmd:{msgid}` 加 TTL，收到 ack 时更新并发布事件即可，超时由延迟任务或查询时惰性判定。

### 11. 幂等与重复下发

**现状**：小程序网络层在超时/断网时会**静默自动重试 2 次**（普通请求单次 10 秒）。如果服务端已经下发成功、只是响应没回来，就会重复下发。上传接口目前不做自动重试，但用户会手动点「重试」。

**建议**

- 所有 `POST /api/device/*` 支持 Header `Idempotency-Key`（前端每次用户操作生成一个 UUID，重试时复用）。服务端在 N 分钟内（建议 10 分钟）对同一 key 返回第一次的结果，不再下发。
- 投屏接口尤其需要：重复投屏会多生成一份 bin、多下发一次、相册多一条记录。

```java
// 伪代码：Redis SETNX 占位 + 缓存首个响应
String k = "idem:" + userNo + ":" + idemKey;
Boolean first = redis.opsForValue().setIfAbsent(k, "PENDING", Duration.ofMinutes(10));
if (!Boolean.TRUE.equals(first)) {
    String cached = redis.opsForValue().get(k);
    return "PENDING".equals(cached) ? R.fail(ErrorCode.REQUEST_IN_PROGRESS) : json.read(cached);
}
R<?> resp = doPlay(...);
redis.opsForValue().set(k, json.write(resp), Duration.ofMinutes(10));
```

### 12. 批量接口

小程序设备列表一次拉取老服务全部绑定设备（目前一页 100 条），每个设备都要展示在线状态和未读角标。按现有接口，N 台设备就是 N 次 `online` + N 次 `unread-count` 请求，每次服务端还要调一次老服务 `checkPermission`。

建议：

- `GET /api/device/online/batch?deviceNos=a,b,c`（或 POST body），上限 100，返回数组。无权限的设备单条标记 `403`，不要整体失败。
- `GET /api/notification/unread-count/batch?deviceNos=...`，同上。也可以加一个「当前用户全部设备未读总数」接口，用于 TabBar 角标。
- WS 支持一次订阅多台：`{ "type": "subscribe", "deviceNos": ["a","b"] }`，返回逐台结果。另外小程序同时最多只能开 5 个 WebSocket 连接，前端会用单连接订阅多台设备，请确认单连接的订阅数上限。

### 13. WebSocket 协议细节

| 现状 | 问题 | 建议 |
| --- | --- | --- |
| `{ "type": "error", "msg": "no permission" }` | 同时订阅多台时不知道哪台失败；按 `msg` 文本判断很脆弱 | 带 `deviceNo`、`code`（同 HTTP 错误码表），以及客户端请求里带上来的 `reqId` |
| `{ "type": "unsubscribed" }` | 不带 `deviceNo` | 带 `deviceNo` |
| 所有事件 | 无时间戳、无序号，断线重连后难以判断新旧 | 每条事件带 `ts`（毫秒）；有条件的话带设备维度递增 `seq` |
| 9.2 踢订阅「不发送客户端消息」 | 被移除分享的用户停在设备页，再也收不到推送，自己不知道 | 推一条 `{ "type": "subscription.revoked", "deviceNo" }`（只是信号，不带原因），前端据此退出设备页并刷新列表 |
| 重连 | 没说重连后订阅是否保留 | 文档写明「订阅随连接失效，重连后需重新 subscribe」（前端按此实现） |
| 心跳 | 90 秒无消息断开 | 认可。请同时确认 Nginx `proxy_read_timeout` 大于 90 秒，默认 60 秒会先断 |

**多实例部署**：如果新服务部署多实例，WS 会话在各实例内存里，`play.result`、`notification.new`、踢订阅都需要跨实例广播，否则会出现「偶发收不到推送」。建议用 Redis Pub/Sub（或 MQ）按 `deviceNo` 频道广播，各实例只推给本机持有的订阅；或者网关按用户粘性会话。踢订阅接口同样要广播到所有实例。

Nginx 参考：

```nginx
location /ws/push {
    proxy_pass http://iot_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 120s;   # 必须大于服务端 90s 空闲判定
    proxy_send_timeout 120s;
}
```

小程序端说明：小程序切到后台后，系统会在短时间内断开网络连接，WS 断线会非常频繁。服务端看到大量短连接、重连属于正常现象，请不要把它当异常告警，也不要对同一用户的重连做过严的频率限制。

### 14. 投屏状态细节

1. **失败原因**：`play.result` 的 `FAILED` 不带设备原始码。前端只能统一提示「投屏失败」，但「设备存储异常」和「下载失败，请检查网络」对用户的指引完全不同。8.4 节其实已经分好了类，建议 `play.result` 与 `GET /api/device/play/status` 也带 `result`（原始码）和 `reason`（短码，取值同 8.4：`PLAY_DOWNLOAD_FAILED`/`PLAY_STORAGE_ERROR`/`PLAY_FAILED`）。
2. **TIMEOUT 时长**：OTA 写了 300 秒 / 900 秒，投屏没写，前端无法设置兜底等待。请写明投屏判定 TIMEOUT 的时间。
3. **状态命名**：投屏 HTTP 返回 `DOWNLOADING` 表示「指令已下发」，OTA 则用 `SENT`。建议投屏也用 `SENT` 作为初始状态，收到 `100`/`106` 再进 `DOWNLOADING`，两套状态机统一：`SENT → DOWNLOADING → FLASHING → SUCCESS | FAILED | TIMEOUT`。前端可以共用一套进度组件。
4. **`corrected`**：认可。建议 1.5 状态查询也返回 `corrected`，断线补查时前端才能保持同样的展示逻辑。
5. **ack `1` 视为成功**：v0.16 起 `1` 按成功处理，请与固件确认 `1` 的确切含义，并在文档里注明出处。

### 15. 轮播参数

- 入参 `timingTime` 单位秒，服务端向上取整为分钟；查询返回 `intervalMinutes`。建议入参也改为 `intervalMinutes`，收发对称，避免「设 90 秒、读回 2 分钟」。
- `beginTime`/`endTime` 的时区见第 3 条。另需说明：跨午夜（`22:00`–`06:00`）是否支持；`beginTime == endTime` 是否表示全天。
- **数据源**：小程序现在以老服务设备字段 `carouselInterval`（分钟）作为轮播设置的权威来源。新服务把配置写在 `iot_device_strategy` 表。WiFi 设备以哪边为准？建议明确「WiFi 设备以新服务 3.1.1 为准，老服务字段不再维护」，或由新服务回写老服务，避免两边不一致。
- 现有 BLE 版轮播只有顺序/随机/手动 + 间隔（UI 选项 1/2/4/8/24 小时），没有时间窗。WiFi 版新增的时间窗、`idle` 需要产品给交互，前端待定，不影响后端接口。

### 16. 休眠两条指令非原子

3.7 先下发 `wifimode` 再下发 `wifi_sleep`，不等 ack。请说明：

- 第一条 MQTT 发布成功、第二条失败时，接口返回什么？`msgids` 是否只有一个？
- 设备会不会处于「已进入休眠模式但没有休眠时间段」的中间状态？是否需要服务端补偿或回滚？
- 有没有「查询当前休眠设置」的接口？像 3.1.1 轮播查询那样回显，前端设置页需要回显。

### 17. 字段规范

- **命名**：响应主体都是驼峰，但 4 章 `payload.wifi_rssi` 是下划线。建议 `payload` 也统一驼峰（`wifiRssi`），并在 8.4 给出每个 `type` 的 `payload` 完整字段表。
- **空值口径**：`shadow` 无数据时是 `{}`，单个字段缺失时是省略还是 `null`？建议统一为「字段始终存在，无值为 `null`」，前端判断更简单。

  ```java
  // 不要全局配置 NON_NULL，否则字段会消失
  spring.jackson.default-property-inclusion: always
  ```

- **枚举**：`statype`（基站类型 `"2"`）、`tagType`、`tagDeviceCode`、`orientation` 等请列出全部取值与含义；`statype` 为什么是字符串而不是数字？
- **电量**：WiFi 版电量来自心跳影子。请注明心跳间隔，即 `battery` 最多滞后多久，前端据此决定是否显示「更新于 X 分钟前」。
- **单位**：`tfTotal`/`tfUsed` 为 MB、`decimal`，请注明返回 JSON 时是整数还是小数。

### 18. 权限校验性能

每个设备请求都实时调老服务 `checkPermission`，设备列表页、批量接口、WS 订阅会把老服务的压力放大 N 倍；老服务抖动时，新服务所有接口一起 503。

建议：

- 按 `(userNo, deviceNo)` 做本地短缓存，例如 Caffeine，TTL 30~60 秒；只缓存「有权限」结果，「无权限」不缓存或只缓存几秒。
- 老服务调用 9.2 踢订阅时同时清除对应缓存（多实例时广播清除）。
- 高危操作（清空 TF、OTA）可以绕过缓存，实时校验。

```java
Cache<String, Boolean> permCache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofSeconds(60)).maximumSize(100_000).build();
```

### 19. 上传与网关配置

投屏是 multipart 上传，以下默认值都会导致「大一点的图片直接失败」，而且失败时返回的不是 JSON：

- Spring Boot 默认 `spring.servlet.multipart.max-file-size=1MB`、`max-request-size=10MB`；
- Nginx 默认 `client_max_body_size 1m`，超限返回 HTML 413 页面。

建议：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB      # 与 4130 阈值保持一致
      max-request-size: 12MB
```

```java
@ExceptionHandler(MaxUploadSizeExceededException.class)
public R<Void> tooLarge() { return R.fail(ErrorCode.IMAGE_TOO_LARGE); } // 统一成 code=4130
```

Nginx `client_max_body_size` 设置得略大于 Spring 的上限，让超限请求进到 Spring，统一返回 `4130` 的 JSON。同时 `proxy_read_timeout` 不小于 30 秒（投屏同步处理最长约 8 秒，留余量）。

## 四、P2：后续迭代

### 20. 投屏接口异步化

现在投屏是同步的：调老服务转 bin → 上传 OSS → 下发，最长约 8 秒，期间占用一个 Tomcat 线程，并发一高线程池会被打满；客户端也要专门调大超时。可以考虑：

- 上传完成即返回 `{ msgid, status: "PROCESSING" }`，后续转码、上传、下发在线程池/MQ 中进行，进度通过 `play.result` 推送：`PROCESSING → SENT → DOWNLOADING → FLASHING → 终态`。
- 前端已经按「先拿 `msgid`，再等 WS」的模式实现，改成异步对前端几乎没有额外成本。也顺带解决了「WS 事件早于 HTTP 响应」的缓存问题。

### 21. 其他

- **小程序订阅消息**：小程序没有常驻推送通道，WS 只在前台有效。低电量、投屏失败这类重要通知，后续可接微信「订阅消息」（需要用户授权和模板，后端调用微信接口、需要用户 openid）。本期不做，但通知模型设计时可预留「是否推送到微信」的标记。
- **`traceId`**：响应 Header 或 body 带 `traceId`，前端报错时上报，后端查日志更快。
- **版本前缀**：接口路径考虑 `/api/v1/...`，小程序发版有审核周期，新老版本会长期并存，接口不兼容变更时可以并行提供 v2。
- **文档拆分**：建议拆成三份：App 对接文档（第一～六、八章）、管理后台文档（第七章）、内部接口文档（第九章，含 token 与内网地址，不外发）。变更记录里对**不兼容变更**加醒目标记（如 `⚠️ BREAKING`），例如 v0.20 下线 `/api/alarm/*`、v0.24 投屏新增必填 `userNo`。
- **第六章待补充**：配网一项仍未勾选，可与第 6 条一起定。

## 六、小程序端自身需要调整（供后端知悉）

以下是对照草稿后，小程序这边要改的地方，不需要后端动，列出来是为了让双方对联调预期一致：

- 新服务的错误信息字段是 `msg`，现有请求层只读 `message`/`retMsg`，需要兼容 `msg`。
