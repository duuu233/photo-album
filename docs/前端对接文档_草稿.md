## 〇、通用约定

| 项 | 约定 |
|---|---|
| 域名 | `https://iot.boltfox.cn` |
| 鉴权 | 每个请求 Header 携带 `userToken`（沿用 App 现有登录 token，来自老服务） |
| 返回结构 | `{ "code": 0, "msg": "ok", "data": {...} }`，`code=0` 为成功 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`，时区 Asia/Shanghai |
| 长连接 | `wss://iot.boltfox.cn/ws/push` |

> 设备相关操作（投屏、设备查询、设备控制、WebSocket 订阅）会实时调用老服务 `checkPermission` 校验设备权限。老服务返回 HTTP `401` 时对外返回 `401`（登录已失效，需重新登录）；无权限返回 `403`；权限服务连接失败、超时或返回 5xx 时返回 `503`，请勿把 `503` 当作无权限处理。

> **时间约定（重要）**：所有接口时间均使用 Asia/Shanghai 本地时间。休眠设置的 `sleepTime` / `wakeTime` **只需传本地 `HH:mm`，前端不要自行转 UTC**；服务端会在下发设备前统一转换为 UTC。

### HTTP 超时（重要）

**投屏接口必须把超时设到 30 秒以上。**

原因：服务端需要同步完成「调用老服务转 bin → 上传 OSS → 下发指令」，最长约 8 秒。若客户端超时设为默认值（Flutter 15s / OkHttp 10s），会出现「请求超时但后台实际已成功」的假失败。

建议各端配置：

| 端 | 默认超时 | 本接口应设 |
|---|---|---|
| OkHttp | 10s | 30s+ |
| Flutter http | 15s | 30s+ |
| URLSession (iOS) | 60s | 默认即可 |

## 一、投屏

### 1.1 接口

```
POST /api/device/play
Content-Type: multipart/form-data
Header: userToken

参数：
  deviceNo  String  必填  设备编号
  userNo    String  必填  当前登录用户编号，必须与 userToken 解析出的 userNo 一致
  file      File    必填  图片文件（从手机相册选择）
  type      String  必填  透传参数，值由前端决定
```

> `userNo` 用于投屏失败时定位发起用户；与登录用户不一致返回 `4000`。

### 1.2 返回

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "msgid": "1729384756123042",
    "binUrl": "https://inkstar.oss-ap-southeast-1.aliyuncs.com/wififile/XT20260001/20261020103015_7f3a9c2d.bin",
    "binSize": 2457600,
    "status": "DOWNLOADING"
  }
}
```

| 字段 | 说明 |
|---|---|
| `msgid` | 本次投屏任务 ID，用于查询状态、匹配推送事件 |
| `binUrl` | 图片转换后的 bin 文件地址（一般前端不用展示） |
| `binSize` | bin 文件大小（字节） |
| `status` | 正常返回 `DOWNLOADING`，表示指令已下发；MQTT 下发失败时返回 `FAILED`，此时直接按失败处理，不用再等 WebSocket |

### 1.3 错误码

| code | 含义 | 前端处理 |
|---|---|---|
| 0 | 成功 | — |
| 4000 | 参数错误 | 检查必填参数后重试 |
| 403 | 无该设备操作权限 | 提示无权限，返回列表 |
| 4130 | 图片过大 | 提示「图片过大，请压缩后重试」 |
| 429 | 并发超限（同账号同时投屏过多） | 提示稍后重试 |
| 4041 | 设备不存在或离线 | 提示「设备已离线，请检查设备网络」 |
| 503 | 服务暂时不可用（老服务不可用） | 稍后重试，**不要**跳转重新登录 |
| 5000 | 服务端未预期异常 | 提示「服务异常，请稍后重试」 |
| 5001 | 图片转换失败 | 提示「图片处理失败，请换一张试试」 |
| 5002 | 文件上传失败 | 提示重试 |
| 5003 | 图片处理超时 | 提示重试 |

### 1.4 进度条方案（前端自行实现）

服务端**不返回任何百分比**，协议也没有设备下载进度上报（见文末「为什么没有真实进度百分比」）。

设备方 App 看到的 0-100 进度条，来源只有两种可能：

1. **App 上传图片到服务端的真实上传进度**（客户端自己可测）；
2. App 本地动画 / 估算，**不是设备下载进度**。

推荐按「上传进度 + 阶段状态」实现，观感与设备方 App 一致：

```text
用户点击「投屏」
  ↓
① 图片上传到本服务：进度条 0% → 100%
   进度来源：客户端 multipart 上传进度（OkHttp / Flutter 均可拿到）
  ↓
② 上传到 100% 但接口还没返回：文案「图片处理中」，进度保持 100%
   原因：服务端还要转 bin、上传 OSS、下发 MQTT 指令，最长约 8 秒
  ↓
③ 接口返回：
   - status=DOWNLOADING → 文案「屏幕即将刷新」，进度保持 100%，不要回退
   - status=FAILED      → 文案「投屏失败」，直接结束（MQTT 下发失败）
  ↓
④ 收到 WebSocket play.result：
   - status=FLASHING → 文案「设备刷屏中」，进度保持 100%
   - status=SUCCESS  → 文案「投屏成功」，关闭进度界面
   - status=FAILED   → 文案「投屏失败」，提供「重试」按钮
   - status=TIMEOUT  → 文案「投屏超时」，提供「重试」按钮
```

> 事件顺序：设备很快时，`play.result` 可能比 HTTP 响应更早到达。此时客户端还不知道 `msgid`，建议按 `msgid` 缓存最近几秒的 WS 事件，拿到接口响应后再匹配；不要因为“没找到对应任务”直接丢弃。

如果客户端拿不到上传进度，可以用分段假涨方案：

```text
① 请求发出 → 「图片处理中」，0% → 30%
② 收到接口响应（status=DOWNLOADING）→ 「屏幕即将刷新」，30% → 98%，到 98% 卡住
③ 收到 play.result(FLASHING) → 「设备刷屏中」，保持 98%
④ 收到 play.result 终态：
   - SUCCESS → 100%「投屏成功」
   - FAILED  → 「投屏失败」，提供「重试」
   - TIMEOUT → 「投屏超时」，提供「重试」
```

**终态修正处理（重要）：**

1. 收到 `status=TIMEOUT` 时**不要立即允许重试**。建议等待 3 秒，或提示「稍后重试」，给迟到 ack 留出修正窗口。
2. 如果之后收到 `corrected=true` 的 `SUCCESS` 事件，直接把 UI 更新为「投屏成功」，**不要**提示「状态已变更」，也不要弹二次确认。
3. 用户点击重试前，建议先调用一次 `GET /api/device/play/status` 确认最终状态。

**文案对照表**（服务端只给状态码，文案与多语种由 App 自行维护）：

| 阶段/状态 | 中文文案 | 触发来源 |
|---|---|---|
| 上传中 | 图片上传中 | 客户端本地上传进度 |
| 请求中 / 服务端处理中 | 图片处理中 | 前端本地（请求已发出但未返回） |
| `DOWNLOADING` | 屏幕即将刷新 | 接口响应 / 状态查询 / WebSocket |
| `FLASHING` | 设备刷屏中 | WebSocket `play.result` / 状态查询 |
| `SUCCESS` | 投屏成功 | WebSocket `play.result` |
| `FAILED` | 投屏失败 | WebSocket `play.result` |
| `TIMEOUT` | 投屏超时 | WebSocket `play.result` |

> 上传进度方案里 100% 只代表「图片已上传到服务端」，不代表设备已下载完成；设备阶段只能靠 `play.result` 的 `FLASHING` / 终态区分。
>
> 分段假涨方案里到 98% 后卡住，不要涨到 100% 后干等。

### 1.5 状态查询（断线兜底）

App 切后台、WebSocket 断开后重新进入时，用此接口补查一次：

```
GET /api/device/play/status?msgid=1729384756123042
Header: userToken
```

```json
{
  "code": 0,
  "data": {
    "msgid": "1729384756123042",
    "status": "DOWNLOADING",
    "sentAt": "2026-10-20 11:02:43",
    "elapsedSeconds": 12
  }
}
```

| 字段 | 说明 |
|---|---|
| `status` | `DOWNLOADING` / `FLASHING` / `SUCCESS` / `FAILED` / `TIMEOUT` |
| `sentAt` | 指令下发时间 |
| `elapsedSeconds` | 已耗时（秒），可用于前端判断是否已超时 |

> 状态只进不退：`DOWNLOADING` → `FLASHING` → 终态。迟到的低档位事件会被服务端丢弃，前端收到旧状态时也不要回退 UI。

> 任务状态在服务端保留 1 小时，超时后查询返回 `4044`，前端按「结果未知」处理。

### 1.6 WebSocket 推送

连接地址：`wss://iot.boltfox.cn/ws/push`

#### 握手鉴权

- 优先读取 Header `userToken`
- 无 Header 时读取 query 参数 `token`：`wss://iot.boltfox.cn/ws/push?token=xxx`
- 缺少 token、老服务返回 4xx 或 `retCode != 200`：握手阶段返回 `401`，表示需要重新登录
- 老服务连接失败、超时或返回 5xx：握手阶段返回 `503`，表示服务暂时不可用，稍后重试即可
- 以上情况连接都不会建立，客户端不会进入已连接状态

#### 客户端消息

订阅设备事件（订阅成功后才能收到该设备的推送）：

```json
{ "type": "subscribe", "deviceNo": "XT20260001" }
```

取消订阅：

```json
{ "type": "unsubscribe", "deviceNo": "XT20260001" }
```

心跳：

```json
{ "type": "ping" }
```

#### 服务端消息

订阅结果：

```json
{ "type": "subscribed", "deviceNo": "XT20260001" }
```

取消订阅结果：

```json
{ "type": "unsubscribed" }
```

心跳响应：

```json
{ "type": "pong" }
```

订阅失败（无设备权限等）：

```json
{ "type": "error", "msg": "no permission" }
```

投屏结果事件：

```json
{
  "type": "play.result",
  "msgid": "1729384756123042",
  "deviceNo": "XT20260001",
  "status": "SUCCESS",
  "corrected": false
}
```

| 字段 | 说明 |
|---|---|
| `status` | `DOWNLOADING` / `FLASHING` / `SUCCESS` / `FAILED` / `TIMEOUT` |
| `corrected` | 首次到达的终态为 `false`；`TIMEOUT` 被迟到的成功 ack 修正为 `SUCCESS` 时为 `true` |

设备 ack 分档（同一投屏可能收到多条）：

| result | 阶段 |
|---|---|
| `100` / `106` | 下载中（`DOWNLOADING`） |
| `107` / `255` | 刷屏中（`FLASHING`） |
| `0` / `1` / `113` | 完成（`SUCCESS`） |
| 其它非 0 | 失败（`FAILED`） |

状态只进不退，服务端会丢弃乱序到达的低档位 ack，不重复推送；`DOWNLOADING` 为投屏接口返回的初始状态，正常流程下不会再单独推送。MQTT 下发失败时服务端会推送一条 `FAILED`；若该事件早于 HTTP 响应到达，客户端按 `msgid` 缓存后匹配即可。

设备上下线事件（需先按 1.6 订阅该设备）：

```json
{
  "type": "device.status",
  "deviceNo": "XT20260001",
  "online": true
}
```

| 字段 | 说明 |
|---|---|
| `online` | `true`=设备上线/登录；`false`=延迟确认离线、关机或对账置离线 |

- 只推信号，不推详情；收到后可调用 2.1 / 2.2 补查在线状态与影子。
- 升级期间设备断连不会推送 `online=false`。

处理原则：

- **WebSocket 只推信号，不推详情**。收到事件后如需更多信息，自行调用 REST 查询。
- 断线期间可能丢失事件，恢复连接后**必须**用 1.5 的接口补查一次状态。
- 重连策略建议：1s、2s、4s、8s… 指数退避，上限 30s。
- 心跳：客户端应保持发送 `ping`；服务端每 60 秒检查一次，超过 90 秒未收到任何消息的连接会被主动关闭。建议客户端每 30 秒发送一次 `ping`。

### 2.3 错误码

| code | 含义 | 前端处理 |
|---|---|---|
| 0 | 成功 | — |
| 4000 | 参数错误 | 检查必填参数后重试 |
| 401 | 未登录或 token 失效 | 重新登录 |
| 403 | 无该设备操作权限 | 提示无权限 |
| 503 | 服务暂时不可用（老服务不可用） | 稍后重试，**不要**跳转重新登录 |
| 5000 | 服务端未预期异常 | 提示「服务异常，请稍后重试」 |

> `503` 表示鉴权依赖的老服务暂时不可用，与 `401`（token 失效需要重新登录）语义不同。客户端遇到 `503` 应保留当前登录态并稍后重试。

> **统一返回字段**：所有错误响应（含 HTTP 401 / 404）均为 `{ "code": ..., "msg": "...", "data": null }`，不再使用 `message` 字段。
>
> **HTTP 状态码约定**：只有鉴权失败、资源不存在、上游不可用会使用非 200 的 HTTP 状态（`401` / `404` / `503`）；其余业务错误统一返回 HTTP 200，客户端以响应体 `code` 为准。

### 2.4 配网流程与状态归属

App 配网页面按以下 4 个步骤展示。**前 3 步由前端 / 设备侧完成，第 4 步调用本服务接口确认。**

| 步骤 | 页面状态 | 完成方 | 说明 / 对接方式 |
|---|---|---|---|
| 1 | 手机网络正常 | **前端完成** | App 本地检测手机网络（Wi-Fi / 蜂窝）是否可用，不需要调用服务端 |
| 2 | 设备网络配置已完成 | **前端完成** | App 通过 BLE BluFi 向设备发送 `mqtt_config`（协议 2.2.3），设备回 `mqtt_config_ack.result=0` 即完成；WiFi SSID / 密码不经过本服务 |
| 3 | 设备正在连接 WiFi | **前端 / 设备侧完成** | 设备内部连接 WiFi 的过程；BLE 协议没有该状态上报，本服务也无法感知。前端可在第 2 步成功后直接展示该状态，同时开始第 4 步轮询 |
| 4 | 设备正在连接云端 | **对接本服务接口** | 轮询 `GET /api/device/online?deviceNo=...`，返回 `online=true` 表示设备已连上云端 |

第 4 步接口：

```
GET /api/device/online?deviceNo=XT20260001
Header: userToken
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "deviceNo": "XT20260001",
    "online": true,
    "lastOnlineAt": "2026-10-24 23:56:43"
  }
}
```

| 字段 | 说明 |
|---|---|
| `online` | `true`=设备已连上云端；`false`=尚未连上 |
| `lastOnlineAt` | 设备最后一次上线时间；设备未登记时为 `null` |

轮询建议：

- 第 2 步 BLE 配置成功后开始轮询，间隔 1~2 秒，最长 60 秒。
- 收到 `online=true` 立即停止轮询，进入配网成功页面。
- 超时仍未上线，提示「设备联网超时，请检查 WiFi 密码或信号后重试」。
- `503` 表示权限服务暂时不可用，保留当前页面稍后重试，不要当作配网失败。

**重要限制：**

- `GET /api/device/online` 会先调用老服务 `checkPermission`。**设备尚未绑定到当前用户时返回 `403`，不能用于绑定前的联网确认。**
- 推荐顺序：BLE 配置成功 → 老服务完成设备绑定 → 轮询本接口。
- 如果产品要求“绑定前就能看到设备是否连上云端”，需要新增一个免设备权限的配网状态接口；当前版本没有该接口。
- WS `device.status` 同样要求先按 1.6 订阅且具备设备权限，不能替代绑定前的轮询。

## 三、设备控制

所有控制接口统一使用 `POST` + `application/json` + Header `userToken`。

通用流程：权限校验 → 设备在线校验 → 下发指令 → 返回 `msgid`。

- 设备不在线统一返回 `4041`「设备已离线」。
- 控制指令不建任务状态机，只记录 pending；接口返回 `msgid` 仅用于关联，不会返回执行结果，也不支持 play 那样的状态查询。
- 通用错误码见 2.3：`4000` 参数错误、`401`、`403`、`503`、`5000`；控制接口额外可能返回 `4041`。

| code | 含义 | 前端处理 |
|---|---|---|
| 4041 | 设备已离线 | 提示「设备已离线，请检查设备网络」 |
| 4045 | 设备升级中 | 提示「设备升级中，请稍后」 |

统一返回：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "msgid": "1729384756123042"
  }
}
```

### 3.7 休眠设置

```
POST /api/device/sleep
```

```json
{
  "deviceNo": "XT20260001",
  "enable": true,
  "sleepTime": "22:00",
  "wakeTime": "07:00"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `deviceNo` | string | 是 | 设备编号 |
| `enable` | boolean | 是 | 是否开启休眠 |
| `sleepTime` | string | 条件必填 | `enable=true` 时必填，本地时间 `HH:mm`（Asia/Shanghai），**不要转 UTC** |
| `wakeTime` | string | 条件必填 | `enable=true` 时必填，本地时间 `HH:mm`（Asia/Shanghai），**不要转 UTC** |

> **前端只传本地时间，不要自行转 UTC。** 服务端会按协议 2.6 把 `sleepTime` / `wakeTime` 转换成 UTC 后再写入 `wifi_sleep`；前端重复转换会导致设备休眠时间偏差 8 小时。

服务端按顺序下发两条指令，不等待 ack：

> 转换示例：`22:00`（本地）→ `14:00`（UTC）、`07:00`（本地）→ `23:00`（UTC）。

| enable | 第一条 | 第二条 |
|---|---|---|
| `true` | `wifimode`：`mode=3`（休眠模式）、`live=600`、`timingTime=240` | `wifi_sleep`：`mode=2`（周期）、`beginTime=UTC(sleepTime)`、`endTime=UTC(wakeTime)` |
| `false` | `wifimode`：`mode=1`（实时通讯）、`live=600`、`timingTime=240` | `wifi_sleep`：`mode=0`（关闭）、`beginTime=""`、`endTime=""` |

返回：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "msgids": ["1729384756123042", "1729384756123043"]
  }
}
```

两条指令按顺序下发，`msgids[0]` 为 `wifimode`，`msgids[1]` 为 `wifi_sleep`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|

服务端把 `url` 解析为协议字段 `host`、`port`、`path`：未显式端口时 https 默认 443、http 默认 80；query 会保留在 `path` 中。该操作会写入 INFO 审计日志。

- 同一设备同一时间只允许一个进行中的升级任务；重复调用返回 `4000`「已有升级任务进行中」。
- 升级期间（下发成功到设备重新登录前），除 `GET /api/device/info`、`GET /api/device/online`、`GET /api/device/ota/status`、`/api/notification/*` 外，其余设备操作（投屏、轮播、刷新、TF、配置、休眠、国家码、OTA）统一返回 `4045`「设备升级中，请稍后」。

### 3.9.1 升级状态查询

```
GET /api/device/ota/status?msgid=1729384756123042
Header: userToken
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "msgid": "1729384756123042",
    "status": "FLASHING",
    "type": "main",
    "version": "EF6_370_V102",
    "baseVersion": "EF6_370_V101",
    "sentAt": "2026-10-20 20:30:00",
    "elapsedSeconds": 120
  }
}
```

| 字段 | 说明 |
|---|---|
| `status` | `SENT`=已下发待设备确认，`DOWNLOADING`=设备下载固件中，`FLASHING`=设备写入/刷机中，`SUCCESS`=设备重启登录且版本已变化，`FAILED`=设备 ack 失败或版本未变化，`TIMEOUT`=下发或升级超时 |
| `version` | 本次升级目标版本 |
| `baseVersion` | 下发前设备登记的固件版本 |
| `sentAt` | 指令下发时间 |
| `elapsedSeconds` | 从下发到现在的秒数 |

- 设备 ack 分档：`100`/`106` 下载中，`107`/`255` 刷屏中，`0`/`1`/`113` 完成；其它未列出的非 0 与 `null` 均按失败处理。
- 状态只进不退：迟到的低档位 ack 会被丢弃，不会回退状态。
- 下发后 300 秒未收到首条 ack 判 `TIMEOUT`；进入下载/刷屏阶段后 900 秒未重新登录判 `TIMEOUT`。
- `TIMEOUT` 后设备仍可能重连：若重连时版本已变化，会修正为 `SUCCESS` 并通过 WebSocket 推送 `corrected=true`；版本未变化则保持 `TIMEOUT`。
- 任务记录保留 2 小时，过期或不存在返回 `4044`。
- 错误码：`4000`、`401`、`403`、`4044`、`503`、`5000`（同 2.3）。

### 3.9.2 升级结果推送

需要先按 1.6 订阅该设备。升级状态每次变更时推送信号：

```json
{
  "type": "ota.result",
  "deviceNo": "XT20260001",
  "msgid": "1729384756123042",
  "status": "SUCCESS",
  "version": "EF6_370_V102",
  "corrected": false
}
```

| 字段 | 说明 |
|---|---|
| `status` | 取值同 3.9.1，`SENT` 表示服务端已成功下发 |
| `corrected` | 首次到达的终态为 `false`；`TIMEOUT` 被设备迟到重连修正为 `SUCCESS` 时为 `true` |

- 只推信号，不推详情；收到后可调用 3.9.1 补查。
- 状态只进不退：`SENT` → `DOWNLOADING` → `FLASHING` → 终态，低档位或重复 ack 不会重复推送。

### 3.10 设备图片列表（设备侧，App 不调用）

```

```

- 无鉴权，供设备按 `strategy_bin` 下发的 `path` 拉取图片列表。

## 四、设备告警（已合并到消息通知）

> 自 v0.20（2026-10-24）起，原 `/api/alarm/*` 接口、`iot_alarm` 表、`alarm.new` WebSocket 推送全部下线，告警统一通过第八章「设备消息通知」下发，不再单独维护告警列表和未读数。

| 场景 | 消息 `category` | 消息 `type` | 说明 |
|---|---|---|---|
| 设备上线 | `DEVICE` | `DEVICE_ONLINE` | 设备登录/重连 |
| 设备离线 | `DEVICE` | `DEVICE_OFFLINE` | 断开确认窗口（默认 10 秒）后即时生成 |
| 电量低 | `ALARM` | `LOW_BATTERY` | `payload.level=2`，`payload.battery` |
| WiFi 弱 | `ALARM` | `WIFI_WEAK` | `payload.level=1`，`payload.wifi_rssi` |
| TF 容量将满 | `ALARM` | `TF_FULL` | `payload.level=1`，`payload.percent` |
| 投屏下载失败 | `ALARM` | `PLAY_DOWNLOAD_FAILED` | `payload.msgid` / `result` / `userNo` / `reason` |
| 设备存储异常 | `ALARM` | `PLAY_STORAGE_ERROR` | `payload.msgid` / `result` / `userNo` / `reason` |
| 投屏通用失败 | `ALARM` | `PLAY_FAILED` | `payload.msgid` / `result` / `userNo` / `reason` |

- 已移除：`TF_ERROR`（不插卡场景）、`OFFLINE` 告警（原“离线超过 30 分钟”规则）。
- 所有设备/告警通知改为**状态变化时只发一次**：`DEVICE_ONLINE` / `DEVICE_OFFLINE` 按设备连接状态变化发送，重复的连接/断开事件不会重复通知；电量、WiFi、TF 告警在条件出现时发一次，条件恢复后再次出现才会再发。
- 异常类通知（`EXCEPTION_*`）按设备 + 类型去重，窗口默认 300 秒（`xt.notification.exception-dedupe-seconds`）。
- App 请改用 8.1 列表 / 8.2 未读数 / 8.3 已读 / 8.5 `notification.new` 推送。

## 五、为什么没有真实进度百分比

协议限制，非实现取舍：

1. 下行 `play` 指令中没有「请上报进度」的约定，只有图片下载地址。
2. 设备上行 `play_ack` 只有 `ack_msgid` 和 `result`，`result` 是状态码，不是百分比。
3. 协议 V1.3.1 的全部上行消息为：`login` / `heart` / 各类 `*_ack` / `shutdown` / `uptag`，**没有 `play_progress` 之类的下载进度上报**。
4. 设备能提供的只有阶段边界：
   - `100` / `106`：指令已收到 / 已加入下载
   - `107` / `255`：图片下载成功（准备刷屏）
   - `0` / `1` / `113`：执行成功
   - `101`~`118`：各类失败

因此「设备下载到 60%」这类数据在协议层面拿不到。设备方 App 的 0-100 进度条，通常是下面两种情况之一：

- **手机上传图片到服务端的进度**：这是客户端自己可测的，和我们的 `POST /api/device/play` 上传阶段对应；
- **App 本地动画 / 估算**：100% 之后显示「屏幕即将刷新」，本质是在等设备的 `play_ack`。

如果设备方 App 是通过蓝牙 / 局域网直传图片，那它确实能拿到传输进度；但本服务走的是「云端 MQTT 下发 URL + 设备从 OSS 下载」，这条链路上服务端看不到设备下载字节数。

结论：

- **可以复刻设备方 App 的交互观感**：上传 0-100 → 「屏幕即将刷新」→ 「设备刷屏中」→ 成功/失败。
- **不能复刻真实的设备下载百分比**：除非固件新增进度上报（例如 `play_progress` 或扩展 `play_ack` 返回 `downloaded/total`），否则任何百分比都只能是客户端上传进度或估算动画。

## 八、设备消息通知

通知是**设备维度**：App 从设备进入消息列表，查看该设备的上线/离线、低电量、WiFi 弱、TF 满、上报异常等消息。服务端不做用户扇出，权限沿用设备 `checkPermission`。

### 8.1 消息列表

```
GET /api/notification/list?deviceNo=XT20260001&page=1&size=20&unreadOnly=false
Header: userToken
```

| 参数 | 说明 |
|---|---|
| `deviceNo` | 必填，设备编号 |
| `page` | 页码，默认 1 |
| `size` | 每页条数，默认 20，最大 100 |
| `unreadOnly` | `true` 时只返回未读 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "total": 25,
    "page": 1,
    "size": 20,
    "unreadCount": 8,
    "list": [
      {
        "id": 101,
        "category": "ALARM",
        "type": "LOW_BATTERY",
        "payload": { "level": 2 },
        "read": false,
        "createdAt": "2026-10-20 18:30:00"
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `category` | `DEVICE` / `ALARM` / `EXCEPTION` / `BUSINESS` |
| `type` | 消息短码，见 8.4 |
| `payload` | JSON 参数，App 按 `type` 翻译文案 |
| `read` | 当前用户是否已读 |
| `unreadCount` | 该设备未读总数（不受 `unreadOnly` 影响） |

### 8.2 未读数

```
GET /api/notification/unread-count?deviceNo=XT20260001
Header: userToken
```

```json
{ "code": 0, "msg": "ok", "data": { "unreadCount": 8 } }
```

### 8.3 标记已读

```
POST /api/notification/read
Header: userToken
Content-Type: application/json
```

```json
{ "deviceNo": "XT20260001", "ids": [101, 102] }
```

- `ids` 为空或 `null` → 标记该设备全部消息已读。
- `ids` 最多 500 个；超出返回 `4000`。
- 返回 `{ "code": 0, "msg": "ok", "data": null }`。

错误码：`4000` 参数错误、`401`、`403` 无权限、`503`、`5000`。

### 8.4 消息类型（App 自行翻译与过滤）

| type | 中文含义 | category |
|---|---|---|
| `DEVICE_ONLINE` | 设备已上线 | DEVICE |
| `DEVICE_OFFLINE` | 设备已离线 | DEVICE |
| `LOW_BATTERY` | 设备电量低 | ALARM |
| `WIFI_WEAK` | 设备 WiFi 信号弱 | ALARM |
| `TF_FULL` | TF 卡容量将满 | ALARM |
| `PLAY_DOWNLOAD_FAILED` | 投屏图片下载失败（设备返回 102/103/104/109/114/116/118） | ALARM |
| `PLAY_STORAGE_ERROR` | 设备存储异常（设备返回 101/105/115/117） | ALARM |
| `PLAY_FAILED` | 投屏失败通用（设备返回 112/110/未知非成功码） | ALARM |
| `EXCEPTION_UP_PARSE` | 设备上报数据解析失败 | EXCEPTION |
| `EXCEPTION_UNKNOWN_ACTION` | 设备上报了未知指令 | EXCEPTION |
| `EXCEPTION_COMMAND_BUILD` | 平台下发指令构造失败 | EXCEPTION |

- 暂时不生成：OTA 失败、TF 卡未识别、TF 卡未插（原 `TF_ERROR`）、离线超过 N 分钟的独立告警（`DEVICE_OFFLINE` 已覆盖）。
- 投屏失败告警：设备 `play_ack` 返回失败码时生成，`payload` 包含 `msgid`、`result`（原始码）、`userNo`（发起用户）、`reason`（中文兜底文案）；同一 `msgid` 只生成一次。
- 去重规则：`DEVICE_ONLINE` / `DEVICE_OFFLINE` 只在连接状态变化时发送；`LOW_BATTERY` / `WIFI_WEAK` / `TF_FULL` 在条件出现时发送一次，条件恢复后清除状态，下次出现再发；`EXCEPTION_*` 按设备 + 类型去重 300 秒。
- 内部接口写入的 `BUSINESS` 消息不做去重，每次调用都会生成一条。
- `BUSINESS` 类由老服务按设备维度写入，`type` 可能扩展；App 遇到未知 `type` 时自行决定忽略或展示通用文案。
- 服务端只提供短码 + `payload`，不提供多语言文案。

### 8.5 WebSocket 推送

需先按 1.6 订阅该设备。新消息生成时推送：

```json
{
  "type": "notification.new",
  "deviceNo": "XT20260001",
  "category": "ALARM",
  "messageType": "LOW_BATTERY",
  "payload": { "level": 2 },
  "createdAt": "2026-10-20 18:30:00"
}
```

> 注意：信封字段 `type` 固定为 `notification.new`，消息短码在 `messageType` 中。

- 只推信号，不推详情；收到后调用 8.1 拉取列表。
- 消息保留 90 天。

## 九、内部接口（老服务调用）

> 仅内网调用，Header 必须携带 `X-Internal-Token`。服务端配置 `xt.internal.token`（生产环境变量 `XT_INTERNAL_TOKEN`）；未配置时返回 `503`，token 不匹配返回 `401`。
>
> - 地址前缀：`http://172.16.1.236:18081`
> - Header：`X-Internal-Token: <与服务端 XT_INTERNAL_TOKEN 一致>`
> - Content-Type：`application/x-www-form-urlencoded`
> - 统一返回：`{ "code": 0, "msg": "ok", "data": ... }`
> - 错误码：`4000` 参数错误、`401` token 不匹配、`503` 服务端未配置 token / 老服务不可用、`5000` 服务端异常

### 9.1 写入设备消息

```
POST /internal/notification/send
Header: X-Internal-Token
Content-Type: application/x-www-form-urlencoded
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `deviceNo` | 是 | 设备编号，最长 64 |
| `category` | 是 | `DEVICE` / `ALARM` / `EXCEPTION` / `BUSINESS`，最长 32 |
| `type` | 是 | 消息短码，最长 64 |
| `payload` | 否 | JSON 字符串，最长 2048 字符 |

```bash
curl -X POST 'http://172.16.1.236:18081/internal/notification/send' \
  -H 'X-Internal-Token: <XT_INTERNAL_TOKEN>' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'deviceNo=XT20260001' \
  --data-urlencode 'category=BUSINESS' \
  --data-urlencode 'type=SHARE_REVOKED' \
  --data-urlencode 'payload={"operator":"U10001"}'
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": { "created": 1 }
}
```

- 该接口不按用户/设备权限校验，由老服务决定写入哪个设备。
- 写入后立即通过 WebSocket `notification.new` 推送；同一 `deviceNo + type` 不做去重（内部接口每次调用都会落库）。
- 不发送分享撤销/删除设备消息；这两类场景由老服务只调用 9.2 踢订阅。

### 9.2 踢出订阅

```
POST /internal/push/subscription/kick
Header: X-Internal-Token
Content-Type: application/x-www-form-urlencoded
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `deviceNo` | 是 | 单个设备号，最长 64；一次只处理一个设备 |
| `userNos` | 是 | 被踢用户，逗号拼接，可传多个；每个最长 32，自动去重，最多 500 个 |

使用场景：

| 场景 | `deviceNo` | `userNos` |
|---|---|---|
| 所有者删除设备，同时解除所有分享绑定 | 被删除的设备 | 所有者 + 该设备全部分享者 |
| 所有者移除分享者 | 当前设备 | 被移除的分享者（可多个） |

```bash
curl -X POST 'http://172.16.1.236:18081/internal/push/subscription/kick' \
  -H 'X-Internal-Token: <XT_INTERNAL_TOKEN>' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'deviceNo=XT20260001' \
  --data-urlencode 'userNos=U10001,U10002,U10003'
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "deviceNo": "XT20260001",
    "userNos": ["U10001", "U10002", "U10003"],
    "removedSubscriptions": 3,
    "affectedSessions": 2
  }
}
```

- 只移除这些用户在指定设备上的 WS 订阅，**不关闭连接、不发送客户端消息、不影响其他设备订阅**。
- 幂等：重复调用返回 `removedSubscriptions=0`。
- 分享撤销/删除设备由老服务自行处理业务状态，本服务不生成通知。
- 错误码：`4000` 参数错误、`401` token 不匹配、`503` 未配置 token、`5000` 服务端异常。
