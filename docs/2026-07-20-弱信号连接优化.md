### 2026-07-21 · 直连缓存：已绑定设备复连跳过扫描

**背景**：后端 `getUserProductList` 返回的 `deviceId`（如 `E9:48:C2:1E:D4:28`）是**唯一且固定**的设备ID
（normalizeDevice 落在 `productDeviceId`）。据此新增「本机直连缓存」，让复连不必每次先扫描。

**关键认知（决定了存哪、怎么存）**：
- 后端这个 `deviceId` 是**固件序列号**，**不是**微信 `createBLEConnection` 能用的句柄——
  微信 deviceId 在**安卓=射频 MAC、iOS=系统给外设生成的 UUID**，两者都拿不到这个固件序列号。
  （旁证：两台样本 `E9:48:C2:1E:D4:28` / `E4:48:C2:1E:D4:28` 只差首字节、后 5 字节全同，
  不符合真 MAC 的 OUI 结构，是厂商自编序列号。）所以**不能**直接拿它去连。
- 微信 deviceId 是「设备 × 手机」的函数（iOS UUID 换机就变、安卓 MAC 隐私地址会轮换），
  故**必须存本机、不能存后端**：存后端会把 A 手机的值发给 B 手机 → B 上必超时失败还白等。

**做法（`utils/device-conn-cache.js` 新增 + `utils/active-device.js` 接入，不动 device-ble/bluetooth 底层）**：
1. 缓存表 `{ 后端稳定设备ID(归一化) -> 本机上次成功连上的微信 deviceId }`，键用 `productDeviceId`。
2. `scanMatchConnect` 开头插 `tryDirectConnect`：命中缓存 → 短超时（`DIRECT_CONNECT_TIMEOUT_MS=3000`）
   自探 `createBLEConnection` → 连上就交给 `ensureConnection` 复用这条已开连接（其内层见「已连接」当成功，
   照常发现服务/特征、登记会话）→ 返回，**跳过定位+扫描**。探测失败（超时/离线）先 `closeBLEConnection`
   释放半连接再 `return ''`，**无损回落**到原有完整扫描。
3. 扫描路径成功连上后 `connCache.put` 记住本次有效 deviceId；直连失败/换机/设备重启时，扫描会用新值覆盖，**自愈**。

**为什么安全**：探测用**自己**的短超时 createBLEConnection（不动底层重试预算），失败即 close + 回落，
**不留悬挂的 device-ble 连接 Promise**（不 race、不 abandon）；`tryDirectConnect` 全程不抛错，
任何异常都 `disconnect` 清理后回落扫描。最坏代价 = 缓存失效时白花 3s，仍能连上。

**收益与边界**：主要吃「同机复连」高频场景，happy path 从「扫描匹配(最长 12s)」降到「一次直连(1~2s)」；
「搜不到/弱信号」在复连路径上被绕开，但**根因仍需厂商数据放行（下方待办）**——缓存未命中/换机时照旧撞上。

**同步**：撤掉 `list.js` 旧注释「直连存下来的 deviceId 必失败」（前提已变）；本条兑现了
`ble-scan-connect-diagnosis` 记忆里待办④的「上次 deviceId 直连快路径」。**未经真机验证**（尤其 iOS 用旧 UUID 直连的命中率）。

### 2026-07-20（第二轮）· 残留的 connect time out：加「重扫再连」分层

**现象**：做完 A+B+C 后，仍偶发 `设备-createBLEConnection:fail connect time out`。

**定性（上一轮的盲区）**：上一轮只在**同一个 deviceId** 上加重试次数。但微信 BLE 的 `deviceId` 是
「本次扫描会话」的临时值——设备重启、安卓随机地址轮换后就失效了，**拿着失效的 deviceId 连多少次都是超时**。
这类失败靠堆内层重试永远解决不了。

**改动：把重试分成两层，各管一类失败**

| 层 | 位置 | 管什么 | 预算 |
|---|---|---|---|
| 内层 | `device-ble.createConnectionWithRetry` | 同一 deviceId 上的**瞬时**失败（蓝牙栈抖动、CONNECT_IND 丢包） | 2 次，超时**逐次拉长** `[5000, 8000]`，退避 400ms |
| 外层 | `active-device.scanMatchConnect` | **deviceId 已失效 / 设备不再广播** | `SCAN_CONNECT_ROUNDS = 2`，每轮**重新扫描**拿新鲜 deviceId 再连 |

- 内层次数从上一轮的 4 次收到 2 次，把预算让给外层重扫；总墙钟 ≈30s，与上一轮 26s 同量级，
  但**覆盖的失败类型多了一类**。
- 超时逐次拉长而非固定值：首次 5s 快速试错（多数失败是瞬时的，早失败早重试更划算），
  末次 8s 耐心等——弱信号下 CONNECT_IND 可能要经过好几个广播事件才被设备收到，一刀切的短超时会把
  「本来能连上、只是慢」误杀。
- `scanMatchConnect` 拆出 `scanForTarget()`（扫描一轮并匹配），主函数变成 `扫描 → 连接 → 失败则重扫再连` 的循环。
- **重扫轮扫不到时报的是上一轮的连接错误**，不是「未搜索到该设备」——设备多半正被我们那次失败的连接占住
  （单连接、被占用时不广播），报「未搜索到」会把用户引到「是不是没开机」的错误方向。

**顺带做了上一轮列为待办的 E（失败文案）**：`showConnectError` 新增 `friendlyConnectMessage()`，
把 `createBLEConnection:fail connect time out` 换成**「设备-连接超时，请靠近设备后重试」**。
只替换这一类，其余原因照旧如实展示；**只改展示不动 error 本身**，console 里仍是原始报错，排查时看得到真相。

**验证**：桩数据覆盖 5 条路径——①一次连上（扫1连1）②首轮超时重扫后连上（扫2连2，**本轮新增能力**）
③两轮都超时→如实报连接错误 ④重扫时设备已不广播→报连接错误而非「未搜索到」⑤一开始就搜不到→仍报「未搜索到」。
**未经真机验证。**

**仍未做**：上一轮列的 D（`discoverMainService` / `discoverCharacteristics` 服务发现预算偏紧）。
若真机上出现「连上了但报未找到主服务」，再放宽。

### 2026-07-20 · 弱信号连接优化 A+B+C

**现象**：信号级别显示「极强」时一点就连上；显示「正常」时经常连不上。
（档位定义见 `bluetooth.rssiToSignalText`：极强 ≥-55、强 -55~-67、**正常 -67~-78**、偏弱 -78~-88、弱 <-88）

**定性**：不是信号弱到物理上连不了，而是连接时机与重试预算对弱信号不友好。三条独立原因叠加。

#### A · 停扫没等它真停就发起连接（`bluetooth.js`）

`teardownScan()` 原来是 `wx.stopBluetoothDevicesDiscovery({})` **发完就不管**，紧接着
`settleSubscriber` resolve，`scanMatchConnect` 立刻 `createBLEConnection`。底层扫描尚未真正停止时发起连接，
**扫描与连接抢射频** —— 强信号能扛过去，「正常」档就扛不住。

改动：
- 新增模块级 `stopDiscoveryPromise`，`teardownScan` 把停扫回调包成 Promise 存下；
- 新增并导出 `whenScanStopped()`：等停扫落地 + 再沉淀 `SCAN_SETTLE_MS=120ms` 才返回；
- `scanMatchConnect` 在 `ensureConnection` 前 `await bluetooth.whenScanStopped()`。

两条重要边界：
- **绝不为了自己连接去掐断别人的扫描**：硬件扫描仍在为其他订阅者运行时 `whenScanStopped()` 直接返回
  （文件头 ② 记着「任一路 stop 把另一路饿死」这个历史坑，不能重蹈）。此时保持原有行为。
- **不会挂死**：个别机型 `stopBluetoothDevicesDiscovery` 不回调，故加了 `SCAN_STOP_TIMEOUT_MS=600ms` 兜底。
  代价是这类机型每次连接多花约 720ms（600 兜底 + 120 沉淀）；正常机型只多约 130ms。

#### B · 只给 2 次连接机会，单次却干等 10 秒（`device-ble.js` + `ota-ble.js`）

原：`attempts=2`、`timeout: 10000`、固定 400ms 间隔 → 总预算「10s + 0.4s + 10s ≈ 20s 然后硬失败」。
BLE 连接的实际形状是「要么两三秒内建起来，要么连接请求在空中就丢了」，干等 10s 基本救不回来。

改为 `CONNECT_ATTEMPTS=4` × `CONNECT_TIMEOUT_MS=6000` + 递增退避 `CONNECT_BACKOFF_MS=[300,600,1200]`：
最坏墙钟 ≈26s，与原来同量级，但**尝试次数翻倍**。退避递增是因为连不上多为瞬时干扰，隔久一点再试更容易撞上好时机。

⚠️ `device-ble.js` 与 `ota-ble.js` 各有一份 `createConnectionWithRetry`，**本轮两份都改了**。
以后改一份必须同步另一份，否则会出现「普通连接连得上、进 OTA 却连不上」这种只在弱信号下现形、极难排查的差异。

#### C · 抢第一帧广播就连，完全不看信号强度（`active-device.js`）

`scanMatchConnect` 的 `until: list => !!match(list, device)` —— 匹配上就立刻停扫开连。
弱信号下第一帧往往是「刚擦边收到的那一帧」，正是整个窗口里信号最差、连接成功率最低的时刻。
`foundMap` 其实一直在更新 RSSI（`bluetooth.js` scan.handler），信息有，只是没用。

改为带信号闸的 `until`：
- RSSI ≥ `WEAK_SIGNAL_RSSI=-70`，或**读不到 RSSI**（部分机型不上报，值为 0）→ 立即连，**行为完全不变**；
- 弱于 -70 → 进入等待窗，期间**只要来一帧达标的就立刻连**（抓住好时机）；
- 等满 `WEAK_SIGNAL_WAIT_MS=1500ms` 仍不达标 → **照常连**，绝不因信号弱阻断用户。

阈值 -70 取在「强(≥-67)」与「正常」的交界略偏弱处：强/极强一律走原路径，只有正常档偏弱的那一段才等。

**已知局限**：等待窗依赖后续广播帧来重新求值 `until`（`until` 只在收到广播批次时被调用）。
若等待期间设备广播彻底断流，会一直等到扫描窗口 12s 到点才连（结果仍是连，只是慢）。
实测弱信号下广播帧仍在持续到达（间隔通常 100~500ms），故风险有限；若真机上出现「弱信号要等很久」，
根治方向是给订阅者加定时重算，而不是缩短等待窗。

#### 验证状态

`node --check` 全过。桩数据验证了 C 的四条分支（极强立即连 / 未上报 RSSI 立即连 / 先弱后强在强帧到达时连 /
一直弱等满 1.5s 照常连）与 A 的「停扫不回调也不挂死、二次调用不重复等待」。

**均未经真机验证。** 尤其：
- A 和 B 是与信号无关的通用可靠性改进，有把握；
- **C 是针对本现象的假设**，方向合理但没有真机数据支撑；
- 三条的真实效果只能靠真机在「正常」档反复试才能确认。

若真机上仍不理想，下一步候选（本轮**未做**）：
- D：`discoverMainService(6×250ms)` / `discoverCharacteristics(4×200ms)` 弱信号下预算偏紧，
  服务发现超时会让整条连接失败、从头再来一遍，代价很高，可适度放宽；
- E：连接失败文案带上信号档位（「设备信号较弱（正常），请靠近后重试」），直接回应用户困惑。
