## 操作日志（最新在上）

### 2026-07-20 · 弱信号连接优化 A+B+C

**现象**：信号级别显示「极强」时一点就连上；显示「正常」时经常连不上。
（档位定义见 `bluetooth.rssiToSignalText`：极强 ≥-55、强 -55~-67、**正常 -67~-78**、偏弱 -78~-88、弱 <-88）

**定性**：不是信号弱到物理上连不了，而是连接时机与重试预算对弱信号不友好。三条独立原因叠加。

#### A · 停扫没等它真停就发起连接（`bluetooth.js`）

`teardownScan()` 原来是 `wx.stopBluetoothDevicesDiscovery({})` **发完就不管**，紧接着
`settleSubscriber` resolve，`scanMatchConnect` 立刻 `createBLEConnection`。底层扫描尚未真正停止时发起连接，
**扫描与连接抢射频** —— 强信号能扛过去，「正常」档就扛不住。

改动：
- 新增模块级 `stopDiscoveryPromise`，`teardownScan` 把停扫回调包成 Promise 存下；
- 新增并导出 `whenScanStopped()`：等停扫落地 + 再沉淀 `SCAN_SETTLE_MS=120ms` 才返回；
- `scanMatchConnect` 在 `ensureConnection` 前 `await bluetooth.whenScanStopped()`。

两条重要边界：
- **绝不为了自己连接去掐断别人的扫描**：硬件扫描仍在为其他订阅者运行时 `whenScanStopped()` 直接返回
  （文件头 ② 记着「任一路 stop 把另一路饿死」这个历史坑，不能重蹈）。此时保持原有行为。
- **不会挂死**：个别机型 `stopBluetoothDevicesDiscovery` 不回调，故加了 `SCAN_STOP_TIMEOUT_MS=600ms` 兜底。
  代价是这类机型每次连接多花约 720ms（600 兜底 + 120 沉淀）；正常机型只多约 130ms。

#### B · 只给 2 次连接机会，单次却干等 10 秒（`device-ble.js` + `ota-ble.js`）

原：`attempts=2`、`timeout: 10000`、固定 400ms 间隔 → 总预算「10s + 0.4s + 10s ≈ 20s 然后硬失败」。
BLE 连接的实际形状是「要么两三秒内建起来，要么连接请求在空中就丢了」，干等 10s 基本救不回来。

改为 `CONNECT_ATTEMPTS=4` × `CONNECT_TIMEOUT_MS=6000` + 递增退避 `CONNECT_BACKOFF_MS=[300,600,1200]`：
最坏墙钟 ≈26s，与原来同量级，但**尝试次数翻倍**。退避递增是因为连不上多为瞬时干扰，隔久一点再试更容易撞上好时机。

⚠️ `device-ble.js` 与 `ota-ble.js` 各有一份 `createConnectionWithRetry`，**本轮两份都改了**。
以后改一份必须同步另一份，否则会出现「普通连接连得上、进 OTA 却连不上」这种只在弱信号下现形、极难排查的差异。

#### C · 抢第一帧广播就连，完全不看信号强度（`active-device.js`）

`scanMatchConnect` 的 `until: list => !!match(list, device)` —— 匹配上就立刻停扫开连。
弱信号下第一帧往往是「刚擦边收到的那一帧」，正是整个窗口里信号最差、连接成功率最低的时刻。
`foundMap` 其实一直在更新 RSSI（`bluetooth.js` scan.handler），信息有，只是没用。

改为带信号闸的 `until`：
- RSSI ≥ `WEAK_SIGNAL_RSSI=-70`，或**读不到 RSSI**（部分机型不上报，值为 0）→ 立即连，**行为完全不变**；
- 弱于 -70 → 进入等待窗，期间**只要来一帧达标的就立刻连**（抓住好时机）；
- 等满 `WEAK_SIGNAL_WAIT_MS=1500ms` 仍不达标 → **照常连**，绝不因信号弱阻断用户。

阈值 -70 取在「强(≥-67)」与「正常」的交界略偏弱处：强/极强一律走原路径，只有正常档偏弱的那一段才等。

**已知局限**：等待窗依赖后续广播帧来重新求值 `until`（`until` 只在收到广播批次时被调用）。
若等待期间设备广播彻底断流，会一直等到扫描窗口 12s 到点才连（结果仍是连，只是慢）。
实测弱信号下广播帧仍在持续到达（间隔通常 100~500ms），故风险有限；若真机上出现「弱信号要等很久」，
根治方向是给订阅者加定时重算，而不是缩短等待窗。

#### 验证状态

`node --check` 全过。桩数据验证了 C 的四条分支（极强立即连 / 未上报 RSSI 立即连 / 先弱后强在强帧到达时连 /
一直弱等满 1.5s 照常连）与 A 的「停扫不回调也不挂死、二次调用不重复等待」。

**均未经真机验证。** 尤其：
- A 和 B 是与信号无关的通用可靠性改进，有把握；
- **C 是针对本现象的假设**，方向合理但没有真机数据支撑；
- 三条的真实效果只能靠真机在「正常」档反复试才能确认。

若真机上仍不理想，下一步候选（本轮**未做**）：
- D：`discoverMainService(6×250ms)` / `discoverCharacteristics(4×200ms)` 弱信号下预算偏紧，
  服务发现超时会让整条连接失败、从头再来一遍，代价很高，可适度放宽；
- E：连接失败文案带上信号档位（「设备信号较弱（正常），请靠近后重试」），直接回应用户困惑。
