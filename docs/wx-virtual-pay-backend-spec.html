小程序虚拟支付：signData / paySig / signature 怎么生成

小程序端已经全部就绪，唯一阻塞项是 POST /Client/Order/addOrder 的出参里少了三个签名字段。 这三个值只能服务端算。本文说明算法、返回格式，以及三个必踩的坑。

接口 wx.requestVirtualPayment mode short_series_goods 需改动 addOrder 出参 + 登录态存储

一、为什么必须服务端做

Token 是虚拟商品，走的是小程序虚拟支付（米大师），不是普通微信支付。 后端 DTO 里那套 wxPayPrepayId / wxPaySign 属于 JSAPI 普通支付，这里用不上，别混。

参数算法密钥来源
signData 被签名的 JSON 原文字符串 ——
paySig hmac_sha256(appKey, "requestVirtualPayment&" + signData) 虚拟支付 AppKey（小程序后台）
signature hmac_sha256(session_key, signData) session_key（jscode2session）
前端做不了

session_key 微信从不下发给小程序，只能由服务端用 AppSecret 调 jscode2session 换取 —— 客户端连算 signature 的原料都没有。appKey 则是硬性机密： .wxapkg 可直接解包，一旦打进小程序包，任何人都能自己构造订单、白嫖 Token。

二、配置项

配置值说明
offerId 1450611724 支付应用 ID，非机密，写进 signData
沙箱 AppKey ${WX_VPAY_APPKEY_SANDBOX} env=1 时用它算 paySig
现网 AppKey ${WX_VPAY_APPKEY_PROD} env=0 时用它算 paySig
密钥不写进本文档

两把 AppKey 单独私发，只进配置中心 / 环境变量。现网 AppKey 曾在 IM 明文传过， 上线前请在小程序后台重置一次，新值直接落配置中心。

建议按 env 做成一张映射表，而不是两个散落的变量 —— 这样物理上不可能出现「用沙箱 key 签了现网单」：

application.yml
wx-virtual-pay:
  offer-id: 1450611724
  app-key:
    0: ${WX_VPAY_APPKEY_PROD}      # 现网
    1: ${WX_VPAY_APPKEY_SANDBOX}   # 沙箱

三、前置：把 session_key 存下来

好消息

登录链路已经在传 code 了（小程序 app.js 的 loginWithWechat → loginByWechat），所以后端本来就拿得到 session_key，大概率是用完 openid 就丢了。 前端这块不用改。

Java · 登录时
JsCode2SessionResult r = wxApi.code2session(appId, appSecret, code);

// 现在多半只取了 openid 就丢了 —— session_key 必须落库/落缓存，
// 因为下单时才要用它算 signature。
sessionStore.save(userToken, r.getOpenid(), r.getSessionKey());
session_key 会失效

每次 wx.login + code2session 都会让旧的 session_key 作废。 小程序里有两条登录路径都会调 wx.login（微信登录、手机号一键登录）， 所以存储必须是覆盖写，不能「已存在就跳过」，否则会出现签名算得出来、微信校验不过的情况。

四、生成三个参数

Java · WxVirtualPaySigner
public PayParams sign(String sessionKey, String outTradeNo,
                      String wxProductId, long goodsPriceFen, int env) {

    // 1) 构造 signData。LinkedHashMap 固定键顺序，
    //    并且【只序列化这一次】，之后所有地方都用这个 String 引用。
    Map<String, Object> m = new LinkedHashMap<>();
    m.put("offerId",      offerId);         // 1450611724
    m.put("buyQuantity",  1);
    m.put("env",          env);             // 0=现网 1=沙箱
    m.put("currencyType", "CNY");
    m.put("platform",     "android");
    m.put("productId",    wxProductId);     // 商品的 wxProductId
    m.put("goodsPrice",   goodsPriceFen);   // 单位：分
    m.put("outTradeNo",   outTradeNo);      // 订单的 orderNo
    m.put("attach",       "");

    String signData = JSON.toJSONString(m);  // ★ 全流程唯一一次序列化

    // 2) 两个签名。注意 paySig 的前缀是接口名 + "&"。
    String appKey    = appKeys.get(env);
    String paySig    = hmacSha256Hex(appKey,     "requestVirtualPayment&" + signData);
    String signature = hmacSha256Hex(sessionKey, signData);

    // 3) 原样带出 signData —— 返回给端上的必须是上面那个 String。
    return new PayParams("short_series_goods", env, signData, paySig, signature);
}

private static String hmacSha256Hex(String key, String msg) {
    try {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(key.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        // 必须是小写 hex，不是 Base64
        return Hex.encodeHexString(mac.doFinal(msg.getBytes(StandardCharsets.UTF_8)));
    } catch (GeneralSecurityException e) {
        throw new IllegalStateException("虚拟支付签名失败", e);
    }
}
字段集以微信文档为准

上面的 signData 字段集按 mode=short_series_goods 列出， 请对照 wx.requestVirtualPayment 文档 再核一遍必填项（缺字段微信回 1001）。 但不论字段怎么调整，「只序列化一次、签它、返回它」这条不变 —— 这是整件事的关键。

DTO 里 signData 的类型必须是 String

JSON 传输时它会被转义（\"），这是正常的 —— 前端 JSON.parse 之后拿到的就是原串。 但如果 DTO 把 signData 定义成 Map 或对象， Jackson 序列化响应时会重新生成一遍，键顺序或空格一旦和签名时不同，微信必回 -15005。

前端不用改

平铺（如上）或包一层（payParams / payData / wxPayParams 等）都能识别， 取哪种看后端方便。后端一发，链路就通。

六、三个必踩的坑

-15005
签名校验失败

signData 被序列化了两次

签名用的串和返回给端上的串不是同一个。修法：全流程只 toJSONString 一次， DTO 字段类型用 String。这是最高频的成因。

-15005
签名校验失败

env 与 AppKey 错配

signData 里的 env、算 paySig 用的 AppKey、 查单接口传的 env 必须三处一致。用第二节的映射表就能杜绝。

-15005
签名校验失败

session_key 已失效

用户重新登录后旧 key 作废，但服务端还拿着旧的算 signature。 表现是「代码没动过、昨天还好好的」。修法：登录时覆盖写。

1001
参数有误

signData 本身不合法

JSON 格式错误，或缺必填字段。和签名无关，先核字段集。

对不上时不要靠猜。签名时把 signData 的原文和字节长度一起打进日志， 再和前端实际收到的串比对：两边字节长度不同 → 是序列化问题； 长度相同但 paySig 对不上 → 是 AppKey 环境错了。 下面这段 Node 脚本可以两边独立跑一次对答案：

verify-paysig.js · node verify-paysig.js '<signData>' <appKey>
const crypto = require('crypto');

const [signData, appKey, sessionKey] = process.argv.slice(2);
const hmac = (key, msg) =>
    crypto.createHmac('sha256', key).update(msg, 'utf8').digest('hex');

console.log('字节长度:', Buffer.byteLength(signData, 'utf8'));
console.log('paySig   :', hmac(appKey, 'requestVirtualPayment&' + signData));
if (sessionKey) console.log('signature:', hmac(sessionKey, signData));

七、签完之后还有一步

三个参数只是让支付能拉起来。用户付完钱，微信会回调服务端做发货， 后端在回调里给账户加 Token —— 这一步同样绕不过服务端。

完整链路
① GET  /Client/Order/getGoodsList    取套餐（含 wxProductId）
② POST /Client/Order/addOrder        建单 + 签名（本文） → orderNo / signData / paySig / signature
③ wx.requestVirtualPayment           小程序用②的参数拉起支付
④ 微信 → 我们后端                     发货回调，给账户加 Token
⑤ GET  /Client/Order/getUserAccount  端上轮询余额，变多了才算「买到了」
③ 的成功回调不是到账凭据

微信异常退出会让它丢失，它来了也不代表 ④ 已经处理完。 前端的判据是 ⑤ 的余额变化，所以 ④ 的幂等和及时性很重要： 同一个 outTradeNo 重复回调只能加一次 Token。

对接问题直接找前端，小程序侧代码在 utils/wx-virtual-pay.js 与 utils/token-api.js。

后端补齐出参后，前端零改动即可联调 —— 建议先用 env=1 沙箱走通再切现网。
