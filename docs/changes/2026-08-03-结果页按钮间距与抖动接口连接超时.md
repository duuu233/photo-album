## 一 · 结果页底部按钮贴住上方内容

### 现象

投屏**失败**页里「重新投屏」按钮紧贴上方「排查提示」卡片，中间没有留白。

### 根因

结果页是 `flex` 纵向两段式布局：

```text
.result-page (flex column)
  ├─ .result-body   flex:1   padding: 48rpx 56rpx 0   ← 下内边距为 0
  └─ .result-actions          padding: 0 56rpx calc(60rpx + safe)
```

`.result-body` 的下内边距是 `0`，两段之间没有任何间距常量。
成功态内容短，`flex:1` 把按钮推到屏幕底部，剩余空白掩盖了这个问题；失败态多出
「排查提示」四条卡片（`.fail-tips`），并且失败原因 `desc` 常是接口原文的多行长文案
（`result.js:171` `desc: result.message || text.desc`），内容一长就正好顶到按钮上。

### 修复

| 文件 | 改动 |
| --- | --- |
| `subpackages/projection/result/result.wxss` | `.result-body` 内边距 `48rpx 56rpx 0` → `48rpx 56rpx 40rpx` |
| `subpackages/projection/result/result.wxss` | `.progress-tips` 补 `margin-bottom: var(--safe-bottom)` |
| `subpackages/device/ota/ota.wxss` | `.ota-body` 内边距 `48rpx 56rpx 0` → `48rpx 56rpx 40rpx` |

- 40rpx 作为「内容 ↔ 底部按钮」的固定间距：略大于卡片之间的 32rpx，视觉上分出层级；
- 进度态没有底部按钮，`.progress-tips` 是最后一屏内容，补 `--safe-bottom` 防止落进 iPhone home 指示条；
- 固件升级页（`ota`）当初就是照抄结果页布局，同一个 `padding-bottom: 0`，失败说明多行时会复现同样问题，本轮一并修。

### 其它「状态相关按钮」核查结论（均无此问题，勿再改）

| 页面 | 底部按钮 | 结论 |
| --- | --- | --- |
| 绑定设备 `device/bind` | `.bind-bottom`（立即绑定 / 取消搜索 / 重新扫描） | `position: absolute` 贴底，`.device-list` 用 `max-height` 预留了按钮空间，不会互相顶 |
| 投屏记录 `projection/records` | 卡片内「重新投屏 / 删除」 | 卡片内联动作，`margin-top: 14rpx`，有间距 |
| 设备列表 / 设备详情 | `.device-actions`、`.confirm-actions` | 分别有 `margin-top: 34rpx / 42rpx` |

## 二 · 投屏失败 `cronet_error_code:-118 / net::ERR_CONNECTION_TIMED_OUT`

完整报错：`接口-抖动bin转换失败：request:fail errcode:-118 error_msg:net::ERR_CONNECTION_TIMED_OUT`
（`utils/dithering.js` `requestOnce` 的 `fail` 分支原样透传 `errMsg`，结果页把它当 `desc` 显示。）

### 结论：TCP 连接没建起来，请求根本没到服务器

- `cronet` = 安卓微信的网络内核，说明这条是**安卓机**上报的；
- `-118` 是 Chromium 的 `ERR_CONNECTION_TIMED_OUT`，含义是**建连（SYN）阶段超时**，
  即 SYN 发出去没有任何回应（被中间设备静默丢弃）。**不是**服务器处理慢、返回慢；
- 也**不是**我们代码里的 20s 超时——那会报 `request:fail timeout`；
- 也**不是**域名白名单没配——那会报 `url not in domain list`；
- 若是服务器主动拒绝会是 `-102 ERR_CONNECTION_REFUSED`，证书问题会是 `-107 / ERR_CERT_*`，
  DNS 解析不出来是 `-105`。都不是本例。

### 可能原因（按嫌疑排序）

1. **非标准端口 8443 被网络侧拦截**（最大嫌疑）。接口地址是
   `https://cloud.seekink.cn:8443/prod-api/api/v1/label/imageDitheringBinDownload`，
   2026-07-24 从 `http://…:8091` 迁过来的。相当多的运营商出口、公司/校园 WiFi、酒店网络、
   家用路由器的安全策略只放行 80/443，对其它端口的 SYN **直接丢包**（丢包 = 超时，而不是拒绝），
   表现就是稳定的 `-118`。同一台手机换 4G/5G 通常立刻恢复。
2. **服务端/线路侧异常**：域名解析到单个 IPv4 `223.84.160.37`（移动线路，无 CDN、无多活）。
   该机重启、防火墙调整、IP 白名单、或转换服务过载导致 accept 队列打满时，SYN 同样被丢 → `-118`。
   本次 2026-08-03 从开发机探测：`connect 0.11s / TLS 0.58s / HTTP 200`，服务当时是活的，
   所以更偏向「当时当地那条网络路径」的问题。
3. **跨网质量**：单 IP 移动线路，电信/联通用户跨网、或弱网/地铁/电梯场景下丢包，
   也会以建连超时的形式暴露。
4. **手机侧代理/VPN/防火墙类应用**接管流量后对非常用端口不放行。

### 已有的容错（说明为什么用户仍看到失败）

`utils/dithering.js` 的 `run()` 对含 `timeout|connect|网络|ERR_` 的失败会退避 800ms 重试，
共 3 次（单次超时 20s）。用户能看到这条报错，意味着**三次都没连上**，基本可以排除瞬时抖动，
指向上面的 1 / 2 类原因。

### 建议动作

- **复现时先做的三件事**：① 手机切 4G/5G 再投一次；② 同一 WiFi 下用手机浏览器打开
  `https://cloud.seekink.cn:8443/prod-api/` 看是否转圈；③ 换一台手机/另一个网络。
  只要「切 4G 就好」，即可判定为端口 8443 被本地网络拦截。
- **长期建议**：推动 seekink 把服务放到标准 `443` 端口，或由我方后端做一层转发代理。
  非标准端口在受限网络下是长期稳定性隐患（也顺带规避 iOS ATS 与企业网络策略）。
- **可选端上优化（本轮未做）**：把网络类错误归一成中文提示（如「接口-出帧服务连接超时，请检查网络后重试」），
  不要把 `cronet_error_code` 原文丢到失败页 `desc`；同时避免长文案把结果页撑高。

## 三 · 失败页「重新投屏」核查与修改

### 1）有没有还在调老接口？——没有

`retry()` → `redirectTo` 投屏预览页 → 「开始投屏」→ 结果页，**与首次投屏完全同一条链路**：

| 环节 | 调用 | 说明 |
| --- | --- | --- |
| 设备帧 | seekink 抖动接口 `imageDitheringBinDownload` | `result.js fetchDitheringFrame` |
| 投屏记录 | `setUserProductUpload`（`deviceUploadState=0`） | `result.js uploadOriginalForRecord`，只建记录/存原图，返回的 `.bin` url **不下载** |
| 记账 | `editUserProductImgRecord`（置 1） | 设备图传成功后才调 |

旧的「下载后端 `imgBle(.bin)` 直传 + `addUserProductImgRecord` 补记」分支已在 2026-07-23 删除；
`api.js` 里 `addUserProductImgRecord` 仍留有封装但**全仓无调用方**（可择期清理，勿再接回）。

### 2）但发现一个副作用：每次重投都会新建一条投屏记录

首次投屏失败时，每张图其实已经建过一条 `deviceUploadState=0` 的记录；点「重新投屏」再走一遍链路，
`uploadOriginalForRecord` 会**再建一条新记录**（接口只支持新建，没有「复用上次 upirId 重传」的入口）。
连续重试 N 次 → 投屏记录「失败」页会出现 N 条同一张图的失败记录，后端也存了 N 份图。

本轮**未改**：修它要么端上带 `upirId` 走「更新已有记录」，要么后端按 `taskId` 幂等，属于要和后端确认的接口口径。
已列入 Follow-up。

### 3）重新投屏必须回到「原图」——已修

**改前**：预览页在「开始投屏」时会把取景框内所见烘焙成设备物理分辨率文件，写回 `image.tempFilePath`
（`preview.js _applyBakedFile`），并 `persistPending` 落回 `pendingProjection`。失败页 `retry()` 直接
`redirectTo` 预览页，预览页 `enterEdit` 取的是 `tempFilePath || url` → **拿成品图当新的编辑底图**：

- 竖向图：在已经裁过的图上二次裁剪，越编越糊，原始画面回不来；
- 横向图：成品是按设备 `rotationDegree`（默认 270°）转进竖向画布的文件，而重进页面后 `_states` 被清空、
  方向回落默认竖向 → 用户看到躺倒的画面，再导出还会再转一次，**设备上必然错位**；
- 想拿回原图只能手动点「原图」按钮，且构图全丢。

**改后**：

| 文件 | 改动 |
| --- | --- |
| `result.js` | 新增 `restorePendingOriginals()`，`retry()` 跳转前把 `pendingProjection.images` 逐张还原：`tempFilePath` 回 `_origSrc`（远程原图则清空回落 `url`）、`cropW/cropH=0`、`wrapStyle/imgStyle/previewSrc/_bakedKey` 清空。口径与预览页「原图」按钮 `restoreOrigin` 一致 |
| `preview.js` | `persistPending` 落盘前先 `_saveEditState()`，并把 `this._states` 存进 `pendingProjection.editStates`；`onLoad` 用 `pending.editStates` 回填 `this._states` |

于是「重新投屏」回到预览页时：**底图是原图（可继续自由编辑，不会二次处理），画面仍是上次构好的构图**
（`editStates` 恢复缩放/平移/旋转/横竖向）。状态按 `src` 认领——`enterEdit` 与 `prepareProjectionImages`
都校验 `state.src === 当前图源`，新选的图/还原过的图自动作废，不会串图。
用户什么都不改直接再投，出图与上次逐像素等价（同一原图 + 同一组几何重新烘焙）。
