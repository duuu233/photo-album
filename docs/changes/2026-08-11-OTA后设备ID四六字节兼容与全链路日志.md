## 现象

真机 OTA 升级成功后，设备对外暴露的 Device_ID 从 4 字节变成 6 字节，**正式入口从此连不上**；
调试台看起来还能连（后续确认那是假象：调试台连上了 GATT，但读设备信息仍提示「请先点获取设备信息」，
属另一回事，本轮按用户要求不追）。

调试台与正式入口的差别正是排查的关键——**调试台把正式入口的每一道闸都绕过了**：

| 环节 | 正式入口（首页/列表/详情/OTA） | 调试台 |
| --- | --- | --- |
| 扫描过滤 | 按产品广播名白名单（`EF6-370`/`EF6-589`）筛 | `allowAll`，附近所有蓝牙设备都收 |
| 选谁连 | 用后端记录的完整 ID 与广播 Device_ID 匹配筛候选 | 用户点哪台连哪台（BLE 句柄直连） |
| 连上之后 | 必须 `0x01 GET_INFO` 读回完整 6 字节并精确相等，否则断开 | 不校验 |

所以「调试台能连、正式入口连不上」＝ 卡在前两道闸，而不是蓝牙连不上。

## 根因（三处，都是 4→6 字节带来的）

### 1. 候选筛选被「长度相同却不相等」一票否决

`active-device.serialsMatch` 的规则 ②：长度相同却不相等 → 判为两台设备。

- 老固件：广播 8 hex vs 后端 12 hex，**长度不同**，走前缀/后缀锚定 → 匹配得上；
- 新固件：广播 12 hex vs 后端 12 hex，**长度相同**，只要广播那 6 字节与 `0x01` 读回的写法
  不完全一致（字节序反过来、或取的是 MAC 的另一段）就被规则 ② 直接否掉
  → `matchScannedDevice` 一个候选都筛不出 → 扫满 12 秒 →「未搜索到该电子纸设备」。

字节序正是 [2026-08-04 变更记录](2026-08-04-广播设备ID扩到6字节.md)「待设备方确认」里列的第 2 条风险，
当时没有新固件、无法验证，这次真机把它兑现了。

### 2. 广播解析「长度够 8 就只按新版解、绝不回退」在布局不符时把整台设备丢掉

同一份文档的「待确认」第 1 条是**字段顺序**。顺序一旦与假设不同，按新布局取到的"电量"会落在 ID 的
字节上、多半 >100 → 校验不过 → 整条广播返回 `null` → 这台设备在列表里没有屏型、没有 ID、没有电量，
既排不进候选也筛不出候选。

### 3. 广播 6 字节现在长得像"完整身份"，能越权认领活动会话

`session.serials` 把「扫描广播 ID」和「`0x01` 读回的 ID」混在一个数组里，上层
`sessionMatchesSerials` 只按 `isComplete`（12 hex）过滤。老固件时代广播只有 4 字节，天然被挡在门外，
这道闸是**隐式**的；广播扩到 6 字节后，明文、可伪造重放的广播值就有了认领会话的资格 ——
一台设备播的 ID 恰好等于另一条记录的完整 ID，投屏/删图/**OTA** 就会打到错的设备上。
这是本轮顺带堵上的安全缺口，不是现场故障的直接原因。

## 改法

### ① 广播解析：优选布局解不通才回退另一种（`utils/frame-protocol.js`）

仍是「长度优选」——新包(rest≥8)先按 6 字节解、老包按 4 字节解；**只有优选布局解不通时**才试另一种。
不违反 08-04 定的「不给错值」：那条针对的是"两种都解得通时不许回退"，而这里的前提是优选布局**已经作废**，
原本要整条丢弃。回退出来的结果带 `deviceIdLayoutFallback: true` 标记，供上层辨别。
解析结果另加 `companyMatched`（厂商数据带 `0xFFFF` Company_ID，即确认是本产品广播）。

### ② 扫描白名单：设备名缺席时按厂商数据放行（`utils/bluetooth.js`）

厂商数据长了 2 字节，31 字节的广播包更挤，设备名很容易被固件挪进 scan response 或干脆不播；
只按名字过滤会把自家设备整台丢掉（正式入口搜不到、调试台 `allowAll` 却看得见）。
现改为：广播名命中白名单 **或** 厂商数据解得通且带 `0xFFFF` Company_ID → 放行。
条件收得很紧，不会把附近别家的蓝牙设备放进列表。

### ③ 候选筛选放宽，身份闸不动（`utils/active-device.js`）

新增 `broadcastCandidateMatch`，**只用于筛候选**：

1. 强匹配：精确相等 / 短的是长的前缀或后缀（老口径）/ 整串字节序相反；
2. 弱匹配：4 字节锚段（首 4 / 末 4 字节，正序或倒序）重合。

`matchScannedDevice` 先挑强匹配、没有才用弱匹配——同批设备共享 OUI，前 4 字节锚段可能偶合到邻居，
让强匹配先挑走正主。**`serialsMatch` 本身保持严格**（它还被活动会话认领使用，那里没有 `0x01` 兜底）。

再加一层兜底：扫描窗口走满、按序列号一个候选都没筛出来时，从「确认是本产品广播 + 屏型/尺寸与本记录
一致」的设备里挑信号最强的一台试连（`matchScannedDeviceFallback`），并打一条 `console.warn`。
它只在完整窗口结束后生效，**绝不放进 `until`**，否则第一帧来的邻居设备就会被抢着连上。

> 身份因此**没有**放宽：放宽的只是"哪些设备值得连一次看看"。连上后照旧 `0x01` 精确校验，
> 不匹配就断开、排除该候选、下一轮重扫（`scanMatchConnect` 本来就是这么设计的）。
> 代价是最坏情况多连错一次，收益是**无论固件把广播 ID 换成哪种写法都还能连上**。

### ④ 会话认领只认 `0x01` 核实过的 ID（`utils/device-ble.js` + `utils/active-device.js`）

`attachSessionSerial(deviceId, serial, verified)` 新增来源标记，`0x01 GET_INFO` 读回的走
`verified=true`；会话对外多暴露一份 `verifiedSerials`。`findConnectedDeviceId` / `applyConnectedIdentity`
改用它。老会话没有该字段时回落到 `serials`，行为与改动前一致（不会把正连着的设备判成断联）。

### ⑤ OTA 全链路 console 日志（`utils/ota-ble.js` + `subpackages/device/ota/ota.js`）

从点「升级」到「升级成功」，每个节点一行，统一前缀 `[OTA#n +x.xxs]`：`#n` 区分同一次会话里的
第几轮升级（失败重试会重新编号），`+x.xxs` 是本轮起算的相对耗时（排查「卡了多久才超时」「设备隔多久
才应答」全靠它）。打印的节点：

| 节点 | 内容 |
| --- | --- |
| 页面 | 点了哪个按钮、当时页面状态、是否已连接、当前/目标版本；进度阶段切换；升级结果与后端上报 |
| 步骤0 | 固件包来源（下载/本地/内存）、下载完成、128 字节头信息字段、包大小/CRC32/面板/版本 |
| 步骤1 | 连接 FF10、服务/特征/通知/MTU/每包字节/写入方式；复用已有会话也会说明 |
| 步骤2 | START(0xF1) 每次尝试的特征×写类型×objType×帧原文、应答原文与结果码中文、生效 PRN/分包 |
| 步骤3 | 128 字节头信息包、发送前延时、每次重发、每次应答原文与结果码 |
| 步骤4 | 每个 PRN 信用窗口发了哪些包、字节区间、是否收尾窗口、DATA ACK 原文与结果 |
| 步骤5 | END(0xF3) 发送、整包校验应答原文与结果、成功汇总（总包数/字节/MTU） |
| 收发 | 设备回的每一帧原文（RX）、控制帧的发送原文（TX）、写入重试、连接断开 |

bin payload 分片默认**按窗口聚合**打印（673 包逐帧打 hex 会把控制台冲爆、反而看不见控制流）；
需要逐帧时给 `upgradeFirmware` 传 `verboseFrames: true`。

## ⑥ 反复升级同一台设备：传输途中的 0x05 + 收尾一律清缓存（同日追加）

现场追加两条：升级中报「电子纸设备-电子纸设备接收数据报错：电子纸设备状态错误」；
以及**OTA 之后有时读不到设备信息、有时连不上**。两条其实是同一件事的两端——设备侧状态没复位、
端上缓存没清。

### 传数据途中被回 0x05 也按「可重试」处理

`0x05` 的语义是**此刻不能受理**，不是「这批数据不对」（数据不对是 `0x01`/`0x09`，包不对是 `0x0A~0x0E`）。
START 和头信息的 `0x05` 早就有「断链复位 → 等 3s → 整轮从 START 重来一次」的自愈路径，唯独
**传数据阶段的 `0x05` 是直接判死**：用户看到那句报错，只能自己再点一次；而链路没断，下一次
START 照样被回 `0x05`，于是"越点越坏"。

现改为与前两者同一套（`OTA_DATA_STATE_ERROR` → `isWedgedDfuSession`）。从 START 重来是安全的：
START 本身会重置设备的写入区与 `total_bytes`，不存在"接着上次的半截数据往下写"。
两轮都过不去才如实失败，提示指向「断电重启设备」并说清**不是升级包的问题**。

### 一轮 OTA 收尾（成功/失败都算）一律断链 + 清缓存

此前只有**失败**才断链，成功路径什么都不做。可设备在 END 校验通过约 100ms 后就复位运行新固件，
这条 GATT 连接立刻作废——端上却还留着一整套"看着都还在"的状态，这正是「升级完读不到设备信息 /
连不上」的来源：

| 缓存 | 谁清 | 不清的后果 |
| --- | --- | --- |
| ota-ble 的 OTA 会话（FF10） | `resetAfterUpgrade` | `isConnected` 谎报已连接 |
| device-ble 的 FF00 会话（**同一条物理连接**） | `resetAfterUpgrade` | 详情页/调试台发指令写进死链路，一直等到超时 |
| `device-info` 的 0x01 读数（张数/掩码/播放配置） | `resetAfterUpgrade` | 展示重启前的旧状态 |
| `battery` 的 15 秒电量缓存 | `resetAfterUpgrade` | 展示重启前的旧电量 |
| `device-conn-cache` 直连句柄（稳定ID → 微信 deviceId） | 页面 `resetDeviceStateAfterUpgrade` | 下次连接先白花 3 秒直连探测，再回落扫描 |
| 本页 `device` 与 `selectedDevice` 的 `connected`/`bleDeviceId` | 同上 | 首页/详情页拿死句柄当"已连接" |

升级成功后 `updatedDevice.connected` 也从 `true` 改成 `false`（设备正在重启，这才是真的），
成功页文案补一句「电子纸设备正在重启，请稍等几秒后重新连接」——否则用户立刻回去点投屏，
会以为是升级把设备刷坏了。中途断链复位重试时也走同一套清理，不让第二轮沿用第一轮的会话与读数。

> ⚠️ **有一类"缓存"是故意不清的**：`transferConnIntervalMs` / `transferPaceMs` / `transferWindow`
> 是调试台「同步投屏」写进 storage 的**用户调参**，不是设备状态。它们跨 OTA、跨重启一直生效，
> 若上次同步的是保守值（大 pace / 小窗口 / 长连接间隔），投屏会一直偏慢——但那是设置，不该由 OTA 悄悄改掉。
> 要恢复默认就在调试台重新调好再点一次「同步投屏」。

## 待设备方确认（本轮按"都兼容"实现，拿到答复可收紧）

1. 新固件广播里那 6 字节与 `0x01 GET_INFO` 返回的**是不是同一个值、同一个字节序**？
   若确认一致，`broadcastCandidateMatch` 的弱匹配（4 字节锚段）就可以去掉，只留精确相等。
2. 新固件广播的**字段顺序**是否仍是 `Screen_Type(1) + Device_ID(6) + Battery(1)`？
   若是，`parseAdvertising` 的布局回退分支永远不会被触发（留着无害，只作兜底）。
3. 广播包里**还播不播设备名**（`EF6-370`/`EF6-589`）？不播的话，白名单已按厂商数据放行，
   但绑定页展示的默认名会受影响。
