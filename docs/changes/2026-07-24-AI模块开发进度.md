  ### 1 · AI 生成图片
  1. **本机照片上传前压到 ~100KB**：新增 `media.compressToTarget(filePath, targetBytes=100KB)`，
     `chat.uploadPending` 在 `api.setFileUpload` 之前先过一遍。策略是**先缩分辨率再降质**
     （长边封顶 1600 → quality 80/62/48/36/26 逐档试，第 3 档起每轮再砍一半分辨率），
     压到 ≤100KB 就收手。为什么这个顺序：降质会糊掉文字/细节，AI 反而看不清；缩分辨率对
     「看懂内容」几乎无损。**PNG 走 `wx.compressImage` 时 quality 是无效的**，只有分辨率这条路
     能压下来，所以砍分辨率这一步不能省。
     - ⚠️ 别和 `projection/result.js` 的 `compressForUpload` 混用：那套是「缩到设备物理分辨率**保画质**」
       （六色抖动帧靠它出细节），目标相反，两个方法各自的注释里都写了这条。
     - 兜底：老基础库没有 `compressImage` / `compressedWidth` 不支持（会自动退回只降质）/ 取不到尺寸 /
       压完反而更大，**一律回原图上传**，绝不因为压缩失败发不出图。
     - 压缩是异步的，压完会**先确认这张还在 `pendingImages` 里**再上传（用户可能已经点 ✕ 删了）。
  2. **图片按传值尺寸预占高宽**（也是下面 5.2「内容被顶出」的正解）：图片外面套一个占位盒
     `.img-box`，高度用 `padding-bottom: {pad}%`（pad = 高/宽×100）**先占住**，图绝对定位铺满它 ——
     所以图加载完不会把上面的内容顶飞。pad 来源三条：生图回来按当前 `img_orientation` 取
     （`ORIENTATION_OPTIONS[].pad`）、用户选图按相册回的宽高算、历史消息取不到就用默认竖向；
     **图片 `bindload` 回来后一律用真实宽高改写 pad**（`onImageLoad`），所以猜错也只是加载前后差一点。
     - 🔴 **待后端确认的比例分歧**：用户口述 `img_orientation` 是 `{square 1:1, landscape 16:9, portrait 9:16}`，
       但 API 文档 v1.0.4（§四 / §参数速查表 / §八 20007）写的是
       `vertical 1104×1472(3:4) / horizontal 1472×1104(4:3) / square 1328×1328(1:1)`，
       **两者的横竖比例对不上**（4:3 vs 16:9）。本次按**文档**取值，理由：同一份文档的 20007
       `INVALID_IMAGE_ORIENTATION` 明确「仅 horizontal/square/vertical」，传 `landscape/portrait`
       必定报错，可见文档这一节是现行有效的。若后端确实改成 16:9/9:16，**只需改
       `ORIENTATION_OPTIONS` 里 pad 三个数**（横 56.25 / 竖 177.78），别处不用动。
     - 顺带加了 `ORIENTATION_ALIAS`（landscape→horizontal、portrait→vertical、16:9/9:16/1:1 也认）
       + `normalizedOrientation()`：以后不管界面/存储用哪套叫法，发给接口的永远是它认的三个值。

  ### 2 · 打字机与滚动
  1. **打字机更顺滑**：原本 `setInterval(30ms)` 每帧追 3 字 —— 30ms 一跳、一跳 3 字，肉眼就是「一顿一顿」。
     现在 `TYPE_TICK_MS=16`（≈60fps）、每帧尽量只追 1 字，且改成**递归 `setTimeout`**：
     `setInterval` 碰上 setData 偶尔变慢会**堆帧**，追上来时一次吐一大段，就是那种「卡一下、蹦一截」的观感；
     自计时永远「渲染完再排下一帧」。长回复不会因此变慢：每帧字数 = `ceil(总字数 / TYPE_MAX_TICKS(420))`，
     整段最长约 6.7s 打完。
     - 顺手修了个真 bug：切字从 `text.split('')` 改 `Array.from(text)`。`split('')` 会把 emoji / 生僻字的
       **代理对劈成两半**，打到一半那一帧渲染出乱码方块 —— 星宝回复里 ✨ 之类相当常见。
  2. **滚动跟不上 / 底部内容被遮住**，两个独立原因：
     - **跟不上**：原来贴底走 `scroll-into-view` 且要「先清空锚点再设锚点」，**一次贴底两次 setData**，
       还开着 `scroll-with-animation`（一帧一帧补动画只会越追越远）。改成 `scroll-top` 交替
       `999998/999999` 两个大值（差 1px 视觉无感，但值必须变化才会重新滚），组件自己夹到底部，
       **一次 setData**；打字期间关动画、按 80ms 节流，打完再强制贴一次底。
     - **被遮住**：真凶是「停止生成」浮标 —— 它 `position: fixed; bottom: 220rpx`，正好压在聊天区
       最后 ~160rpx 上。改成 `sending` 期间给底部留白 `.bottom-anchor--sending: 180rpx`
       （算法写在 wxss 注释里）。
     - 附带加了「用户上翻就别拽回来」：`bindscroll` 算距底距离（`onReady` 量一次聊天区高度），
       超过 60px 就停止自动贴底，发消息/打完/切会话时复位。量不到高度就退回「一直自动贴底」＝改造前行为。
       注释里记了「为什么量一次就够」：onReady 那刻输入区最矮，量到的是聊天区**最大**高度，
       之后偏大只会让距底被算小 → 偏向继续贴底，正好是安全的那一侧。

  ### 3 · AI 回复图文合并进一个气泡
  消息模型改动：AI 回复恒为 `kind='rich'`，**图不再各自成一条消息**，而是挂在同一条消息的
  `images: [{ url, serverId, pad }]` 上；占位气泡（三点 loading）就是最终那个气泡，文字打进它的
  `content`、图打完字后挂进它的 `images`。
  - **历史消息同样合并**（`buildHistoryMessages`）：接口是按行存的（文字一行、每张图一行），
    连着的 assistant 图片行会并回它前面那条 —— 一轮对话＝1 条 user + 1 条 assistant 文字 + N 条图，
    所以「连着的 assistant 行属于同一轮」成立，不会把两轮并到一起。这样**重进会话与刚回复时长得一样**。
  - **长按菜单因此要分两层**：气泡本体长按＝删整条（`onBubbleLongPress`）；气泡里**某一张图**
    长按＝下载/投屏/删这一张（`onImageLongPress`，在图上 `catchlongpress` 不冒泡）。
    合并后一条消息可能对应**多个 message_id**（文字行 + 每张图各一行），`deleteMessage` 逐个删，
    漏一个重进会话就会诡异地只剩半条。

  ### 2 · 下载/投屏一律提示「图片过期」——真正原因不是过期
  两条独立原因叠加，与图片有没有过期无关：
  1. **接口回的是 `http://` 地址**（见 API 文档 §四 images 示例），而 `wx.downloadFile` **只认 https**。

     → 新增 `toHttpsUrl()` 自动升级协议。
  2. **`downloadFile` 的 `success` 只代表请求完成**，404/403 也会走 success。原代码不看 `statusCode`，
     会把一份错误页当图片存进相册 / 送去投屏。→ 统一走新的 `downloadAiImage()`，校验 `statusCode === 200`。
  - 顺带把错误文案分清楚（`describeDownloadFail`）：域名没配 / 超时 / 真过期(403,404) 各说各的，
    原先两处都硬写「图片过期」，把配置问题误报成过期，排查会被带偏。
  - 下载与投屏现在共用 `downloadAiImage()` 一处实现（原先两处各写一遍 `wx.downloadFile`）。
  - 🔴 **另一半必须在小程序后台配**：「开发管理 → 服务器域名 → **downloadFile 合法域名**」加上图片所在

## 关键决策记录

- **小程序只能走非流式** `boltstaat-agent-fwdomalzks...fcapp.run`（wx.request 无 ReadableStream），流式 URL 仅存常量备 Web/Flutter 用
- **user_id 规则**：`boltfox_<用户userNo>`，未登录兜底 `boltfox_demo_user`（见 ai-api.getAiUserId；同一 user_id 多端历史互通）
- **独立接口层不复用 request.js**：第三方 FC 的 Base URL/响应结构/错误码体系与 BoltFox 后端完全不同，公共参数注入也不适用
- chat/enhance 超时 120s（生图上游可能 30s+），普通接口 15s，均不重试（生图 POST 重试有重复扣费风险）
