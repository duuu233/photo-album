# 「我的相册」删除：跳过设备上已经没有的槽位（多手机共用一台设备）（2026-08-10）

> 状态：current
> 适用范围：微信小程序「我的相册」删除链路（`subpackages/album/list`）、`utils/frame-protocol.js`、`utils/device-ble.js`
> 相关决策：[设备图片槽位索引](../decisions/image-slot-index.md)
>
> ⚠️ 仅小程序，Flutter APP 待同步（App 的删除链路同样只发 `0x12`，会踩同一个坑）。

## 现象

同一台电子纸设备被两部手机连过：

```
起点        设备：[0]A [1]B [2]C        后端记录：A→0  B→1  C→2
另一部手机  删掉 A
            设备：[0]空 [1]B [2]C
本机「我的相册」仍然列出 A / B / C 三张（列表是按后端投屏成功记录铺的，A 那条记录还在）
全选三张点删除 → 整批失败，toast：「电子纸设备-掩码不一致(该位置已有图/索引越界)」
```

**是的，那句提示就是这个问题。** 0 号位在设备上已经是空槽，客户端却把它和 1、2 一起塞进
`0x12` 的 `IMG_INDEX_MASK`，固件按 v1.5 §6.6.1 回 `RESULT=0x07`。旧代码把任何非 0 结果码
都当失败中止，于是**没问题的 B、C 也跟着删不掉**，用户在相册里永远清不掉这三张。

## 新口径（2026-08-10 产品确认）

删除以「**从我的相册里消失**」为准，设备侧尽力而为：

| 情况 | 设备侧 | 后端记录 |
| --- | --- | --- |
| 槽位上还是这张图 | 发 `0x12` 删掉 | 删 |
| 槽位在设备上已空（另一端删过） | **跳过**，不影响同批其它张 | 删 |
| 槽位上现在是另一端后传的**别的图** | 仍**按索引删掉**，不做内容比对 | 删 |
| 设备忙 / Flash 写失败 / 传输中断 / 断连超时 | 如实中止 | 不删 |

第三行是产品明确接受的取舍：索引是我们唯一的定位手段，撞上了就按索引删。真正的根治仍是后端的
`imgIndex` 唯一性规则（见决策文档「三、待后端确认」第 1 条）。

第四行是这次刻意**没有**放宽的部分——那几类代表「设备可能真的没删掉」，放行会变成
「记录删了、图还挂在相框上」，留下谁也找不到的孤儿槽位。

## 改动

### 1. 下发 `0x12` 前按设备真实 `IMG_MASK` 分拨（`subpackages/album/list/list.js`）

`confirmDeleteSelected` 第 3 步新增一次 `0x01` 回读（`deviceInfo.read(deviceId, {force:true})`），
把选中槽位切成两拨（纯函数 `splitSlotsByDeviceMask`，可单测）：

- `onDevice`：掩码里有这一位 → 进 `0x12`；
- `gone`：掩码里没有 → 设备侧跳过，只删后端记录；
- `onDevice` 为空 → 整个 `0x12` 都不发，直接删记录。

⚠️ **掩码读不到时一张都不能判 `gone`**（`splitSlotsByDeviceMask` 对 `null`/空数组/`undefined`
整体按 `onDevice` 返回），否则弱网/刚断连时会退化成「记录全删了、图还留在设备上」。
这与「设备真的一张图都没有」不同——后者是 12 个 0 的合法掩码，全判 `gone` 正是对的。

> 2026-08-10 上午刚写下的「**不读 0x01**」在此**部分收回**：不读掩码去*推算*缺失索引这条不变
> （记录没给有效 `imgIndex` 仍整批终止，绝不猜位置），但「这个槽位现在还有没有图」必须问设备，
> 否则本节的场景无解。

### 2. `0x12` 的良性结果码放行（`utils/frame-protocol.js`、`utils/device-ble.js`）

掩码回读与真正下发之间，另一端仍可能再删一张，所以还要兜一层：

- `frame-protocol.js` 新增 `isSkippableDeleteResult(code)` / `isSkippableDeleteError(error)`，
  放行 `0x05 图片不存在`、`0x07 掩码不一致`；`0x04`/`0x09`/`0x0B` 等一律不放行。
- `device-ble.js` 的 `deleteImage` 在抛错时把原始结果码挂到 `error.resultCode`——
  上层按码判定，不再匹配中文文案（`prefixDeviceError` 只改 `message`，自定义属性保留）。
- `subpackages/device/detail/detail.js` 的 `isBenignDeleteError`（一键清空用，2026-08-01 就有
  同样的放行需求）改为直接委托给协议层，两条链路自此**同一套口径、同一份实现**。

### 3. 顺手修掉的既有问题

- `tests/album-slot-index.test.js` **自 2026-08-10 上午起就是坏的**：那次改动删掉了
  `backendImageIndexOf`，用例还在调它，一跑就 `TypeError`。本次按现实现重写（改测
  `resolveDeleteTargets` + `splitSlotsByDeviceMask` + 良性结果码），并补上本轮的新分支。
- `subpackages/device/debug/debug.wxml` 文本节点里的 `&lt;15ms` 改成「小于 15ms」：
  WXML 不还原实体，页面上会原样显示 `&lt;`。这条是 `tests/token-page-layout.test.js`
  （随 `test-ai` 分支合入）扫出来的，与本需求无关但同处一次改动，一并修掉。

## Risks

- **每次删除多一次 `0x01` 往返**：与一键清空同款做法，弱网/设备忙时这一步可能失败——已按
  「读不到就不过滤」处理，不会因此拦住删除。
- **按索引误删另一端的新图**：新口径明确接受。发生前提是后端没有 `imgIndex` 唯一性规则
  （决策文档待办 1），根治仍在后端。
- **记录缺 `imgIndex` 仍整批终止**：本轮**没有**放宽。这类记录来自「投屏成功但记账失败」
  （决策文档问题 B），设备上那张图的位置无从得知，跳过设备侧只会留孤儿槽位。
  若产品希望这类也能从相册里删掉，需要单独定夺。
- 设备上被跳过的那些槽位若其实**没**被另一端删掉（掩码回读到的是脏数据），记录会先删掉，
  图留在相框上成为孤儿——只能靠一键清空兜底。目前没有观测到该路径。
