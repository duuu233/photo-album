# 2026-08-08 微信虚拟支付对接（Token 支付体系接后端）

> 状态：current
> 适用范围：微信小程序
> 微信文档：<https://developers.weixin.qq.com/miniprogram/dev/api/payment/wx.requestVirtualPayment.html>
> 后端来源：BoltFox Swagger `/Client/Order/*`、`/Client/Pay/*`
> Flutter 同步：**未同步**（APP 端 iOS 走 Apple IAP，接口另有 `/Client/Pay/setApplePayVerify*`）

## Background

2026-08-06 建好了 Token 三个页面，数据全部来自 `utils/token-api.js` 的本地 mock，
`createOrder` 直接把 Token 加到本地余额。当时的结论是「后端接口都还不存在」。

复核 Swagger 后发现**接口其实已经就绪**：`/Client/Order/` 下有账户、商品、订单、流水四个端点，
`/Client/Pay/` 下有整套虚拟支付（查单/扣代币/取消/退款）与 Apple Pay 验证。本轮把小程序端接上。

## 为什么是「虚拟支付」而不是普通微信支付

Token 是虚拟商品，微信对小程序内虚拟商品的支付有单独通道：**小程序虚拟支付**
（`wx.requestVirtualPayment`，米大师/Midas），不能用 `wx.requestPayment` + JSAPI prepay 那一套。
两条链路的下单、签名、回调全不一样，别混着看后端的 `支付创建接口输出参数`
（那个 DTO 里是 `wxPayPrepayId`/`wxPaySign`，属普通微信支付，当前没有 Client 端点暴露它）。

虚拟支付有两种 `mode`，后端两套都实现了：

| mode | 含义 | 后端配套 |
| --- | --- | --- |
| `short_series_goods` | 道具直购：选套餐直接付钱，微信支付后回调我们发货 | `addOrder` + 发货回调 |
| `short_series_coin` | 代币充值：先充米大师代币，再由服务端扣减 | `setWxVirtualPay`（扣代币） |

按当前需求（拿商品的 `wxProductId` 去微信下单）走的是 **goods**，
但端上**不写死**——`mode` 以服务端返回为准，缺省 goods。哪天改代币模式，端上一行不用动。

## 链路

```
① GET  /Client/Order/getGoodsList     取套餐（含 wxProductId = 微信侧道具 id）
② POST /Client/Order/addOrder         在我们平台建单 → orderId / orderNo(=outTradeNo) / amount
                                      + signData / paySig / signature  ← 后端待补，见下
③ wx.requestVirtualPayment            用②的签名参数拉起支付
④ 微信 → 我们后端                     发货通知回调，后端给账户加 Token
⑤ GET  /Client/Order/getUserAccount   端上退避轮询余额，变多了才算「买到了」
```

**③ 的 success 回调只是弱确认**：微信异常退出就可能丢，它来了也不代表 ④ 已经处理完。
所以判据只能是 ⑤。这条是整个模块最关键的约束，`tests/token-pay.test.js` 把它锁成了用例。

## Solution

### 新增 `utils/wx-virtual-pay.js`

只做三件事：可用性判断、把服务端签好的参数**原样**透传、把微信错误码翻成人话。
它不拼 `signData`、不算签名——`appKey` 与 `session_key` 都是服务端秘密，
放到端上等于把支付签名交给任何人伪造。

```
paySig    = hex(hmac_sha256(appKey,      'requestVirtualPayment&' + signData))
signature = hex(hmac_sha256(session_key, signData))
```

### `utils/token-api.js` 全量改写

| 方法 | 变化 |
| --- | --- |
| `getAccount` | → `/Client/Order/getUserAccount`，三个 **String** 字段归一为数字 |
| `getPackages` | → `/Client/Order/getGoodsList`，字段映射 `num/giveNum/amount` → `tokens/gift/price` |
| `getRecords` | → `/Client/Order/getUserAccountTrade`，返回 `{list, hasMore, pageIndex}`（原来是数组） |
| `createOrder` | **删除**，拆成 `addOrder` + `purchase`（建单 → 拉起支付 → 确认到账） |
| 新增 | `confirmPurchase`、`queryVirtualPayOrder` |

### 页面

- `confirm`：`createOrder` → `purchase`；结果分三档——已到账（报数字）/ 已到账（拿不到基线不报数）/
  已付款但回调未到（**不说失败**）。用户取消从弹窗降级成 toast。
- `records`：补上拉翻页。后端默认一页 10 条，不翻页等于「买过多少次都只显示 10 条」。
- `index`：仅注释更新，逻辑不动（套餐 `id` 是 `goodsId` 的字符串形态）。
- `mine`：Token 余额已是真实数据，注释里只剩收藏数还是 mock。

## Technical Decisions

1. **到账判据是余额差值，不是接口回执**。`purchase` 先记一次支付前余额当基线，支付成功后按
   `[900,1200,1800,2500,3000]ms` 退避轮询 `getUserAccount`，余额变多才算成。
   轮询期间 `showError:false`——中途一次网络抖动弹红字，会让刚付完钱的用户以为钱没了。
   超时也不报失败：查一次 `getWxVirtualPayQueryOrder` 的 `payStatus`，把提示分成
   「已付款、稍后到账」与「结果确认中」。**没有任何一条路径会因为客户端回调就给用户加余额。**

2. **`signData` 原样透传，端上绝不重新序列化**。签名是对那个字符串本身算的，
   键顺序、空格差一点微信就回 `-15005`。服务端只给对象时端上会 `JSON.stringify` 兜底并打 warn，
   但那条 warn 出现基本就等于下一步要报 -15005，修法是让后端直接返回字符串。

3. **只传微信文档列出的四个参数**（`mode`/`signData`/`paySig`/`signature`）。
   `env`、`offerId`、`productId`、`outTradeNo` 都已经在 `signData` 里，端上再平铺一份没有意义，
   还多一处能和签名内容对不上的地方（社区里 `-15005` 的常见成因之一就是多塞了 `platform`）。
   `env` 我们自己留着，仅用于查单接口。

4. **错误码不猜**。只映射有把握的两个（`1001` 参数错误、`-15005` 签名校验失败），
   其余原样带上 `errCode` 进弹窗——联调期用户截个图就能定位，比看一句编出来的中文有用。
   `cancel` 单独识别成 `PAY_CANCELED`，页面据此走 toast 而不是「购买失败」弹窗。

5. **支付参数解析容错**。后端可能把签名参数平铺在 `addOrder` 响应里，也可能包一层
   （`payParams`/`payData`/`virtualPay`…），端上两种都认。这不是偷懒，是为了让「字段放哪」
   这种小事不必来回改端上；真缺参数时会抛 `ORDER_PAY_PARAMS_MISSING` 并点名缺哪几个，不会静默走空。

6. **可用性前置判断**。`wxVirtualPay.isAvailable()` 在 `addOrder` **之前**调用——
   微信版本太老时提前拦住，别在后台留一串永远付不掉的待支付单。

7. **单价仍在端上算**，不用后端 `ClientGoodsApiOut.unitPrice`：那个字段是 integer，
   且不含赠送口径，直接渲染会变成 `≈ ¥0/Token`。口径以 `unitPriceOf`（含赠送总数）为准，与设计稿一致。

## Risks / Follow-up

1. ⚠️ **后端待补：`addOrder` 出参缺 `signData` / `paySig` / `signature`**（可选带 `mode`/`env`/`offerId`）。
   Swagger 的 `ClientAddOrderApiOut` 只有 `amount`/`orderId`/`orderNo`。这是当前**唯一**的阻塞项：
   没有这三个值，`wx.requestVirtualPayment` 根本调不起来。要么 `addOrder` 一并返回，
   要么补一个「创建支付」端点。端上已经写好，后端就位后不改客户端。
2. ⚠️ **`signature` 需要新鲜的 `session_key`**。它由 `code2session` 得到、会过期。
   若后端用的是登录时缓存的那把，长时间未重登的用户会稳定报 `-15005`。
   微信社区的建议是**每次支付前重新 `wx.login` 取 code 交给后端刷新**——
   要不要加这一步，取决于后端 `session_key` 的管理方式，**待联调确认**。真要加，落点在
   `token-api.purchase()` 里 `addOrder` 之前，把 code 一起提交。
3. ⚠️ **开通与配置项未核对**：小程序后台「虚拟支付」是否已开通、`offerId`（米大师应用 id）、
   `appKey`、发货回调地址、沙箱白名单用户 —— 这些都在后端与小程序后台侧，端上看不到。
   联调第一步应先用 `env=1`（沙箱）跑通，再切 `env=0`。
4. ⚠️ **PayPal 仍未接入**，`purchase` 直接 reject `PAYPAL_UNAVAILABLE`。
   小程序内无原生 SDK，需 H5/webview 承载，合规性与跳转方式要先与后端和微信审核确认。
   `addOrder` 的 `payType=3` 已预留。
5. **`subpackages/ai/chat/chat.js` 的 `TOKEN_LIMIT_ENABLED` 仍是 `false`**，本轮**没有**打开。
   后端目前只有购买侧端点，没有「消费 Token」的 Client 接口（消费流水 `getUserAccountTrade`
   能查到，说明扣费发生在服务端某处），扣费口径要和 AI 网关谈定后再开——
   否则只是把一种假扣费换成另一种假扣费。
6. **未真机验证**：本轮只跑了 Node 单元测试与静态检查。虚拟支付**必须真机验证**，
   开发者工具里 `wx.requestVirtualPayment` 行为与真机不一致。记录页上拉翻页也需真机回归。
7. **Flutter APP 未同步**。iOS 侧是 Apple IAP（`setApplePayVerifyReceipt` / `setApplePayVerifyPayment`），
   与本轮完全是两条链路。
