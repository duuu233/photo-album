## 二、修好真实升级「点了没反应」

### 根因

升级页的主按钮是否**画出来**由 `screenForLoaded()` 决定（`state==='available'` 即
`showPrimary: true`），而是否**点得动**由 `deriveViewData().canUpgrade` 决定 —— 后者要求
`device.connected !== false && bleDeviceId`。于是「有新版本但此刻没连着设备」时：

```
按钮画着「设备未连接」→ 用户点它 → startUpgrade 首行 if (!canUpgrade) return → 什么都不发生
```

而 OTA 页**自己从不连接设备**（它只读 `activeDevice.findConnectedDeviceId`），
用户唯一能做的是退回详情页手动连一次再进来——大多数人只会觉得「这个按钮坏了」。

### 改法

1. **`canUpgrade` 不再含「已连接」**：只表示「有升级包、按钮可以按」。未连接时按钮文案改成
   **「连接并升级」**，标题补一句「（将先连接电子纸设备）」。
2. **升级前就地自动扫连**：新增 `ensureConnectedDevice()` —— 已连接直接用；否则切到
   「连接电子纸设备中」画面并走 `activeDevice.ensureConnectedForAction`（与「我的相册」删除、
   一键清空同一套：扫描 + 连接 + 权限引导），连上后把有效句柄写回本页与全局选中设备。
   连不上则回到可重试画面（提示已由 ensureConnectedForAction 弹过，不再叠 toast）。
   ⚠️ 认的是**设备身份**不是缓存句柄：OTA 写错设备不可逆。
3. **任何一条分支都不再静默 return**：
   - 检查失败且无固件信息 → 重新检查；
   - 没有可用升级包（已是最新 / 包信息无效）→ 如实 toast + 重新检查一次；
   - 升级中再点 → 提示「正在升级中，请稍候」。
4. **并发闸门补齐**：`runUpgrade` 原来只看 `state === 'upgrading'`，而自动扫连可达十几秒、
   期间 state 还没变，用户点一下就能并发出第二条 DFU 流（同一 session 交叉写 DATA 必败）。
   改为同步 `_running` 闸 + 拆出 `doRunUpgrade`。
5. **详情页入口去掉「未连接直接拦住」**：版本检测走后端接口、根本不需要蓝牙，先拦一道只会让
   没连设备的用户连版本都看不到。真正需要连接的是「立刻更新」，`enterOtaUpgrade` 本来就有
   `ensureConnectedForAction`。

## 三、修「升级必报『记录缺少完整的6字节电子纸设备ID，请删除后重新绑定』」（同日追加）

上面第二节把「升级前就地自动扫连」接到了 `ensureDeviceConnected`，也就把升级页接上了它开头的
**身份闸**（`utils/active-device.js` 开头 `deviceSerials(device).length` 判断）。而升级页的记录
偏偏是全 App 唯一没走身份补齐链的一条 —— 缺口从「显示不准」升级成「点升级必报错」。

### 两处根因

1. **升级页不补齐身份**：`ota.js loadFirmware` 用 `getDeviceDetail` 重拉记录，`mergeSelectedDevice`
   只从 `selectedDevice` 继承 `deviceId/bleDeviceId/firmwareVersion`，**不含 `productDeviceId/deviceNo`**，
   也不查身份登记表。于是 `this.data.device` 没有稳定身份：
   `findConnectedDeviceId` 遇空 serials 直接返回 `''`（**设备连着也显示未连接**、电量不刷、按钮恒为
   「连接并升级」），点升级则被身份闸拦下报上面那句话。
   改法：`mergeSelectedDevice` 里补 `activeDevice.inheritStableIdentity(merged, isSelected ? selected : null)`，
   与详情页(`detail.js`)、设备列表(`list.js`)、轮播设置(`slideshow.js`)、首页(`home.js`)同一套补齐链。
2. **完整 ID 被残缺候选挡掉**：`utils/api.js normalizeDevice` 取设备 ID 是「第一个非空候选」
   （`productDeviceId > deviceNo > serialNo > productSerialNo > deviceId`）。老记录常同时带历史
   4 字节 `deviceNo` 与完整 6 字节 `deviceId`，取到短的 → `canonical` 归零 → **接口明明下发了完整 ID，
   端上仍报「请删除后重新绑定」**。改为**完整候选优先**，一个完整的都没有才退回原来的第一个非空值
   （`rawProductDeviceId` / `deviceIdentityInvalid` 的排查语义不变）。

> 身份闸本身没动：没有完整 6 字节 ID 时依旧终止，不用短 ID / 名称 / BLE 句柄兜底。
> 改的是「记录本来就有身份，却在页面或归一化环节被丢掉」。

## 四、真机首刷暴露的两个协议层问题（同日追加）

现场日志：第一次升级 →「OTA 传输中断：**已发送 673/673 包后**，电子纸设备未在 1.5s 内应答（疑似丢包）」；
之后每次点升级 →「OTA 启动被拒绝：设备状态错误（ACK=`FC F1 05 F2`）」。

1. **收尾窗口被当成丢包**（`utils/ota-ble.js transferData`）。设备按 PRN 信用窗口每收满 3 包回一次
   DATA ACK，而 673 = 3×224 + **1**：最后一窗只有 1 包，本就等不到应答。旧实现对每一批都强等 1.5s，
   于是**数据已经全部发出**却判失败。改为收尾窗口的 ACK 可选，直接发 END——整包完不完整由 END(0xF3)
   的 `total_bytes` + CRC32 校验裁决（不匹配设备回 `0x09`），真丢包一样抓得住。
2. **失败后不断链，设备卡在 DFU 状态**。第 1 条中断后连接还留着，设备状态机停在升级态，
   之后每次 START 都被回 `0x05`。三处改动：失败/中断一律断开 OTA 链路；START 收到 `0x05` 时
   自动断链 → 等 3s → 重连重发一次（用户再点一次就能自愈）；重试仍被拒才提示「请断电重启电子纸设备」。

3. **头信息握手无应答**。复位后再试出现第三种现象：START 应答正常，却收不到 128 字节头信息的
   校验结果。规格书 §8 步骤 2 明确设备要回 ACK，且**包不对/面板不匹配/CRC 不过都会回明确的
   `0x0A~0x0E`**——能等到超时，只可能是设备没收到这一包，或收到了但顾不上应答。
   关键点在于 `writeNoResponse` **被丢是静默的**：设备收到 START 后立刻初始化写入区（擦 Flash），
   紧跟着发的头信息包很可能就丢在这段忙碌期里，端上却毫不知情，只会干等超时。三层兜底：
   - START ACK 后先等 **800ms** 再发头信息（`headerDelayMs`）；
   - 同一连接内最多发 **3 次**头信息、每次等 10s（`headerAttempts` / `headerTimeout`，
     依据 §6.3.4「设备端通过首包长度判断为头信息」——只要设备还没收下过，重发的仍按头信息处理）；
   - 三次都没应答才断链复位、**整轮重来一次**（与 `0x05` 同一套）。
   重发的代价写进了 END 的错误文案：若设备其实已收下第一包、只是应答丢了，重发的 128 字节会被
   计入 bin 数据，END 回 `0x09` 时会带上这条线索，免得又去查信号。
   加了延时后现场变成「设备**会**应答头信息了，但回 `0x05`」——于是再补一条：
   **头信息 ACK 回 `0x05` 按可重试处理**（退避 1.5s/3s 重发 → 仍不行才断链复位整轮重来），
   而 `0x0A~0x0E` 是包本身不对，立即停止、绝不重发。延时也从 800ms 收到 **300ms**：
   若固件同样有「约 1s 没等到下一包即中断」的口径，久等反而会让它先把这轮 DFU 判死。

4. **发包前没有任何本地校验**（现场提示「可能是 OTA 文件传错了」后补）。刷错固件不可逆，
   「传错文件」不该等刷到设备上才由错误码兜。`prepareFirmware` 新增本地预检：按 §6.3.4 字段表
   解析那 128 字节头信息（只读不改，仍原样发送），四类明确不对的在碰蓝牙前就终止——
   缺 `OTAINFO` 标识 / 头部长度≠128 / 声明 bin 大小与文件对不上 / 面板与设备不符。
   CRC16、CRC32、版本号不同形**只记日志不拦**（口径未定义，误拦会挡住好包，设备侧本就会校验）。
   面板由 `panelOfDevice` 从 `screenType` 或分辨率换算，判不出就跳过该项，不误伤。

> 协议层其余部分（握手/窗口/END 校验/超时/重试）未动；「未收到 0xF3 不判成功」的口径也不变。

### 按文档截图逐条比对的结果（2026-08-11 晚）

拿 `assets/ota文档.png`（§6.3.2~§6.3.4 全文）与实现逐字段核对，**只有一处真出入**：

| 项 | 文档 | 端上 | 结论 |
| --- | --- | --- | --- |
| FW_SIZE 范围 | `0x3000 ~ 0x3C000` | 曾"更正"为 `0x30000` 下限 | **已改回原文**。现场固件 bin ≈164KB 落在原文范围内，却被误判越界白打告警 |
| FF11 属性 | `Write Without Response, Notify` | 优先 writeNoResponse | 一致。**只有无应答写**⇒丢包静默，正是头信息超时要延时+重发的依据 |
| 首包识别 | "设备端通过首包长度判断为头信息" | `[0xF2][128B][CHK]`=130 字节 | 一致（真机第一轮已 ACK 过这个帧，框架正确） |
| 后续 F2 | "不再校验长度，直接缓存写入" | 每包 244 字节数据 | 一致 |
| END | `total_bytes==bin_size` 且 `CRC32(payload)==bin_crc32`，否则 `0x09` | 只认 `0x00` 为成功 | 一致 |
| PRN | "固件返回 3，APP 每发送 3 个 DATA 包等待一次 ACK" | 收尾窗口不强等 | 一致（收尾不足一窗，文档未定义应答） |
| 头信息字段表 | 偏移 9 面板 / 10 头长 128 / 12 bin 大小 / 22 CRC16 覆盖 0~21+24~127 | 预检查前三项，CRC16/CRC32 只记日志 | 一致（CRC 多项式口径文档未给，不能本地拦） |
| 版本号示例 | 截图作 `..._5D89_v100`（小写 v），PDF 正文作 `V100` | 不校验，仅告警 | 文档自身不一致，无影响 |
| OBJ_TYPE | 只写"当前作为固件对象使用"，无取值 | 默认 `0x00`，失败再试 `0x01` | 文档缺值；真机已确认 `0x00` 可用 |

### 核对了规格书原文（此前只依据 docs/ 二手文档）

本轮改动后回到 `assets/电子相框产品需求规格书1.5.pdf` §6.3.3 / §8 逐条核对：

- 「`CREDIT / PRN 1 固件返回 3，APP 每发送 3 个 DATA 包等待一次 ACK`」、流程图
  「`loop [每 PRN 个 DATA 包]`」——**收尾不足一窗的包，规格书本就没有为它定义应答**，第 1 条改法与原文一致。
- 顺带查出 `docs/protocols/ota-dfu.md` 的一处旧错：「超过约 1 秒未收到应答即判中断」是 §6.4
  **图传**协议的参数（`MTU 247 / Credit 5 / 超时 1s`），被搬到 OTA 段了，OTA 没有这条红线。已改正。
- 流程图失败分支写的是设备「保持连接或等待 APP 重新发起 DFU」，而真机回 `0x05` 拒绝 ——
  **固件与规格书不一致**，端上的断链复位只是兜底，建议向固件方确认。

## 待确认（本轮**没有**擅自实现）

1. **低电量门槛**：页面上有电量展示、`firmware.minBattery` 也留着字段，但协议文档
   （`docs/protocols/ota-dfu.md`）没写 OTA 的最低电量要求，端上因此没有拦截。
   刷固件中途没电的后果是变砖，建议固件/产品给一个阈值（如 <30% 禁止升级），给了就在
   `deriveViewData` 里加一条拦截。
2. **升级完成后的版本回读**：现在成功后是把本地版本号乐观改成 `latestVersion`。
   设备升级完会重启，理论上应等它重连后读 `0x03` 固件版本核对一次再落库。
   要做需要先确认「设备重启后多久能重新广播/被连上」，属于真机联调项。
