## 二、修好真实升级「点了没反应」

### 根因

升级页的主按钮是否**画出来**由 `screenForLoaded()` 决定（`state==='available'` 即
`showPrimary: true`），而是否**点得动**由 `deriveViewData().canUpgrade` 决定 —— 后者要求
`device.connected !== false && bleDeviceId`。于是「有新版本但此刻没连着设备」时：

```
按钮画着「设备未连接」→ 用户点它 → startUpgrade 首行 if (!canUpgrade) return → 什么都不发生
```

而 OTA 页**自己从不连接设备**（它只读 `activeDevice.findConnectedDeviceId`），
用户唯一能做的是退回详情页手动连一次再进来——大多数人只会觉得「这个按钮坏了」。

### 改法

1. **`canUpgrade` 不再含「已连接」**：只表示「有升级包、按钮可以按」。未连接时按钮文案改成
   **「连接并升级」**，标题补一句「（将先连接电子纸设备）」。
2. **升级前就地自动扫连**：新增 `ensureConnectedDevice()` —— 已连接直接用；否则切到
   「连接电子纸设备中」画面并走 `activeDevice.ensureConnectedForAction`（与「我的相册」删除、
   一键清空同一套：扫描 + 连接 + 权限引导），连上后把有效句柄写回本页与全局选中设备。
   连不上则回到可重试画面（提示已由 ensureConnectedForAction 弹过，不再叠 toast）。
   ⚠️ 认的是**设备身份**不是缓存句柄：OTA 写错设备不可逆。
3. **任何一条分支都不再静默 return**：
   - 检查失败且无固件信息 → 重新检查；
   - 没有可用升级包（已是最新 / 包信息无效）→ 如实 toast + 重新检查一次；
   - 升级中再点 → 提示「正在升级中，请稍候」。
4. **并发闸门补齐**：`runUpgrade` 原来只看 `state === 'upgrading'`，而自动扫连可达十几秒、
   期间 state 还没变，用户点一下就能并发出第二条 DFU 流（同一 session 交叉写 DATA 必败）。
   改为同步 `_running` 闸 + 拆出 `doRunUpgrade`。
5. **详情页入口去掉「未连接直接拦住」**：版本检测走后端接口、根本不需要蓝牙，先拦一道只会让
   没连设备的用户连版本都看不到。真正需要连接的是「立刻更新」，`enterOtaUpgrade` 本来就有
   `ensureConnectedForAction`。

## 未改动（有意保留）

- DFU 协议层（`utils/ota-ble.js` 的握手/窗口/END 校验/超时/重试）一字未动。
- 「未收到设备 0xF3 确认不判成功」的口径不变（如实报「未确认(请重试)」，不上报 success、
  不改本地版本号）。
- 升级期间的返回拦截、常亮、切后台即中断的行为不变。

## 待确认（本轮**没有**擅自实现）

1. **低电量门槛**：页面上有电量展示、`firmware.minBattery` 也留着字段，但协议文档
   （`docs/protocols/ota-dfu.md`）没写 OTA 的最低电量要求，端上因此没有拦截。
   刷固件中途没电的后果是变砖，建议固件/产品给一个阈值（如 <30% 禁止升级），给了就在
   `deriveViewData` 里加一条拦截。
2. **升级完成后的版本回读**：现在成功后是把本地版本号乐观改成 `latestVersion`。
   设备升级完会重启，理论上应等它重连后读 `0x03` 固件版本核对一次再落库。
   要做需要先确认「设备重启后多久能重新广播/被连上」，属于真机联调项。
