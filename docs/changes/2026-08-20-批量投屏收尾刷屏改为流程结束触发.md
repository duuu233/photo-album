## Background

产品口径（本次确认）：**在预览页点「开始投屏」、选中多张图片的批量投屏里，要等整个投屏流程结束，
再去找本批第一张投屏成功的图片，用它刷新设备当前显示的图片——不是第一张上传成功就去刷设备。**

按这条口径逐行核对两端，"第一张成功就刷"的行为**从来不存在**：`firstSuccessfulIndex` 在循环里只是被
**记下**（`??=` / `=== null` 判空，槽位 `0` 合法所以用 `null` 当哨兵），真正下发 0x24 的判据是
`i === total - 1`。中途张一律不刷是刻意的：部分固件收到 0x24 会断开蓝牙，批量传输中途刷屏会让后面
几张全部失败。

但有一处对不上：**触发点写的是「最后一张传完」，不是「整个流程结束」**。任一张失败即中断本单，
于是「选 5 张、第 3 张失败」时——

- 第 1、2 张已经物理写进设备（失败的第 3 张已按原逻辑回滚 0x12，前两张不回滚）；
- 结果页按 `uploaded>=1` 判**部分成功**，跳成功页；
- 但一次 0x24 都没发过，**相框上仍停在投屏前那张**，用户看到的是「提示投成功了、设备没反应」。

## 本次改动

两端各抽出一个收尾函数（小程序 `scheduleFinalRefresh()` / Flutter 同名闭包），把「排这一次 0x24」
从循环体里挪出来，在**三条收尾路径**上调用：

| 收尾路径 | 改前 | 改后 |
| --- | --- | --- |
| 整批传完 | 循环最后一格发 0x24 | 循环结束后发（同一时刻，行为不变） |
| 中途某张失败 | **不发** | 按第一张成功的槽位发一次 |
| 用户中断（息屏/切后台/退页） | **不发** | 同上 |
| 一张都没成功 | 不发 | 不发（设备上没有本批的图，没什么可刷） |

不变量一律没动：

1. **整单只刷一次**——函数内部 `firstSuccessfulIndex === null || 已排过` 直接返回，收尾路径只会走其一；
2. **刷的是本批第一张成功写入的真实槽位**，不是最后一张、也不是刚失败那张；槽位 `0` 是相框第一个位置、
   是合法值，判空只认 `null`；
3. **中途张一律不刷**（固件收 0x24 会断蓝牙）；
4. **fire-and-forget**：不 `await`，图片已写入设备就立刻进收尾/结果页，刷屏在后台跑（真机墨水屏刷完 ~4s）；
   失败被吞掉，不影响本单成功/失败判定，只补记 trace 与一条独立日志；
5. **连接间隔回落**仍等在途刷屏跑完再发（刷屏期间设备对新指令回忙 `0x0B`）；没有在途刷屏才立即回落。

失败路径上这次 0x24 有可能因链路已断/设备忙而失败——这与原本就在失败路径上下发的回滚 0x12 同态，
失败即忽略，不会把已判「部分成功」的单子改判成失败。

## 刷屏索引的来源（口径确认，代码本就如此）

预览页「开始投屏」这条链路——**不管选了一张还是多张**——收尾刷屏用的索引只有一个来源：
**本张图传时由设备 `0x01` 回的 `IMG_MASK` 现算出的空闲槽位**（`protocol.firstFreeIndex`），
也就是这张图真正被写进相框的物理位置。整条链路里它只往一个方向流动：

```text
0x01 读回 IMG_MASK → firstFreeIndex 选空闲槽位 index
    → 0x20/0x21/0x22 按这个 index 写进设备
    → 第一张成功时记进 firstSuccessfulIndex（只记不刷）
    → 收尾 0x24 用 firstSuccessfulIndex 刷新设备当前显示
    → （另一条支流）index 作为 imgIndex 上报后端，仅供日后图库删除/定位
```

⚠️ **绝不能改成拿后端回的 `imgIndex` 去刷屏**：后端那份是我们事后写上去的账
（`editUserProductImgRecord` 是 fire-and-forget 的记账队列、允许失败且不回滚设备），
拿账本去定位物理槽位，等于用可能过期/写失败的值刷屏，刷出来就是别的图——这正是
[设备图片槽位索引](../decisions/image-slot-index.md) 里「删错图/刷错图」那一类问题的成因。
现状核对：`result.js` 全流程只把 `imgIndex` 往后端写，**一次都没有读回来用**。
