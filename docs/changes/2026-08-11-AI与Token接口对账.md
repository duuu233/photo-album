## 改动

### 1. `availableToken` 打通（登录 → 会话 → 页面）

- `utils/api.js normalizeUserProfile`、`app.js normalizeUserInfo` 新增 `availableToken`。
- ⚠️ **`null` 与 `0` 必须分开**：`null` = 本次响应没带这个字段（老后端灰度期），`0` = 余额真的是 0。
  混为一谈的后果是二选一的错——要么白多打一次 `getUserAccount`，要么把 0 显示成上次的旧余额。
- 「我的」页（`pages/mine/mine.js`）改为直接用 `userInfo.availableToken`，**不再固定并发一次
  `/Client/Order/getUserAccount`**；只有该字段为 `null` 时才回退查账户。每次进「我的」少一个请求。

### 2. AI 模块余额切真实（本轮重点）

`utils/ai-token.js` 重写：

- 读：`cachedBalance()` 取登录时落在 `app.globalData.userInfo` 里的 `availableToken`（同步、进页面即有）；
  `fetchBalance()` 取权威值 `getUserAccount`，失败回退 `getUserInfo`，都失败返回「未知」。
- 显示：未知一律 `--`，**不用 0 兜底**——有余额的用户看到「0 Token」会以为不能用了；
  余额真的是 0 就显示 0。
- 写：**`spend()` 整个删除**。swagger 的 `/Client/Order` 下只有购买侧四个端点、没有「消费 Token」，
  而消费记录能从 `getUserAccountTrade(inOutType=2)` 查到 —— 扣费只可能发生在服务端，
  端上再减一次就是双重记账。聊天页调用完 AI 之后改为**重取余额**。
- `LIMIT_ENABLED` 保持 `false`，但语义收窄成「余额不足是否**拦截**发送」（不再控制展示）。
  余额未知时也放行：读不到数字就锁死功能是更糟的失败模式。

页面侧：会话列表页顶部余额改为「先显示登录带回的值 → 异步刷新权威值」，`onShow` 重取
（聊天页生成过图之后余额会变）；聊天页 `guardToken` 改用真实余额，`spendToken` 改为刷新。

### 3. 支付查单端点纠正

`/Client/Pay/getWxVirtualPayQueryOrder` **在当前 swagger 里已不存在**（`/Client/Pay/` 下只剩
`getPayQuery` 与 Apple Pay 四个）。改调 `GET /Client/Pay/getPayQuery`：

| | 旧（端上） | 新（文档） |
| --- | --- | --- |
| 入参 | `outTradeNo`（微信侧）+ `env` | `payType` + `orderNo`（**我们平台的订单号**） |
| 出参 | `payStatus` | `payState`（另有 `payNo`/`exceptionMsg`/`resData`） |

`confirmPurchase` 的返回字段与确认购买页的判定一并由 `payStatus` 改为 `payState`。

`docs/reference/client-api-matrix.md` 的 `addOrder` 待办关闭、查单行改写、新增用户信息行；
`docs/architecture/ai-client.md` 的「Token 是演示逻辑」整段改写。

## 待后端确认

1. **AI 调用的扣费口径**（唯一阻塞「余额不足拦截」的事）：一次对话/生图扣多少、在哪一步扣、
   余额为 0 时 AI 网关返回什么错误码。端上现在只展示与刷新，不做拦截。
2. **`payState` 的枚举**：swagger 只写「支付状态」。端上沿用旧口径按 `1=已支付` 判定，
   其余值一律说「结果确认中」（绝不说成失败——钱可能已经付了）。
3. `getUserInfo` / 登录出参里的 `availableToken` 是否**所有环境都已上线**。端上按 `null` 回退
   `getUserAccount`，灰度期不会显示错数字，但多一次请求。
