# 2026-10-28 投屏 type 改取产品屏幕方向 screenType

> 分支：`main-wifi`｜依据：用户口径——产品列表接口返回 `screenType`（屏幕方向，0=竖屏、1=横屏），投屏的 `type` 直接用它，不再写死

## 做了什么

- `api.resolveScreenType(device)`（新增）：取当前设备所属产品的 `screenType`，返回字符串（`'0'` / `'1'`），不抛错。
  - 按 `productId` 查产品列表（`getProductList`，会话缓存，最多等 3 秒）；
  - 没配再按设备ID（去冒号）查 `getProductByDevice`；
  - 都取不到返回空串。
  - 只认产品接口的字段：设备对象上同名的 `screenType` 是固件 0x01 / 蓝牙广播里的型号字节（如 3.7 寸 0x01），不拿来用。
- 三处投屏改用它作 `type`，产品没配 / 查不到时回退原来的按分辨率口径（`dithering.typeForDevice`：480×720 传 1，其余 0）：
  - 蓝牙版结果页抖动出帧（`result.js` `ditherTypeFor`，一轮投屏只查一次，预取与主循环共用，控制台记 `[投屏][出帧] type=…` 及来源）；
  - WiFi 投屏结果页 `POST /api/device/play`（一次进页查一次，重试复用，投屏日志记 `type=…` 及来源）；
  - 轮播设置页保存后投第一张。
- 调试台（`subpackages/device/debug`）没有产品上下文，仍按分辨率取。

## 需注意

- 取值语义变了：原来 `type` 是出帧策略（0=5.8 寸大设备、1=3.7 寸小设备），现在传的是产品的横竖屏方向。后台 3.7 寸产品若配的是竖屏 `0`，蓝牙版出帧的 `type` 会从 1 变成 0，以真机出帧结果为准。
- 产品列表是会话缓存：后台中途改了屏幕方向，小程序重进后才拿到新值。
