# 2026-10-27 WiFi版首页与列表订阅状态推送

> 分支：`main-wifi`｜依据：[WiFi 版状态刷新分析](../wifi/WiFi版状态刷新分析.md)（用订阅长连接 + 补查，不做定时轮询）

## 做了什么

- 新增 `utils/wifi-watch.js`：页面级的设备状态推送订阅器。`update(devices)` 按 WiFi 设备 deviceNo（去冒号）订阅、多余的退订；`stop()` 退订并摘掉监听；回调 `onChange(deviceNos, reason)`：
  - 收到 WS `device.status`（上下线 / 关机 / 对账离线）→ 只重查那一台；
  - 长连接断线后重连成功（如熄屏回前台）→ 断线期间推送会丢，全部重查一次；首次连上不重查（进页已查过）。
  - 只退订自己订阅的；已被别处（WiFi 设备详情页）订阅的设备不重复订阅、不替它退订。
  - 没有 WiFi 设备（纯蓝牙版用户）不订阅、不建长连接。
- 首页：`onShow` 先按页面上已有的设备卡订阅（回前台时长连接立刻重连，重连成功即重查，不等老服务设备列表），`loadHomeState` 拉完列表后按最新设备再更新一次；`onHide` / `onUnload` 退订。`refreshWifiCards(deviceNos)` 支持只查指定几台。
- 我的设备列表：同样在 `onShow`、`loadDevices` 之后订阅，`onHide` / `onUnload` 退订；推送触发 `refreshWifiStatus(id)` 只重查那一台。
- WiFi 设备详情页的订阅逻辑未改。

## 没改的

- 不做定时轮询。
- 电量推送：`device.status` 不带电量，停留在页面期间电量不会自己变；需后端在心跳更新影子时也推一条（待确认）。
- 长连接没断的情况下回前台，首页那次查询仍排在老服务设备列表接口后面（只有断线重连时才会提前补查）。
