## 1. 「投屏明细」那一行改进「我的相册」

投屏结果页信息卡里的「投屏明细 · n/n」原本点进**投屏记录页**
（`subpackages/projection/records`），现改为进**我的相册**（`subpackages/album/list`）。
刚投完屏的人想看的是「刚才那几张现在长什么样」，而我的相册渲染的正是投屏成功的记录。

- 行文案与右侧 `n/n` 计数**没动**：它说的是本次明细，与点进去看哪一页是两件事。
- 仍用 `redirectTo`（与改动前一致）：结果页是流程终点，不该留在返回栈里让人退回来。
- 方法名 `goRecords` → `goAlbum`，wxml 绑定同步改。

⚠️ **副作用：投屏记录页从此在全项目没有入口了**（`grep 'projection/records'` 只剩注释）。
该页承载的是**失败记录与「重新投屏」重传**，代码原样保留、随时可挂回来 ——
「我的」页那行入口 2026-08-04 随模块合并去掉时，留下的唯一入口就是这次改掉的「投屏明细」。
**若产品仍要保留失败重传的入口，请指定挂在哪里**（建议「我的 → 我的相册」页内加一个二级入口）。

## 2. 确认购买页：支付中给全屏 loading

`subpackages/token/confirm` 在 `paying` 期间盖一层全屏遮罩 + 转圈 + 文案。

为什么需要：这条链路最长约 10s —— 建单 ~1s → 拉起微信支付 → **等服务端到账的退避轮询约 9.4s**。
中间这段此前**没有任何反馈**（只有按钮文字变成「支付中…」），用户很容易以为卡住了而反复点。
页面原有的同步闸只防重复下单，解决不了「看起来没反应」。

文案按阶段换（`utils/token-api.purchase` 新增可选的 `onStage` 回调）：

| 阶段 | 文案 | 说明 |
| --- | --- | --- |
| `order` | 正在下单… | `addOrder` |
| `pay` | 正在拉起支付… | 微信原生支付面板期间会盖住整屏，这句主要用于面板弹出前后与取消回来那一瞬 |
| `confirm` | 正在确认到账… | 到账轮询（最长 9.4s），**没有它用户会对着「正在下单」干等** |

配套两处：

- `addOrder` 新增 `options.loading`（默认仍弹原生「下单中」），`purchase()` 里传 `false` ——
  整段已由页面的全屏 loading 盖着，再叠一层原生 loading 就是两个转圈叠在一起。
- `onStage` 回调抛错不连累支付流程（`try/catch` 包住），不传 `onStage` 时行为与改动前完全一致。

遮罩 `z-index: 30`：必须高于贴底「立即购买」按钮那一层（`.cta-button` 是 2），
否则按钮会从遮罩里透出来还能点。转圈复用全局 `.page-loading__spinner`。
