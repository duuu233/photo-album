# 图库列表：从详情页返回后横图被拉长（2026-09-04）

> 状态：**已改**，⚠️ **两端均未真机验收**（App 侧本机无 Flutter SDK，`dart analyze` / `flutter test` 没跑；小程序 `node --test` 57 个用例全过）
> 最后核对：2026-09-04
> 适用范围：微信小程序 `subpackages/gallery/{list,favorites}` + Flutter `official_gallery_page.dart` / `official_gallery_favorites_page.dart`
> 相关：[2026-08-12 图库接口对接](2026-08-12-图库接口对接.md)（缺口①的由来）、[2026-08-12 图库收藏入口与详情版式](2026-08-12-图库收藏入口与详情版式.md)
> 权威来源：产品报障原文「图片默认是宽度大于高度的，点击进入图片详情，返回回来图片的长度被拉伸了，不要做这个多余的逻辑」
>
> 🔁 **本轮两端都要改**：成因是两端**同一套**版式约定（占位高度 + 加载后校正 + 返回重拉）叠出来的，App 一条不落，且比小程序多一条触发路径（下拉刷新）。

## 一、现象

官方图库列表里一张**宽 > 高**的横图，首屏显示正常（横着的）→ 点进详情 → 返回 → 那张卡**变高**，图被放大裁切，看着就是「被拉长了」。再也回不去，除非切个分类回来或杀掉页面重进。

## 二、根因：三条各自正确的既有设定叠在一起

| # | 既有设定 | 出处 |
| --- | --- | --- |
| ① | 后端列表项**不给图片比例**，端上一律先按 `DEFAULT_RATIO = 0.75`（3:4 **竖图**）占位 | `utils/gallery-api.js` 缺口①（App：`official_gallery_api.dart`） |
| ② | 真实比例靠图片加载完**量一次**补上（小程序 `bindload` → `onImageLoad`；App `imageBuilder` → `_onRatioResolved`） | 同上 |
| ③ | 从详情页/收藏页返回要**重拉一遍列表**对账收藏态（图库页静默重拉；收藏页每次 onShow 整页重拉） | 2026-08-12 需求 4 |

③ 会把每张卡的高度按 ① **重算一遍**（重拉回来的 `ratio` 仍是 0 → 又是 3:4），而此时：

- **小程序**：屏上 `image` 的 `src` 没变，节点按 `wx:key="id"` 复用 → **不会再触发 `bindload`**；
- **App**：`_PhotoCard` 的 State 按 `ValueKey(id)` 复用，`_measuring` 还是 `true` → **不会再量第二次**。

于是 ② 再也不会发生，量准的比例**永久丢失**。317rpx 宽的列里，16:9 的横图本该 178rpx 高，被打回 423rpx 的竖盒子，`aspectFill` / `BoxFit.cover` 只能放大裁切 —— 这就是「拉长」。

竖图看不出来（本来就接近 3:4），所以只有横图报障。

## 三、改法（两端同一套账）：量准的比例不许被重拉抹掉

比例是**端上量到的既有事实**，跟着页面实例活着，任何一次重拉都只能补充它、不能覆盖它。

| | 小程序 | Flutter |
| --- | --- | --- |
| 记在哪 | 页面实例上的 `this._ratios`（id → 宽/高） | State 里的 `final Map<int, double> _ratios` |
| 谁写 | `onImageLoad` 量到宽高时顺手记一笔 | `_onRatioResolved` 同上 |
| 谁读 | 新增 `sizePhoto(photo)`：比例三选一 **后端给的 → 已量准的 → DEFAULT_RATIO 兜底**，顺带算出 `imgHeight` | 新增 `_withKnownRatios(photos)`：`ratio == 0` 且量过的，`copyWith(ratio:)` 贴回去 |
| 用在哪 | `buildColumns` / `appendColumns` 一起换成走 `sizePhoto` | `_loadPhotos` / `_loadMore`（图库页）、`_load` / `_loadMore`（收藏页） |

两点顺带的好处：

- **分列更准**：`splitColumns` 是按累计高度选短列的，重拉后拿到的是真实比例而不是清一色 3:4，两列不再假性齐平。
- **`onImageLoad` 现在同时把 `ratio` 也写回 `data`**（原先只写 `imgHeight`），续页 `appendColumns` 累加高度时用的就是真值。

⚠️ **没有动的东西**（都是有账的既有决定，别顺手改）：返回本页仍然重拉对账收藏态（2026-08-12 需求 4）、校正高度后**不重新分列**（重排会把用户正看的卡片挪走）、收藏页取消收藏仍然整页重拉（那张要消失）。

## 四、测试

新增 `tests/gallery-return-ratio.test.js`：用真的 `gallery-api` 算占位高度与真实高度（写死数字会跟着 `DEFAULT_RATIO` 一起过期），只把网络那几个函数打桩成「每次都返回同一张 `ratio: 0` 的横图」，两个页面各走一遍**首屏占位 → 量准 → 重拉**：

1. 图库列表页：`loadPhotos` → `onImageLoad(1600×900)` → 走真实入口 `onShow()` 静默重拉；
2. 收藏页：`loadFavorites` → `onImageLoad(1600×900)` → 再 `loadFavorites`（＝每次 onShow）。

断言重拉之后高度仍是 178rpx（16:9）而不是 423rpx（3:4）。**改回旧实现这条用例立刻红**（实测 `423 !== 178`，正是报障现场）。

App 侧无对应用例（本机无 SDK）。

## 五、风险与取舍

- `_ratios` / `this._ratios` 只跟着**页面实例**活：杀掉页面重进会重新量一次（首屏依旧 3:4 占位一瞬间）—— 这是刻意的，不做跨页面/持久缓存，免得图换了内容而 id 没换时长期用错比例。
- 后端哪天在列表项里补上 `ratio` / `width` / `height`，这层记忆连同 ①② 的兜底一起可以删干净（`sizePhoto` 的第一档就会一直命中）。
- 首屏「3:4 占位 → 量准后归位」的那一跳**依然存在**（这是缺口①的固有代价，本轮没碰）。
