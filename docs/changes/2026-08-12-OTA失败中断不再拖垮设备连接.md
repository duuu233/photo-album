# OTA 升级失败/中断不再拖垮设备的连接与读取（2026-08-12）

## 现象与判据

现场两句话：**「升级失败，设备就连接不上了」**、**「退出小程序重新进入，又正常了」**。

第二句直接把范围锁死了。重启小程序会清掉什么、不会清掉什么：

| 状态 | 重启小程序 | 说明 |
| --- | --- | --- |
| `bleDirectConnCache`（直连句柄）、`deviceIdentityMap`（身份登记表）、`selectedDevice` | **不清**（storage） | 所以故障与它们无关——何况 OTA 收尾已经主动清过前两者 |
| 各模块内存会话（`device-ble.sessions` / `ota-ble.sessions` / `device-info` / `battery`） | 清 | |
| **微信持有的全部 BLE 物理连接** | **清** | |

设备是单连接，被连着时**不再广播**。所以「重进就好」＝ 之前有一条**还连着、但本机账本上没有**的
连接占着设备。它是无主的：`disconnectAll` / `disconnectOthers` 都按 `sessions` 账本遍历，
账本里没有就谁也关不掉，只能靠杀掉小程序让微信统一释放。

## 根因

### ① 连上候选之后，只有「身份不匹配」才断链

`active-device.scanMatchConnect` 的失败分支此前长这样：

```js
} catch (error) {
  if (error.code === 'DEVICE_ID_MISMATCH') { …排除候选… deviceBle.disconnect(target.deviceId) }
  // 其它错误：什么都不做 ← 链路留在设备上
}
```

而 OTA 刚失败/中断时最容易撞上的**不是**身份不匹配，是 `readAndVerifyDeviceIdentity` 里的
`指令 0x1 应答超时`——设备还在收拾自己的 DFU 状态，或者干脆停在升级态。于是：
连上了 → 0x01 读不回来 → 不断链 → 会话没登记成功、账本上看不见 → 设备被自己占住不广播 →
第二轮重扫「未搜索到」→ 之后每次点连接都是「未搜索到该电子纸设备」，**只有杀掉小程序才恢复**。

一次失败的连接尝试就足以把设备「锁」到重启小程序为止，与升不升级无关，OTA 只是最容易触发它的场景。

### ② 没有任何机制能回收「账本外的连接」

`closeBLEConnection` 是 fire-and-forget（无 `fail` 回调、不校验），而 `cleanupSession` 在它之前
就把会话从账本删了。close 一旦静默失败，这条连接就此无主。

### ③ 收尾复位一刀切：没碰过设备的失败也断链清缓存

`upgradeFirmware` 的 catch 覆盖了 `prepareFirmware`（下载 / 读文件 / 解析 128 字节头信息），
而这一段**全程不碰蓝牙**。一次网络抖动 → 断掉用户已经连着的那条链路 + 删掉直连缓存 +
把设备标记成未连接，下次连接白花一整轮扫描。错误还被扣上「电子纸设备-」前缀
（「电子纸设备-固件包下载失败(404)」），把用户引去排查设备。

### ④ 中断（退出升级页）的收尾只做了一半

`ota.js onUnload` 只调 `otaBle.disconnect`：断了物理连接，却把 device-ble 的 **FF00 会话**、
`device-info` 的 0x01 读数、`battery` 缓存、直连缓存、`selectedDevice.connected` 全留在原地。
FF10 与 FF00 是**同一条物理连接**，于是详情页/首页拿着一条死链路继续发指令，一直等到超时——
正是「升级完/中断后读不到设备信息」。

### ⑤ 成功路径整体替换了全局选中设备

`app.setSelectedDevice(updatedDevice)`（本页记录来自 `getUserProductDetail`）会把 `selectedDevice`
上别处才拿得到的运行时字段一并抹掉（`screenType` 等），升级成功后详情页分辨率、OTA 面板预检
（`panelOfDevice` 先看 `screenType`）都跟着降级。三行之前的 `resetDeviceStateAfterUpgrade` 用的却是合并口径。

## 改法

| 文件 | 改动 |
| --- | --- |
| `utils/active-device.js` | `scanMatchConnect`：连上候选后**任何**失败都 `deviceBle.disconnect(target.deviceId)`（断链幂等，代价只有下一轮重扫）；扫描前先调 `releaseStrayConnections()` 自愈 |
| `utils/device-ble.js` | 新增 `releaseStrayConnections()`：按 `getConnectedBluetoothDevices([FF00, FF10])` 与 device-ble / ota-ble 两个会话池对账，释放无主连接。best-effort，查不到/关不掉都不抛错 |
| `utils/ota-ble.js` | ① `upgradeFirmware` 记 `deviceTouched`：准备升级包阶段的失败**不**断链清缓存，错误带 `code='OTA_PACKAGE_FAILED'` / `deviceUntouched=true` 且不加「电子纸设备-」前缀；② `disconnect` 给 `closeBLEConnection` 补 `fail` 日志（无主连接的来源留下线索）；③ 头信息重发循环补 `shouldAbort()` 检查（中断最坏少空转 30s）；④ 导出 `resetAfterUpgrade` |
| `subpackages/device/ota/ota.js` | ① `onUnload` 中断收尾改走 `otaBle.resetAfterUpgrade` + 记录级复位（新增 `skipSetData`，页面已卸载不 setData），并解除返回拦截；② 失败路径遇 `deviceUntouched` 跳过记录级复位；③ 成功路径 `setSelectedDevice` 改为合并、判据改用 `devicesMatch` |
| `tests/ota-connection-safety.test.js` | **新增**（见下） |

一句话口径：**「碰没碰过设备」决定收尾力度；「连上过就一定要断干净」没有例外。**

## 仍未覆盖的风险（需固件方确认）

1. **设备失败后是否会停在只暴露 FF10 的 DFU/bootloader 态**。若会，正式入口全链路都过不去：
   `establishConnection` 找不到 FF00 会明确报「电子纸设备只暴露 OTA 服务(FF10)，未发现相框主服务(FF00)」，
   而升级页自己也救不了它——它的重试前置条件正是「FF00 连上 + `0x01` 身份校验通过」。
   若确认存在这种状态，需要给升级页开一条只走 FF10 的恢复路径（DFU 本来就只需要 FF11）。
2. **DFU 态下还播不播产品广播名/厂商数据**。都不播的话 `isAllowedFrame` 会把整台设备过滤掉
   （调试台 `allowAll` 却看得见，与 08-11 那次的观感一样）。
3. **START 是否会立即擦除正在运行的分区**。`FW_SIZE` 取的是 APP2 写入区大小，按双区理解中断是安全的，
   需要固件方确认，否则「中断」这件事的风险等级要重估。
