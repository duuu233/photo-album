# 2026-10-22 搜索列表设备ID只取本次广播

> 分支：`main-test`（从 main/e04198d 切出）。连接后读取（`0x01 GET_INFO`）、连接候选匹配、会话认领、身份登记表与直连缓存均未改动。

## 问题

搜索设备列表里的「设备ID」在安卓、iOS 上不一致，也与设备真实ID对不上。以 EB-169 为例：

- 第三方蓝牙工具看到的广播：设备名 `EB-169`，系统蓝牙地址 `5A:44:D0:00:0B:37`，
  厂商数据 `<0xFFFF> 0x04370B00D0445A61`；
- 产品确认的正确设备ID：`37:0B:00:D0:44:5A`。

厂商数据按协议 6.10.7 拆开：

```
FF FF | 04   | 37 0B 00 D0 44 5A | 61
厂商标识 | 屏型 | 设备ID（6 字节，原顺序）| 电量 97%
```

## 原因

1. **屏型被当成整条广播的有效性闸**：`parseAdvertising` 只认识 `SCREEN_TYPES` 里的 0x01~0x03，
   EB-169 的屏型 0x04 不在表里，整条厂商数据被丢弃，设备ID、电量一起丢失。屏型与设备ID无关。
2. **兜底用了手机系统给的 BLE `deviceId`**：广播解析不出时，安卓显示系统蓝牙地址
   `5A:44:D0:00:0B:37`——与设备ID字节序相反，是错的；iOS 的 `deviceId` 是随机 UUID，只能隐藏。
   两端表现取决于解析是否失败，而不是设备本身。
3. **共享扫描会话的存量结果**：搜索页挂到别处在途的扫描时，会先拿到加入前累计的设备；
   列表刷新签名也不含广播设备ID，ID 变化时不会重新渲染。

## 改动

| 文件 | 改动 |
| --- | --- |
| `utils/frame-protocol.js` | `parseAdvertising` 只认 `0xFFFF + 屏型1 + ID6 + 电量1`（不带前缀时恰好 8 字节）；以 `0xFFFF` 开头的一律按带前缀处理，避免把老格式误读成错误ID。设备ID按原顺序取，不受屏型/电量影响；屏型不认识记 0、电量超出 0~100 置空。删除 4 字节老格式及「6 字节解不通退回 4 字节」的回退 |
| `utils/bluetooth.js` | 白名单在设备名缺席时只看 `0xFFFF` 厂商数据，不再要求屏型认识；新增 `freshOnly` 订阅，只列出本次订阅后收到新广播的设备；刷新签名加入广播设备ID；`normalizeDevice` 增加 `advertisHex`（原始厂商数据），去掉已不存在的 `broadcastDeviceIdComplete` / `broadcastLayoutFallback` |
| `subpackages/device/bind/bind.js` / `.wxml` | 设备ID只取本次广播的完整 6 字节，取不到统一显示 `--`；去掉安卓系统蓝牙地址兜底；搜索使用 `freshOnly` |
| `subpackages/device/debug/debug.js` / `.wxml` | 调试台扫描结果显示原始广播与解析出的设备ID，日志同步打印，便于与第三方工具对照 |
| `utils/active-device.js` | 仅删除兜底候选日志里已不存在的 `broadcastLayoutFallback` 字段 |

## 测试

- `tests/advertising-parse.test.js`：改为 6 字节口径，加入 EB-169 实测数据（带/不带前缀、ArrayBuffer），覆盖未知屏型、非法电量、4 字节老格式返回 null。
- `tests/device-id-4-6-compat.test.js` ①：原「布局回退」已有意删除，判据「不让整台设备从列表消失」改到屏型/电量不认识时仍给出ID；②③ 候选匹配与会话认领未改。
- 新增 `tests/search-device-id.test.js`：列表只显示广播完整 6 字节，系统地址/UUID/短ID/全0全F/旧字段一律 `--`；EB-169 原始广播解析；名称缺席时按厂商数据放行；`freshOnly` 不取存量、ID 变化即刷新、缺ID不沿用。
