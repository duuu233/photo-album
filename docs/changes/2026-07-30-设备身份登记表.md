## Problem

三台设备 A/B/C 全部已绑定，实测复现路径：

1. 连接 C（可重复多次）；
2. 进 C 的详情，在详情页手动点「断开连接」；
3. 返回设备列表，连接 A —— A 连上；
4. 再进 C 的详情，操作（连接/轮播设置/固件升级等）报
   「设备-当前设备记录缺少完整的6字节设备ID，请删除后重新绑定」。

C 只是**没有连接**而已，设备和绑定记录都好好的，却把用户引向「删除后重新绑定」。

根因是身份来源被绑在了「当前选中设备」上：

- 后端「设备详情」`getUserProductDetail` **不返回设备 ID**，详情页拿到的记录天生没有完整 6 字节身份；
- 此前唯一的补齐来源是 `app.globalData.selectedDevice`，而它表示「当前选中的那一台」；
- 详情页只在 `isSelected`（详情记录 == 选中设备）时才 `inheritStableIdentity`。

第 3 步连上 A 后 `selectedDevice` 被改写成 A，第 4 步进 C 的详情 `isSelected` 为假，继承落空，
C 的记录没有完整 ID，`ensureDeviceConnected` / `connectBoundDevice` 开头的身份闸
（`deviceSerials(device).length === 0`）直接拦下并抛出上面那句话。

注意：身份闸本身是对的，缺完整 ID 时绝不能用短 ID/名称/尺寸兜底连接（防串台）。
错的是「C 明明有完整 ID，只是这一刻没人把它交到详情页手上」。

## Solution

新增按后端记录主键存完整 ID 的登记表 `utils/device-identity.js`，把「这台设备的完整 ID」
与「当前选中的是谁」彻底解耦：

| 时机 | 动作 |
| --- | --- |
| 设备列表接口返回记录（首页/设备列表） | `rememberMany` / `inheritStableIdentity` 顺手登记 |
| 连接成功、0x01 校验通过 | `applyConnectedIdentity` 登记（最权威的一手来源） |
| 任何页面缺完整 ID | `inheritStableIdentity` 按 `userProductId` 取回 |
| 解绑设备 | `forget(userProductId)` |
| 退出登录 | `app.clearSession` → `clear()` |

取值顺序固定，登记表只是最后兜底，永不反向覆盖后端最新值：

```text
记录自身的完整 ID  >  fallback(selectedDevice，仅同一台时传入)  >  登记表
```

## Technical Decisions

- **只收完整 6 字节 ID**：广播 4 字节短 ID、微信 BLE 临时句柄一律不进表。否则等于把「只能筛候选的短 ID」
  升格成身份，正是 EF6-370 串到 EF6-589 那类串台故障的来源。
- **登记键只取记录自己的主键**，不退到 fallback 的主键。否则调用方一旦传进来不是同一台的 fallback，
  就会把这台的完整 ID 登记到另一台名下——用登记表制造串台。无主键的记录（扫描结果等）不参与登记表。
- **存本机 storage**：按手机、按微信账号天然隔离；`userProductId` 是后端主键，换账号后与新用户无关，
  故退出登录整表清空、解绑单条清除，避免主键复用把旧身份带回来。
- **内存镜像 + 值未变不写盘**：列表/首页每次刷新都会为每台设备走一遍 `remember`。
- **没有 `wx` 时降级为纯内存**：Node 单元测试可直接跑，功能不缺，只是不跨启动保留。

## Risks

- 登记表是**本机缓存**，冷启动后首次进详情若还没拉过设备列表接口，仍会缺 ID 并如实被身份闸拦下。
  当前所有进详情的路径都要先经首页或设备列表（两者都会拉列表接口并登记），故实际不触发。
- 后端若复用 `userProductId` 主键且解绑事件丢失（例如在别的端解绑），表里可能残留旧 ID；
  已用 `forget`/`clear` 覆盖本端解绑与退出登录，且记录自身带的 ID 永远压过表值。
