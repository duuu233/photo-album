# 调试台「上传相册图片」改走真实投屏竖向链路 + 传输参数放开为输入框

> 状态：current
> 最后核对：2026-08-07
> 适用范围：小程序硬件联调调试台（`subpackages/device/debug`）
> 权威来源：[图片投屏流水线](../architecture/image-projection-pipeline.md)、`utils/dithering.js`、`utils/device-ble.js`

## Background

调试台的图传链路是 2026-07-22「设备帧改由第三方（seekink 抖动接口）生成」之前留下的：
选图后由**客户端自己**做缩放 + 六色量化（自定义调色板 / 对比度 / 饱和度 / 抖动开关，即页面上
「上传转换参数」那一大块），再把量化结果发给设备。真实投屏早已不这么干了——它把设备分辨率的图
交给第三方接口，拿回算好的六色 4bpp 二进制原样发给设备。两条链路长期不一致，调试台上看到的
颜色/方向/耗时都不能代表真实投屏。

同时设备侧 2026-08-07 完成一轮传输优化：收包缓冲扩到 50 包，单个 0x21 包的图片数据由 236 字节
放宽到 489 字节（配套 MTU 500）。调试台需要能直接调这几项做真机对照。

## Problem

1. 调试台「上传相册图片」与真实投屏投的**不是同一张图、也不是同一套算法**，联调结论不可迁移。
2. 「发包窗口」是 5/10 两个单选档，试不了设备新支持的 50 包；0x21 数据字节与 MTU 根本没有入口。
3. 「上传转换参数」整块（校准档 / 自定义六色 RGB / 色差算法 / 裁剪 / 缩放 / 预压缩 / 抖动 /
   对比度 / 饱和度 / 同步到真实投屏 / 恢复默认）已随第三方出帧作废——留着只会误导联调。

## Solution

### 1. 「上传相册图片」＝真实投屏的竖向链路

与投屏预览页 `coverCropOne` + 结果页 `fetchDitheringFrame` 逐步对齐：

```text
选图(sizeType=original，走 utils/media.chooseFromAlbum，与真实投屏同一个入口)
  → 竖向构图：按设备物理分辨率 aspectFill 中心裁切 + 按竖向导出角旋转 → 导出 jpg(q0.92)
  → 统一压缩：长边缩到设备长边（构图产物恰为设备分辨率 → 原样通过，不二次降质）
  → 第三方 seekink 抖动接口出六色 4bpp 帧（color=BWRYGB / imageDitheringModes=2 / type 按大小尺寸）
  → 铁闸校验：字节数 = 宽×高÷2，对不上一律不发
  → BLE 图传 0x20 → 0x21 → 0x22，传完顺手 0x24 刷屏
```

- **大/小尺寸按广播ID判**：`EF6-370` = 小尺寸 480×720（`type=1`）、`EF6-589` = 大尺寸 680×960
  （`type=0`），分辨率取自 `protocol.SCREEN_TYPES`，据此决定「压到哪个物理分辨率」和第三方
  `type` 参数。广播名认不出时回落 0x01 自报的 `screenType`；两者不一致时**以 0x01 为准并在控制台
  告警**——0x20 帧头宽高与帧字节数必须跟设备实际屏幕严格对齐，否则设备直接拒收。
- **竖向导出角**取 `deviceRotation.verticalDegreeFor(device)`。调试台不查后端设备记录，
  故落在缺省 0°（不旋转），与「后端没下发 `verticalRotation`」的真实设备表现一致。
- **不调设备管理 / 投屏记录接口**：`setUserProductUpload`、`editUserProductImgRecord` 一概不发，
  联调不会在真实环境留下投屏记录与图库图片。只调第三方出帧所必需的
  `/Client/Basic/getXTYUserToken` + 抖动接口（页面上本来就有单独的 Token 按钮）。
- 客户端不再做任何量化/调色：第三方给什么二进制就发什么。

「上传彩条测试图」与「上传本地 .raw/.bin 直发」两条路径不变。

### 2. 三项传输参数改为输入框，改完立即生效

| 参数 | 调试台默认 | 真实投屏 | 说明 |
| --- | --- | --- | --- |
| 发包窗口 | **50** 包 | 10 包（未同步时） | 设备侧收包缓冲扩到 50；`TRANSFER_WINDOW_MAX` 10 → 50，`DEFAULT_TRANSFER_WINDOW` 仍 10 |
| 0x21 数据字节 | **489** | 236 | 0x21 的 PAYLOAD = PKT_SEQ(2) + 数据，故 PAYLOAD 最大 491；按 `uploadImage` 的 `options.chunkSize` 逐次传入 |
| MTU | **500** | 247 | 489 + 8 字节整帧开销 = 497 = 500-3，正好卡满单次可写上限 |

- 改完输入框即生效，下一次图传就按新值走；MTU 点「应用 MTU」当场重协商（`renegotiateMtu`），
  安卓无需断开重连，iOS 不支持手动设置、只会把系统协商的实际值读回来。
- 每包数据会按当前 MTU 夹一次（`数据 ≤ MTU-11`），塞不下自动降到链路能承载的值并在控制台标红，
  绝不会写出「被静默丢弃」的大包。页面实时回显「当前实际每包 N 字节」。
- 这三项**只作用于调试台**。「同步投屏」按钮仍只同步连接间隔 / 发送速度 / 发包窗口三项
  （历史行为），0x21 数据字节与 MTU 不参与同步。

### 3. 删除「上传转换参数」整块

页面模块、样式，以及 `debug.js` 里配套的校准档常量、Lab/RGB 色差、Floyd 抖动、自定义六色输入、
按机保存/恢复、分阶段缩放与 `wx.compressImage` 预采样等约 900 行一并删除。
`imageCodec.setTransferQuantizeOptions / clearTransferQuantizeOptions` 的唯一调用方就是这块，
删除后真实投屏不受影响（`getTransferQuantizeOptions` 早已无人读取——帧来自第三方）。

## Technical Decisions

- **为什么不把新参数写进连接流程**：`establishConnection` 仍按 247 / ≤236 建会话，真实投屏读的是
  `session.dataChunk`。调试台把链路 MTU 顶到 500 后，`renegotiateMtu` 也只重算 ≤236 的
  `dataChunk`——即便会话被后续的真实投屏复用，它的分包大小也不会被调试台带跑。
- **大包只按调用传参生效**：`uploadImage` 不缓存 `chunkSize`，每次图传由调用方给；真实投屏不传，
  代码路径与改动前完全一致。
- **窗口上限抬到 50 而默认仍 10**：真实投屏没点过「同步投屏」时行为一字不变；抬上限只是让调试台
  和「同步投屏」这条既有的显式入口能写到设备新支持的值。
- **广播ID 与 0x01 冲突时以 0x01 为准**：广播名是外壳标识，帧头/帧长必须跟设备自报的屏幕走，
  否则必然被拒收；冲突在控制台标红提示核对机型。

## Risks

- 调试台图传耗时/成功率会与之前不可比：每包 489 字节 + 窗口 50 是新组合，若真机卡在某包，
  先把这两项调回 236 / 10 做对照，再看是不是链路问题。
- iOS 顶不到 MTU 500（系统协商），每包会被夹到 `MTU-11`，包数与安卓不同属正常。
- 调试台现在会真实调用第三方出帧接口（消耗 token/配额），但不写任何后端投屏记录。
