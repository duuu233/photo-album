# 虚拟支付 -15013：goodsPrice 价格错误与端上的金额自检

2026-09-18

## 现象

某些套餐拉起支付稳定失败，弹「支付失败(-15013)」：

| 金额 | 结果 |
| --- | --- |
| 1.00 元 | ✅ 成功 |
| 79.99 元 | ❌ -15013 |
| 298.99 元 | ✅ 成功 |

## -15013 是什么

官方文档（`wx.requestVirtualPayment` 页底部错误码表）写明：**`-15013 goodsPrice道具价格错误`** ——
签进 `signData` 的价格与微信虚拟支付后台该道具配置的价格对不上。

## 为什么偏偏是 79.99

`goodsPrice` 的单位是**分**，且必须是整数。元转分若用**截断**，IEEE754 双精度会在某些数上少 1 分：

```
 1.00 * 100 = 100                  → 截断 100    ✅
79.99 * 100 = 7998.999999999999    → 截断 7998   ❌ 比真实价少 1 分
298.99 * 100 = 29899.000000000004  → 截断 29899  ✅
```

三条线上数据与这个规律**完全吻合**。按同样规则，下列常见价位也会中招：
**19.99、69.99、79.99**；而 9.99 / 29.99 / 39.99 / 49.99 / 59.99 / 89.99 / 99.99 / 199.99 / 299.99 不会。
这可以直接用来验证：若 19.99、69.99 也失败而 29.99、89.99 正常，基本可以定案。

## 实锤（2026-09-18，线上失败订单的下单报文）

```json
{
  "orderId": 102,
  "orderNo": "2026091880466540002000223",
  "amount": 79.99,
  "signData": "{\"buyQuantity\":1,\"currencyType\":\"CNY\",\"env\":0,\"goodsPrice\":7998,\"offerId\":\"1450611724\",\"outTradeNo\":\"2026091880466540002000223\",\"productId\":\"xb2\"}",
  "paySig": "（略）",
  "signature": "（略）"
}
```

`amount = 79.99` 元，而签进去的 `goodsPrice = 7998` 分 —— **正好少 1 分**，与上面的推断一致。
其余字段都正常：`productId` 有值、`offerId` 有值、`env = 0`（正式）、`currencyType = CNY`、`buyQuantity = 1`、
`outTradeNo` 与 `orderNo` 一致。所以问题只有价格这一处。

## 谁该改

**客户端不产出 `goodsPrice`**：下单只发 `goodsId` + `payType`（`utils/token-api.js` 的 `addOrder`），
金额与签名全部由服务端算。修法在服务端。

### 错在哪

```java
// ❌ 会丢 1 分：79.99 * 100 在 double 下是 7998.999999999999
int cents = (int) (amount * 100);          // 或 Math.floor / intval / (int) 强转
```

### 怎么改（任选，按稳妥程度排序）

1. **最稳：价格全程用整数分**。商品表存 `price_cents`，下单、签名、对账都不碰浮点，
   只在展示时除以 100。这样以后不管谁写都不会再踩。
2. **用十进制类型**：
   ```java
   int cents = new BigDecimal(String.valueOf(amount))   // 注意用 String 构造，别用 double 构造
           .movePointRight(2)
           .setScale(0, RoundingMode.HALF_UP)
           .intValueExact();
   ```
   ```php
   $cents = (int) round($amount * 100);   // 或 bcmul((string)$amount, '100')
   ```
3. **至少改成四舍五入**：`Math.round(amount * 100)`。能解决当前这批，但金额位数变多时仍有理论风险。

⚠️ 改完要确认**签名是对新的 signData 重新算的**：goodsPrice 变了，`paySig` / `signature` 都得跟着变，
否则从 -15013 变成 -15005/-15006。

另一种成因是后台那个道具本身价格没配对（比如 `xb2` 在虚拟支付后台配的不是 79.99）。
两者用下面的日志一眼区分。

## 端上这轮加了什么

1. **金额自检**：`extractPayParams` 把我们平台订单的 `amount`（元）带出来，调起支付前与
   `signData.goodsPrice`（分）对账，不一致就 warn 并点名 -15013：

   ```
   [虚拟支付] ⚠️ 金额自检不一致：订单 79.99 元 → 应为 7999 分，但 signData.goodsPrice 签的是 7998 分（差 -1 分）。
   ```

   一致时也留一行「金额自检通过」，确认这条自检确实跑过。
2. **错误码表按官方文档补全**到 -15021（原来只收了有把握的 -15001~-15010），
   -15013 的提示直接写明「先看金额自检那行」。
3. **-15013 有了给用户看的话**：「商品价格有误，请联系客服」，不再甩裸错误码。

## 怎么定位是哪一边

复现一次失败支付，看控制台：

- 有「金额自检不一致」→ **服务端元转分截断**，把那行截图给后端；
- 显示「金额自检通过」却仍回 -15013 → 金额是对的，问题在**后台道具的价格配置**
  （或该道具压根没配这个价位）。

## 用例

`tests/virtual-pay-amount-guard.test.js`：锁住 amount 带出、少 1 分必须告警（含 7998/7999 两个数）、
金额一致不误报、298.99 不误报、-15013 有用户文案。全量 60 个用例通过。
