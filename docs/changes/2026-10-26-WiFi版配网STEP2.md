## 产品确认（2026-10-26）

- `mqtt_config` 的 host/port/usr/pwd 来源未定：**先留接口位、本次不下发**（`config.iotMqttConfig` 为 null 即跳过，设备沿用出厂配置）。
- 绑定 WiFi 设备的 deviceId：12 位 deviceNo 转 `AA:BB:CC:DD:EE:FF`，与蓝牙版同口径。
- BluFi **先不做加密协商**（与 EspBlufi 未协商时一致，WiFi 密码明文经蓝牙）；固件若强制加密，联调时再补 DH + AES。

## 改动

- `utils/blufi.js`：乐鑫 BluFi 协议。服务 `FFFF`，写 `FF01`、通知 `FF02`（只认 FFFF 服务下的特征，与蓝牙版 FF00 下同名特征互不干扰）；帧编码（序号逐帧递增、超长分片）、解帧（分片重组、带校验时按长度截取）、WiFi 状态报告与自定义 JSON 解析（协议表格的 `date` / 示例的 `data` 都认）、UTF-8 编解码（中文 WiFi 名）。会话：连接 → 找服务 / 特征 → 开通知 → 协商 MTU；串行写帧；`configureSta`（STA 模式 + 名称 + 密码）、`connectWifi`、`request(action)`（发 `{msgid, action, data}` 等 `${action}_ack`）。通知经 `ble-notify-hub` 登记（key `blufi`），不另挂 `wx.onBLE*`。
- `utils/wifi-provision.js`：配网四步。
  1. 手机网络：`wx.getNetworkType` 不是 none。
  2. 设备网络配置：BluFi 连设备 → 下发 WiFi；有 MQTT 配置时发 `mqtt_config` 并要求 `result=0`。
  3. 连接 WiFi：发「连接」，等设备 WiFi 状态报告（30s）：连上通过、明确失败停下；等不到报告放行，交给第 4 步裁决。通过后释放蓝牙。
  4. 连接云端：先老服务绑定（绑定前 IoT 在线接口 403），再带 `since`（本次配网开始时间）每 2s 轮询 `GET /api/device/online`，`online=true` 成功；503 / 403 / 网络失败继续轮询，60s 超时；401 停止。
  页面交接（设备 BLE 句柄、deviceNo、查到的产品、WiFi 名称 / 密码）放内存，**密码不进页面路由**。
- `utils/api.js` `bindWifiDevice`：老服务 `addUserProduct`，productId 用搜索时 `getProductByDevice` 查到的产品；先查已绑定列表，同一台已绑定就复用（重配网不重复绑定）；新绑定后回查列表补真实 `userProductId`。不弹 loading / 错误。
- WiFi 配置页：进页面读当前 WiFi（`getConnectedWifi`），2.4G 直接回填；没连或 5G 直接弹列表。列表：安卓 `getWifiList`，只留 2.4G（frequency < 3000MHz）、同名取信号强的、按信号排序；定位没开等失败给提示，可直接输入。iOS 拿不到附近列表，只列当前连接的那个并提示手动输入；拿不到频段时按可能是 2.4G 回填。去掉示例数据。
- 配网状态页：接 `wifi-provision.run`，执行中转圈、通过打勾、失败打叉 + 具体错误，「重新配网」整套重来、「取消」返回；成功「立即体验」把刚绑定的设备设为当前选中并回首页。配网期间保持亮屏；离开页面即取消并释放蓝牙。去掉演示节奏和 `?demo=fail`。
- `utils/config.js` 新增 `iotMqttConfig: null`。

## 同日追加：WiFi 配置页按文档收紧（真机反馈连着 5G 被回填）

- 原因：iOS 的 `getConnectedWifi` 不回频段，原逻辑在频段未知时也回填；另外安卓传了 `partialInfo: true`，该参数下只回 SSID / BSSID，同样拿不到频段。
- 现在**只有确认是 2.4G（2400~2500MHz，个别机型按 GHz 给也认）才回填**；没连、5G、频段判不了一律直接弹列表。去掉 `partialInfo`。
- iOS 列表：先放当前连接的网络（标「当前连接」，点一下回填）；附近列表要跳系统设置才能取，给「获取附近WiFi（将跳转系统设置）」入口由用户自己点，取回的列表不带频段、无法筛 2.4G，原样列出；选了频段未知的网络，名称框下提示「请确认是2.4G网络」。

### 文档要求里做不到的部分（微信能力限制）

| 文档要求 | 安卓 | iOS |

## 同日追加：设备 WiFi 列表的字段与频段过滤

- 乐鑫标准 BluFi 的 WiFi 列表（数据帧 0x11）每条只有 `len(1) | rssi(1) | ssid(len-1)`：**只有 SSID 和 RSSI，没有信道 / 频率**，按协议本身做不了频段过滤。ESP32 绝大多数型号只支持 2.4G，扫到的本来就是 2.4G；若用的是双频芯片（如 ESP32-C5），需要固件在列表里追加信道，或改用自定义数据（0x13 JSON）回传，前端再按信道过滤。
- 联调查看：开发版 / 体验版的 WiFi 列表页不去重、隐藏网络也列，每个 WiFi 下打出 SSID、RSSI（dBm 与格数）、信道 / 频率（标准格式下显示「未返回」）、长度字节和这一条的原始字节；列表上方给整包原始字节与解析不了的残尾。正式版不显示、照常去重。控制台 `[BluFi] 设备扫描到 WiFi` 同时打整包。

## 同日追加：按真机日志接本设备的列表格式，只留 2.4G，边收边显示

真机日志（`[BluFi] 自定义数据`）表明本设备**不走乐鑫标准 0x11**，而是用自定义数据（0x13）回文本，每行一条：
`ssid:<名称>,rssi:<dBm>,ch:<信道>`，名称可为空（隐藏网络）、可带中文；信道里有 36/40/44/48/56/157 等，说明是双频芯片、扫得到 5G。
此前只等 0x11，所以列表一直出不来。

- `blufi.parseCustomWifiList`：按行解析（名称可能带逗号，从行尾认 rssi / ch），附 `frequency`（信道换算中心频率）；自定义数据里认出 WiFi 行就按 WiFi 列表发出。标准 0x11 照旧支持。
- 频段：**信道 1~14 为 2.4G、36 起为 5G**，国内外通用（各国只是可用信道不同，12/13 国内可用、14 仅日本，都属 2.4G；6GHz WiFi 6E 也从 1 编号，但本设备芯片不支持 6G，不会混淆）。列表只留 2.4G；设备没回信道（标准格式）时无从判断，照常列出。
- 边收边显示：`scanWifi(timeout, onBatch)` 每到一批回调一次，页面立即刷新；最后一批后再等 5 秒没有新的才结束转圈（反馈原先 5~6 秒就收掉了），总上限 60 秒。
- 已收到列表后，设备再报错只记日志、蓝牙断开则直接用已收到的结束——不让设备收尾时的一条报错把列表作废；一条都没收到时报错 / 断开仍立即提示。
- 联调查看：统计里加「过滤掉 5G N 条」，每条显示信道与换算的频率；联调日志记录每一批、断开。

## 同日再调整：第 4 步改为先在线、后绑定

真机日志里第 4 步「在线查询 #1 失败：code 503，接口(IoT)-服务暂时不可用」。产品要求改顺序：**IoT【在线状态】查询成功（online=true）之后，再调老服务绑定**（原为先绑定、后轮询）。

- `wifiProvision.run` 第 4 步：带 `since` 每 2 秒轮询在线，503 / 403 / 网络失败继续、401 停止、60 秒没上线判联网超时（不绑定）；上线后调 `api.bindWifiDevice`（查已绑 / 绑定 / 回查），绑定成功才算配网成功，绑定失败停在第 4 步。
- ⚠️ 与接口文档 2.4 的推荐顺序相反：文档写在线接口会调老服务 `checkPermission`，设备还没绑到当前账号时返回 403。若后端仍是这个口径，新顺序下会一直 403 到超时——需后端确认在线接口对未绑定设备的返回（或提供文档里提到的免权限配网状态接口）。日志里每次查询的返回都看得到。
- 测试：`tests/wifi-provision.test.js` 断言调用顺序为 online → bind、没上线不绑定、登录失效不绑定。
