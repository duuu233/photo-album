## 1. OTA 后「指令失效 / 设备连不上」第三轮：复位链路自身的三处险情

现场反馈升级页已提示「升级成功」，设备却连不上、与设备的交互和指令失效——**硬复位（08-13 第一轮）
落地后仍复现**。全链路重查（device-ble / ota-ble / bluetooth / active-device / ota.js 五个文件逐行），
主链的时序与判据本身是对的；问题收敛到**复位机制自己**的三处险情，全部特征都与「重进小程序就好」吻合
（都是进程内状态，重启即清零）：

### 1.1 监听重挂赌了 wx.offBLE* 的语义（主嫌疑，正好产生本病）

复位后两个模块各自「`off(自己的引用)` 再 `on`」重挂通知监听。这套写法把宝押在两个**没有跨机型保证**
的行为上：`wx.onBLE*` 处处是累加注册；`wx.offBLE*(fn)` 处处能按引用精确移除。真机上任何一条不成立，
产生的恰是本轮要治的症状本身：

| 机型实际语义 | 复位后的结局 | 表现 |
| --- | --- | --- |
| off(fn) 实为「移除全部」 | 后重挂的 ota-ble 把先重挂的 device-ble 那份也清了 | FF00 通知没人收：**连接建得起来、0x01 永远应答超时** → 重扫→再连→再超时 → 「连不上/指令失效」，直到重启小程序 |
| on 是「替换」语义 | 只剩最后注册的模块能收到通知 | 同上 |
| off(fn) 没移除成功 + on 累加 | 每帧派发两遍，解帧缓冲灌两份 | 全部指令超时，同上 |

**改法：wx 层收口成一个分发器**（新增 `utils/ble-notify-hub.js`）。两个模块把处理函数按 key
（`device-ble` / `ota-ble`）挂到 hub 名下；wx 层只注册 hub 的 `dispatchValue`/`dispatchState`
（引用永远稳定）。复位后的重挂变成「**off 不带参数**（各基础库口径一致的“移除全部”）→ 重新 on
这一个分发器」——上面三种机型差异下，结局都是**恰好一份**注册。off 接口不可用的老基础库维持原状不动
（与旧回退一致）。

⚠️ 由此产生一条新约定：**全项目不许再直接调 `wx.onBLECharacteristicValueChange` /
`wx.onBLEConnectionStateChange`**（off 不带参数会把 wx 层同名监听全部移除），新增监听必须经
`ble-notify-hub.subscribe` 登记。当前全项目仅 device-ble/ota-ble 两处注册点，均已迁入。

### 1.2 中断收尾的两次硬复位会撞上用户的新连接（可证伪的时序漏洞）

升级中途退出页面时有**两条**收尾路径：`onUnload` 立即 fire-and-forget 一次
`resetAfterUpgrade`；同时 `_abortUpgrade` 置位，传输循环在**下一个窗口间隙**才检查到中断、抛
`OTA_ABORTED`，`upgradeFirmware` 的 catch 再收尾一次。第二次可能晚**几秒到二十秒**
（`shouldAbort` 不在 await 中途生效：END 应答等待最长 20s）——此刻用户往往已经回详情页点了连接，
第二刀 `closeBluetoothAdapter` 正好把用户刚建的连接连适配器一起拆掉；若砍在
`createBLEConnection 成功 → 会话落账` 之间，还会制造一条账本外的无主连接（设备被占住不广播，
又回到「只有重进小程序才好」）。

**改法两道**（都在 `device-ble.resetBluetoothStack`）：
- **单飞（single-flight）**：在途复位期间的并发复位请求合并成同一次落地，等同一个 Promise；
- **忙判定**：`device-ble`/`ota-ble` 任一侧还有就绪会话、或存在**新鲜**（<30s）在途连接时，
  复位**整个拒绝执行**（连账本都不动）——宁可这一轮没修到，也不能把用户正用着的连接拆了。
  OTA 收尾的正常调用不受影响：`resetAfterUpgrade` 先断链清账，走到复位时账面必然是空的。

### 1.3 在途连接 Promise 在复位后成为「毒药引用」

`connecting[deviceId]`（并发 ensureConnection 合并用的在途连接 Promise）复位时**不清**：
复位后对同一台设备的所有 `ensureConnection` 都会 await 一条永远不会落地的旧连接，表现同样是
「这台设备再也连不上，直到重启小程序」。iOS 的 BLE deviceId 是稳定 UUID、安卓是 MAC，复位前后
**键不变**，必然命中。两处修：

- 复位时丢掉全部 `connecting` 引用（走到这一步已确认只剩陈旧条目）；
- `ensureConnection` 的 finally 由无条件 `delete` 改为**只清自己那一条**（`connecting[id] === promise`
  才删）——否则被复位丢掉后又被新调用方占位的条目，会被旧连接的收尾误删。

### 1.4 顺带：复位重开后确认适配器真的可用了再返回

`openBluetoothAdapter` 的 success 只代表调用被受理，安卓上底层可能还在收尾；状态没就绪就去扫描，
第一轮 `startBluetoothDevicesDiscovery` 会静默扫不到任何设备（12s 窗口白走）。复位末尾补
`getBluetoothAdapterState` 轮询（3 次 × 300ms，best-effort），不就绪只记日志——08-13 第一轮
风险清单里「600ms 是第一个该调的旋钮」，这一手比盲调数值更对症。

### 真机验证怎么区分三种失败（给下轮真机排查用）

- 复位后首次连接**建立成功但 0x01 超时** → 1.1 的监听问题（本轮应已根治；若仍出现，看日志有没有
  `[设备连接] 蓝牙栈硬复位` 之后紧跟的 `RX` 帧——一条 RX 都没有＝通知真的丢了，两条一样的＝派发两遍）；
- 升级中断后回详情页连接，**连上又莫名断开/蓝牙报未开启** → 1.2 的第二刀（本轮应已消除；日志找
  `跳过蓝牙栈硬复位（有正在使用/建立中的连接）`，出现＝防线生效）；
- 复位后对同一台设备的连接**没有任何底层报错、直接无响应** → 1.3 的毒药引用（本轮应已消除）。

## 2. 微信登录「隔日首次必失败、重试即成功」——是前端问题，已按方案 2（登录页预取 code）修复

**结论：前端的调用顺序踩了微信官方文档明写的坑，后端不用排查**（后端日志里对应请求应是
`wxEncrypData` **解密失败**，可顺手确认）。

### 根因

一键登录走的是旧版手机号授权（`encryptedData + iv`，`app.js loginWithWechatPhone`）：

```js
async loginWithWechatPhone(detail = {}) {
  const loginRes = await wxLogin()        // ← 授权回调之后才 wx.login
  const profile = await api.setWechatAppLogin({
    code: loginRes.code,
    wxEncrypData: detail.encryptedData,   // ← 用「授权那一刻的 session_key」加密
    wxIvData: detail.iv
  })
  ...
}
```

`encryptedData` 由微信用**按钮授权那一刻**端上的 `session_key` 加密；而 `wx.login` 可能刷新
`session_key`，后端拿新 code 换到的是**新 key**，解不开旧密文。这正是 `getPhoneNumber` 文档里
明写的警告：*在回调中调用 wx.login，服务器用 code 换取的 sessionKey 可能不是加密时使用的
sessionKey，导致解密失败；建议提前 login*。

「隔日必现、同日不复现、重试即成功」由 `session_key` 的**最短刷新周期**机制精确解释
（官方：短时间内多次调用 wx.login 并非每次都刷新）：

| 场景 | 授权时的 key | wx.login 后 | 结果 |
| --- | --- | --- | --- |
| 当天刚登录过，再次登录 | 今天的 key | 处于最短刷新周期内，**不刷新** | 两边同 key，解密成功 |
| **隔了一天**首次点登录 | 昨天的旧 key | 超出刷新周期，**刷新成新 key** | 后端拿新 key 解旧密文 → **必失败** |
| 紧接着第二次点登录 | 刚刷新的新 key | 又落在刷新周期内，不刷新 | 两边同 key，成功 —— 「再点一次就好」 |

退出登录只是让用户「不得不重新走登录」而已，与 token/请求头无关（`setWechatAppLogin` 本就
`auth:false`，登出也已清空缓存），任何 ≥1 天间隔后的首次授权登录都会命中。

### 修复：方案 2「登录页预取 code」（2026-08-13 当日拍板并实施）

> 备选的方案 1（切新版手机号快速验证 `detail.code`，全程不涉及 session_key）更彻底，但需后端在
> `setWechatAppLogin` 增收参数；本轮按纯前端的方案 2 落地，后端零改动。

- `app.prefetchLoginCode()`：`wx.login` 预取一枚 code 存 `_prefetchedLoginCode`（`{code, fetchedAt}`）。
  关键不在 code 本身，而在**这次 login 把 session_key 刷新到位**——之后的授权密文用的就是新 key，
  预取的 code 与它必然配对。
- `app.consumePrefetchedLoginCode()`：取出并作废（**单次使用**，无论提交成败）；超过 **4 分钟**
  （官方 5 分钟有效期留 1 分钟余量）判超龄返回空——临期 code 上送，网络一慢就是「code 已过期」的新失败。
- `loginWithWechatPhone`：优先用预取 code；缺失/超龄/已消费时回退**现取**——此时本页刚 login 过，
  key 落在最短刷新周期内不会再变，现取的 code 与密文仍是同一把 key（这正是「重试即成功」的机理，
  兜底沿用它，最坏也只是回到旧行为）。⚠️ 用了预取 code 就不再补调 `wx.login`：没有收益，
  反而可能提前刷掉下一次授权要用的 key。
- 登录页两处调用：`onShow`（未登录时；从协议/隐私页返回也顺带换新鲜的）与**提交失败的 catch**
  （失败已消费掉旧 code，立刻补一枚，用户马上重试才用得上配对的那份）。
- 时序边界：用户点授权到确认弹窗要一两秒，`onShow` 的预取在那之前早已落地；极端情况下预取未返回
  就交卷，走的也是现取兜底，不比旧行为差。
- 由 `tests/login-code-prefetch.test.js` 锁住四件事：预取命中时用预取 code 且**不再现取**、
  code 单次使用不复用、超龄回退现取、预取失败不阻断登录。

## 3. 固件升级页：去掉返回箭头 + 进度条下方加两条升级规则

### 3.1 去掉返回箭头

`page-nav` 传 `show-back="{{false}}"`（默认是 `true`，不传就还有箭头）。升级不可逆、中断有代价，
页面里不留「随手点一下就走」的入口。

⚠️ **去掉的只是顶部箭头，底部「返回」按钮保留**——否则升级成功后用户在页面上找不到任何出口，
就从「防误触」变成「把人困住」。两处口径合起来是：

| 画面 | 顶部箭头 | 底部按钮区 |
| --- | --- | --- |
| 检查版本 / 发现新版本 / 已是最新 / 成功 / 失败 | 无（本轮去掉） | 有（主按钮按情况 + **返回**） |
| **进行中**（准备升级 / 连接设备中 / 传输中） | 无 | 无（`wx:if="{{screenStatus !== 'progress'}}"`，本来就不画） |

也就是说升级途中页面上确实没有任何返回入口了 —— 这正是需求要的。走系统手势/安卓返回键仍走得掉，
但那条路上还有 `enableAlertBeforeUnload`「退出将中断本次升级」的二次确认拦一道（既有逻辑，未改）。
标题不会因此偏移：`page-nav` 在 `showBack:false` 时渲染等宽占位块，且 `.nav-title` 是左右对称
绝对定位的。

### 3.2 两条升级规则

挂在百分比进度条（与 `progressText`）下方，**只在进行中这一屏出现**：其余画面挂着它只会跟结论
文案抢注意力——「已是最新版本」下面写「意外中断可能导致设备无法使用」是没有意义的。

```
1）升级过程请耐心等待升级结果，意外中断可能导致电子纸设备无法使用
2）若升级失败造成设备无法连接，请尝试重新进入小程序\app或断电重启设备
```

文案逐字按需求写死在 wxml（与设备/接口无关的固定告知，不走 `data`，免得被状态刷新覆盖）。
⚠️ 第 2 条里的 `小程序\app` 是需求原文的写法（反斜杠），未擅自改成 `/`。

版式两点：
- 整块**左对齐**（页面其余部分是居中的）：两条长句居中后每行断点参差、像散文，而序号
  「1）2）」必须对齐同一条左边界才读得进去；
- 这一屏没有底部按钮区，所以规则块自己 `padding-bottom: calc(24rpx + var(--safe-bottom))`
  让开安全区，否则全面屏上末行压在手势条上。

`tests/ota-screen-rules.test.js` 按结构锁住：`show-back="{{false}}"`、两条文案逐字、排在进度条
**之后**且在 `progress` block **之内**、底部「返回」按钮仍在。
