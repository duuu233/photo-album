## 需求（产品原话，三条）

1. 官方图库 → 选择图片 → 点击投屏 → 选择设备点「连接并开始投屏」，这个连接有问题，**进入预览页后还是提示未连接**；
2. 下载超时提示修改，**小程序尽量不要用英文，改中文就行**；

## 1. 「连接并投屏」其实没连

**根因**：弹层里的设备来自 `api.getDevices()`，后端记录**不带本机 BLE 句柄**——`normalizeDevice` 的 `deviceId`
只取 `bleDeviceId/wxDeviceId/bluetoothDeviceId/bleId`，后端不下发，连过这台设备才有。官方图库与 AI 对话的
`startProjection` 把这份记录原样写进 `pendingProjection`、自己「不碰 BLE」，指望预览页 `onLoad` 的后台预热去连。
预热没连完（扫描要几秒）、或静默失败时，预览页「开始投屏」的前置校验 `!device.deviceId` 就报
「电子纸设备未连接，请重新绑定后再投屏」——用户明明刚按过「连接并投屏」，而「重新绑定」也不是解法。

「我的相册」「投屏管理」的再次投屏一直是先 `ensureConnectedForAction` 再写 `pendingProjection` 的，只有这两处漏了。

**改法**：

- 官方图库 `detail.js` / AI 对话 `chat.js` 的 `startProjection`：已有活动会话就直接认领（低电量照旧提醒一次）；
  没有就 `ensureConnectedForAction`（「连接电子纸设备中」loading、连不上如实提示原因、低电量提醒）。连上后用
  `applyConnectedIdentity` 生成带句柄的设备写进 `pendingProjection`；连不上停在本页、按钮复位，不下载不跳转。
- 预览页兜底：`onLoad` 的预热留一个 `_warmup`；「开始投屏」时仍无句柄，先等预热（带 loading），还没有就当场
  `ensureConnectedForAction` 连一次（`ensureDeviceHandle`）。首页 / 设备列表 / 设备详情等入口也可能带着没句柄的
  记录进来，这一处兜住所有入口。

## 2. 下载失败的英文原文

`wx.downloadFile` 失败只给一句 errMsg（`downloadFile:fail timeout` 等）。这几处原来原样抛给用户：

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 官方图库投屏下载图片 | toast `downloadFile:fail timeout` | 「图片下载超时，请检查网络后重试」 |
| 结果页取原图（`downloadFileWithRetry`） | 失败页显示 errMsg | 「原图下载超时，请检查网络后重试」；是否重试仍按原文判断（`rawErrMsg`） |
| 固件包下载（`ota-ble.downloadFirmware`） | 升级页显示 errMsg | 「固件包下载超时，请检查网络后重试」；原文进 OTA 日志 |
| AI 对话下载/投屏 | 已是中文 | 改用同一个 `utils/download-error.js`，超时文案统一成「…请检查网络后重试」 |

合法域名没配单独一句「XX 域名未配置（小程序后台 downloadFile 合法域名）」（配置问题别说成网络问题）。
结果页 `classifyFailureMessage` 另加兜底：其它 `xxx:fail …` 英文原文（如上传超时）显示「网络超时/网络连接失败，
请检查网络后重试」，原文仍在 console 的「原始错误」里。

## 3. 一键清空：设备早清完了，端上还在等应答

**根因**：0x12 删除全部是设备**全删完才回一次**应答。为了不在删几十张时误报超时，`deviceBle.deleteImage` 的等待
预算按张数给（每张 2s、下限 6s、封顶 180s）；这份预算期间端上**只等这一条应答**。应答迟到或丢了（屏幕刷新期间
链路抖一下就可能），转圈就要转满预算——几十张就是一两分钟，之后还要再走一轮「失败回读」。设备那边早已刷出默认图。

**改法**（`utils/clear-watch.js`）：发出 0x12 后 5 秒起、每 3 秒读一次 0x01（`readTransferInfo`，只发 0x01）：

- 掩码清空 → 立刻按成功收尾，`deviceBle.cancelPending(deviceId, 0x12)` 收回那条还在等的应答（新增函数；
  不收回的话它会一直占着 0x12 直到超时，期间再删图会被拒成「正在等待应答」）；
- 读不到（设备正忙回 0x0B / 应答超时）或还有剩余 → 下一拍再看；
- 0x12 自己先回来（成功或失败）→ 以它为准，失败照旧走原来的「越界放行 / 回读核对」。

协议依据：设备处理指令期间收到新指令回 0x0B「设备繁忙」（规格书 v1.5 §6.6.1）；应答按命令字分别配对，
0x01 与在途的 0x12 互不干扰。删得快（5 秒内回应答）时一次都不回读，行为与原来相同。「删除设备」走同一个
`confirmClearCopies`，一并生效。
