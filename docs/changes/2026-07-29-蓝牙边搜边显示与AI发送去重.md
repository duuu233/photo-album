## Problem

### 1. 蓝牙搜索经常搜不全（7 台实测）

两个客观条件叠在一起：

- 设备广播 ID **每 3s 才发一次**；
- 多台设备同时在场时还要抢同一条广播信道。

12s 窗口下每台设备只有几次现身机会，7 台同时测经常少 1~2 台。

但**单方面拉长窗口不可行**：旧交互下设备列表挂在 `!scanning && devices.length` 上，
即使 `onUpdate` 已经把设备增量塞进 `devices`，用户也要干等满整个窗口才看得到**任何**一台。
窗口越长，干等越久——这也是这次「窗口」和「交互」必须一起改的原因。

### 2. AI 加载中气泡占满屏宽

AI 气泡按需求是铺满屏宽的。但「等待回复」的占位气泡里只有三个跳动的点，
铺满就变成一个占满整行的空白大框，看着像出错或空回复。

### 3. AI 首次发送能连点重复发出去

`sending` 要等 `sendChat` 内真正发出请求那一刻（追加 loading 气泡时）才置起，
而在它之前还隔着「AI 服务协议确认 + 建会话」最多两次网络往返。
**首次进入 AI 在空态发第一条消息**时这段空窗最长（必须先 `POST /session/new`），
期间发送按钮仍是亮的、guard 里 `sending` 仍是 false，用户连点就能把同一条消息发出去好几遍。

`createSession` 的在途去重（`_createReq`）只去重了「建会话」，没去重「发送」，挡不住这个。

### 4. 设备详情页看不到物理分辨率

用户需要在「设备ID」后面看到屏幕物理分辨率（如 `680*960`）。

## Solution

### 1. 边搜边显示 + 窗口拉长到 20s

- `SCAN_TIMEOUT_MS = 20000`：按 3s 广播间隔算，每台设备约 6~7 次现身机会。
- 列表门控从 `!scanning && devices.length` 改为 `devices.length`：搜到一个显示一个。
  搜索期间雷达 gif **继续转**，下面的列表同步追加——这就是需求里的理想效果。
- `applyScanResult` 按**首次被搜到的先后**钉死展示顺序（`scanOrder` 序号表，新设备追加到末尾）。
  这一步是必须的：`bluetooth.subscriberList` 回吐的是**按 RSSI 降序**的列表，边搜边渲染时
  信号一抖动整列表就重排，行与行来回跳，用户指头底下那台可能在按下的瞬间换成了别台（误绑）。
- `stopScanForBind()` 立刻停扫但**保留已搜到的列表**，两个入口：
  ① 用户点台数同行的「结束搜索」文字链；② 搜索还没结束就点「立即绑定」。
  `scanSeq` 自增让在途扫描结果不再回写列表（在途 `discoverDevices` 仍会在自己 timeout 到点后
  resolve，但那时 seq 已对不上，直接丢弃）。
- 搜索中隐藏「重新搜索」按钮（列表正在自己长，重搜只会把已搜到的清光重来），
  已有结果时标题统一为小号灰色「已找到 N 台」；搜索中同行追加橙色「，结束搜索」，
  扫描结束后右侧恢复重新搜索图标。
- **点绑定要等停扫落地**：`confirmBind` 新增 `await bluetooth.whenScanStopped()`。
  扫描与连接抢同一路射频，弱信号下这是连不上的主因之一。旧交互下不需要这一步（点绑定时扫描早停了），
  「边搜边显示」后用户绝大多数时候是在扫描中点绑定的。
  连带把 `binding` 改成在这个 await **之前**同步置起，别给连点留空窗。

### 2. 加载气泡按内容收缩

`.bubble--ai.bubble--loading { width: auto; max-width: 520rpx; }`——只在 `item.loading` 时挂这个类，
内容一到（`content`/`images` 上屏、`loading` 转 false）就回到铺满的正常 AI 气泡。

### 3. 发送入口加同步闸 `submitting`

`guardedSend(task)`：在**任何 await 之前**同步 `setData({ submitting: true })`，
finally 归位。WXML 里 `submitting` 与 `sending` 一起决定按钮灰不灰。

覆盖全部三条发送路径：`onSendTap`（发送按钮）、`onStyleTap`（一键生图，也要先建会话）、
`sendVoiceText`（语音松手；被闸挡下时按原约定把文字**回填输入框**，别让用户白说一遍）。
`beginVoice` 与 `startNewSession` 也一起挡 `submitting`。

`onSendTap` 内 `await this.sendChat(...)`（原来不 await）：让 `submitting` 一直持有到请求真正发出、
`sending` 接棒，中间不留空窗。

### 4. 详情页分辨率行

`resolutionText(device)`：`SCREEN_TYPES[device.screenType]` 查表 → 后端记录的 `width`/`height` → `--`。

与设备ID/内存不同，分辨率是**产品静态属性**而非实时数据，所以**不跟随连接状态置 `--`**：
未连接时后端记录里的宽高一样准，硬要置 `--` 只会让常态未连接的设备永远看不到分辨率。
（断开分支里照常刷新而不置 `--`，见 `detail.js` 注释。）

## 2026-07-30 信号展示口径补充

- 小程序搜索列表的 RSSI 只在**展示层**保守下调一级：`极强 → 强`、`强 → 正常`、
  `正常 → 偏弱`、`偏弱/弱 → 弱`。
- 原始 RSSI、弱信号等待门槛、停扫沉淀及连接重试策略均不改变，避免为了改文案误伤实际连接能力。
- Flutter 同步使用完全相同的边界与降档规则，双端文案不再出现口径差异。
