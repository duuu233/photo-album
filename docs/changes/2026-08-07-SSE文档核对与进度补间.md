## 一、先说结论：协议本身没变

把「-改」版与上一版（`assets/BoltStar-流式版接入文档 (1).md`，已删）逐条对完：
**地址、请求体、事件类型、字段名、事件顺序一律未变**，`tests/ai-stream-doc-conformance.test.js`
里照抄的报文一条都不用改（只把示例中的 `44` 跟着改成 `45`）。所以 `utils/ai-api.js`
的解析层这次一行没动。

真正的差异只有四处：

| # | 差异 | 处理 |
| --- | --- | --- |
| 1 | 请求体新增可选 `model_type`（`lite`/`pro`，**不传即 `pro`**） | `buildChatPayload` 支持透传，页面暂不开放选档 → 请求体与改动前逐字相同 |
| 2 | §三 明确「**后端只发里程碑，前端负责平滑动画**」，给了每 80ms 走 1~3 的补间实现 | 照做，见下 |
| 3 | §四 把 `85 downloading` 的文案从 80~90 那一档里拆了出来（「正在下载图片…」） | 文案表改成认 `stage`，见下 |
| 4 | §五 写明 `pre_text` 约 **15s** 才到（纯文字约 10s），此前无明确数字 | 只影响注释；等待期本来就有自定义 loading |

顺带纠正一处**此前理解错了**的地方：`image` 事件排在 `progress 90 (uploaded)`
**之后**，不是 50%。50 那一级（`partial_succeeded`）只是「初稿完成」，图还没下载上传完、URL
拿不到。两版文档的完整事件流示例都是这么写的，是代码注释一直写着「图约 50% 就推过来了」。
这不影响行为（真图本来就压到 100% 才换上去），但会误导下一个人去猜「占位盒为什么挂那么久」。

## 二、进度补间（本次主要改动）

后端只推 `5 / 15 / 30 / 45 / 50 / 80 / 85 / 90 / 100` 这几级。占位盒正中间摆的是一个
**数字**，数字没法像进度条宽度那样靠 CSS 过渡抹平 —— 直接贴上去就是 45 → 50 → 80 地跳。
设计稿 `assets/demo.png` 上那个 **47%** 根本不在里程碑里，本身就说明中间读数要前端补。

实现（`subpackages/ai/chat/chat.js`）：

```
applyProgress(index, value, stage)   收到里程碑 → 只记 target（只增不减），叫醒 pumpProgress
pumpProgress()                       每 80ms 一步：离目标 >20 时一步 3，近了一步 1
showProgress(index, value)           把补出来的读数上屏；到 100 时收起占位盒换真图
```

三条不变量，用例锁在 `tests/ai-stream-render.test.js`：

- **只补到服务端给的目标值，绝不自己往前跑** —— 宁可停在 45% 等下一条，也不能爬到 99% 再倒回去；
- **只增不减** —— 迟到/乱序的小 `progress` 连同它的 `stage` 一起丢弃；
- **读数爬到 100 的那一刻**才把占位盒换成真图（不是收到 `progress:100` 那一刻，否则会出现
  「占位盒消失时数字还停在 92%」）。流被中断或服务端漏推 100 时，`settleStream` 直接落到 100 兜底。

## 三、进度文案改成认 `stage`

旧实现按数值分档，有两处对不上文档 §四：

- `progress=5` 有 `starting` 和 `request_sent` 两种 `stage`，**光看数值分不开**；
- `85 downloading`（「正在下载图片…」）被并进了 `80 completed`（「正在优化细节…」）那一档。

改成 `STAGE_LABELS` 优先、数值分档兜底（纯文字流、老服务端、以及补间途中的中间值都没有
`stage`）。两张表的边界对齐，所以「45→50 爬到一半」和「刚好落在 50」不会给出矛盾的两句话。
文案跟着**已上屏的读数**走，爬到目标那一刻才用目标的 `stage` —— 否则会出现「52% + 正在优化细节…」。

设计稿上那行灰字是固定的「正在生成图片」，本次按需求方确认**保留分档文案**（信息量更大）；
`pre_text` 的橙底胶囊同样保留（demo 图整体配色不是本项目的橙色系，按通用交互示意图看待）。

## 四、一键生图点下去要立刻上屏

`sendChat` 原本是「先 `await createSession()`（`POST /session/new`，真机约 1s）→ 再把用户气泡上屏」。
空态下点风格按钮，界面得干等一整趟网络往返才有反应，像是没点着。

改成 **气泡先上屏、再建会话**；建会话失败就把刚上屏的气泡和会话标题一起撤回去，
界面回到点击前的样子（错误提示仍由 `createSession` 内部弹，用户重点一次即可）。

⚠️ 这次顺序反转带出一个连带坑，已一并修掉：`_doCreateSession` 原本无条件
`sessionTitle: session.title || '新对话'`。新建会话后端一律回占位的「新对话」，而这时页面上
标题**可能已经**被 `sendChat` 同步成首条用户消息了，照写就会把它盖回「新对话」。现在只有
后端给了真标题、或本地还是占位时才覆盖。

`onSendTap`（输入框发送）**保持原样**：它多走一趟建会话是为了护住草稿 —— 它有输入框要清，
而 `sendChat` 的回滚只撤得掉气泡、撤不回已经清掉的草稿。

用例：`tests/ai-send-instant-bubble.test.js`（扣住在途的 `/session/new`，断言此刻气泡已在
`messages` 里；再验失败回滚）。

## 五、第二轮：服务端下发文案 + 气泡内三项排版（同日追加）

### 5.1 进度文案改由服务端下发

服务端在 `progress` 事件上加了 `message`：

```json
{"type":"progress","progress":35,"stage":"generating","message":"正在创作图片"}
```

前端改成 **`message` 优先、老映射兜底**（`if (message) 用它; else 走 STAGE_LABELS; else 按数值分档`）。
不接也能跑，只是文案还走老逻辑。**两级兜底一个都别删** —— `pre_text` / `done` 这两处本来就没有
`message`，老部署也没有，删了占位盒里会空着一行。空串和纯空格按「没给」处理，同理。

文案的归属自此在后端：改文案不用发版。上面 §三 那张本地表退居兜底，不再是唯一事实源。

### 5.2 `pre_text` 现在会推两条

先秒回一句占位的「星宝努力思考创作中」顶掉空等，约 3s 后 LLM 出结果，再推真正的
「正在为您绘制…」。前端直接覆盖即可，不用分辨是哪一条 —— 所以代码里**没有**「只写第一次」
的判断，别加。

只有贴底策略分了一下：第一条是凭空多出一块内容，强制贴底；第二条只是就地换字，
这时候再硬拽用户回底部，正在上翻看历史的人会被打断。

（顺带：`ai-api.js` 里「`pre_text` 约 15s 才到」的注释已作废 —— 那是加占位文案之前的事。）

### 5.3 气泡内排版三项

| # | 问题 | 改法 |
| --- | --- | --- |
| 1 | 进度文案在占位盒**外**上方 | 移进盒内、压在百分比正下方（半透明白字），盒外不再留字 |
| 2 | 回复正文在图片**上方**，图从下面顶出来 | 正文改到图片**下方** —— SSE 里 `text` 本来就排在 `image` 之后，这样才对得上 |
| 3 | 正文顶部平白空一行 | `<text>` 组件内的空白**会原样渲染**，`{{item.content}}` 原本是换行 + 缩进写的，等于给正文顶部加了个空行。改成紧贴标签写 |

第 3 条是那种「看一百遍代码也看不出来」的坑：WXML 里给 `<view>` 换行缩进无害，给 `<text>`
换行缩进就是实打实的空白节点。本文件里其它 `<text>` 若要塞插值，同样必须紧贴标签。

### 5.4 图下面那段文案「没有打字机效果」

打字机一直在，是**太快了**看不出来。`STREAM_TYPE_TICKS` 从 60（≈1s）放慢到 180（≈2.9s）。

病灶：服务端的 `text` 事件往往连着涌进来（尤其响应体一次性到达、靠 `unescapeEventSeparators`
兜底解析的那条路，所有事件在**同一帧**解析完），积压瞬间就是全文。每帧字数
`ceil(积压 / 60)` 压在 1 秒内打完 —— 100 字就是每帧 2 字、0.8 秒冲完，肉眼基本看不出在打字。
放慢后：100 字积压 → 1 字/帧 ≈ 1.6s；1000 字积压 → 6 字/帧 ≈ 2.7s（长回复照样不拖尾）。
非流式那条老路是 `TYPE_MAX_TICKS=420`(≈6.7s)，改完两条路观感也接近了。

### 5.5 100% 之后补推的 progress 会把占位盒翻出来

读数走到 100 时占位盒已收起、真图已上屏，这时服务端若再补推一条 `progress`（重复/迟到的都可能），
`markStreamStarted(index, true)` 会把 `streaming` 重新置真，占位盒盖回真图上。
`applyProgress` 只挡了「进度倒退」，挡不住这里的**显形**。现在按 `stream.target < 100` 开闸。

真机上大概率遇不到（文档里 `progress:100` 就是最后一条），但代价只有一个条件，Flutter 侧同步加了。

排版顺序变成 **预描述 → 占位盒 → 真图 → 正文**，`chat.wxss` 里那几条相邻选择器
（`.pre-text + …` / `… + .bubble-text`）跟着改了，原来的 `.bubble-text + .bubble-imgs` 已删。
`tests/ai-image-aspect.test.js` 里锁顺序的断言也跟着更新 —— 真正要锁的不变量不是「正文在上还是在下」，
而是**占位盒与真图必须在正文的同一侧**：它俩是同一个位置的两个状态，跨到正文两边去的话，
100% 换图那一下图会整块跳过正文。
