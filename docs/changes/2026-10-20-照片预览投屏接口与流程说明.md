## 1. 核心结论

照片投屏由小程序、我方BoltFox后端、第三方seekink和相框设备共同完成：

- **小程序**：构图、按设备尺寸导出、调度网络请求、校验二进制帧、通过蓝牙发送。
- **我方后端**：提供第三方访问Token，保存图片及投屏记录，记录设备上传状态和图片槽位。
- **第三方seekink**：将构图后的普通图片转换成电子纸需要的六色4bpp二进制图片帧。
- **相框**：通过蓝牙接收图片帧、校验并存储，再按指令刷新电子纸显示。

核心涉及**4类HTTP接口**。取Token可以发生在进入预览页时；点击投屏后，两路图片请求并行。因此不能理解成“点一次按钮，固定串行调用4次接口”。

第三方成功响应体就是俗称的 **`.bin` 图片数据**。小程序直接以`ArrayBuffer/Uint8Array`接收，再经BLE发送给设备；正常链路不需要先取得`.bin`下载地址再下载，也不必先保存成一个本地`.bin`文件。

## 2. HTTP接口：按业务阶段说明

我方接口源站：`https://api.boltfox.cn`。

| 阶段 | 调用方 → 服务 | 方法与地址 | 目的和关键结果 |
| --- | --- | --- | --- |
| 进入预览页时预取；无缓存时才请求 | 小程序 → 我方后端 | `GET /Client/Basic/getXTYUserToken` | 获取seekink访问Token。常规`isNewLogin=0`；鉴权失效后强制刷新用1。 |
| 点击投屏后，每张图片一路 | 小程序 → 我方后端 | `POST /Client/Basic/setUserProductUpload` | 上传原图来源的图片，允许经过压缩；保存图片并建立初始未成功记录，取回`taskId/upirId`。 |
| 与上一行并行，每张图片另一路 | 小程序 → seekink | `POST https://cloud.seekink.cn:8443/prod-api/api/v1/label/imageDitheringBinDownload` | 上传预览构图后的设备分辨率图片，响应体返回六色二进制帧。 |
| 设备蓝牙确认写入成功后 | 小程序 → 我方后端 | `POST /Client/UserProduct/editUserProductImgRecord` | 用`taskId/upirId`把记录置为成功，并写入实际物理槽位`imgIndex`。 |

设备选择通常还涉及`GET /Client/UserProduct/getUserProductList`，提供设备、宽高及旋转等信息；它属于上游设备列表来源，不是每次进入预览页必定重新请求的接口。预览页一般读取上页通过`pendingProjection`传入的设备与图片。

### 2.1 获取第三方Token

- 进入预览页调用预热逻辑；同时可以预热蓝牙连接。
- Token缓存在本次小程序运行的内存中，后续投屏复用，不写入Storage。
- 预热失败静默处理，真正转换图片时会重新获取并按正常失败流程提示。
- seekink返回HTTP401或识别出的Token失效错误时，清缓存，调用`getXTYUserToken?isNewLogin=1`，取得新Token后重发转换请求；鉴权刷新最多一次。
- 这是第三方服务的访问Token，获取它的请求发往我方后端；与图片转换请求本身的服务归属要区分。

### 2.2 上传图片并建立投屏记录

`setUserProductUpload`以文件上传方式发送，文件字段名是`fileParam`。主要业务参数：

| 参数 | 当前客户端用途 |
| --- | --- |
| `userProductId` | 本次投屏对应的后端设备记录ID。 |
| `targetWidth/targetHeight` | 目标设备的物理像素宽高。 |
| `deviceUploadState=0` | 建立初始未成功记录；此时尚未证明照片写入设备。 |
| `isCompress=1`、`compressSize=1024` | 客户端当前固定发送的存图压缩配置；实际后端支持与输出大小以接口服务为准。 |

当前调用方从响应中取`taskId`和`upirId`。至少一项应存在，否则报“服务器未返回投屏记录”。这路上传用的是**进入预览编辑前的原图来源**，可能经过端上统一压缩，用于相册和记录展示。

当前客户端**不下载、不使用该接口返回的旧`.bin`地址**。部分旧封装注释仍描述后端转码，但当前设备帧使用seekink响应；仅凭旧注释不能断言后端当前是否仍生成某种文件。

### 2.3 第三方seekink图片转换

当前请求为`multipart/form-data`，上传字段如下：

| 字段 | 值与含义 |
| --- | --- |
| `file` | 预览构图后的图片，正常为设备物理分辨率JPG；客户端文件名使用`image.jpg`。 |
| `color` | `BWRYGB`：当前六色策略。 |
| `imageDitheringModes` | `2`：当前抖动模式。 |
| `type` | 480×720（含宽高对调匹配）设备沿用1，其余尺寸沿用0。它不是后台横竖屏字段，也不是固件型号字节。 |

请求头包含`Authorization: Bearer <第三方Token>`、`AcceptLanguage: en`及`Accept-Language: en`。文档不记录真实Token。

“抖动/量化”用于把普通照片的颜色和明暗细节映射到电子纸支持的黑、白、红、黄、绿、蓝六色。第三方负责出帧，实际把数据传给相框的是小程序。

当前客户端按`responseType: 'arraybuffer'`接收响应，成功后转换为`Uint8Array`。如果响应是JSON/文本错误、状态不是200或内容为空，就不能当成有效设备图片帧使用。

### 2.4 编辑投屏记录

设备图传成功后，客户端提交：

| 字段 | 说明 |
| --- | --- |
| `taskId/upirId` | 来自该张图片的上传建记录响应。 |
| `deviceUploadState=1` | 设备图传成功。 |
| `imgIndex` | 本次实际写入相框的物理槽位，0也是合法值。 |

`imgIndex`来自设备图片掩码计算出的空闲槽位；后端保存它，供后续定位。不能用可能过期的后端记录反过来决定本次刷哪个槽位。

## 3. `.bin`里面是什么

当前设备协议使用**六色4bpp原始图片帧缓存**。每个像素占4位，两个像素一个字节，所以发送前的长度要求是：

```text
帧字节数 = ceil(设备宽 × 设备高 ÷ 2)

400 × 400 →  80,000 字节
480 × 720 → 172,800 字节
```

JPG压缩大小与这个固定帧长度是两回事：压缩可以减少上传网络耗时；同一分辨率的4bpp帧字节数仍固定。`type`也不是自动修正图片分辨率的替代品，上传图应先按目标物理宽高正确导出。

拿到二进制响应不代表已经能投屏。小程序还会检查帧长度是否符合设备尺寸；不符合就停止，不把错误数据发给设备。仅长度正确也不能单独证明颜色顺序或实际画质正确，仍需对应屏幕真机验证。

## 4. 点击“投屏”后的完整业务流程

```text
进入照片预览页
  ├─ 读取上页传来的设备、图片、编辑状态
  └─ 并行预热：第三方Token + 蓝牙连接

点击“投屏”
  → 校验设备和图片，锁定按钮防连点
  → 本地Canvas应用构图，导出目标设备尺寸JPG
  → 保存pendingProjection，进入投屏结果页
  → 并行准备（尺寸可用时首张网络准备可提前启动）
      ├─ 连接设备、0x01读取并校验完整硬件身份/图片槽位
      └─ 每张两路HTTP并行
          ├─ 我方上传原图来源 → 初始记录taskId/upirId
          └─ seekink转换构图图 → 二进制图片帧
  → 等待本张准备完成，校验最终设备身份/尺寸及帧长度
  → 选空闲物理槽位，准备CRC32及分包
  → 蓝牙0x20开始 → 0x21数据/0x23确认 → 0x22结束校验写入
  → 本张成功：队列提交后端成功记录；下一张可以继续传
  → 整单结束：0x24刷新到本批第一张成功槽位；等待记账任务收敛
  → 展示整单结果；物理刷屏仍可能在后台进行
```

### 4.1 预览页本地处理

先检查是否选择设备、是否有图片，以及是否已经在执行，避免重复跳转。缺少可用BLE句柄时先等待预热或主动连接。

随后应用平移、缩放、旋转和横竖构图，正常按目标设备物理尺寸导出JPG。横向构图仍应按设备的物理画布和旋转配置导出，不是仅将宽高交换就直接发送。图传实际发生在后续结果页。

当前实现保留出图失败后回退原图的分支，因此异常时“传给第三方的图片一定符合设备尺寸”不能直接保证；后续帧长度检查仍会拦下不匹配数据。

### 4.2 连接与设备信息校验

结果页重新按完整设备身份确认连接，不能只相信缓存BLE句柄。通过`0x01 GET_INFO`核验完整6字节Device_ID，并读取图片掩码、当前图片等信息。物理分辨率优先使用匹配设备记录的`width/height`，缺失才兼容旧型号表；`0x01`本身不直接返回宽高字段。

首张网络准备可以与连接重叠，所以抓包里可能先看到上传建记录/图片转换，再看到完整的蓝牙读取完成；但发送图片数据前仍须通过设备身份与尺寸检查。

### 4.3 两路网络准备

`acquireFrame`使用`Promise.all`并行等待我方上传建记录和第三方出帧。两路图片源不同：记录存原图来源版本，设备帧使用构图后的版本，均可能经过统一上传压缩。

任一路失败，本张就不会进入正常图传；另一请求可能已经执行成功，不应认为两路会被一起撤销。当前张蓝牙传输期间会预取下一张的网络结果，因此日志也可能跨图片交错。

### 4.4 蓝牙图传指令

| 指令 | 小程序与相框之间的含义 |
| --- | --- |
| `0x01` | 读取设备信息，核验目标及图片掩码等。 |
| `0x20` | 开始接收：携带屏幕型号、槽位、宽高、格式0x01、数据长度和整图CRC32；设备同意后才发数据。 |
| `0x21` | 分包发送二进制图片数据，包大小由实际BLE协商参数决定。 |
| `0x23` | 设备累计确认连续收到的包号，驱动进度、窗口推进与重传。 |
| `0x22` | 结束传输，设备检查总长度和CRC、写入存储，并返回更新后的图片掩码/数量/剩余空间。 |
| `0x24` | 指定相框当前显示哪个图片槽位，并触发刷新。 |

设备接受`0x20`只表示允许开始；收到全部`0x21`也不替代最终校验。当前本张图传成功以`0x22`成功应答为依据，之后才排队提交后端成功记录。

### 4.5 收尾与物理显示

每张传成功后，后端记账进入队列，不阻塞下一张蓝牙传输。整单收尾会等待这些记账尝试结束，但其失败已被单独捕获，不回滚设备照片。

刷新`0x24`默认开启，整单只发一次，指向本批第一张成功写入的物理槽位；不是最后一张，也不是从后端再读一个槽位。整批完成、中途失败或用户中断，只要已有成功图片，都会尝试这次收尾刷新；没有成功图片就不刷。

该刷新是异步的，不等待电子纸物理刷完才显示结果。因此“手机显示投屏成功”表示图片已被设备确认写入，不能单独保证相框已经完成切图；当前刷屏失败或回报槽位异常只记录，不撤销前面的图传成功。

## 5. 失败在哪一步，意味着什么

| 失败位置 | 当前处理与影响 |
| --- | --- |
| 我方Token接口 | 预热时静默；真正转换时仍拿不到就失败。不能把它直接归为seekink图片转换服务故障。 |
| 我方上传建记录 | 本张准备失败，无法继续正常记账/图传。 |
| 第三方鉴权 | 强制取新Token后重试一次；不能无限刷新。 |
| 第三方网络 | 每次20秒超时；匹配网络失败条件时退避800ms重试，最多3次网络尝试，鉴权刷新另算。 |
| 第三方业务错误/空帧/错误状态 | 转换失败，不将响应作为设备图片发送。前台通用提示与原始失败原因应分开判断。 |
| 帧长度不匹配 | 禁止发送；先核对上传图实际像素、目标设备尺寸和本地导出分支。 |
| 蓝牙图传失败 | 尝试通过`0x12`删除本次槽位作回滚，中断后续图片；初始后端记录不置成功，回滚本身也可能失败。 |
| 设备成功，后端成功状态写入失败 | 图片保留在设备，记录/云端可能不同步；不把已成功照片误删。 |
| 收尾刷屏失败 | 不撤销图片写入成功；屏幕可能仍显示旧图，需要结合设备应答排查。 |

第三方转换失败时，我方建记录请求可能已完成，留下`deviceUploadState=0`记录。因此“HTTP上传成功”“设备存图成功”“电子纸刷新完成”必须分别看证据。

多张投屏遇一张失败会中断后续传输；之前成功的照片仍保留。当前页面可能展示部分成功结果，不能只按最终页面标题判断每一张都完成了。

## 6. 再次投屏与代码依据

再次/重新投屏也回预览页，按当前设备重新构图、调用seekink出帧，并通过`setUserProductUpload`建立新记录。不会直接下载历史`imgBle`发送，也不再用`addUserProductImgRecord`补记旧bin直传结果。失败页会恢复原图来源和编辑状态，避免把上次成品重复旋转、重复裁切。

| 源码 | 核查入口 |
| --- | --- |
| [`preview-page.js`](../../subpackages/projection/preview/preview-page.js) | `warmupPreview`、`confirmProjection`、`prepareProjectionImages`。 |
| [`result.js`](../../subpackages/projection/result/result.js) | `runRealProjection`、`acquireFrame`、`uploadOriginalForRecord`、`fetchDitheringFrame`及整单刷新。 |
| [`dithering.js`](../../utils/dithering.js) | Token缓存、multipart请求、ArrayBuffer接收、鉴权刷新与网络重试。 |
| [`api.js`](../../utils/api.js) | 我方HTTP接口地址、文件字段及投屏记录参数。 |
| [`device-ble.js`](../../utils/device-ble.js) | `uploadImage`、`refreshScreen`、ACK与重传。 |
| [`frame-protocol.js`](../../utils/frame-protocol.js) | 图传指令、帧头和应答的协议定义。 |
