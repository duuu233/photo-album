# 「我的相册」去掉「我的图库」接口：再次投屏与删除都只吃投屏成功记录（2026-08-17）

> 状态：current
> 适用范围：微信小程序「我的相册」（`subpackages/album/list`）、投屏记录页（`subpackages/projection/records`）、`utils/api.js`
> 相关决策：[设备图片槽位索引](../decisions/image-slot-index.md)
> 相关参考：[客户端接口矩阵](../reference/client-api-matrix.md)
>
> ⚠️ 仅小程序，**Flutter 待同步**（`lib/src/state.dart` 仍在用图库列表）。

## 结论

「我的相册」的数据源只有两个：

| 来源 | 接口 | 用途 |
| --- | --- | --- |
| 设备列表 | `getUserProductList`（`api.getDevices`） | 铺导航栏设备下拉；删除/再次投屏据此定位目标设备 |
| **投屏成功记录** | `getUserProductImgRecordList`（`api.getProjectionRecords` + `deviceUploadState=1`） | 铺网格；**再次投屏与删除都只吃这一份** |

「我的图库」的两个接口（`getUserProductImgList` / `delUserProductImg`）**从端上整体删除**。

## 为什么现在能删

这是 2026-08-04（相册合并）与 2026-08-10（删除索引改口径）两次改动留下的尾巴。清理前，图库列表
只剩两个消费方，两个的理由都已经不成立：

**① 再次投屏「取图库原图」**（`album/list.js findPhotoOfRecord`、`records.js resolveAlbumOriginalUrl`）

代码里的理由写于 2026-07-06：

> 记录里的 img 是后端按设备尺寸转换/压缩过的图，比例可能与原图不一致（预览会显得被拉伸），
> 而图库 img 与首次投屏同源

**这条自 2026-07-22 起就已失效**：那次改动把 `setUserProductUpload` 改成传**原图**
（`result.js uploadOriginalForRecord`，只按设备长边等比缩、不改比例，见
[图片投屏流水线](../architecture/image-projection-pipeline.md)）。图库里那条照片和这条投屏记录
本就是**同一次上传产生的同一张图**，绕图库那一跳换不到任何画质/比例上的差别，只多一个请求
（记录页还多一次「准备中」loading）。现在两处都直接用 `record.img`。

**② 默认设备规则「第一台有照片的设备」**（`pickDefaultFilter` 原第三档）

判据是图库照片的归属设备，而本页数据源是投屏记录，两者不同源。要按「哪台有照片」排就得把每台
设备的记录都拉一遍（一台一个请求），代价远大于收益。规则收成三档：

```
① 保留用户当前选中的那台（仍在列表里）
② 连接中的设备（activeDevice.findConnectedDeviceId 现算）
③ 第一台
```

②已经覆盖了最常见的场景——用户在首页/设备列表连好设备再进来。

**顺带修掉一个失败模式**：`getAlbumPhotos()` 原本和 `getDevices()` 并列在首屏的 `Promise.all` 里，
**一个用不上的接口有权把整页打成「加载失败」**。

## 明确保留：一键清空提醒

`checkDeviceClearStatus`（`getUserProductClearImg` → 弹「照片在此电子纸设备异常，请删除重新上传」
→ 确认后 `editUserProduct` 把 `isClearImg` 复位为 0）**原样保留**，进入页面和每次切换设备都查。

设备在别处被执行过「一键清空」时，这是用户唯一能感知到的入口。它查的是 UserProduct 侧的**设备
状态**，不属于「我的图库」列表链路——名字里带「图库」的是后端那个 `clearUserProductImg`
（后端文档口径「一键删除我的图库」），端上照旧调用，不在本次清理范围内。

## 改动后的两条链路

```text
再次投屏（单选/多选，一次最多 utils/upload-limit 张）
  选中投屏成功记录 → 取 record.img → 连接该记录所属设备
  → 写 pendingProjection → 预览页构图 → 结果页：
       seekink 抖动接口出帧 → 读 0x01 取 firstFreeIndex（第一个空槽）
       → BLE 0x20/0x21/0x22 发数据 → editUserProductImgRecord 记账 imgIndex
  → 产生一张新照片、一条新记录，不改动被选中的那条

删除（多选）
  选中投屏成功记录 → 取该记录自己的 imgIndex（缺失/非法则整批终止，绝不推算）
  → 连接该记录所属设备 → 读 0x01 的 IMG_MASK 分拨（设备上已无的跳过）
  → 0x12 删仍在的槽位（0x05/0x07 按「本来就没有」放行）
  → delUserProductImgRecord 删来源记录 → **端上到此为止**，图库照片的清理归后端
```
