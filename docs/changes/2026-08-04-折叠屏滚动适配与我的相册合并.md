## 第 1 项 · 折叠屏滚动适配

### 问题

折叠屏（尤其展开态）下首页只显示上半屏，手指怎么滑都不动。

三个成因叠加：

1. **`rpx` 随屏宽放大**。`rpx = 屏宽 / 750`，折叠屏展开后屏更宽，按 rpx 写死的内容（问候语、设备轮播
   372rpx、投屏入口卡 310rpx…）整体等比放大，而窗口反而更矮更方，内容必然超出一屏。
2. **页面级滚动本来就是关掉的**。`pages/home/home.json` 与 `pages/mine/mine.json` 都写了
   `"disableScroll": true`（自定义导航 + 固定底栏的常规配置，防止整页跟着回弹）。
   这正是「滑也划不动」的直接原因——超出的内容既不滚动，也没有任何容器接管。
   > 保留 `disableScroll: true`，改用页面内的 `scroll-view`：页面禁滚不影响 `scroll-view` 自身滚动，
   > 这样导航栏与底部导航仍然固定，只有中间内容滚。
3. **没有滚动容器**。`.home-root` 是 `min-height: 100vh; overflow: hidden`，`.binding-content` 更是
   写死 `height: calc(100vh - …)`：超出的部分既没有容器接管，又被 `overflow: hidden` 直接裁掉，
   表现就是「只显示一半」。
   > 注：`100vh` 本身**不是**成因（初版曾据此改成 JS 实测高度，反而引入新 bug，见下方「修正记录」）；
   > 真正缺的是滚动容器。

### 改法

| 位置 | 改动 |
| --- | --- |
| `pages/home/home.js` | 新增 `onResize` 重测状态栏/安全区；新增 `onNavMeasure` 接收导航栏实测高度 |
| `components/page-nav/page-nav.js` | `attached` 里把实测 `navHeight` 通过 `triggerEvent('measure')` 回抛给页面（不监听的页面无副作用） |
| `pages/home/home.wxml` | 导航栏以下整块包进 `<scroll-view scroll-y>`；底部导航与三个弹层移到滚动容器**外** |
| `pages/home/home.wxss` | `.home-root` 改 `display:flex` + `height: 100vh`；`.home-bg` 改 `position: fixed`；新增 `.home-scroll`；`.binding-content` 由写死 `height` 改 `min-height` 并预留贴底按钮的 `padding-bottom` |
| `pages/mine/mine.*` | 同一套改法（「我的相册」入口在这一页，折叠屏下必须能滚到）：`height: 100vh` + `.mine-bg` 改 `fixed` |

关键约束（改动时不要退回去）：

- **页面高度只用 CSS 的 `100vh`，绝不要用 JS 测出来的 `windowHeight` 当高度**
  （本轮初版踩过这个坑，当天即回滚，详见下面的「修正记录」）。
- **`.home-scroll` 的 flex 基准必须是 `0`（`flex: 1 1 0`）**。写成 `1 1 auto` 时该项基准 = 内容高度，
  内容一超屏就产生「负剩余空间」，flex 会把**导航栏一起按比例压扁**（标题被切、返回键错位）。
- **`min-height: 0` 不可省**，否则滚动区按内容撑开、整块顶出根容器，又回到「滑不动」。
- **`position: fixed` 的固定层（底部导航、遮罩弹层）必须放在 `scroll-view` 之外**，否则会跟着内容滚。
  移出去时要把原来由父级 `block` 提供的场景判断补进各自的 `wx:if`（`!pageLoading && isHomeScene` 等）。
- 内容块的 `min-height` 用 `calc(100vh - var(--nav-h))`。`--nav-h` 是导航栏**已渲染节点**的实测高度
  （不是窗口快照，不会失真），旧写法里的 `88rpx` 会随屏宽放大，折叠屏上误差可达几十 px。
- **背景层用 `position: fixed`**（同图库页的 `.mock-bg`），铺满视口而不是根容器，
  根容器高度万一与视口差几十 px 也不会在底部露出一条没有背景的缝。

### 修正记录（同日）

初版把窗口高度写成 JS 实测的 `wx.getWindowInfo().windowHeight` 并下发成 `--win-h`，真机暴露两个 bug：

1. **首页背景填不满**：首页是 tabBar 页，`windowHeight` 按 `app.json` 的配置扣掉了原生 tabBar 高度，
   而本页 `wx.hideTabBar()` 之后视口其实是整屏 → 根容器比视口矮一截 → 底部露缝。
2. **展开态冷启动滑不动**：那一刻取到的窗口高度偏大，滚动区比真实视口还高，
   内容装得下就不产生滚动，下半屏却在屏幕外；折一次再展开会触发 `onResize` 重测，所以「合上就能用」。

两个都是同一个根因——**JS 快照 ≠ webview 真实视口**。改回 `100vh` 后由 webview 自己解析，
折叠/展开/分屏/三折叠时窗口一变就重新布局，也不存在冷启动快照过期的问题。
`onResize` 保留，但只用来重测状态栏高度与底部安全区（内外屏的刘海/Home Indicator 确实不同）。

窗口装得下时观感与改动前完全一致；装不下时可上下滚动。

## 第 2 项 · 「我的相册」

### 模块合并

「我的」常用功能：`我的设备 / 设备照片 / 投屏管理` → `我的设备 / 我的相册`。卡片改为等分宽度
（`flex: 1 1 0` + 21rpx 间距），不再是三张 204rpx 定宽。

投屏记录页 `subpackages/projection/records` **保留且未改动**：它仍是查看**失败**记录与重新投屏的地方，
入口改为只从投屏结果页的「投屏明细」进入。「我的」不再有它的入口。

### 页面与数据

页面沿用 `subpackages/album/list`（原「设备照片」），UI 原样保留，数据口径整体换成投屏记录：

```text
进入页面
  → getAlbumPhotos()  // 相册照片：槽位账本 + 原图，仅供 JS 使用，不渲染
  + getDevices()      // 设备下拉（分类器）
  → 选中设备（沿用原默认选中规则）
  → getProjectionRecords({ deviceUploadState: 1, userProductId })   // 网格数据源
  → 端上再按 status === 'success' 兜一层（兼容后端忽略该参数）
```

- **按设备分类**由后端按 `userProductId` 过滤完成，不在端上按记录字段猜归属——记录不一定回
  `userProductId`。切换设备会重新请求（与投屏管理页同口径，列表区域局部 loading）。
- 网格缩略图取记录的 `imgThumb`，即**当次投屏的那张图**，与设备上的画面一致。
- 瓦片 `id` = 记录 id（`upirId`）；`photoId` = 记录关联的相册照片 id（`uProductImgId`，
  大小写两种写法都兼容）。

### 再次投屏（底部橙色按钮）

与投屏记录页的「再次投屏」完全同链路：取图 → 连设备 → 写 `pendingProjection` → 投屏预览页。
用户可在预览页重新构图，点「开始投屏」后照常 seekink 出帧 + BLE 图传 + `setUserProductUpload`
**建新记录**——所以再次投屏产出的是一张新照片、一条新记录，不改动被选中的那条。

- **单选**：投这一张。
- **多选 / 全选**：一次把选中的多张写进 `pendingProjection.images`，走与首页相册多选完全相同的
  批量传输链路（预览页左右切图逐张构图，结果页按张串行图传）。张数上限复用
  `utils/upload-limit`（常规 10 张，白名单 100 张），超出直接提示不放行。
- 图源优先「相册里同一张照片的原图」（按 `uProductImgId` 关联），退回记录里的投屏图——
  记录里的 `img` 是按设备尺寸转换过的，直接拿去预览会显得被拉伸。与 `records.js` 同口径。
- 选中项按**网格展示顺序**投，不是 `Object.keys` 顺序。

### 删除（底部红色按钮）

沿用图库删除链路，末尾追加一步。2026-08-10 又按 v1.5 §6.7.10 收敛了设备侧步骤，当前流程为：

```text
连接「这些照片所属设备」
  → 记录 → 相册照片(uProductImgId) → 直接读取后端 imgIndex
  → imgIndex 组成固定 12 字节、低字节在前的 IMG_INDEX_MASK
  → 直接发送 0x12 批量删槽位
  → delUserProductImg     删相册记录
  → delUserProductImgRecord  删来源投屏记录（新增，串行批量）
  → 重新加载
```

- **必须删来源投屏记录**：本页列表就是按成功记录铺的，只删设备与相册记录的话，下次进来照片还在列表里。
  新增 `api.deleteProjectionRecords(ids)`：后端无批量接口，串行逐条调用，单条关掉 loading 与自动错误提示
  （批量删 10 张会闪 10 次「删除中」、失败弹 10 条 toast），返回 `{ total, failed }` 允许部分失败——
  设备与相册记录已经删掉，不能因为记录没删干净就整体报错回滚。
- 记录找不到对应相册照片、或相册照片没有合法 `imgIndex` 时，整批删除终止；不猜槽位，也不单独
  删除来源记录。
- 当前 `backendImageIndexOf` 的入参仍是**相册照片 id**，不是记录 id；单测
  `tests/album-slot-index.test.js` 直接按 `this.photos` 调它，改签名会一并失效。

### 保持不变的既有口径

- 连接的是「这些照片所属的设备」，不是首页选中的那台（2026-08-03 与 Flutter 对齐的口径）：
  记录带 `userProductId` 就按它找设备，跨设备直接拦下；没带则退回当前下拉选中的那台——
  列表本就是按该设备ID向后端筛出来的。
- `imgIndex=0` 仍是合法槽位；一键清除状态提醒（`getUserProductClearImg`）保持不变。删除链路已取消
  0x01 预读、槽位推算、删除后补刷屏和错误后重读等兜底逻辑。
