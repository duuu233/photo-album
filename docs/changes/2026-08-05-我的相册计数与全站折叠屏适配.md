## 第 1 项 · 「我的相册」张数 = 全部设备的投屏成功记录条数

### 为什么改

「我的相册」这个入口在 2026-08-04 由「设备照片」+「投屏管理」合并而来，**列表数据源已经换成投屏成功记录**，
但卡片上的「N 张照片」当时还留着老口径——用户信息接口的 `imgCount`（相册口径）。
两个口径对不上：`imgCount` 把投屏失败的、已从设备删掉的照片也算在内，用户点进去看到的却是成功记录。
这正是上一份文档 Risks 里记的那条遗留项，本轮补齐。

### 实现

新增 `api.getProjectionSuccessCount()`，「我的」页并行拉三个接口时用它替掉原来的 `getAlbumPhotos()`：

```text
loadUserInfo()
  ├ getUserProfile()              头像/昵称/ID + 设备数(productCount)
  ├ getDevices()                  productCount 缺失时的设备数兜底
  └ getProjectionSuccessCount()   ← 「我的相册」张数（新）
```

计数口径与「我的相册」列表**完全一致**：`deviceUploadState=1` + 端上再按 `status === 'success'` 兜一层；
**不带 `userProductId`**——卡片统计的是全部设备的合计，不是当前选中的那台。

只要数字不要数据，所以尽量少打请求：

- 后端认 `deviceUploadState` 时（回来的整页都是成功记录），直接取分页元数据 `recordCount`，
  **一次请求**就拿到真实总数，超过一页（100 条）也不会被截断；
- 后端忽略该参数时 `recordCount` 是「成功+失败」的合计，不能当成功数用，退回逐页翻 + 按状态计数。
  判停优先看 `pageCount`/`recordCount`，**不拿「回包条数 < 请求的 pageSize」当依据**——后端可能无视
  pageSize 按自己的默认值分页（`guide.js fetchAllFaq` 踩过同款坑）；20 页封顶做死循环保险丝。

回归用例锁在 `tests/projection-success-count.test.js`（成功数超一页、后端忽略过滤参数、
无分页元数据、空列表、裸数组返回五种情况）。

### 保持不变

- 「我的设备」卡片仍取 `productCount || devices.length`，没动；
- 用户信息里的 `imgCount` 仍照常解析，只是「我的」页不再用它做展示口径；
- 接口失败时保留上次成功值（弱网切页把数字清零，用户会以为照片没了），首次进入即失败才落 0。

## 第 2 项 · 折叠屏适配方案（全站）

### 方案位置（与原有布局解耦）

| 文件 | 职责 |
| --- | --- |
| `styles/fold-adapt.wxss` | 样式方案：`.fold-viewport` / `.fold-scroll` / `.fold-scroll-body` / `.fold-page` / `.fold-bg`，在 `app.wxss` 里 `@import` 一次，全站（含分包）可用 |
| `utils/fold-adapt.js` | JS 方案：`fold.adapt(pageOptions)` 给页面**叠加**「形态变化后重测状态栏/底部安全区」「接住 page-nav 实测导航高度」两件事 |

两者都是**纯叠加**：不加类的节点、不包 `adapt()` 的页面，一行样式、一个字段都不受影响。
接入一页的成本是「根节点加个类 + 内容外面包一层 scroll-view + `Page(fold.adapt({…}))`」。

### 成因（沿用 2026-08-04 首页的结论，不再重复推导）

1. `rpx = 屏宽/750`，屏一宽内容整体放大，而窗口反而更矮更方；
2. 自定义导航 + 固定底栏的页面常规配置是 `"disableScroll": true`，页面级滚动本来就是关的；
3. 根容器还写着 `overflow: hidden` 或写死高度，超出的部分没人接管、直接被裁。

⚠️ 页面高度一律用 CSS 的 `100vh`，**绝不要**用 `wx.getWindowInfo().windowHeight`
（tabBar 页会扣掉已 `hideTabBar` 的原生 tabBar → 底部露缝；展开态冷启动的快照失真 → 滚不动。
首页 2026-08-04 当天踩过并回滚，见 `pages/home/home.wxss` 顶部注释）。

### 两种模式

- **模式 B · 容器滚动**（`"disableScroll": true` 的页）：根节点 `.fold-viewport`（一屏高 + 纵向 flex），
  背景层/导航栏/固定底栏/弹层留在滚动区**外**，中间内容包进 `<scroll-view class="fold-scroll">`。
  滚动区必须是 `flex: 1 1 0` + `min-height: 0`：写成 `1 1 auto` 时内容一超屏会把**导航栏一起压扁**。
- **模式 A · 页面滚动**（`"disableScroll": false` 的页）：本来就能滚，只要根容器别写死高度
  （`min-height` 不是 `height`，别 `overflow: hidden`）。

`.fold-scroll-body`（`min-height: 100%`）用于原本依赖「根容器就是一屏高」的内容块
（如投屏结果页的 `.result-body`，它原来靠 `flex: 1` 撑满剩余高度）。

**贴底按钮一律留在滚动区外**：设置类页面那摞 `position: absolute; bottom: …` 的按钮
（退出登录 / 用户注销 / 保存设置 / 立即更新 / 确认）仍以根容器为定位父级，位置一像素不动，
也不押在「百分比高度能不能解析」上；只给滚动内容块补 `padding-bottom` 把它们占的高度让出来
（统一在 `.settings-scroll-body`），否则变长的内容会从这些脱离文档流的按钮底下穿过去。
`position: fixed` 的提交按钮（个人信息 / 绑定·修改邮箱）本来就钉在视口上，留在原处不动。

### 逐页处理结果

| 页面 | `disableScroll` | 处理 |
| --- | --- | --- |
| `pages/home`、`pages/mine` | true | 2026-08-04 已适配，**本轮未动**（各自的 `.home-scroll`/`.mine-scroll` 就是这套方案的原型） |
| `subpackages/settings/guide`、`subpackages/ai/chat` | true | 页面早已是「一屏高 + 内部 scroll-view」，本轮只补 `fold.adapt`（重测状态栏/安全区） |
| `pages/login` | true | 模式 B：内容包滚动区；背景层/过渡层/toast 留在外面 |
| `settings/index`、`language`、`update`、`forgot-password` | true | 模式 B + `.settings-scroll-body`；贴底按钮（`position: absolute`）留在滚动区外，只用 `padding-bottom` 让出它们占的高度 |
| `settings/profile`、`bind-email`、`change-email` | true | 模式 B；提交按钮本来就是 `position: fixed`（钉视口），留在原处 |
| `projection/result` | true | 模式 B：正文进滚动区（`.result-body` 的 `flex:1` 改由 `.fold-scroll-body` 的 `min-height:100%` 承担），底部按钮组留在外面 |
| `projection/preview` | true | **不套滚动容器**（见下）：改为宽高比 ≥ 3:4 的窗口下让编辑舞台让高度 + `onResize` 作废实测矩形 |
| `device/bind` | true | 内容区高度由 `100vh - var(--status-bar) - 88rpx` 改用 page-nav 回抛的实测 `--nav-h`（88rpx 会随屏宽放大，展开态误差可达几十 px） |
| `device/detail`、`device/slideshow` 的状态块 | false | `height` → `min-height`：这两页是页面级滚动，放开后超出部分能滚到 |
| `album/list`、`device/list`、`device/ota`、`projection/records`、`ai/sessions`、`device/debug`、`settings/agreement`、`privacy`、`ai-agreement` | false | 根容器本就是 `min-height`，页面能滚；本轮只补 `fold.adapt` |

**投屏预览页为什么不能包 scroll-view**：本页是「一屏装完」的手势编辑器，滚动会和长按拖拽/双指缩放抢手势，
`_measureStage()` 实测的舞台矩形也会随滚动漂移。改成让舞台自己让高度：

```css
@media (min-aspect-ratio: 3/4) { .preview-stage { flex: 1 1 auto; min-height: 40vh; } }
```

门槛取宽高比 3:4——普通手机竖屏约 0.46 **不匹配**（样式一行不变），折叠屏展开态(≈0.9)、分屏、平板、
横屏才命中。同时补 `onResize`：舞台尺寸变了就作废 `_stageRect` 并按当前图重进编辑态，
否则取景框还按旧尺寸算，**导出的构图会和用户所见对不上**。

### Risks

- **折叠屏改动未真机验证**：本轮涉及 20+ 页面，`scroll-view` 高度、导航栏是否被压扁、
  贴底按钮位置、弹层是否跟着滚，都要真机确认。
- **贴底按钮与内容的遮挡关系变了**（设置类页面）：按钮本身没挪（仍以根容器定位），
  但内容现在会在它们下方滚动。真机要逐页对一眼滚到底时的观感，尤其是有 Home Indicator 的机型
  （`--safe-bottom` 同时参与按钮 `bottom` 与内容 `padding-bottom` 的计算）。
- **预览页的 `@media (min-aspect-ratio)`**：折叠屏展开态是否命中、命中后 40vh 的舞台够不够构图，
  只能真机看；不命中时样式与改动前完全一致，风险只在展开态。
- **张数与列表可能仍差一条**：同一张照片多次成功投屏会有多条成功记录，卡片与列表都按记录计数，
  两边一致；但与设备上实际图片数不是同一回事（这一条与 2026-08-04 的结论相同）。
- `getProjectionSuccessCount` 在后端忽略 `deviceUploadState` 时最多翻 20 页（2000 条）；
  超出部分不计入，属于刻意的上限。
