## 第 2 项 · 切图先闪回上一张（小程序真因）

### 现象

左右滑动切图，过场本身跟手且正常，但**落位那一刻会先显示刚滑走的那张**（从第一张往后切时
就是「第一张图片」），过一小会儿才换成目标图 —— 看起来像「每切一次都要重新加载一遍」。

### 根因：三个固定槽位复用 `<image>` 节点

2026-08-01 的自绘轨道把「上一张 / 当前 / 下一张」写成三个**固定槽位**
（`.slide-cell--prev / --current / --next`），切图时槽位不动、只换各自的 `src`。
微信的 `<image>` 在**新图解码完成之前会继续显示旧位图**，于是：

1. 过场里进场那张由 `--next` 槽位承担，整段过场都在屏上，早已解码；
2. 落位时 `activeIndex` 一换，`--current` 槽位的 `src` 从「刚滑走那张」变成「目标图」——
   但它是同一个节点，屏幕上还挂着**刚滑走那张的位图**；
3. 目标图在这个节点里要重新解码一次，解码完才跳过去。

即：过场里已经解码好的那份位图在 `--next` 槽位里被丢掉了，落位后又在 `--current` 槽位重来一遍。

### 改法：轨道改成带 `wx:key` 的列表，让节点跟着图片走

`preview.js` 的 `_neighborPatch` 换成 `_trackPatch(images, index)`，产出
`trackCells = [{ idx, offset, src, wrapStyle, imgStyle }]`（`idx` = 图片在 `images` 中的下标，
`offset` = 该格相对当前格的屏数 −1 / 0 / +1）；`preview.wxml` 用
`wx:for="{{trackCells}}" wx:key="idx"` 渲染，横向站位由内联
`transform: translateX(offset * 100%)` 下发（`.slide-cell--prev/--next` 两个类已删）。

切图后列表由 `[n-1, n, n+1]` 变成 `[n, n+1, n+2]`，微信按 `wx:key` 复用节点：
过场里解码好的那张**原地留在屏上**，只改自身偏移量，落位零解码、零闪回。

> ⚠️ `wx:key="idx"` 不能去掉，也不能改回按位置的固定槽位——那等于回到「换 src」，
> 这个 bug 会原样复现。

### Flutter 侧

Flutter 用的是底层 `PageView.builder`，页节点天然按 index 建、落位时不会被换成别的图，
**不存在小程序那个复用错位**。它的短板在另一头：邻页是**手指开始滑动的那一刻**才建
`Image.file` 的，几 MB 的手机照片读盘 + 解码常要一两百毫秒，正好压在 300ms 过场里——
过场里先是一张白卡，落位后图才姗姗补上，观感同样是「重新加载了一遍」。
`cast_preview_page.dart` 新增 `_precacheNeighbors(index)`（在 `_enterEdit` 末尾调用，
对齐小程序早就有的 `_prefetchNeighbors`），进页 / 每次落位后预热相邻两张，过场直接命中
ImageCache。取源与 `_buildPager` 同一优先级（`_previews[i]?.path ?? _paths[i]`），
失败只 `debugPrint`，展示时仍有 `errorBuilder` 兜底。

## 第 4 项 · 容量行改成 `已用/上限`

行名回到「最大照片数量」，已用与上限全部挪进右侧值里，写成分数式 `8/51`：

| 端 | 位置 |
| --- | --- |
| 小程序 | `detail.js` `memoryText` → `${used}/${total}`；`detail.wxml` 行文案 |
| Flutter | `app_l10n.dart` `devMaxPhotoCount`（四语种）；`device_details_page.dart` 值 → `'${device.imageCount}/${device.capacity}'` |

口径不变：容量取 `0x01` 的 `capacity`、已用取 `imgCount`；**容量未知（未连接 / 没读到 0x01）
整行仍回落 `--`**，绝不用 0 冒充真实值；已用数缺省时按 0 计（`0/51` 比整行 `--` 更有信息量）。
⚠️ 行文案与取值口径成对，改一个必须改另一个。
