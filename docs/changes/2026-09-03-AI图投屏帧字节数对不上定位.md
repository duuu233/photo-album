## 一、现象

用户在 AI 助手模块生成图 → 保存到手机相册 → 从相册选图投屏，结果页报：

```
后端返回的不是电子纸设备要的六色4bpp帧：收到 258720 字节(头16=11 11111111 11 1111)，
电子纸设备 680×960 需要 326400 字节
```

对照条件（用户实测，**同一台鸿蒙手机、同一条投屏链路、同一个选图入口**）：

| 图片来源 | 结果 |
| --- | --- |
| 微信聊天里的图 → 保存到相册 → 投屏 | ✅ 正常 |
| AI（豆包）生成图 → 保存到相册 → 投屏 | ❌ 报上面这句 |

样本图属性：`IMG_6609.jpg` / `image/jpeg` / 423.93 KB / **1774×2364** / 位置「图库/豆包」。

> ⚠️ 用户看到的这句是**小程序 2026-09-03 之前**的文案（`git show 57ce474` 刚把它换掉）。
> App 端同位置的措辞是「不是**设备**要的」，少「电子纸」三字——按这个可以区分是哪一端报的。

## 二、定位：结论与证据

### 结论

**不是第三方（seekink）返回了错格式，也不是图片编码格式问题。**
是**端上出图那一步失败后静默回退了原图**，原图带着原比例进了抖动接口。

### 证据链

**① 帧字节数只跟着「上传图的像素」走**，第三方不按 `type` 补齐/缩放
（`result.js fetchDitheringFrame` 注释、`image-projection-pipeline.md` 关键约束）。所以：

```
收到 258720 字节  ⟺  抖动接口收到的图是 517440 像素  ⟺  那张图不是 680×960
```

这是等价关系，不是推测。头 16 字节全 `0x11`（六色索引重复）也说明**第三方正常出了六色帧**，
只是尺寸随了我方喂的图——查 seekink 是白查。

**② 出图这一步全项目无旁路。** 7 处写 `pendingProjection` 的入口（AI、首页、相册、图库、
设备详情/列表、记录页）全都 `navigateTo` 预览页；跳结果页的地方只有一处——
`preview.js:1534`，就在 `prepareProjectionImages()` 之后。设计上每张图都必须过设备物理分辨率导出。

**③ 那它就是失败了，而失败是静默的。** `preview.js` 四个逃生口把**原图**当成品图往下传：

```js
// coverCropOne（未编辑图的必经之路）
fail: () => resolve(image)                       // getImageInfo 失败
.catch(() => resolve(image))                     // canvas 导出失败
if (!(natW > 0) ...) { resolve(image); return }  // 尺寸不可用
// bakeEditedImage（编辑过的图）
.catch((err) => { console.warn(...); return image })
```

除最后一个外**都不打日志**、不报错、不阻断。所以从代码意图看「每张都处理成设备分辨率」，
从运行时看「这一张悄悄没处理」。Flutter 端同构：`_startCast` 的 `outPaths.add(out ?? src)`
与 `catch (_) { out = null; }`。

**④ 517440 = 960 × 539，长边精确等于设备长边 960。** 这是 `result.js compressForUpload`
「长边等比缩到设备长边、不改比例、不补边」的特征产物。反过来说明：`wx.getImageInfo` 与
`wx.compressImage` 对这个文件**都成功了**，`<image>` 组件也显示正常——
**唯独 canvas 2d 的 `createImage()` 没能解码**。这三者不是同一套解码器。

若是「处理了但尺寸算错」，出来的会是老设备尺寸 480×720（→172800）或别的怪数，
不会精准落在长边 960 上。

### 已排除

- ❌ **第三方/后端返回格式错** —— 见证据①
- ❌ **绕过了预览页** —— 见证据②
- ❌ **图片编码格式（WebP/HEIC）** —— 用户提供的样本是 `image/jpeg`，canvas 解 JPEG 不会失败
- ❌ **设备尺寸取错**（`getDeviceCropSize` 回落 480×720）—— 那会得到 172800，不是 258720

### 当前假设（**未经日志实证**）

canvas 2d 解码/绘制**大图**时失败：豆包图 1774×2364 ≈ **419 万像素**，
而微信发送时会把图压到长边 1280 上下（**≤130 万像素**）——这正是那组对照实验里唯一真正变了的量。
`wx.getImageInfo` / `wx.compressImage` 走原生解码路径、内存管理不同，所以照样成功。

⚠️ 这一条只是当前最合理的解释，**还没有日志证实**。本轮加的日志就是为了证实或证伪它。

### 可证伪的预测

拿这张 1774×2364 直接投屏，若假设成立，报的字节数应是 **345600** 而非 258720：

```
compressForUpload: 长边 2364 → 960，ratio = 960/2364 = 0.40609
  1774 × 0.40609 = 720.4 → 720
  2364 × 0.40609 = 960.0 → 960
→ 上传图 720×960 = 691200 像素 → 帧 345600 字节（设备需 326400）
```

另：报 258720 那张**不是**这一张。258720 反推是 `539×960`，原图比例约 0.561（接近 9:16），
是另一张竖长的豆包图。两张不同比例的图失败字节数都精确等于「原图等比缩到长边 960 的像素数 ÷ 2」，
说明回退是**整体性**的，不是偶发。

## 三、本轮改了什么

### 3.1 前台提示文案（两端）

| | 改前 | 改后 |
| --- | --- | --- |
| 小程序 `result.js` | `图片转化出错，请重新投屏` | **`图片文件错误，请尝试通过工具转码后重新投屏`** |
| Flutter `projection_service.dart` | `后端返回的不是设备要的六色4bpp帧：收到 X 字节(头16=…)，设备 W×H 需要 N 字节` | 同上，经新 l10n key `castFailureImageFileBroken`（中/英/日） |

文案沿革与理由：

1. **「后端返回的不是…六色4bpp帧」** —— 帧自 2026-07-22（App 07-23）起就不是我方后端出的，
   这句把用户和客服全引到我方接口上去；
2. **「图片转化出错，请重新投屏」** —— 不再甩锅后端，但用户照着做只会原样再失败一次：
   帧字节数只跟上传图像素走，重投同一张不改变任何东西；
3. **现文案** —— 根因已定位到**这张图片文件本身**在端上出图那步过不去，
   引导换图或先转码，这是当前唯一能自救的动作。

⚠️ **只改了提示文案，判定逻辑与回退行为一字未动。** 根因修复另立一轮（见第五节）。

**归类兜底已核对**，新文案三语都不会被误归成别的桶：

- 小程序 `classifyFailureMessage`：不含 `内存已满|已存满|空间不足`、不含 `BUSY_MESSAGE`、
  不匹配 `^(设备|电子纸设备)-` 与 `连接已断开|连接中断|连接失败|已断开|连接超时|链路|该型号暂不支持图传`
  → 走 `return msg` 原样透出，由 `applyStatus` 的 `desc: result.message || text.desc` 落到失败页正文。
  ⚠️ **唯一会被盖掉的情形**：`connLost` 第一项 `(deviceId && !deviceBle.isConnected(deviceId))` ——
  抛错这一刻恰好断连的话，用户看到的是「电子纸设备未连接…」。这是既有行为，本轮没动。
- Flutter `_friendlyFailure`：`FrameBleException` 默认 `kind = unknown` → 落子串匹配 →
  中/英/日三语都不命中 `忙|busy|0x0b`、`空间|已满|内存|storage|full`、`断|未连接|disconnect`、
  `超时|timeout`、`中止|取消|abort` → `return raw` 原样透出。
  （日文「変換」含「換」不含「断」，已逐字核过。）

## 四、日志判读

跑一次投屏，按顺序看：

```
[AI][图片格式] 真实编码=JPEG 扩展名=.jpg 微信认的type=jpeg 像素=1774x2364 orientation=up
[预览][coverCrop] 源图：1774x2364 type=jpeg orientation=up 设备=680x960
[预览][导出] 解码成功：img=1774x2364 目标画布=680x960 耗时 42ms
[预览][coverCrop] 出图成功：680x960（= 设备物理分辨率）
[预览][出图] 第 1/1 张 分支=③ 未编辑-coverCropOne 结果=680x960 设备=680x960 预计帧=326400 字节 设备需=326400 字节
[投屏][出帧] 喂给抖动接口：680x960 type=jpeg 88KB (原样) … 预计出帧=326400 字节 设备需=326400 字节
```

失败时的分叉：

| 现象 | 结论 |
| --- | --- |
| `[预览][导出] createImage 解码失败` | canvas 2d 没能解码。配合 `[预览][coverCrop] 源图` 的 type/像素判断是格式还是尺寸 |
| 有「解码成功」但接着 `canvasToTempFilePath 失败` | 解码过了、绘制或导出这步炸，同样指向内存/尺寸 |
| 有「解码成功」且 `img=WxH` 与源图行的 `WxH` **对不上** | EXIF 方向问题：`getImageInfo` 报旋转后尺寸、canvas 拿旋转前，源矩形越界。修法完全不同 |
| `[预览][导出] 画布不可用` | 页面/节点问题，与图片无关 |
| `[预览][出图] 分支=②` 且结果尺寸 ≠ 设备尺寸 | 换过设备，`cropW` 是**老设备**尺寸（另一条隐患，见第五节） |
| `[预览][出图] 结果=680x960` 却仍报出帧尺寸不符 | **本文整套模型被证伪**，改从「出图之后、抖动接口之前」重查（`persistPending` 落盘 → 结果页读回 → `resolveLocalFilePath`） |

## 五、未修：根因与两条隐患

本轮**只改提示、只加日志**，以下都留到下一轮：

1. **静默回退本身是设计缺陷**（主因）。出图失败时回退的原图**注定**在结果页被铁闸拦下，
   却被当成正常流程一路传下去，最后变成一句指向第三方的报错。合理的做法是：出图失败就地
   重试（先降采样再喂 canvas）或直接判本张失败，而不是把必定失败的结果往下传。
2. **预期修法**：`coverCropOne` / `_bakeToFile` 喂给 canvas 之前，先用 `wx.compressImage`
   把源图降到设备长边再交给 `createImage`——`compressImage` 已被证明能处理这些大图，
   降采样发生在中心裁切之前、画质无损失（最终要量化成六色）。App 侧对应
   `CastImageEditor._coverCrop` 的 isolate 内解码。⚠️ 待日志证实后再动手。
3. **顺带发现的隐患**：`prepareProjectionImages` 的 `else if (image && image.cropW)` 分支
   原样保留旧产物，而 `cropW` 是**上一轮出图时记的尺寸**——换过设备后它就是老设备尺寸
   （480×720 → 帧 172800 ≠ 326400）。`restorePendingOriginals` 会清 `cropW`，但换设备这条路不会。
4. **AI 图下载后未做格式/尺寸归一化**：`chat.js downloadAiImage` 拿到什么就用什么。
   治本的另一条路是下载后统一 `wx.compressImage` 转一道，把上游未知产物在进预览页前就归一。
