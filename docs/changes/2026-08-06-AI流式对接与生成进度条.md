## 事件 → 界面映射

```
pre_text  → 气泡顶部预描述行「正在为您绘制…」，同时进度条显形（≥5%）
progress  → 进度条宽度 = event.progress，文案按 §4.3 分档
image     → 追加进**同一个气泡**的 images（按 img_orientation 先占好高度）
text      → 进打字机队列，逐字上屏
done      → 进度条到 100% 并隐藏，typing 归位，sending 放行
```

进度文案分档（接入文档 §4.3）：`<5` 正在连接… / `<50` AI 正在创作中… / `<80` 图片初稿已完成 ✨ /
`<100` 正在优化细节… / `100` 生成完成。

## 三个必须写进代码的坑

### ① `chunk.data` 是 ArrayBuffer，不是字符串

接入文档 §4.1 的示例写的是 `buffer += chunk.data`——那是 Web 的写法。小程序
`RequestTask.onChunkReceived` 回来的是 **ArrayBuffer**，直接拼会得到 `[object ArrayBuffer]`。
而且一个汉字的 3 个字节完全可能被切在两个 chunk 之间，按 chunk 各自解码就会吐出半个字的乱码。

`utils/ai-api.js` 的 `createUtf8Decoder()` 按字节缓存：每次只解出「完整字符」那一段
（`completeByteLength` 从尾部回退到本序列首字节，判断够不够长），残字节留给下一个 chunk。
4 字节序列（emoji）也照顾到了，解成 UTF-16 代理对。

### ② SSE 行也会被切断

同理，`data: {...}` 这一行可能横跨两个 chunk。`createSseParser` 按 `\n` 切，
**最后一行永远留在缓冲区**等下一块，连接结束时再 `flush()` 一次（服务端最后一条不带换行时用得上）。
`\r\n`、`[DONE]`、`event:`/`id:` 行都做了兼容。

### ③ 流式下的错误体不走 SSE

网关 JWT 缺失（403 + 大写字段 JSON）和服务端直接回业务错误 JSON 时，响应体并不是 SSE。
所以原始文本全程另存一份：`statusCode !== 200` 或「200 但一个事件都没有」时按 JSON 解析，
沿用原有的 `gatewayErrorMessage` 白名单（含 `RequestId`）与 `{ code, params, detail }` 协议，
页面的错误分发（`utils/ai-i18n.js`）完全不用改。

## 页面侧状态机（`subpackages/ai/chat/chat.js`）

`this._stream` 只跟着「当前这一条在途回复」走（`sending` 期间不允许再发，所以一次只可能有一条）：

| 字段 | 作用 |
| --- | --- |
| `holderId` | 内容写进哪个气泡（每帧按 id 重新定位，用户中途删消息也不会写错行） |
| `chars` / `shown` | 已收到的全部文字（按码点拆，emoji 不会被劈开）与已上屏字数，差值即「积压」 |
| `ended` | 流已结束；打字机排空后才 `settleStream` 收尾 |
| `hasContent` | 已经吐出过预描述/图/文字——决定中断时是**保留**还是换失败卡片 |
| `progress` | 已应用的进度，**只增不减**（服务端重复/乱序推也不会让进度条倒退） |

打字机改成「追着积压打」：每帧字数 = `max(1, ceil(积压 / 60))`，即任意时刻的积压约 1 秒内打完
——来得慢就一字一字（最顺滑），突然来一大段也不会拖出十几秒的尾巴。队列空了但流没结束时
按 60ms 空转等下一段，不再 16ms 空跑。与旧的整段打字机共用 `this._typeTimer`，
`stopGenerate` 那套清理原样有效。

几个边界：

- **停止生成**：已流出的内容留着（都已经看到图了，这时候换成失败卡片更像 bug）；
  只收到进度、连预描述都没来的空气泡才丢掉。
- **中途断线**：同上保留已生成部分，只 toast 一句「生成中断，已保留已生成的内容」，不进重试卡片。
- **兜底校对**：`chatStream` 同时 resolve 汇总的 `{ text, images }`，事件漏推时按它补齐。
- **空回复**：文字、图、预描述都没有就把占位气泡收掉，不留空白框。

## 界面

AI 气泡内部新增两块（`chat.wxml` / `chat.wxss`），沿用气泡自身的宽度与背景，不另起卡片：

- `.pre-text`——预描述行，橙色火花图标 + 淡橙底，生成完成后**保留**（用户要求「增加一个预描述的回复」）；
- `.gen-progress`——进度条，头部左「正在优化细节…」右「85%」，轨道 10rpx、橙色渐变、
  `transition: width .35s ease` 把服务端的台阶值（5→45→50→80→85→90→100）抹成连续增长。
  本地**不做补间**：进度只由 `event.progress` 驱动，避免假进度跑到 99% 卡着。

纯文字场景没有进度事件，界面表现与改造前完全一致（三点动画 → 打字机）。

## 降级

`aiApi.supportsStream()`（`wx.canIUse('request.object.enableChunked')`）为 false 时，
页面回退到原来的非流式 `chat()`——**它显式打回旧的非流式地址**，因为流式部署只会回 SSE。
两个部署是同一套服务、同一份会话数据，降级期间会话与历史不会对不上。
降级路径不缺功能，只是没有预描述和进度条。
