## 1. 横向出图时，彩色占位盒下面没有留白

生成中的渐变占位盒（`.gen-canvas`）此前一律贴着气泡底边：`.bubble--gen { padding-bottom: 0 }`。
这一手是给竖向/方形定的——那种占位盒又高又满，整只气泡看着就是「一张正在生成的图」，贴到底反而干净。
横向只有 56.25% 高（16:9），气泡里是一条扁扁的彩色带子，上面留着 20rpx、下面 0，看着就是掉出气泡外了。

改法：只给横向补回底边距，与气泡上内边距等值（20rpx），上下对称。

- 判据用 `genPad`（= 高/宽×100，见 `ORIENTATION_OPTIONS`）：**横向 56.25 < 100 < 竖向 177.78**，
  方形正好 100 归到「贴底」那档，与竖向同观感；
- wxml 里直接算（`item.streaming && item.genPad < 100`），不额外往消息对象里塞字段；
- 留了边距之后渐变盒四角整个在气泡内部，`.bubble--gen` 那两条「圆角对齐」不再起作用，但留着无害
  （竖向/方形仍贴底，仍需要它）。

## 2 & 3. 「选择投屏设备」弹层：AI 对话页与图片详情页共用一份，且改「先选再连」

两处此前**各抄了一份** wxml + 一套样式（`.device-sheet` / `.picker-sheet`），交互也同构。
本轮需求恰好是两处都要改的那种，于是先合并再改：新增公共组件
`components/device-picker-sheet/`，两页各删掉自己那份 wxml 与整块样式。

三项变化：

| | 改前 | 改后 |
| --- | --- | --- |
| 列表版式 | 自绘方块占位（「屏」字色块）+ 单行设备名 + 自绘单选圈 | **照搬搜索设备页**（`bind.wxml` 的 `.nearby-device`）：`home-icon02` 设备图 + 设备名 + 设备ID 两行 + `selected-icon` 对勾，选中态橙描边/浅橙底/橙色设备名 |
| 默认选中 | 打开就把「当前设备」选上 | **不选中任何一台** |
| 触发连接 | **点一行立刻**开连接并投屏 | 点一行只选中；按下底部「连接并投屏」才开始 |

为什么这几条值得改：投屏是**往设备写图**。端上替用户选好、他顺手一点就投到了别的设备上，
而这一步没有撤销——只能再投一次正确的图。选中态因此收在组件内部（页面只关心「按按钮时选了哪台」），
每次打开重置为空。未选中时主按钮置灰**且 JS 里直接 return**：观感与行为必须一致，不给哑按钮。

⚠️ 组件样式是隔离的，两个页面里的旧样式副本已整块删除（留着既不生效、又会误导下一个人）。

## 4. 图片详情页顶部大图不再裁剪

原来是「宽 100% + **写死高 58vh** + `aspectFill`」。两个比例对不上时 `aspectFill` 会按填满去放大、
再把多出来的部分裁掉——横图裁上下、竖图裁左右，正是反馈里说的「图片被压缩了」。

改法：宽度仍是满屏，**高度按图片真实比例算**——`heroPad = 高/宽×100`，wxml 内联 `height: {{heroPad}}vw`。
盒子比例＝图片比例，`aspectFill` 就一个像素都裁不掉，也不会拉伸变形。

- 真实宽高只能从 `bindload` 拿（⚠️ 后端列表/详情**都不下发图片宽高**，见 `utils/gallery-api.js`
  文件头的缺口清单）；首屏先按 3:4 占位（与图库列表 `DEFAULT_RATIO` 同源），加载完校正这一张；
- `.detail-spacer`（白卡起点）必须用**同一个 heroPad** 算：`calc({{heroPad}}vw - 3vh)`。
  写死就会在图矮时露出一条底色、图高时提前盖住图。差值 3vh 保持不变——白卡圆角压在图上，设计稿如此；
- 极端比例钳在 `[40, 240]`：太扁的图会让白卡几乎顶到导航栏，太长的图下半截本来就在屏幕外；
- ⚠️ **固有取舍**：大图是 `absolute`、不跟着滚，所以比 100vh 还高的长图下半截看不到。
  这是「白卡盖大图」这套版式自带的，不是裁剪；真要全图可见得把大图放进滚动区，那是另一套版式。

## 5 & 6. AI 上游供应商改为火山引擎，同意弹窗文案按产品原文替换

面向用户的三处「阿里云百炼 / 阿里云计算有限公司」全部改为「火山引擎 / 北京火山引擎科技有限公司」：
同意弹窗（`utils/ai-service-consent.js`）、协议正文 1.1 与 2.1、协议 2.3「技术提供方」。

弹窗文案按产品给的原文逐字替换：

```
为了使用AI服务（包括文本对话、根据文字生成图片、以及上传图片进行美化），我们需要将您当前发送的内容
（文字或图片）传输至“火山引擎”AI服务进行处理，该服务由北京火山引擎科技有限公司提供。

发送的内容仅用于本次操作，不会被用于模型训练
```

⚠️ **`CONSENT_VERSION` 必须一起升版**（`2026-07-28-v2` → `2026-08-13-v3`）：同意书里的**数据接收方**
变了，这正是要重新取得同意的那一类实质变更——不升版的话，老用户带着「同意发给阿里云」的旧记录，
端上直接就把内容发给了另一家公司，再也不会问他第二次。升版后所有老用户下次进 AI 页会重新看到弹窗。

### 当日续修：弹窗文案按产品新稿定稿（三段，新增**境外传输告知**）

产品当日又给了一版终稿，弹窗正文定为三段（`CONSENT_SUMMARY` = 三段以空行相连）：

```
为了使用 AI 服务（包括文本对话、根据文字生成图片、以及上传图片进行美化），我们需要将您当前发送的
内容（文字或图片）传输至“火山引擎”AI 服务进行处理，该服务由北京火山引擎科技有限公司提供。

您发送的内容仅用于本次操作，不会被存储或用于模型训练。

因该 AI 服务网关部署于境外（新加坡），上述内容将传输至境外处理，详情请见《BoltStar 隐私政策》第八节。
```

两处变化都不是措辞润色：

1. **「不会被存储」回来了** —— 上文记的「不再声明不会被存储」被这一版推翻，于是它与协议正文 2.2
   的口径重新一致，本文下面「待定夺」的第 1 条**随之关闭**；
2. **新增第三段：境外传输告知**（新增常量 `CONSENT_CROSS_BORDER_NOTICE`，`chat.wxml` 多画一段）。
   AI 网关部署在新加坡，内容出境属于**单独告知**事项，与「发给谁」同等重要；细则（接收方、目的、
   行使权利的方式）在隐私政策第八节，弹窗只告知并指路，不复述整节法律文本。
   ⚠️ 这句指路**当天才落到实处**：端上原来的隐私政策是 2026-5-13 的旧短文、根本没有第八节，
   同日已换成法务 v3.0 全文，见 [隐私政策换法务 v3 全文](2026-08-13-隐私政策换法务v3全文.md)。

⚠️ **`CONSENT_VERSION` 仍留 `2026-08-13-v3`**：v3 是当天新建、尚未发布，没有任何线上用户带着 v3 的
同意记录，改它的文案等于改一个还没发出去的版本。**若 v3 已经发过版，这一次必须再升一版** ——
境外传输是新的实质告知。

**未改、需产品/法务定夺的两处**（都在协议正文，属于法律文本，不擅自动）：

1. ~~协议 2.2 仍写「您发送的内容……**不会被存储**」，而新的弹窗文案已经把「不会被存储」拿掉了~~
   → **已关闭**：当日终稿把「不会被存储」写回了弹窗，两处口径重新一致（见上一节）；
2. 协议页顶部的「更新日期 / 生效日期」仍是 2026年7月28日，正文已改（换了技术提供方），是否同步更新日期。

⚠️ `utils/ai-api.js` 注释里的「阿里云 FC / 阿里云网关」**未动**：那说的是 AI 服务的部署与网关
