# 2026-08-06 「内容不够一屏却有滚动条」修复（滚动内容块的外边距合并）

> 状态：**小程序端已实现**，**未真机验收**
> 最后核对：2026-08-06
> 适用范围：微信小程序（登录页 + 首页绑定态 + 设置类四页；Flutter 侧核对后不涉及，见文末）
> 权威来源：本次问题反馈、当前源码
> 取代/被取代：修正 [2026-08-05 我的相册计数与全站折叠屏适配](2026-08-05-我的相册计数与全站折叠屏适配.md)
> 里 `.fold-scroll-body` 的实现缺陷（两种模式、逐页处理表等结论**全部不变**），
> 与 [2026-08-06 登录页协议勾选行贴左修复](2026-08-06-登录页协议勾选行贴左修复.md) 同源
> ——都是「内容搬进块级的 `.fold-scroll-body` 后，原先依赖 flex 父容器的行为变了」

## 现象

登录页在**普通直板手机**（非折叠屏）上能上下滑动、出现滚动条。可这一页只有
logo + 「微信登录」按钮 + 协议勾选行，加起来 908rpx，连半屏都不到，本不该能滚。

**与折叠与否无关**：折叠屏适配改的是所有机型都会走的 DOM 结构，不是媒体查询里的分支。

## 根因：首个子元素的 `margin-top` 穿透出去，把「一屏高」的内容块整体下推

`.fold-scroll-body` 的职责是「内容不够高时也撑满滚动视口」，所以写了 `min-height: 100%`。
问题出在它是**普通块级元素、且自己没有 `padding-top` / `border-top`**——这正是 CSS
**外边距合并（margin collapsing）** 的触发条件：首个子元素的 `margin-top` 不会留在块内，
而是穿透出去、变成**这个块自己的上外边距**。

```text
                    ┌─ scroll-view(.fold-scroll)：高度 = 一屏 - 导航栏 ─┐
 ↕ 376rpx           │  ← .login-main 的 margin-top 穿透成了内容块的外边距 │
 ┌──────────────────┴─────────────────────────────────────────────────┐ │
 │ .fold-scroll-body   min-height: 100%  ← 整整一屏高，起点却被推下去了  │ │
 │   .login-main（logo + 微信登录按钮）                                 │ │
 │   .login-agreement                                                 │ │
 └────────────────────────────────────────────────────────────────────┘ │
                    └────────────────────────────────────────────────────┘
   滚动内容高 = 376rpx + 一屏 > 滚动视口高 → 凭空多出 376rpx 可滚动区域
```

多出来的量**正好等于首个子元素的上外边距**。登录页的 `.login-main` 是 `margin-top: 376rpx`，
在 390px 宽的机器上约 196px——将近半屏的空滚动，这就是用户看到的滚动条。

内容的**视觉位置一点没变**（外边距合并前后，子元素都落在滚动区顶端往下 376rpx 处），
所以这个 bug 只表现为「多了一截滚不到东西的滚动」，页面看着是对的。

### 为什么改动前没有

改动前登录页的根容器 `.login-page` 是 `display: flex; flex-direction: column`，
**flex 容器不与子元素合并外边距**；设置类页面则是首个卡片前面还排着导航栏，
合并只发生在「块级父容器的首个在流子元素」身上。2026-08-05 把内容整体搬进块级的
`.fold-scroll-body`，两个前提同时消失，合并才开始生效。

同源的另一条（`align-self: center` 在块级父容器里失效导致协议行贴左）已于同日单独修复。

## 改法：让撑满视口的内容块自成 BFC

| 文件 | 元素 | 改动 |
| --- | --- | --- |
| `styles/fold-adapt.wxss` | `.fold-scroll-body` | 加 `display: flow-root` |
| `pages/home/home.wxss` | `.binding-content` | 加 `display: flow-root` |

`display: flow-root` 让这个块成为独立的 BFC，外边距合并被挡在块内：
子元素的 `margin-top` 老老实实留在块里，块自己从滚动区顶端开始、正好一屏高，
**滚动内容 = 视口高 → 不再有多余滚动**；而子元素的落点与改动前逐像素一致。

选它而不是别的挡法的原因（都能挡住合并，但各有副作用）：

| 写法 | 为什么不用 |
| --- | --- |
| `overflow: hidden` | 会裁掉 `.glass-card` 的投影（48rpx 外边距 vs 52rpx 模糊半径，横向就已经压线） |
| `display: flex` | 改变子元素的排布规则（兄弟外边距不再合并、`flex-shrink` 开始生效），风险面远大于本次问题 |
| `padding-top: 0.01px` | 玄学值，后人看不出用意，容易被「清理」掉 |

`display: flow-root` 只断开合并，**不改变子元素的布局方式**：仍是普通块级流，
兄弟之间的外边距合并、`text-align`、百分比高度全部照旧。

> iOS 12 及更早的 WKWebView 不认 `flow-root`（Safari 13 才支持），那里会退回本次修复前的
> 表现（多一截空滚动），不会更糟；Android 微信自带 XWeb 内核，全部支持。

## 回归用例

`tests/fold-scroll-phantom.test.js`（新增）把约束锁死：**凡是撑满视口（写了 `min-height`）
的滚动内容块，必须自成 BFC 或自带 padding-top**。清单里目前是
`.fold-scroll-body`、`.home-content`、`.binding-content` 三个；
删掉任意一处 `display: flow-root` 用例即红，并打印出「会凭空多出一截滚动条」的原因。
以后新增同类块时把它补进 `viewportFillers` 清单。

## Flutter 侧核对（不涉及，无需同步）

Flutter **不存在外边距合并**这个机制（`Padding`/`SizedBox` 是实打实的布局节点），
所以本次的根因在 App 侧不成立。同一症状在 Flutter 里唯一的等价陷阱是
「`minHeight` 按视口算、`padding` 却加在 `ConstrainedBox` 外面」——那会让内容恒比视口高一个
padding，同样凭空多出一截滚动。全库逐个核对了 `SingleChildScrollView + ConstrainedBox(minHeight)`
的五处用法：

| 位置 | padding | 结论 |
| --- | --- | --- |
| `figma_common.dart` `FigmaScreen.fillViewport` | `bodyPadding` | 已显式 `constraints.maxHeight - bodyPadding.vertical`，并留了注释 |
| `auth_page.dart`（登录页） | 仅 `horizontal: 26` | 纵向 padding 为 0，`minHeight` 恰好等于视口 |
| `register_page.dart` | 仅 `horizontal: 26` | 同上 |
| `mine_page.dart`、`home_main_view.dart`、`home_bind_device_view.dart` | 无 padding（内边距在 `IntrinsicHeight` 内部） | 同上 |

## Risks

- `display: flow-root` 在 iOS ≤ 12 的 WKWebView 上不生效（该机型退回修复前表现，不会更糟）。
- `.fold-scroll-body` 是公共类，一处改动影响 6 个页面；虽然理论上「装得下时逐像素一致」，
  仍需逐页真机对一眼（尤其是内容刚好接近一屏时，滚动的临界点会往后挪一点点——
  这正是修复的目的：以前是「不该滚也滚」）。
- 首页绑定态的 `.binding-content` 里贴底按钮是 `position: absolute`，定位父级仍是本块，
  `flow-root` 不改变定位父级（本块原本就有 `position: relative`），按钮位置不受影响。
