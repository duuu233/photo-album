# 电量取数治理（小程序侧已完成，App 侧待改）

> 起因：来回切「首页 / 设备列表 / 设备详情」，同一台设备的电量一直在变。
> 日期：2026-07-20

---

## 一、问题定性

**三个页面里只有设备详情页的电量是设备真实数据。** 首页和设备列表显示的都不是。

先厘清一个容易误解的前提：**后端不存 battery 这个字段**（`utils/api.js` 里 `battery` 恒为 null）。
所以页面上的电量只可能来自「上次 BLE 读到后写进 `selectedDevice` 的缓存」。

电量的三个来源：

| 来源 | 解析处 | 需要连接 |
|---|---|---|
| **BLE 指令 0x01 GET_INFO** | `frame-protocol.js` `battery: b[20]` | 要 |
| BLE 广播包（6.10.7 厂商数据） | `frame-protocol.js` `parseAdvertising` | 不要，仅绑定页在用 |
| 后端接口 | `api.js` | 恒为 null |

`readBattery`（0x04）虽然存在，注释还写着「用于详情页刷新」，但**全仓唯一调用方是调试页**，
业务链路完全不走它 —— 那句注释是过时的，照着理解会走偏。

---

## 二、根因（三条，叠加成跳变）

### ① 详情页读到的真值被丢掉了

`doLoadDetail()` 是三个页面里**唯一真读 BLE** 的地方，但它只把结果塞进 `this.setData`，
全函数没有一次 `app.setSelectedDevice` —— 真值从不共享给另外两页。

### ② 首页用常量 30 冒充，而且会污染缓存

`normalizeDevice` 把未知电量兜底成 **30**，随后 `loadHomeState` / `markCurrentDeviceConnected`
又把这条记录写回 `selectedDevice`。特别是点「连接蓝牙」复用已有会话时 `info` 为 null
（`active-device.connectBoundDevice` 的 `verifyReuse`，首页不传即 false），电量直接取
`current.battery`（已经是 30）当成本次读到的值写回。**假值就这样横向扩散到设备列表页。**

另外 `utils/battery.js` 自己还有个 `DEFAULT_BATTERY = 100` 的兜底，是第二个假值源。

于是切换序列典型是：详情 87% → 回首页 30% → 进列表 30% → 再进详情 87% → …

### ③ 缓存永不过期

`selectedDevice` 经 `wx.setStorageSync` 落盘、`app.js` 启动时恢复，**无时效**。
冷启动后首页展示的可能是几天前的电量，还带着百分比和图标，比显示 `--` 更有欺骗性。

---

## 三、方案

### 关键设计：两个 TTL，回答不同问题，都需要，别合并

| | 读取节流 15s | 展示有效期 10min |
|---|---|---|
| 位置 | `utils/device-info.js` `FRESH_TTL_MS` | `utils/battery.js` `BATTERY_TTL_MS` |
| 问题 | 「要不要再去读一次设备」 | 「缓存的值还能不能拿来显示」 |
| 防的是 | 反复切页面猛读 0x01、占用 BLE 链路 | 陈旧值冒充当前值 |

只有 15s 节流不够：首页/列表按设计**不主动读 BLE**（onShow 必须快），连着设备在首页放 20 分钟，
会一直显示 20 分钟前的值且看起来完全正常。只有 10min 有效期也不够：反复切详情页仍会猛读设备。

### 新增 `utils/device-info.js`：0x01 结果的全局单例缓存

此前 15s 节流只做在**详情页私有字段**（`_lastBleInfo`）上，切到别的页面就失效；
别处读 0x01 的地方（连接收尾、一键清空、图库删除/刷屏）各读各的。现在收归一处，并带来：

- **读取节流**：同一连接 15s 内复用，不碰 BLE
- **在途去重**：并发读共享同一个 Promise。此前 onShow 与「操作后刷新」并发会撞设备的
  `CMD_PENDING`（同指令正在等待应答）—— 详情页注释里早记过这个坑
- **断链自动作废**：`isValidFor` 内查 `deviceBle.isConnected`。放在这里而不是去 7 个
  `deviceBle.disconnect` 调用点各清一次 —— 那正是「各页面各自维护」的老毛病
- **`force` 逃生口**：破坏性操作的依据（删除/刷屏的 imgMask、清空后的核对）必须真读

### `utils/battery.js` 重写为唯一收口

- 写入侧 `stampBattery(value)` —— 每次 BLE 读到就打时间戳
- 读取侧 `resolveBattery(device)` —— 三道闸：未连接 / 无时间戳 / 超时，任一命中即未知
- 展示侧 `batteryText(device)` —— `'87%'` 或 `'--'`，**绝不用假数值冒充**
- `normalizeBattery` 取代原 `clampBattery`：非法值返回 `null`，不再兜底成任何数字

> 「无时间戳视为未知」这条同时处理了本次改动前已落盘的旧缓存 —— 来路不明的历史值不予采信。

## 四、改动清单（小程序，已完成）

| 文件 | 改动 |
|---|---|
| `utils/device-info.js` | **新增**。0x01 全局缓存：15s 节流 + 在途去重 + 断链作废 + force |
| `utils/battery.js` | 重写。时间戳/新鲜度/文案统一收口；废除 `DEFAULT_BATTERY=100` 与 `clampBattery` |
| `subpackages/device/detail/detail.js` | ①`doLoadDetail`/`refreshDeviceMemoryFromBle` **回写 selectedDevice**（根因）；②私有节流删除，改用全局模块；③清空前后两处读改 `force`；④显示统一走 batteryUtil |
| `pages/home/home.js` | 删除本地 `clampBattery`（30 兜底）；`DEFAULT_DEVICE.battery` 30→null；电量与时间戳成对搬运；复用会话时**不再把旧值当新值重新打戳**；删除死状态 `batteryWidth`（6 处 setData，模板零消费） |
| `pages/home/home.wxml` | `{{item.battery}}%` → `{{item.batteryText}}` |
| `subpackages/device/list/list.js` | 电量与时间戳成对搬运；显示统一走 batteryUtil；连接收尾打时间戳 |
| `subpackages/album/list/list.js` | 删除/刷屏的 imgMask 读改走缓存模块的 `force` |
| `utils/active-device.js` | 真读结果登记进全局缓存；`verifyReuse=false` 时用 `peekFresh` 顺带带回新鲜信息（零成本，首页因此也能拿到真实电量） |

已过 `node --check`；本机无小程序工具链，需在开发者工具里跑一遍真机验证。

### 一个刻意的取舍

`verifyReuse=true` 的活性校验（`active-device.js`）**故意不吃节流缓存** —— 校验的意义
就在于真的发一次指令，命中缓存会把死会话误判成活的。

## 五、验收

1. 连上设备 → 进详情页记下电量 X
2. 返回首页、进设备列表、再回详情 —— 三处应**全部显示 X**，不再跳变
3. 15s 内反复切详情页 → 抓包/日志应只有**一次** 0x01
4. 断开连接 → 三处均显示 `--`
5. 杀掉小程序冷启动 → 首页显示 `--`（不再是 30%），连上后才出现真实值

App（`/home/pg/dh/flutter`）的病灶**不同**，不能照搬：

| 项 | 小程序 | App 现状 |
|---|---|---|
| 假值 | 常量 30 / 100 | 无假值常量，但未知渲染成 **`0%`** |
| 时效 | 无（已修） | 无时间戳，`DeviceItem` 没有 `batteryUpdatedAt` |
| 真值丢弃 | 详情不回写（已修） | 多处 0x01 读**丢弃电量**只取 imgMask |

具体待办：

1. **`state.dart` `DeviceItem` 加 `batteryUpdatedAt`**，`_applyConnectedInfo`（`:802`）打戳，
   `_carryOverBleFields`（`:769`）连时间戳一起搬 —— 现在它无条件把旧值搬过来，是陈旧值永生的原因
2. **接通 25s 心跳的电量**：`keepAlivePing`（`device_ble.dart:914`）每 25s 发一次 0x04 GET_BATTERY
   却**把应答丢掉**。接出来就能让连接期间电量始终 ≤25s 新鲜 —— 这是 App 侧最便宜的一处收益，
   小程序没有这个条件
3. **多处 0x01 读丢弃电量**：`state.dart:1535/1655/2270/2300`、
   `projection_service.dart:178/494/723` —— 一整场投屏跑完电量都不更新
4. **三页 `0%` → `--`**：`home_widgets.dart:761`、`my_devices_page.dart:475-497`、
   `device_details_page.dart:400`。注意详情页同页的 memory/设备ID/轮播行**已经**用 `--` 占位，
   唯独电量不守这个约定
5. **首页刷新时机**：`home_page.dart` 只在 `initState` 读一次，没有 `RouteAware`/`didPopNext`，
   也没有 `AppLifecycleState.resumed` 钩子（`bolt_star_app.dart:326` 的 `_resumeBleSession`
   只对连接标志做核对，不重读设备信息）。设备列表页和详情页都有 `didPopNext`，首页没有

另注：App 的 `_applyConnectedInfo` 有个 `if (info.battery > 0)` 的守卫，
而 `parseDeviceInfo` 在短帧时把电量解析成 `0` —— 「真的没读到」和「真的 0%」不可区分，
一并在第 1 项里处理掉。
