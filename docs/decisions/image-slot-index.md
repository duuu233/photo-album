## 一、背景与结论

**设备支持这套逻辑。** 依据 v1.5 规格书 §6.7.2「图片管理策略」：

> 系统采用 12 字节图片掩码直接标识和管理图片。用 0-95 的位索引直接标识对应图片，APP 和设备通过相同的位位置来识别。

也就是说**位索引就是图片的唯一身份**，设备侧不存任何图片元数据（没有文件名、CRC、时间戳）。谁在哪个位置，**完全靠 APP 端记住**。所以把索引持久化到后端，正是规范设定的做法。

删除指令 `CMD=0x12` 的入参就是 12 字节 `IMG_INDEX_MASK`，一条指令可批量删多个槽位（`utils/device-ble.js` 的 `deleteImage`）。

### 改之前的问题

索引在投屏时是已知的（`result.js` 用 `firstFreeIndex` 选出的槽位），但传完就丢了。图库删除/刷屏时只能靠「上传先后顺序 ↔ 升序占用槽位」反推——一旦中间删过图、槽位被复用，推算就错位，表现为「删错图」「指定刷新的图不对」。

## 二、字段与链路

| 动作 | 谁做 | 说明 |
|---|---|---|
| **写** imgIndex | 每次投屏成功，**三条链路都要** | 正常投屏 → `editUserProductImgRecord`；再次/重新投屏 → `addUserProductImgRecord` |
| **读** imgIndex | 「我的相册」删除图片 | 投屏记录按 `uProductImgId` 关联图库照片，只读取该后端记录的 `imgIndex`；无索引直接终止，不推算 |
| 不涉及 | 设备管理（一键清空、轮播设置）、投屏记录页 | 一键清空是全删，不需要定位；再次/重新投屏是重新找空位 |

**再次投屏 / 重新投屏的语义**（易误解，记录在此）：

- **再次投屏**：图在设备和后端都有过，点它是为了复用已有的 `.bin` 地址，省掉重新上传+转码。走正常投屏流程，设备自己找新空位，拿到**新索引**存起来。图库因此会出现两条一样的图，各带各的索引——**这是预期行为**。
- **重新投屏**：区别仅在于上次「传后端成功、传设备失败」，设备上本来就没有。同样复用 `.bin`，同样拿自己的索引，之后完全一致。

**0 是合法槽位**（相框第一个位置）。判空只能判 `undefined / null / ''`，绝不能写 `if (!imgIndex)`，否则第一个位置上的照片永远删不掉。前端已封装 `parseImgIndex()`（list.js）与 `imgIndexParam()`（api.js）统一处理。

## 三、待后端确认 / 待办

1. **（关键）唯一性规则**：同一台设备下，一个位置号只能属于一条记录；新记录写入某个 imgIndex 时，把旧的同位置记录的 imgIndex 清空。**这一条是问题 A 的唯一解**，且只需后端做，前端不用任何配合。
2. **`addUserProductImgRecord` 是否已加 imgIndex 入参**？前端已按加了实现。同时确认：再次/重新投屏后图库里那条新记录，是否就是由这个接口创建的。
3. **`clearUserProductImg`（一键清空）是真删记录，还是只打「已清除」标记**？（旁边的 `getUserProductClearImg` 返回 0/1，怀疑是后者。）若是打标记、记录留着，那批记录的 imgIndex 需要后端顺手清掉。
4. 历史数据：约定上线时**重置/清除历史数据**，因此不考虑「老照片没有索引」的存量兼容。前端已于
   2026-08-10 删除推算兜底；运行期若产生无索引记录，删除操作明确失败，等待后端数据修复。

## 四、已知问题（暂不处理，后续跟进）

> 以下问题在本次改动中**有意未处理**。清除历史数据只能擦干净起点，A 和 B 是运行期持续产生的，不会因为清库而消失。

### 问题 A：删除半成功 → 幽灵记录 → 删错图【严重度：高，会误删用户照片】

删一张照片实际是两件独立的事：① 告诉相框擦掉 X 号位（蓝牙）② 告诉后端删掉记录（网络）。目前 ① 失败会整体中止（安全），但 **② 失败只弹一句提示就结束，而 ① 已经做完了**（`list.js` `confirmDeleteSelected` 的后端删除失败分支）。

举例：

```
起点   相框：[0]猫 [1]狗 [2]全家福      后端：猫→0  狗→1  全家福→2
删「狗」相框删了1号位（成功），后端没删（没信号）
       相框：[0]猫 [1]空 [2]全家福      后端：猫→0  狗→1 ⚠️  全家福→2   ← 幽灵记录
投新图 设备报「1号位空着」→ 海边填进1号位
       相框：[0]猫 [1]海边 [2]全家福    后端：… 狗→1 ⚠️  海边→1        ← 两条指同一位置
再删狗 手机照记录删1号位 → 海边被删掉
```

**新图必然填回刚腾出来的位置**（`firstFreeIndex` 从最小空闲槽位起填），所以幽灵和新图撞车不是小概率事件。

**解法**：后端唯一性规则（见上方待办 1）。海边写入 `imgIndex=1` 的那一刻，狗那条的索引被清空，之后删「狗」就不会再动 1 号位。前端无需改动。

### 问题 B：记账失败 → 成功被显示成失败 → 用户重投 → 孤儿占位【严重度：中】

投屏的记账是**尽力而为**的：图传成功后去后端标记「成功 + 索引」，这一步失败只写日志，不重试、不提示（`result.js` 的 `queueRecordTask`）。

举例：小王投「海边」，蓝牙传完、相框里确实有了，但标记那一下网断了。

```
相框：[3]海边                        ← 图真的在
后端：海边 → 状态「投屏失败」，无索引   ← 后端以为没传上去
```

小王在投屏记录里看到「投屏失败」，于是点**重新投屏**（完全合理的操作），手机复用 `.bin` 再传一次，落到 4 号位：

```
相框：[3]海边  [4]海边
后端：海边→4（新记录，有索引）  +  海边→(无索引，失败态)   ← 3号位那张没有任何记录指向它
```

3 号位那张成了**无主孤儿**：图库看不到、删不掉、不知道在哪，但实实在在占着相框一个位置，只有一键清空能清。网络抖动比删除失败常见得多（投屏常在户外弱网下进行），所以这个场景发生率不低。

**可选解法**（未定）：
- 记账失败时把索引暂存本地（Storage），下次有网/下次进图库时补报——能根治；
- 或「重新投屏」前先问相框该位置是否已有图，有就不重传；
- 或最省事：记账失败时明确提示「投屏已完成，但记录同步失败」，至少别让用户误以为失败。

### 问题 C：回滚失败 → 孤儿占位【严重度：低】

图传失败时手机会删掉相框上那个半成品槽位（`rollbackDeviceImage`），但**回滚失败是静默忽略的**——而图传失败最常见的原因就是设备断连，断连状态下回滚基本也删不掉。结果同样是一个没有记录指向的孤儿位置。要连续两次失败才会触发，暂时靠一键清空兜底。

### 问题 D：幽灵记录导致刷错图【严重度：低，不破坏数据】

「刷新屏幕」也读 imgIndex。幽灵记录不光会删错，也会刷错——点「狗」刷新，相框上亮出来的是「海边」。根因同 A，A 修好即消失。

### 问题 E：0 号位判空【已处理】

0 是合法槽位，转成数字后 `0` 在 JS 里是假值，任何 `if (!index)` / `index || 默认值` 都会把它当成「没有索引」，导致每台相框第一个位置上的照片永远删不掉。而且投三张删后两张完全测不出来。**已通过 `parseImgIndex()` / `imgIndexParam()` 统一处理。**

## 五、协议层面的固有限制

设备只回答「几号位有图」（12 字节占用掩码），**不回答「几号位装的是谁」**。所以 APP 端记录一旦与设备实际内容脱钩，无法靠询问设备来发现——位置对得上、内容对不上时是彻底的盲区。

规范 §6.7.2 原则 4 给的「APP 和设备通过对比 IMG_MASK 比特位确保一致」只能检测**数量/位置分歧**（本子说 5 张、柜子只有 3 个位置亮灯），检测不到内容被替换。

若要真正可校验，需固件侧支持「读指定槽位的图片标识」（CRC32 即可，图传时本就已计算）。**当前不做**——问题 A 修好后，残留幽灵指向的都是空位置，删它们只会收到「图片不存在」，无破坏性。

## 六、历史方案：双端槽位推算（2026-08-03，删除链路已于 2026-08-10 废止）

> 本节保留 2026-08-03 的演进背景，不再描述小程序当前删除行为。凡是“读取设备掩码、校验命中、
> 按上传/列表顺序推算、删除后补刷屏”的内容，均已被本页 2026-08-10 操作日志中的单一路径取代。

同一个账号同一台设备，用户会**两端交替**投图/删图。设备侧只有一份 12 字节掩码、后端只有一份记录，
所以「照片 → 槽位」的解析规则**必须两端逐字一致**：规则不一致时，同一张照片在小程序解析成 2 号位、
在 App 解析成 3 号位，用户看到的就是「删错图 / 刷错图 / 索引乱了」。

### 上传侧：本来就是一致的（不是混乱的源头）

| 环节 | 小程序 | Flutter |
|---|---|---|
| 批次开始读掩码 | `deviceBle.readTransferInfo`（无缓存） | `client.readTransferInfo()`（无缓存） |
| 选槽位 | `firstFreeIndex(indexesToMask(usedIndexes), capacity)` | 同 |
| 批内累计 | 每张成功后 `usedIndexes += index` | 同 |
| 上报 | `editUserProductImgRecord({imgIndex})` | 同 |

两端都在批次开始真实回读 0x01、都从最小空闲槽位起填、都上报真实槽位；BLE 又是独占连接，
两端不可能同时写同一台设备。**所以上传本身不会撞槽位。**

### Flutter 侧逐点复核（2026-08-03）

| 检查点 | 位置 | 结论 |
|---|---|---|
| 批次读掩码 / 选槽位 / 上报 | `features/cast/projection_service.dart:223 / 289 / 365` | 与小程序一致，无缓存、无预检 |
| `firstFreeIndex(mask, capacity)` | `device/ble/frame_protocol.dart:426` | 与小程序 `frame-protocol.js` 同实现（含容量上限） |
| 刷新屏幕的目标设备 | `state.dart refreshGalleryPhotoOnScreen:1916` | 用 `photo.deviceId`，本就正确 |
| 删除的目标设备 + 跨设备拦截 | `state.dart deleteAlbumPhotos:1732` | 本就正确，另有「只能删同一台设备」拦截 |
| 槽位解析三条规则 | `state.dart _resolveDeviceImageIndex:1991` | 本就是严格版（小程序照它改） |
| 删后刷屏 | `state.dart:1795` | 只在删到屏显图时刷，取删除后最小占用槽位，与小程序一致 |
| `addUserProductImgRecord` | 全仓 | **无调用方**（与小程序同样已废弃，勿再接回） |
| 一键清空 | `state.dart clearDeviceMemory:2560` | 设备 0x12 全删 + `clearUserProductImg` 清后端，与小程序 `detail.js` 一致 |

App 侧本轮只改两处：`devicePhotoAbnormal` 触发条件（第 5 条）、以及新增 `resolvedCount` 计数
（`slotIndexes` 去过重，直接比长度会误报）。

### 图库侧：原来有 6 处不一致，已全部对齐（以 Flutter 的严格口径为准）

| # | 点 | 原小程序 | 原 Flutter | 现口径 |
|---|---|---|---|---|
| 1 | 真实 imgIndex 是否校验掩码 | 直接返回 | 要求该槽位在掩码里有图，否则 -1 | **要求命中掩码** |
| 2 | `claimed`（已被真实索引钉住的槽位） | 取全部在库照片（跨设备） | 只取同一 `deviceId` | **只取同设备** |
| 3 | 候选为空时 | 硬套位置号 `pos` | `occupied` 为空才 `pos`，否则 -1 | **设备有图就 -1** |
| 4 | 删除/刷屏的目标设备 | 首页轮播「当前选中设备」 | 照片所属设备 `photo.deviceId` | **照片所属设备** |
| 5 | 「照片在此设备异常」提示 | 有一张对不上就提示 | 一张都对不上才提示 | **有一张对不上就提示** |
| 6 | 排队兜底（主键与时间都取不到） | 稳定排序＝保留后端顺序（最新在前）→ 方向反了 | 合成时间「固定基准 − 下标秒」→ 后端列表倒序 | **后端列表倒序**（小程序补 `orderOf` 兜底） |

第 6 条平时不触发（`uProductImgId` 是主键，恒存在且自增），但图库列表接口**不下发任何时间字段**，
一旦主键也取不到，两端就会排出相反的顺序——留着就是一颗哑弹，本轮一并对齐。

第 1 条是双端并用时最关键的护栏：另一端删过图/一键清空过之后，本端列表里的记录还带着旧
`imgIndex`，那个槽位在设备上可能**已经换人**了——照着旧索引下 0x12/0x24 就是删错、刷错。
现在两端都要求「后端说的槽位必须在固件掩码里确实有图」才采用，否则返回 -1（跳过该张，
删除仍会删掉后端记录并提示「照片在此设备异常，请删除重新上传」）。

第 4 条是小程序独有的老问题：图库按设备筛选后，用户选的是 B 设备的照片，指令却发给了首页选中的
A 设备——拿 B 的槽位号去删/刷 A 的图。

### 仍然存在的结构性隐患

上面对齐的是**规则**，不是**数据**。只要记录缺 `imgIndex`（问题 B：记账失败；或后端图库列表不回该字段），
两端都会退回「第 N 张 ↔ 第 N 个占用槽位」的推算，而这个假设在「删过中间槽位后再上传」时必然错位——
两端交替使用只会更快踩到。根治仍然依赖上方「三、待后端确认」的第 1 条（唯一性规则）与
图库列表稳定回传 `imgIndex`。排查时先看一条：图库列表接口返回的 `imgIndex` 是否非空。
