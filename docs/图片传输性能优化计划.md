## 第二阶段实施记录（D1 / D2 / F1）

实施日期：2026-07-10。协议字节与 v1.5 完全一致，不改图片格式、BLE 协议、窗口/pace 调速逻辑（遵守 B6）。

### D2. 整图 CRC32 查表化并移入预取

- `utils/image-codec.js`：`crc32Mpeg2` 由逐位改为查表实现（新增模块内常量 `CRC32_MPEG2_TABLE`）。
  多项式 0x04C11DB7、初值 0xFFFFFFFF、不反转不异或均不变，结果与旧实现完全一致。
- 实测（桌面 Node，仅供参考量级）：5.89 寸一帧 326KB 由 23ms → 4ms；低端手机预计收益更大。
- CRC32 计算时机从「uploadImage 内、0x20 发出前」提前到预取阶段（见 D1 的 `prepareImageTransfer`）。

### D1. 0x21 数据帧预组包 + CRC16 查表化

- `utils/frame-protocol.js`：
  - `crc16Modbus` 改查表实现（新增 `CRC16_MODBUS_TABLE`），多项式 0xA001/初值 0xFFFF/字节序不变；
  - 新增 `buildImgDataFrame(data, seq, chunkSize)`：用 Uint8Array 整块 set + 查表 CRC16 组一帧完整
    0x21 帧，与旧路径 `buildFrame(CMD.IMG_DATA, buildImgDataPayload(...))` 逐字节等价（已验证）。
- `utils/device-ble.js`：
  - 新增导出 `prepareImageTransfer(deviceId, data)`：整图 CRC32 + 按会话 dataChunk 预组全部 0x21 帧；
    每 256 帧 yield 一次，避免饿死并行进行中的上一张图传 ACK 处理；会话未就绪时只算 CRC32（frames=null）。
  - `uploadImage` 新增可选 `options.prepared`：dataSize 对得上才用其 CRC32；chunkSize/帧数对得上才用
    预组帧；任一不符自动回退现算现组（调试页等旧调用方不传 prepared，行为不变）。
  - `writePacket` 改为接收已组好的整帧 ArrayBuffer；原 `writeFrame` 辅助函数删除（仅它在用）。
  - 实测（桌面 Node）：1384 包组帧 57ms → 21ms，且全部移出「两次 BLE 写之间」的串行热路径。
- 新增 stats 字段（单张汇总日志）：`crcPrecomputed`（CRC32 是否预取算好）、`prebuiltFrames`（是否用了预组帧）。
  真机排查时先看这两个标志：均应为 true；为 false 说明走了回退路径（首张早预取时会话未就绪属正常）。

### F1. 首张转码/下载与「连接 → 0x01」并行

- `subpackages/projection/result/result.js`：
  - 预取流水线（framePrefetch/startPrefetch）从「0x01 之后」提前到连接之前声明；`startPrefetch(idx, sizeInfo)`
    显式传尺寸：首张早启动用设备记录尺寸，其余张用 0x01 真实尺寸。
  - 早启动条件：设备记录带后端按型号下发的 width/height（`guessedSize`），或首张是再次投屏 imgBle
    直传（`firstDirect`，完全不依赖尺寸）。满足即在 `ensureConnection` 前启动第一张的转码+下载。
  - 0x01 返回后校验：`guessedSize` 与真实 info 宽高不一致 → 作废首张预取（`framePrefetch[0]=null`）
    按真实尺寸重取，日志 `[投屏] 设备记录尺寸(…)与设备实际(…)不一致`；原有「帧字节数=宽×高÷2」
    校验保留，错帧绝不会发往设备。
  - `acquireFrame` 两条链路（正常转码/imgBle 直传）在下载完成后统一调 `prepareTransfer`（内部调
    `deviceBle.prepareImageTransfer`），把 D1/D2 的预处理并入预取；失败只 console.warn，不阻断本张。
  - 整单汇总新增：`firstPrefetchEarly`（首张是否早启动）、`firstPrefetchDiscarded`（是否因尺寸不符作废）；
    单张 timings 新增 `prepareMs`。
- 预期收益：首张开始 BLE 前等待由「(连接+0x01) + (转码+下载)」串行变为两者取大，冷连接场景省 1~3s。
- 已知代价：早启动的转码会先建一条 deviceUploadState=0 的投屏记录，若整单在图传开始前失败/中止，
  该记录与「转码成功但 BLE 失败」场景一致（可重传），非新增问题；尺寸不符作废时会多一次转码调用（极少发生）。

### 回滚指引

- 三项相互独立，可按文件粒度部分回滚：
  - 仅回滚 F1：还原 `result.js`（预取流水线退回 0x01 之后启动、acquireFrame 去掉 prepareTransfer）；
    device-ble/frame-protocol/image-codec 可保留，D1/D2 自动退化为「uploadImage 内现算现组（仍查表加速）」。
  - 仅回滚 D1 预组包：删 `prepareImageTransfer`/`buildAllImgDataFrames`、`uploadImage` 的 prepared 分支、
    result.js 的 prepareTransfer；`writePacket`/`buildImgDataFrame` 可保留（等价实现）。
  - 仅回滚查表 CRC（怀疑真机 CRC 不一致时优先查这里）：把 `crc16Modbus`/`crc32Mpeg2` 换回逐位实现即可，
    两者已做等价性验证，理论上不存在差异。
- 定位问题线索：
  - 设备回 0x0A「校验失败(整图CRC32不符)」→ 查 D2（prepared.crc32 是否配错图，uploadImage 已按 dataSize 拦截）；
  - 设备回 0x03「CRC 错误」（单帧）→ 查 D1 `buildImgDataFrame`/查表 CRC16；
  - 首张投错尺寸/「后端返回的不是设备要的六色4bpp帧」→ 查 F1（guessedSize 来源 device.width/height 是否可信）；
  - 单张日志 `prebuiltFrames=false` 且非首张 → prepared 帧数/分包对不上（MTU 变化、prepared 配错图）。

### 第二阶段验证（非真机）

## A：性能测量

为每次投屏生成一次 trace，按整单和单张图片记录以下数据：

### 环境信息

- 手机平台、系统版本、微信版本和小程序基础库版本
- 设备型号、屏幕类型、固件版本
- 网络类型
- 协商 MTU、图片分包大小、窗口大小和配置 pace

### 阶段耗时

- 预览页自动裁剪和临时文件导出
- BLE 连接或已有连接复用
- 读取设备核心信息（0x01）
- 读取/设置连接间隔（0x05/0x13）
- 原图上传及服务器转换总耗时
- frame.bin 下载和本地读取
- CRC32 计算
- IMG_START（0x20）应答
- IMG_DATA（0x21）数据发送
- IMG_END（0x22）校验和落盘
- 投屏记录更新
- 最终刷新屏幕（0x24）

### BLE 统计

- 原始字节数、总包数、已确认包数和实际数据吞吐（KB/s）
- 写入调用耗时、ACK 推进次数和 ACK 等待耗时
- 重试次数、重发包数、最终实际 pace
- 成功、失败和中断原因

日志只记录性能与协议元数据，不记录图片内容、完整图片地址或用户隐私数据。每张图片结束时输出一条汇总，整单结束时再输出一条总汇总，避免逐包日志本身影响传输性能。

## B：小程序低风险优化

### B1. 修正 MTU 查询方式

`getBLEMTU` 按实际数据写入方式使用 `writeNoResponse`，避免部分设备按错误写入类型查询失败后回退到较小分包。

### B2. 缩短首张关键路径

- 投屏只同步读取 0x01 所需的屏幕尺寸、类型、容量和图片掩码。
- 固件版本 0x03 移出首张关键路径，改为后台读取或复用已有信息。
- 0x01 返回后立即启动第一张的上传、转码和下载，同时执行连接间隔优化。
- 保留现有预览页 BLE 连接预热和结果页连接复用。

### B3. 后端记账移出图片间串行路径

设备完成一张图片后，投屏记录更新不再阻塞下一张 BLE 发送。记账任务仍需保证最终执行，并保留成功/失败日志；记账失败不能改变设备已传成功的事实。

### B4. 限制进度 UI 更新频率

BLE ACK 继续实时参与流控，但页面进度最多约每 100~200ms 或百分比变化时更新一次，避免高频 `setData` 占用 JS/UI 通道。开始、完成、重试和错误状态必须立即更新。

### B5. 修正尾包 ACK 竞争窗口

最后一轮发送后，在进入 600ms ACK 等待前再次检查最后包是否已经确认；ACK 等待超时后也先复查确认位置，再决定是否重发，避免已完成却额外等待或重发。

### B6. 暂不继续激进调速

第一阶段不提高 10 包窗口上限，也不强制把 pace 固定为 0。先通过 A 记录写入耗时、ACK 延迟和重传成本，再决定是否调整调速算法。

## 验收与测试

至少覆盖以下组合：

- Android 和 iOS
- 3.7 寸和 5.89 寸设备
- 单张和连续 5 张
- 首次投屏和再次投屏
- Wi-Fi 和移动网络（网络阶段对比）
- 已连接复用和冷连接

对比指标：

- 首张开始 BLE 发送前耗时
- 单张端到端耗时
- BLE 纯数据段耗时和 KB/s
- 5 张整单耗时
- 重传率、失败率和尾包额外等待次数
- 投屏记录最终一致性

先取得修改前基线，再使用同一组图片、设备和手机复测修改后版本。只有成功率与记录一致性不下降时，性能优化才算通过。

## 暂缓方案

完成 A+B 真机测试后，按瓶颈决定是否继续：

- C：若图片准备/上行占比最高，改为上传原图和裁剪/旋转参数，由后端完成目标尺寸处理。
- D：若重复下载或批量等待明显，增加 frame.bin 本地缓存，并评估有界并发预取。
- E：若 BLE 数据段占比最高，与固件协作增加六色 3bpp 格式或流式无损压缩，并评估更大的设备缓冲、DLE/2M PHY。
